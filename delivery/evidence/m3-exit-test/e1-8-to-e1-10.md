## E1.8, the fix round and the verification stage that `full` mode requires

The plan clause is at delivery/plan/kernel-plan-m3.md:5262 and it is
unambiguous: a run whose fix round skips `fix-round-verification` FAILS the
exit test.

**The fix round.** One round, answering both reviews. The mechanism, not the
instances: the check reported on PRESENCE where the property that matters is
what the install RESOLVES. Round 0 had closed one instance of the gap, the
empty directory; the hazard review forced three more directory shapes and the
FILE shape and measured every one PASS with FAIL count zero. Fix round 1
replaces the proxy with a resolution predicate whose suffix per directory is
read off the CONSUMING command's own filter, plus a content floor that applies
to the file member of the class as well as to the directory members.

The two behaviours the criteria review proved had no red-witness coverage at
all now have it, in `witness/doctor-kernel-artifacts.json`, which is also the
filename the plan and criterion 7 name literally. The full account, with the
derivation the fix-round contract requires and the two claim greps, is the
subject branch's own work history.

## Two facts about the STAGE rather than about the change

Both come from the E1.7 hazard review, and both are recorded here because they
are properties of the exit test's own construction that a later run will meet
again.

1. **A `charter.yaml` in the verdict context makes E1.7 unsatisfiable for an
   uncommitted verdict.** With the bundle's charter and `assurance-modes.yaml`
   copied into the context directory, `validate --type verdict` turns
   `INVALID #/phase this verdict is not among the 0 verdict document(s)
   committed under delivery/review for phase M3-P13`, exit 1. A clean-room
   reviewer commits nothing by contract, so `dual-review-decorrelation` can
   only be satisfied after the orchestrator lands the document. The context
   that makes E1.7 exit 0 is therefore the plan-and-work-history one, and the
   decorrelation judgement is the orchestrator's separate step.

2. **The bundle shipped no `work-history.yaml`, so
   `verdict-deviations-judged` compared each verdict against a document its own
   reviewer had authored.** The check reads `work-history.yaml` from the
   context directory and compares its declared deviations against the verdict's
   `deviations-judged[]`; with no such file in the bundle, both reviewers wrote
   one. The check still exited 0, which is exactly the shape that makes it
   worth recording: vacuous and green are indistinguishable from the outside.
   `e1/e1-9/work-history.yaml` closes half of this, since a context assembled
   from the bundle now compares against the implementer's declaration. The
   other half, having the E1.7 dispatch NAME the context directory rather than
   leaving each reviewer to assemble one, is a change to the stage and is left
   to the orchestrator.
