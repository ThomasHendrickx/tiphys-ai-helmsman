### The citation linter could NOT be run over the plan instance, and that is a finding


The runner exited 21. The mechanism, from the gate's own source: its
`documents` globs are `delivery/plan/**/*.md`, `delivery/verification/**/*.md`,
`delivery/decisions/**/*.md`, `delivery/tuition/**/*.md`,
`delivery/requirements/**/*.md` and `delivery/STATE.md`
(src/gates/citations.ts:233), every one of which requires `*.md` except the
last. A plan INSTANCE is a YAML document, and this run's instance additionally
lives under `delivery/evidence/`, which no glob and no precondition path
names. So the linter selects it under neither its extension nor its location.

Three things follow, and the third is the reason this is written up rather than
worked around:

1. The gate did what it is built to do. It reported `not-applicable` with its
   precondition id and the evaluated reason, which is exactly the shape
   DR-0018 requires instead of a silent skip.
2. Recording that not-applicable as "the linter exits 0 over the plan" would be
   the vacuous pass this exit test exists to refuse. The runner's exit 21 is
   recorded as it stands.
3. **Making it applicable would require an intervention E0.3 forbids.** A human
   invoking the linter's internals directly over the plan file, or inventing a
   markdown document under `delivery/plan/` so the gate has something to bite
   on, is "a human running a gate the registry did not select", which the
   binding rule names as an exit-test failure rather than a footnote. So the
   criterion is reported unmet and handed back.

The repair is a decision for the orchestrator and is not taken here. The two
shapes it could take, with no recommendation between them because both change a
merged artifact: widen the citation gate's `documents` config to cover the
delivery artifacts a run produces, or amend E1.4's text to name the linter's
real subject.
