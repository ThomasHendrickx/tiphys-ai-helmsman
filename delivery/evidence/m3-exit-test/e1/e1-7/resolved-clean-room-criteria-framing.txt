checklist clean-room
framing criteria-contract
entry-point Treat the plan's acceptance criteria as a contract the diff either meets or does not. Start at criterion 1 and walk to the last one before you form any opinion about the code.
probes 27
1. criteria-walked-with-evidence [criteria-walk] evidence-required
   Quote each acceptance criterion of the phase VERBATIM from the plan, cite the file and line that discharges it, and record met or not-met. A criterion discharged by a CI-deferred reason is not-met with that reason recorded; a criterion you could not evaluate is not-met, never omitted.
2. criteria-none-silently-dropped [criteria-walk] evidence-required
   Does the phase's plan section carry an acceptance criterion that your walk has no entry for? Count the criteria in the plan and the entries in your walk, and name any difference. A review that quietly skipped a criterion is the shape `verdict-criteria-complete` exists against, and this probe is what catches it before the check does.
3. subject-resolver-not-the-artifact-under-test [criteria-walk] evidence-required
   The plan review's high finding (PR-1) was that the kernel's only existing root resolver, `kernelRoot` in src/roles.ts, searches upward for the very directory this check exists to find missing, so it answers about an ancestor or throws. Establish BY EXECUTION, not by reading, that the delivered check does not have that property: stage an install with `roles/` removed INSIDE a parent that does carry `roles/` with a `.md` file, run the check against it, and record what it reported. Then say whether any OTHER upward search remains in the delivered code path, and name where you looked.
4. correctness-negative-values [changed-code] evidence-required
   What does each changed function do with a NEGATIVE number where the caller passes a count, a size, an index or a duration? Name the input you tried and the observed behaviour, not the behaviour you expect.
5. correctness-zero [changed-code] evidence-required
   What does each changed path do at ZERO: zero rows, zero bytes, zero matches, a zero-length list, a zero timeout? The process document's own illustration is a report whose amount rows are all zero and which is therefore indistinguishable from a report that measured nothing.
6. correctness-empty [changed-code] evidence-required
   What does each changed path do with EMPTY input: an empty string, an empty array, an empty file, an absent optional field? Say which of those the diff actually reaches and which it does not.
7. correctness-unicode [changed-code] evidence-required
   What does each changed path do with non-ASCII text: multi-byte characters, combining marks, a right-to-left run, a character whose UTF-16 length differs from its codepoint count? Name the string you tried.
8. correctness-state-that-cannot-exit [changed-code] evidence-required
   Is there a state this change can enter and NOT LEAVE: a wait with no timeout, a retry with no ceiling, a lease that cannot be broken, a queue entry nothing dequeues, a status no transition moves off? Name the state and the transition that is missing, or name the exit and cite it.
9. subject-two-stored-specs-repaired-not-weakened [changed-code] evidence-required
   This change edits two witness specs it does not own, `witness/doctor-retention-absent-path-and-full-profile.json` and `witness/doctor-retention-not-applicable-without-a-charter.json`, because it edits a source line their mutations quote. Establish that the repair preserves what those witnesses guarded rather than defanging them: compare each edited member against its pre-change form and say what the mutation still proves. A repair that makes a sibling phase's witness easier to satisfy is a finding.
10. test-red-without-the-fix [test-honesty] evidence-required
   Would each new test FAIL if the fix were reverted? The accepted proof is the red-witness harness's captured evidence file for that behaviour (`witness-records.json`, whose per-member `runs[].exitCode` and `failedNamedTests` record what actually ran), not a sentence in the work history saying it was checked. Cite the record. Where the behaviour is guarded against a DANGEROUS STATE rather than an absent feature, say which state the member encodes.
11. test-asserts-behavior-not-implementation [test-honesty] evidence-required
   Does each new assertion test BEHAVIOUR or an implementation detail? An assertion on a private helper's name, on call order, on a log string the program does not promise, or on the exact spelling of an internal flag passes while the behaviour rots. Name the assertion and the observable it stands for.
12. fence-catches-its-named-failure [test-honesty] evidence-required
   Does each guard, gate or fence in the diff catch the failure mode it is NAMED for? Construct the failure the name promises and run the guard against it. A guard whose condition does not test the property that matters is green and worthless; this repository has shipped one that tested a report file's EXISTENCE while its name said freshness, and one whose grep could not see the single byte it existed to catch.
13. claim-impossibility-constructed [test-honesty] evidence-required
   For every IMPOSSIBILITY claim, in the record's `claims[]` section and in any prose the section does not declare ("cannot be", "impossible", "there is no way to"), is the executed construction present? The distinction that makes this different from the universal-claim probe: a universal claim needs someone to try to FALSIFY it, an impossibility claim needs someone to try to BUILD the thing. T-006's own reviewer settled one in minutes with symlinkSync(p, p) raising ELOOP, where the record had claimed the state could not be constructed without privileges. Try to build it, and record the attempt either way.
14. claim-coverage-constructed [test-honesty] evidence-required
   For every COVERAGE claim ("is covered", "catches", "would catch", "recovers", "handles that anyway"), is the executed construction present? A coverage claim is settled by CONSTRUCTING the case said to be covered and running it, never by reading the guard and agreeing with it. T-006 records that the universal-quantifier rule already in the plan would have caught NONE of the three false claims M1-P5 produced, because impossibility, coverage and remedy claims are existential and causal rather than universal.
15. class-witness-has-two-members [test-honesty] evidence-required
   For any test the record presents as guarding a CLASS rather than one instance, have at least TWO structurally different members of that class been demonstrated red? M1-P6 produced two consecutive medium findings from this alone: one defang reddened a guard test and three others left it green, and the round after repeated the mistake one abstraction up. Name the two members and say how they differ structurally, not just in their values.
16. subject-staged-install-not-the-checkout [test-honesty] evidence-required
   Every assertion this change makes is about a resolved install. Determine which of its tests exercise a STAGED INSTALL and which exercise this checkout, and say whether any criterion is witnessed only by the second. A test that passes because the developer's own tree is complete is the hazard the phase declares as H2, and it is invisible to a green suite.
17. subject-capture-is-real-and-reproduced [test-honesty] evidence-required
   The change ships a captured CLI transcript at `witness/captures/doctor-kernel-artifacts-staged-install.txt` and a test that claims to reproduce it live. Verify the capture is real output rather than a hand-written string, and that the reproducing test would fail if the transcript and the program disagreed. State how you established each, and note that the red-witness rule treats a hand-written string here as the failure it exists to prevent.
18. deviation-judged-by-reviewer [deviations] evidence-required
   For each deviation declared in the work history's `deviations[]`, judge it yourself against the plan's intent and record the judgement. R-057b's words are "judged, never assumed by the implementer": the implementer's reason for a deviation is an input to your judgement, not a substitute for it. Name every declared deviation, including the ones you agree with.
19. unit-tests-for-changed-service-methods [gate-probe] evidence-required verifies-gate:unit-tests-for-changed-service-methods
   Does every service method changed in this diff have a unit test that exercises the changed behaviour? List the changed methods from the diff, and for each name the test or say there is none. "Service method" is not machine-enumerable, which is why this is a probe and not a script (D-11); enumerating it is your half of the gate.
20. fixtures-for-changed-component-states [gate-probe] evidence-required verifies-gate:fixtures-for-changed-component-states
   Does every component state changed in this diff have a story or a fixture? List the states the diff adds or alters, and for each name the fixture or say there is none. Same reason as the probe above: a component state is not machine-enumerable (D-11).
21. fix-round-not-covered [fix-round] evidence-required
   What regions did the round's derivation NOT cover, and why? Read `fix-round.not-covered` in the work history and name the excluded regions. A search whose scope is wrong returns an empty result that is indistinguishable from an absence of defects, and this project has been bitten by that three times: state/session.lock probed when the lease is state/orchestrator.lock; an inventory scoped to tasks/, state/ and worktrees/ while the missed path sat at the fleet root; a usage error read as a clean result. If the field is absent or says nothing was excluded, that is the finding.
22. fix-round-mechanism-named [fix-round] evidence-required
   Is the round's stated `mechanism` a MECHANISM or the finding restated? "A FIFO at the beacon hangs the guard" is a finding. "Reading a path whose type has not been established" is the mechanism. A round that fixed the instance the reviewer named, when the defect was the mechanism, is the shape that consumed roughly a third of M1's elapsed time. Quote the field and say which of the two it is.
23. fix-round-derivation-published [fix-round] evidence-required
   Is the derivation's FULL output present, or a summary of it? The contract asks for the exact command that enumerates every call site of the mechanism and its complete output, because a summary is where a call site the author did not think mattered stops being visible.
24. destructive-authority-declared [destructive-command] evidence-required
   For every command in the diff that can destroy work, answer all three: (1) does the command's OWN contract state that it holds destructive authority, in its own documentation rather than in a caller's; (2) are its force semantics INHERITED from a caller rather than declared here, which is how a command becomes destructive without any document saying so; and (3) does the command appear in `gates.manifest.json`'s `destructiveCommands` list? Open the manifest and quote the list. No script can judge (1) or (2); (3) is M2's computable list and this probe is you reading it rather than re-deriving it.
25. blast-radius-consumers [blast-radius] evidence-required
   Who else reads what this change writes? Run the search rather than recalling it: grep the repository for every exported name the diff changed, for every file path it writes, and for every field name it adds or renames, and paste the hit list. Then say, per hit, whether that consumer still holds. An empty hit list is a result only if you show the command that produced it.
26. blast-radius-behavior-under-old-callers [blast-radius] evidence-required
   For each consumer the search found, does it still behave the same? Name the call sites you opened, and the one you did NOT open and why. A blast-radius answer whose scope is unstated is indistinguishable from an absence of consumers.
27. shared-consumer-render-and-decide [blast-radius] evidence-required
   Does any field the diff touches both RENDER and DECIDE? A field that renders and decides is two fields. Search for each such field name across the repository and split the hits into the sites that display it and the sites that branch on it; if both sets are non-empty, that is the finding, and the concrete fix names the two fields it should become. Paste the search and the split.
