## Key decisions and the why that is invisible in the diff

1. WHAT AN EVALUATION IS, and therefore when the beacon is written. An
   evaluation is a pass over the wake sources that also rewrites
   state/watcher.beacon, and it happens at resident startup, on every
   heartbeat tick, whenever a wake is surfaced, and on every watch --once
   pass including a no-wake one. Between heartbeats a resident watcher
   SCANS every poll interval (and immediately on a filesystem event) and a
   scan that surfaces nothing writes nothing.
   This is the load-bearing design decision of the phase and it is forced
   by the criteria, not chosen for convenience. Criterion 1 requires beacon
   gaps that GROW; a beacon written every poll would produce flat gaps.
   PR-009's invariant is threshold > cap + poll, and that sum is exactly
   the oldest a healthy beacon can be under this rule (one full backoff cap
   between heartbeats, plus up to one poll interval before the due
   heartbeat is noticed). Under the every-poll reading the bound would
   simply be "poll" and the invariant would be meaningless. Witness W2
   (beacon written on every scan) is red 3/3.
2. Cadence, seen-state and the wake log all live under state/, which init
   gitignores, so nothing this phase writes is durable fleet content. The
   cadence file is the schedule (FM-006, FM-045): three separate --once
   processes share one schedule because none of them holds it in memory.
   Witness W10 (cadence not persisted) is red 3/3.
3. The heartbeat ordinal n in "heartbeat <n>" is the number of heartbeats
   since the last cadence reset, which is the backoffStreak the cadence
   file records. --max-heartbeats bounds THIS RUN's ticks, not the
   ordinal, so a bounded run behaves the same on a long-lived fleet as on
   a virgin one; the line it prints then reports the fleet's ordinal,
   which can be larger than the bound. Both directions are tested.
4. Stale conditions are NOT suppressed by the seen state, only turn-end
   edges are (PR-204 says "a turn-end wake"). A passed deadline with no
   turn-end is a standing condition that stays true until someone acts on
   it, so repeating it on the next pass is correct. A turn-end outranks a
   passed deadline for the same task: a task that finished late is
   finished, not abandoned. Both are asserted.
5. The seen-state advance mirrors src/lock.ts's discipline (an O_EXCL
   claim file, a re-read inside the claim, a staged rename, a confirming
   read) rather than reusing it: applyLeaseMutation is lease-shaped and
   src/lock.ts is out of this phase's edit scope. Enqueue-before-suppress
   is honored inside the claim: the wake record is appended and fsynced
   BEFORE the seen record advances, so a stop between the two duplicates a
   wake rather than dropping it (FM-046).
   CORRECTION TO THIS ENTRY, per the second reviewer's finding 1 (fix
   round): as first written this said a claim that cannot be taken within
   the bounded wait "is treated as 'someone else owns this wake': the pass
   reports no-wake and leaves the seen state alone, so the wake is still
   pending for the next pass. Duplicate rather than drop, in every arm."
   THAT WAS FALSE for the case that matters. It assumed the obstruction is
   always transient; a claim file left behind by a pass that stopped inside
   the window is permanent, and the reviewer reproduced two consecutive
   passes reporting no-wake against a real unconsumed turn-end with the
   beacon fresh throughout. The fix round makes a claim that cannot be
   taken a STUCK outcome: nonzero exit, one reason line naming the file,
   and no beacon write. See the fix-round section below.
6. state/last-wake.json is JSON Lines (one JSON object per line). The plan
   fixes the file's name and its append discipline, not its internal
   framing, and an appended JSON array would need a read-modify-write of
   the whole file on every wake. Declared rather than assumed. NOTHING IN
   THE KERNEL READS IT (C-1); the behavior watcher-currency-not-from-log
   fills it with garbage and then deletes it and asserts that neither
   changes a decision. Witness W12 (seen-ness read off the log tail, which
   is FM-052's exact incident) is red 3/3.
7. The check request is claimed by RENAME, which is the cheapest atomic
   exclusion available and makes the request genuinely one-shot: two
   racing passes cannot both surface one request, and the file is gone
   before the line is printed.
8. How a raised error is classified, decided once and applied
   structurally, because this module does filesystem work in a loop and
   the previous phase's two worst defects were raises walking past
   handlers that only understood returned failures. ABSENT is not an
   error: every task-state read goes through a helper that turns ENOENT
   into "not there" and rethrows everything else, because task directories
   legitimately vanish under a concurrent teardown. Any OTHER raise ends
   the pass with one reason line and a nonzero exit, through runStep
   (src/task.ts, reused, not re-implemented) and an async twin of it. The
   watcher stops LOUDLY rather than looping blind, and that composes with
   the guard: a stopped watcher stops advancing the beacon, so the next
   spawn, teardown or doctor tells the operator.
9. The guard is TOTAL: guard() never raises, whatever the filesystem does,
   because its three callers use it as an advisory that must not be able
   to take down the command it is advising. The classification is stated
   in both directions at the code: an unreadable or unparseable beacon
   counts as no supervision (fail toward warning), and a meta.json that
   does not parse is not counted as an open task.
   CORRECTION TO THIS ENTRY, per the second reviewer's finding 2 (fix
   round). Two things were wrong. The parenthetical justification, "(C-1:
   a file with no status carries no status, and inventing one would be
   worse than a missed advisory, which doctor reports anyway)", NAMED A
   SAFETY NET THAT DOES NOT EXIST: doctor reads no task state at all and
   its own module doc says so, so nothing anywhere reported an unreadable
   task record. And the choice it justified was wrong on its own terms:
   dropping a torn meta.json from the count made the guard announce
   "nothing is in flight to supervise" for a task that was genuinely open
   and genuinely unsupervised, which is the T-002 shape with the guard
   manufacturing the "nobody noticed" half itself. The fix round counts an
   unreadable record as in flight and the watcher surfaces it as
   "stale <task-id> meta"; see the fix-round section below.
10. The guard's predicate has two halves and both are load-bearing: open
    tasks AND an absent-or-old beacon. A fleet with nothing in flight
    cannot be stale. A guard that dropped the in-flight half would warn on
    every command in every idle fleet and the warning would stop meaning
    anything; witness W8 is red 3/3 against exactly that.
11. The PR-009 invariant is enforced wherever a cadence is built: at module
    load for the process-wide one (which is what makes criterion 12's
    second clause real) and again for every set of watch flags, so a
    generous --backoff-cap cannot quietly break the guard. The flag form
    reports it as a usage error naming both values; the environment form
    fails at import, which is what "load fails" costs (see the rough edge
    in the environment warnings below).
12. Defaults: base interval 60s, poll 15s, backoff cap 900s, stale
    threshold 1200s. FM-044 is a calibration starting point rather than a
    measured optimum; these satisfy the invariant with room to spare
    (900 + 15 = 915 < 1200) and put the guard's warning about twenty
    minutes after supervision goes quiet.
13. doctor's beacon check now uses the guard's threshold, so the two
    cannot disagree about what fresh means, and beacon-stale is
    promotable to FAIL under the watch profile alongside beacon-absent
    (R-095, the clause the M1-P2 code left for this phase). The check and
    the guard warning are deliberately different questions and the code
    says so: the check reports the beacon, the guard reports supervision
    missing while work is in flight.
14. Test-hold seam (TIPHYS_WATCH_TEST_HOLD), modelled on the one
    src/commands/lock.ts already carries, so criterion 7's interleave is
    STAGED rather than hoped for. It is loud when it fails to hold: a
    monotonic bound, a raise on timeout, and a <barrier>.released file the
    test asserts on, which is M1-P3's D-3 lesson applied before it could
    bite again.

   standing clerical gap, mandated by the section 3 test accounting rule
   and criterion 15. Pure append; nothing existing was modified or removed.
4. test/teardown.test.ts edited, which is NOT on the files-to-touch list
   and is the one real scope extension of this phase. Wiring the guard into
   teardown necessarily adds a line to teardown's stderr, and six M1-P4
   tests asserted on the WHOLE stderr (a line count, or a startsWith) as a
   proxy for teardown's single-reason-line contract (CR-303). Every scratch
   fleet in that file is exactly the state the guard fires on: work in
   flight, no watcher, no beacon. The edit is confined to that file's
   runCli helper, which now separates the advisory from the command's own
   stderr AND asserts the guard produced at most one line, so the CR-303
   contract is still checked, an unexpected second line still fails, and no
   assertion was weakened or deleted. The alternative would have been to
   soften the guard so it stays quiet when the beacon is absent, which the
   plan's step 2 explicitly forbids ("the beacon is absent or older than a
   threshold"). Flagged for the reviewer as the item most worth attacking.
5. Cadence flags and environment variables (--interval, --poll,
   --backoff-cap; TIPHYS_WATCH_INTERVAL_SECONDS, TIPHYS_WATCH_POLL_SECONDS,

   names "a configurable base" and a documented threshold without fixing a
   transport. This is the discharge of the first inherited input; see

### The shared property, which is what I actually fixed

Read together, the critical, the high, CR-501 and CR-503 are one defect
wearing four costumes: THE GUARD AND THE WATCHER COULD REPORT HEALTH FROM
EVIDENCE THEY DID NOT HAVE. For a component whose entire job is to notice
things, reassurance is the dangerous output, worse than a crash, because
everything above it trusts the silence.

The property now enforced, stated once in both module docs and applied at
every point where either module can produce a quiet outcome:

    NO HEALTH FROM AN ABSENCE OF EVIDENCE. Silence means "there is nothing
    to surface", and it may only be said about a state the code has
    POSITIVELY ESTABLISHED. Wherever the code cannot establish one, the
    output is the loud one.

Concretely, four places where the quiet branch used to be the default and
is now the one that has to earn it:

1. A seen-state claim that cannot be taken within the bounded wait is a
   STUCK CLAIM, not ordinary contention: nonzero exit, one reason line
   naming the file, and NO beacon write, so the guard sees supervision
   stop. No steal protocol, exactly as src/lock.ts refuses one.
2. A meta.json that exists and does not parse is not evidence that a task
   finished: the watcher surfaces "stale <task-id> meta" and the guard
   counts it as in flight.
3. A beacon that is absent, unparseable, or dated in the FUTURE are one
   class, no evidence that supervision ran, in the guard and in doctor.
4. The freshness floor is at least the cadence the watcher itself declared
   in the beacon it wrote, so a differently configured reader cannot call a
   healthy watcher stale. Crying wolf and never crying are the same defect
   from the operator's side, and the fix has to cover both directions.

One consequence found by my own tests while implementing (2): a task is a
DIRECTORY under tasks/, and treating every entry as one turned init's own
`tasks/.gitkeep` into a loud "unreadable record" failure. The loud-on-unknown
rule applies to task records; a stray file is not a broken task. Both
modules now check that the entry is a directory first.

### NEW-2 (HIGH): the ordering, and where it is enforced

A named pipe at tasks/<id>/meta.json hung `guard()` and the watcher
FOREVER, on this head and on every earlier one. Opening a FIFO for reading
with no writer blocks in the kernel; it is not an exception, so none of
this module's try/catch wrapping and none of its "the guard never raises"
reasoning touched it. The consequence is a live-lock of doctor, spawn and
teardown, which is the exact opposite of the warn-never-block charter
stated at the top of the same file. It predates the delta, and my own
module doc and work history claimed FIFO coverage, so the delivered claim
was false rather than merely silent.

THE ORDERING, enforced in one place, `surveyTaskRecords` in
src/liveness.ts, which is the only classifier either caller has:

1. `lstat` the record path (the link itself). Absent is not a record;
   any other raise is a problem.
2. `stat` the record path (what it resolves to). Raising ENOENT means a
   link resolving to nothing: it exists, so it is unreadable. Any other
   raise is a problem.
3. Only if that resolves to a REGULAR FILE is `readTaskMeta` called.
   Everything else (directory, FIFO, socket, device node, symlink to any
   of those) is classified as unreadable WITHOUT being opened.

So no path reaches a blocking read until the probe has established it
cannot block. Both callers inherit it because both call the one
classifier, which is the same property the previous round factored.

I did NOT add a non-blocking reader as defence in depth, and the reason is
the previous round's own lesson rather than laziness: a second reader
beside `readTaskMeta` would be a second implementation of "read a task
record", which is precisely what the factoring round removed and what
T-005 is about. The residual is stated at the code instead: the probe and
the read are two syscalls, so a path that changes type between them could
still be opened as something other than a regular file. Nothing in this
kernel writes that state.
