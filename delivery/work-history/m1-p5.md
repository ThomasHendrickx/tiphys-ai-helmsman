## Key decisions and the why that is invisible in the diff

1. WHAT AN EVALUATION IS, and therefore when the beacon is written. An
   evaluation is a pass over the wake sources that also rewrites
   state/watcher.beacon, and it happens at resident startup, on every
   heartbeat tick, whenever a wake is surfaced, and on every watch --once
   pass including a no-wake one. Between heartbeats a resident watcher
   SCANS every poll interval (and immediately on a filesystem event) and a
   scan that surfaces nothing writes nothing.
   This is the load-bearing design decision of the phase and it is forced
   by the criteria, not chosen for convenience. Criterion 1 requires beacon
   gaps that GROW; a beacon written every poll would produce flat gaps.
   PR-009's invariant is threshold > cap + poll, and that sum is exactly
   the oldest a healthy beacon can be under this rule (one full backoff cap
   between heartbeats, plus up to one poll interval before the due
   heartbeat is noticed). Under the every-poll reading the bound would
   simply be "poll" and the invariant would be meaningless. Witness W2
   (beacon written on every scan) is red 3/3.
2. Cadence, seen-state and the wake log all live under state/, which init
   gitignores, so nothing this phase writes is durable fleet content. The
   cadence file is the schedule (FM-006, FM-045): three separate --once
   processes share one schedule because none of them holds it in memory.
   Witness W10 (cadence not persisted) is red 3/3.
3. The heartbeat ordinal n in "heartbeat <n>" is the number of heartbeats
   since the last cadence reset, which is the backoffStreak the cadence
   file records. --max-heartbeats bounds THIS RUN's ticks, not the
   ordinal, so a bounded run behaves the same on a long-lived fleet as on
   a virgin one; the line it prints then reports the fleet's ordinal,
   which can be larger than the bound. Both directions are tested.
4. Stale conditions are NOT suppressed by the seen state, only turn-end
   edges are (PR-204 says "a turn-end wake"). A passed deadline with no
   turn-end is a standing condition that stays true until someone acts on
   it, so repeating it on the next pass is correct. A turn-end outranks a
   passed deadline for the same task: a task that finished late is
   finished, not abandoned. Both are asserted.
5. The seen-state advance mirrors src/lock.ts's discipline (an O_EXCL
   claim file, a re-read inside the claim, a staged rename, a confirming
   read) rather than reusing it: applyLeaseMutation is lease-shaped and
   src/lock.ts is out of this phase's edit scope. Enqueue-before-suppress
   is honored inside the claim: the wake record is appended and fsynced
   BEFORE the seen record advances, so a stop between the two duplicates a
   wake rather than dropping it (FM-046). A claim that cannot be taken
   within the bounded wait is treated as "someone else owns this wake":
   the pass reports no-wake and leaves the seen state alone, so the wake
   is still pending for the next pass. Duplicate rather than drop, in
   every arm.
6. state/last-wake.json is JSON Lines (one JSON object per line). The plan
   fixes the file's name and its append discipline, not its internal
   framing, and an appended JSON array would need a read-modify-write of
   the whole file on every wake. Declared rather than assumed. NOTHING IN
   THE KERNEL READS IT (C-1); the behavior watcher-currency-not-from-log
   fills it with garbage and then deletes it and asserts that neither
   changes a decision. Witness W12 (seen-ness read off the log tail, which
   is FM-052's exact incident) is red 3/3.
7. The check request is claimed by RENAME, which is the cheapest atomic
   exclusion available and makes the request genuinely one-shot: two
   racing passes cannot both surface one request, and the file is gone
   before the line is printed.
8. How a raised error is classified, decided once and applied
   structurally, because this module does filesystem work in a loop and
   the previous phase's two worst defects were raises walking past
   handlers that only understood returned failures. ABSENT is not an
   error: every task-state read goes through a helper that turns ENOENT
   into "not there" and rethrows everything else, because task directories
   legitimately vanish under a concurrent teardown. Any OTHER raise ends
   the pass with one reason line and a nonzero exit, through runStep
   (src/task.ts, reused, not re-implemented) and an async twin of it. The
   watcher stops LOUDLY rather than looping blind, and that composes with
   the guard: a stopped watcher stops advancing the beacon, so the next
   spawn, teardown or doctor tells the operator.
9. The guard is TOTAL: guard() never raises, whatever the filesystem does,
   because its three callers use it as an advisory that must not be able
   to take down the command it is advising. The classification is stated
   in both directions at the code: an unreadable or unparseable beacon
   counts as no supervision (fail toward warning), and a meta.json that
   does not parse is not counted as an open task (C-1: a file with no
   status carries no status, and inventing one would be worse than a
   missed advisory, which doctor reports anyway).
10. The guard's predicate has two halves and both are load-bearing: open
    tasks AND an absent-or-old beacon. A fleet with nothing in flight
    cannot be stale. A guard that dropped the in-flight half would warn on
    every command in every idle fleet and the warning would stop meaning
    anything; witness W8 is red 3/3 against exactly that.
11. The PR-009 invariant is enforced wherever a cadence is built: at module
    load for the process-wide one (which is what makes criterion 12's
    second clause real) and again for every set of watch flags, so a
    generous --backoff-cap cannot quietly break the guard. The flag form
    reports it as a usage error naming both values; the environment form
    fails at import, which is what "load fails" costs (see the rough edge
    in the environment warnings below).
12. Defaults: base interval 60s, poll 15s, backoff cap 900s, stale
    threshold 1200s. FM-044 is a calibration starting point rather than a
    measured optimum; these satisfy the invariant with room to spare
    (900 + 15 = 915 < 1200) and put the guard's warning about twenty
    minutes after supervision goes quiet.
13. doctor's beacon check now uses the guard's threshold, so the two
    cannot disagree about what fresh means, and beacon-stale is
    promotable to FAIL under the watch profile alongside beacon-absent
    (R-095, the clause the M1-P2 code left for this phase). The check and
    the guard warning are deliberately different questions and the code
    says so: the check reports the beacon, the guard reports supervision
    missing while work is in flight.
14. Test-hold seam (TIPHYS_WATCH_TEST_HOLD), modelled on the one
    src/commands/lock.ts already carries, so criterion 7's interleave is
    STAGED rather than hoped for. It is loud when it fails to hold: a
    monotonic bound, a raise on timeout, and a <barrier>.released file the
    test asserts on, which is M1-P3's D-3 lesson applied before it could
    bite again.

## Disposition of the three inherited inputs

1. A FLAG FOR THE WATCHER'S BASE AND POLL INTERVAL: DISCHARGED, and named
   for the M1-P6 harness to adopt.
   `tiphys watch [--once] [--interval <seconds>] [--poll <seconds>]
   [--backoff-cap <seconds>] [--max-heartbeats <n>]`, all accepting
   fractional seconds. The harness can replace its fixed upper bounds (a
   beacon within 120s, a wake within 180s) with bounds derived from its own
   `--interval` and `--poll`: this phase's own tests run the component at
   0.1s to 0.5s and the suite's total addition is 4.4s.
   The guard's threshold has no flag, because the guard runs inside spawn,
   teardown and doctor, which have no watch flags; it and the cadence are
   settable for every command through TIPHYS_WATCH_INTERVAL_SECONDS,
   TIPHYS_WATCH_POLL_SECONDS, TIPHYS_WATCH_BACKOFF_CAP_SECONDS and
   TIPHYS_WATCH_STALE_SECONDS. A harness that shortens the cadence and
   wants the guard to match should set the environment variables, and any
   combination violating PR-009 is refused with both values named, so the
   harness cannot silently configure a guard that cries wolf.
   Note for the harness author: exit-test step A5 starts the resident
   watcher with the harness owning the process (C-3). With a short
   `--interval` that watcher will still be silent until A6's turn-end
   arrives, which is the behavior A8 asserts.
2. SPAWN'S STDOUT IS NOT ASSUMED, ANYWHERE: DISCHARGED, structurally. The
   watcher reads tasks/<id>/meta.json, tasks/<id>/turn-end,
   tasks/<id>/executor.json, state/check-request and its own state files,
   and nothing else. It never runs a program, never opens a pipe and never
   reads any other program's output, so there is no stdout contract for it
   to depend on. The suite's assertions on spawn's stdout are the TEST
   asserting what the CLI printed, never the watcher consuming it. The
   T-002 witness deliberately makes the point: it discovers the abandoned
   task from files alone, after the process that would have printed
   anything was stopped.
3. TUITION T-002 ABANDONED-TASK DETECTION: DISCHARGED for the declared
   deadline, and explicitly NOT extended beyond it, with the reason.
   Discharged half: an open task whose executor.json deadline has passed
   with no turn-end is surfaced as "stale <task-id> deadline" from file
   evidence alone (C-2), and it is witnessed against the real incident
   shape rather than a synthesized file state. The behavior
   watcher-abandoned-spawn-detected runs a real `tiphys spawn` with a real
   git worktree and a payload that writes uncommitted work, stops the
   SPAWN PROCESS ITSELF with the payload still running, then asserts the
   dangerous state as it actually is (no turn-end file, meta status open,
   `git status --porcelain` non-empty in the worktree, a deadline in the
   executor record) before asserting that `watch --once` exits 0 with
   exactly "stale ab1 deadline". W6 is red 3/3 against the detector's
   removal. M1-P4's note to this phase was right: because M1's only adapter
   runs the payload to completion in the foreground, this state can only
   arise if the spawn process stops, and that is exactly what the test
   does.
   NOT DONE, deliberately: the deadline-LESS half. T-002 asked for "task
   open, no turn-end, worktree dirty" as a wake condition. The plan's stale
   enumeration adds exactly one entry (PR-207, deadline) and the plan's own
   section 4 not-proven list states that abandonment of a task spawned
   without a deadline is not auto-detected in M1, with manual teardown as
   the recovery. Adding a dirty-worktree probe would contradict a written
   plan clause and would put a git call in the watcher's idle loop, and
   M1-P3's five rounds were spent hardening machinery for states the
   milestone never enters. The requirement is therefore recorded here and
   passed on rather than improvised: whoever plans the milestone that wants
   deadline-less abandonment detection (M2 or M4) inherits it, and the
   cheapest honest route is to make --deadline mandatory or defaulted at
   spawn rather than to teach the watcher to inspect worktrees.

## Simplicity, and what was deliberately NOT built

The M1-P3 filter (five rounds spent hardening machinery for a scenario the
milestone never enters) was applied deliberately. Left out, each with its
reason:

- No classification, triage or absorption of wakes. The watcher surfaces
  one line and exits. FM-057 records that firstmate's absorb-triage grew to
  most of its 1126 lines because its completion signals were weak; ours are
  files with exit codes.
- No dirty-worktree probe in the stale enumeration (inherited input 3).
- No retry, repair or recovery machinery around the seen-state claim: a
  claim that cannot be taken means the wake stays pending, which is one
  line of code and the correct outcome.
- No lease integration in the watcher. Supervision is not a mutation and
  the plan asks for no holdership check on watch; adding one would have
  invented a rule.
- No log reading of any kind (C-1), no process questions of any kind (C-2),
  and no way to run either mode outside the caller's process (C-3).
- No second wake-source abstraction: three sources, one function, sorted
  task ids, one priority order.

   the PR-009 invariant fails at IMPORT, so the CLI reports it as a raised
   error with a stack trace rather than as a single reason line. The
   message names all three values. This is what the plan's "load fails"
   costs; the flag form (`--backoff-cap`) gives a clean exit-64 usage
   error. Worth a one-line top-level handler in bin/tiphys.ts if a later
   phase owns that file.

   file is one level down). Any platform where that throws falls back to
   the poll interval silently, which is what the poll interval is for; the
   only observable difference is wake latency.
9. NEW: suite wall time is 71.2s (66.8s at the end of M1-P4). The addition
   is this phase's real-clock cadence waits, which are stated at each test
   and total about 15s of sleeping inside a file that runs in parallel with
   the rest. Budget harness timeouts off 72s, not off the older figures.
10. NEW: the resident watcher wins the natural race against a concurrent
    `--once` essentially always (10 of 10 measured), because it is already
    armed while the single pass pays Node startup. A test that wants the
    single pass to win must stage the interleave with
