## What this phase is

Two things that the plan says are one unit of value, and it is right about
that. The fleet home is brought up on the REAL remote, and the blindness that
bring-up exposes is fixed in the same pull request. Fixing it elsewhere would
mean landing a measurement that says the kernel's own doctor calls a
charterless fleet ready, and then landing the repair later.

The third thing is smaller and is the other half of an edit M4-P15 could only
do one side of: `assurance-modes.yaml` carried DR-0012's fix-round bound of 2
while DR-0035's ceiling is 3.

## The mechanism, not the finding

The plan's criterion 5 could be read as one line of table data. It is not. The
defect is a SHAPE this repository has paid for repeatedly and has a name for:
**a guard whose condition does not test the property that matters is green and
worthless.**

`tiphys doctor --for full` is the command an operator runs to ask whether a
fleet is ready for full mode. Full mode is the one whose pipeline resolves
roles, checklists and retention duties out of a charter. The profile promoted
`retention-undeclared` (a charter exists and declares no retention paths) and
deliberately left `retention-not-applicable` (no charter document at all) a
WARN. So the command exited 0 on a fleet that had no charter, and its green was
not evidence about the one thing a reader takes it for.

The reason the condition was left unpromoted is in the code and it is a good
reason for the GENERIC profile: a fleet legitimately sits charterless before
its charter is written, `tiphys init` writes none because authorship is an
owner duty, and M3-P8 fix round 1 broke `scripts/m1-exit-test.sh` step A2 by
failing every freshly initialized fleet. Carried into `full` that reason stops
holding, because `full` is exactly the mode the charter is a precondition of,
and because the operator's remedy (write the charter) is reachable, unlike the
`branches` check's remedy of deleting a remote ref, which this container
refuses.
