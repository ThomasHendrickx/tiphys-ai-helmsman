**The dispatch and the spec name two different vocabularies, and they are two
AXES rather than one disagreement.** The dispatch says each row is `PORTED`, a
`GAP`, or `FALSE`. The spec at delivery/plan/kernel-plan-m4.md:3158 says the
closed vocabulary of three is `PORT` naming a kernel artifact, `DELETE` with a
reason, or `KEEP` with the DR-0029 side. Collapsing them loses information
either way: `PORTED` is a FINDING about the world as it is now, and `PORT` is a
DISPOSITION about what happens next. A rule can be a `GAP` today and still be
`KEEP`, because it belongs to this project's predicate rather than to the
kernel's process.

Resolution, recorded before any code: every row carries BOTH, as `status` in
`{PORTED, GAP, FALSE}` and `disposition` in `{PORT, DELETE, KEEP}`, and the
checker enforces the cross-consistency that makes them non-redundant
(`PORTED` if and only if `PORT`; a `GAP` row must name what kernel destination
is missing; a `FALSE` row must say what this phase corrected).

delivery/verification/m4-prototype-probes.md:1. The probe document overturns

## The grammar, and why the count is 279 rather than 24

Criterion 1 requires the row count to be produced by a committed extraction
command rather than a human count. The extraction is
`node scripts/check-retirement-inventory.mjs --extract`, and the grammar it
implements is declared in the script's own header.

**Choosing the grammar was the one real design decision in this phase, and the
alternatives were measured rather than argued.** A rule anchor is a line at
COLUMN ZERO that is a markdown heading, a top-level enumerated item, a top-level
bullet, a bolded lead-in paragraph, or (in the JavaScript root) a top-level
function or binding declaration. Measured on the three roots:

| grammar | rules found | what it drops |
|---|---|---|
| headings only | 24 in `CLAUDE.md` | the 7 binding conventions, the 14 standing warnings, the 7 `## Never` bullets |
| headings and numbered items | 82 in `CLAUDE.md` | the `## Never` bullets, and the bolded lead-ins |
| headings, numbers, bold lead-ins | 208 across three roots | every top-level bullet |
| **all four kinds (shipped)** | **279 across three roots** | nothing above column-zero granularity |

The third row is the one that decided it: **the rule this phase was dispatched
to correct is a bolded lead-in**, not a heading and not a numbered item, and a
heading-only grammar would not have given it a row at all. The fourth row is the
one I nearly did not take, because 71 more rows is real work; the `## Never`
bullets settled it, since C-1, C-2 and C-3 are stated there and nowhere else in
that file.

Column zero is load-bearing: an indented `1.` inside a fenced block is
CONTINUATION of the rule above it, not a new rule, and treating it as one would
inflate the count with fragments.

## The defect this phase found in its own checker, with the derivation

**MECHANISM, not the finding: a program that writes a large report to stdout and
then calls `process.exit()` loses the tail of the report, because a pipe makes
that write asynchronous and `process.exit()` does not wait for it.**

The finding was three failing tests. The first run failed tests 3, 7 and 14; the
next run of the same code failed 3, 7 and 8; test 7 passed alone and failed in
company. That is not a flaky test, it is a truncation point moving with timing.
The checker prints one line per unresolved row, so a negative fixture emits tens
of kilobytes and the assertions look for a line near the end.

The fix is `process.exitCode = main(...)` at scripts/check-retirement-inventory.ts:551
(the shipped file is the `.mjs` of that name; quoted here because the line moves
with edits). Fifteen of fifteen tests pass after it, three consecutive runs, and
that repeat is in the capture below.

## What this phase did NOT cover

1. **The verification is per DESTINATION CLAUSE, not per rule.** Where several
   rows share a kernel clause they share its probe, so the row-level claim is
   "this rule's destination is that clause" and the command-level claim is "that
   clause exists and carries the named obligation". 279 rows map to 118
   disposition groups.
2. **"Not weaker" is mechanical in FORM and still a reading in SUBSTANCE.** The
   witness pair proves the probe resolves in the destination and does not
   resolve in a same-kind sibling. It does not prove the destination's clause is
   as strong as the retired rule. The claim-grep row is the exception where the
   mechanical form reaches the substance, because roles/implementer.md:295
   carries the grep PATTERN literally; most rows are not that lucky. This is the
   thing a reviewer should spot-check, and it is named here rather than left to
   be discovered.
3. **The negative witnesses are all `sibling` kind, none `history`.** A witness
   that runs the probe against a pre-port git blob would be literally "red under
   the old rule". I chose sibling because a history witness needs full history
   and fails in a shallow clone, which would make the checker's verdict depend
   on how the repository was fetched. The checker accepts both kinds, so a later
   phase can strengthen individual rows without changing the guard.
4. **The checker does not compare captured OUTPUT, only exit codes.** Byte
   comparison would redden every time a file grew a line, which would train a
   reader to regenerate captures without reading them. The output is recorded
   for a human; the exit code is what is enforced.
5. **Two of the four FALSE rows are recorded and not edited**, because their
   text is in the skills tree and this phase's files-to-touch list does not
   include it.
6. **Nothing in the three roots is deleted** (criterion 7). It needs no separate
   mechanism: a deletion removes an anchor and the surviving row goes red as
   stale, which is what the rule-without-a-row and stale-row tests assert.
7. **The rows were assigned by reading**, in groups, by section span. The
   assignment is committed as data in the JSON and every assignment is
   re-verified by a command, but the JUDGMENT that a given rule belongs to a
   given kernel clause is mine and is the reviewable part.
