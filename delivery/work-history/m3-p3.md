### D2. SCOPE GAP, reported not worked around: `templates/charter.example.yaml`

Step 4 replaces the charter schema's placeholder mode enum
(`full, standard, fast, yolo`) with this phase's mode ids
(`full, direct-pr, local-only`); criterion 4 requires `delivery-mode: yolo` to
exit 1. The SHIPPED template `templates/charter.example.yaml` declares
`delivery-mode: standard` and `assurance-tier: standard`, and three EXISTING
tests in `test/schemas.test.ts` parse that template and assert
`assert.deepEqual(validateToLines(...), [])`, an EXACT empty diagnostic list:

  - "a charter with no release-verification field is rejected naming the field"
  - "mode none with no reason is rejected naming reason and with a reason is accepted"
  - "an invented release-verification shape is rejected naming the offending property"

So the enum edit that criterion 4 requires makes the shipped template invalid
and reddens three tests this phase does not own. There is no form of criterion 4
that avoids it: keeping `standard` in the enum fails
`charter-mode-enum-matches-modes`, and keeping `yolo` fails criterion 4 directly.

`templates/charter.example.yaml` is NOT on
`delivery/plan/phase-declarations/m3-p3.json`. It is edited here (two values,
`standard` to `full`) because the phase cannot be delivered otherwise (SETTLED
BY CAPTURE in the claim-grep section below: the template reverted and three
existing tests observed red), and the gap is REPORTED to the orchestrator rather than fixed by widening the
declaration from inside the branch. The scope gate reads the declaration from
the MERGE BASE, so only an amendment on `main` (the shape commit c2e2009 used)
can clear it.

Second, smaller: `test/fixtures/charter-no-escalation.yaml` also carries
`delivery-mode: standard`. Its test asserts by `assert.match` on one pointer and
still passes, so nothing reddens, but the fixture stops being "the valid example
with exactly one thing changed" (section 2.3 rule 1) and now carries two
defects. `test/fixtures/` is not on the declaration either. NOT edited here;
reported.

### D3. Criterion 1's literal command and criterion 3(d)'s standing rule contradict

Criterion 1 says `tiphys validate --type assurance-modes assurance-modes.yaml`
exits 0. Criterion 3(d) says `mode-gate-sets-resolve` is run with `--context`,
and the hazard map adds "plus M3-P1 criterion 4c's standing rule that the same
check invoked WITHOUT `--context` prints `SKIPPED <check-id> no context` and
exits nonzero, so the cross-document rule cannot pass by not being run".

Both cannot hold for the same invocation. The hazard-covering half wins:
`mode-gate-sets-resolve` and `charter-mode-enum-matches-modes` both carry
`requiresContext: true`, so the bare command exits 1 with two SKIPPED lines and
the context-bearing form exits 0. Both forms are captured under criterion 1
below and both are asserted by registered tests. Nothing was softened to make
the plan's sentence true.

### D4. `charter-mode-enum-matches-modes` watches BOTH charter mode fields

Step 4 says "Add `mode` and `assurance-tier` validation to the charter schema's
enum". M3-P1 shipped the identical placeholder enum on `delivery-mode` and on
`assurance-tier`. The check compares the declared mode ids against BOTH, and
both were replaced. A check watching one of two identical lists leaves the other
free to drift, which is the hazard rather than a smaller version of it.

### D5. `full`'s merge authority is `delegated-under-conditions`, not `owner`

Blueprint section 8's table says `owner` for the full row. The shipped `full`
declares `delegated-under-conditions` with DR-0012's six conditions verbatim and
`granted-by: DR-0012`. Reasoning, in the order it decided the question:

1. Criterion 4c REQUIRES `full` to carry DR-0012's own escalation bounds. A mode
   carrying DR-0012's limits while declaring an authority regime DR-0012
   replaced is internally incoherent, and incoherence in this artifact is the
   hazard class the phase is named after.
2. DR-0015 removed the owner from the merge path for this project entirely,
   milestone boundaries included. `owner` would record a regime this project has
   left.
3. The plan's own justification for the third enum value is that "a mode
   vocabulary that cannot express the authority regime actually in force would
   force the next such grant to live outside the artifacts". The regime actually
   in force IS this one.

`owner` and `owner-approves-orchestrator-merges` both remain representable and
`local-only` still declares the second, so no other project's governance was
made unexpressible. The blueprint's value and the departure from it are stated
in a comment at the field itself, not only here.

### D6. `orchestrator-diff-review` was added to the stage vocabulary

Blueprint section 8's local-only row is "implement, orchestrator diff review,
local fast-forward". The plan enumerates twelve stages for `full` and does not
enumerate the CLOSED SET, so local-only's middle stage had no id. Two options
were considered: describe local-only as `[implement, merge-on-green]` and lose
the review, or add the id the blueprint already names. The second is faithful to
the source and the first misdescribes the mode, so there was no comparable pair
to escalate (DR-0016). The enum is thirteen ids; `full`'s pipeline is twelve.

### D7. One behavior beyond the plan's list of fifteen

The plan names fifteen new behaviors and all fifteen are registered. A
sixteenth, `role-model-config-tiers-by-risk`, is registered for the test that
asserts R-075's rule over the SHIPPED role data (which roles took which tier,
that both review roles carry a family constraint, that the implementer carries
the phase-class half). Criterion 1 only asserts that the document validates, and
the schema permits `cheaper` on any role, so without this test nothing said what
the data actually is. Registered rather than left unregistered because
CLAUDE.md requires every new behavior to be in the registry.

### D8. `strongest-for` is a field the plan's field list does not name

R-075 is phase-class scoped for the implementer ("strongest for money-path and
architecture phases ... cheaper for mechanical phases"). The plan's field list
for `role-model-config` is `{tier, charter-override, review-model-family?}`, and
a flat `tier` drops half of R-075's rule. `strongest-for` is an optional array of
phase classes, DATA only: nothing in M3 classifies a phase and no resolver reads
it. Recorded here because adding a field the plan's prose does not enumerate is a
deviation even when the requirement it serves is cited.

### D9. `charter-override: allowed` is uniform across all six roles

The plan asks for "a `charter-override: allowed` flag". Every role ships
`allowed`, so today the field discriminates nothing. It is shipped despite that
because the charter override is L4 and lands at M4 (R-075's migration-table
note), so the M4 adapter has a field to read rather than a convention to infer.
Said plainly rather than presented as if it carried information.

## Mechanism 1 (HIGH): a uniqueness constraint asserted by a predicate that does not test identity

### The mechanism, not the instance

`uniqueItems` is DEEP-OBJECT equality. On an array of records keyed by an id
field it asserts "no two entries are identical", which is not the property any
consumer relies on. Two entries may share an `id` and differ anywhere else and
the array is `uniqueItems`-clean; every consumer that resolves an entry BY ID
then silently takes one of them, chosen by document order.

The finding named `modes[]`. The mechanism is the predicate, and it had already
occurred once in this milestone: M3-P1's B-003 was the same predicate on
`acceptance[].id`, closed at that instance. It came back one phase later in a
different document, and the two sweeps below are the first time the class has
been enumerated in this repository: M3-P1's fix added occurrence counting to one
check over one array, which is visible in `src/checks.ts` at

## Mechanism 4: control bytes in authored source

### The two bytes, and what the separator was for

`src/checks.ts` carried two literal NUL bytes as the separator of a `join()`
inside `charter-mode-enum-matches-modes`. Rendered with the byte shown as the
two characters `^@`, which is how `cat -v` prints it:

```
      const enumerated = stringsAt(definition, "enum").slice().sort();
      if (enumerated.join("^@") !== declaredIds.join("^@")) {
```

The criteria lens is right that this is worse than an unreviewable diff: the
byte sits past git's sniff window, so `git diff --stat` reports no `Bin` and the
hunk renders as `join("")`, which LOOKS CORRECT to a reviewer reading the diff.
The guard half is the orchestrator's and is fixed in PR #55.

### The fix, and the semantics change, stated rather than slipped in

The instruction was not to silently change the join's semantics. **They did
change, and here is exactly how.** The comparison is now element-wise with no
separator at all:

```
function sameStringList(left: readonly string[], right: readonly string[]): boolean {
  if (left.length !== right.length) {
    return false;
  }
  return left.every((value, index) => value === right[index]);
}
```

- Before: exact list equality for every input CONTAINING NO NUL, and a false
  equal for any pair whose values straddle a NUL.
- After: exact list equality for every input, with no separator to straddle.

The direction is strictly more correct and no observable behaviour moved,
because no caller can produce a NUL-bearing value today: both lists come from
YAML or JSON decoding of documents whose values are enum-constrained.

**Why the byte was not simply rewritten as an escape.** Writing the same
separator as a six-character escape would have been the INSTANCE fix. The
mechanism is that a separator join answers "are these lists equal" with a PROXY
faithful only for separators the values cannot contain, which is the same shape
as the two findings this round is mostly about. And the obvious human-readable
separator, a single space, would have introduced a real defect: `["a b"]` would
compare equal to `["a", "b"]`.

### The tests that cover it

The existing behavior `charter-mode-enum-drift-detected` covers both directions
of the comparison and is unchanged. A new registered behavior,
`charter-mode-enum-compared-element-wise`, covers the separator class directly
with two arms, and the test asserts the discriminating fact inline:

```
assert.equal(["a b"].join(" "), ["a", "b"].join(" "));
```

- **Arm 1** is length-DIFFERING and join-equal under a space separator.
- **Arm 2** is length-EQUAL and content-different.

**Arm 2 exists because arm 1 alone was not a witness, and that was measured
rather than reasoned.** The first version of the witness spec carried a member
that replaced the whole comparison with the space join, and it came back
**GREEN**: the surviving `left.length !== right.length` guard caught arm 1
before the join ran, so the member proved nothing about the element-wise loop.
The captured run is in the witness table below. Adding arm 2 gave each member a
property only it can break: member 1 (space join) is red on arm 1, member 2
(length-only comparison) is red on arm 2.

That is this project's own rule catching this round's own work: a guard whose
condition does not test the property that matters is green and worthless.

### The mechanism: a containment predicate standing in for an equality predicate

`resolved.text.includes(condition)` over the record as one normalized blob asks
"does this string occur ANYWHERE", when the property that matters is "is this
string a WHOLE CONDITION of that record". Containment is monotone in shortness:
the shorter the fabrication, the likelier it passes, so the check was weakest
exactly where an attacker or a careless author is strongest.

**The instance was the six conditions. The mechanism is the predicate**, and
this repository already carries it elsewhere: `scripts/check-clause-map.mjs:195`
marks a clause discharged because its id OCCURS in the artifact, which the M3-P2
arbitration recorded as the fourth instance of a guard whose condition does not
test the property that matters. This is the fifth.

### The fix

`quotableUnits(text)` extracts the record's markdown list items and paragraphs,
strips each marker, normalizes whitespace, and returns a Set. A condition is
accepted only if it EQUALS one of those units. Both halves are load-bearing:

- **whole**, so a fragment cannot match, which is what kills containment;
- **item rather than document**, so the check reads no section boundary at all:
  `quotableUnits` takes every list item and paragraph of the record and the
  comparison consults the whole set. That is what keeps the check free of the
  structure assumption that would have made it project-specific, and it is why
  the omission direction still cannot live in the shipped check.

Blank lines, headings and code fences terminate a unit and belong to none, so a
heading is not in the returned set. That is asserted in the registered test
rather than claimed here: `units.has('What "clean" means, defined here so it
cannot be softened later')` and `units.has("Decision")` are both asserted false,
against DR-0012's own two heading texts.

**The cost to a consuming project, stated because it is a real constraint**: a
condition must be quoted as a COMPLETE list item or paragraph. A paraphrase, or
half of a longer item, is now a violation. That is exactly what the schema's own
`$comment` already claimed ("quoted from the decision record rather than
summarized") and it is now enforced instead of asserted.

   did not reuse it. `quotableUnits` now applies the same rule (see
   `closesFence`), so the two agree instead of disagreeing.

What the machine models now: fenced code (content contributes nothing), indented
code (same), ATX headings at any indent, setext headings, thematic breaks, list
items with their content column, and paragraphs.

**Every ambiguity is resolved towards EXCLUDING more, and that is a decision,
not a default.** The two directions are not symmetric. Excluding a unit that
should have been quotable makes a legitimate condition fail to match, and that
is a loud diagnostic naming the condition. Admitting a unit that should not be
quotable makes a FABRICATED condition pass, silently, which is the entire hazard
`mode-conditions-quote-granted-by` exists for. So a fence opens at any indent
(CommonMark allows at most three spaces), an unclosed fence swallows the rest of
the document, `#` at any indent is a heading, and a paragraph followed by a
setext underline is discarded rather than kept.

### The comment that was stronger than its code

`src/checks.ts:825-826` said "a blank line, a heading and a code fence all END
the unit in progress and belong to none, so a condition can never match a
heading or a fence". The second half was FALSE for a fence and false for an
indented heading. This is the same failure this repository's own rules name in
two places (T-008's postscript, the red-witness rule one level up): a claim that
overstates what the code does is how the next reader stops checking. The
docstring now states what is modelled, and, in its own paragraph, what is NOT.
