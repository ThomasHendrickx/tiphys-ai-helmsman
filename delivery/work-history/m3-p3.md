### D2. SCOPE GAP, reported not worked around: `templates/charter.example.yaml`

Step 4 replaces the charter schema's placeholder mode enum
(`full, standard, fast, yolo`) with this phase's mode ids
(`full, direct-pr, local-only`); criterion 4 requires `delivery-mode: yolo` to
exit 1. The SHIPPED template `templates/charter.example.yaml` declares
`delivery-mode: standard` and `assurance-tier: standard`, and three EXISTING
tests in `test/schemas.test.ts` parse that template and assert
`assert.deepEqual(validateToLines(...), [])`, an EXACT empty diagnostic list:

  - "a charter with no release-verification field is rejected naming the field"
  - "mode none with no reason is rejected naming reason and with a reason is accepted"
  - "an invented release-verification shape is rejected naming the offending property"

So the enum edit that criterion 4 requires makes the shipped template invalid
and reddens three tests this phase does not own. There is no form of criterion 4
that avoids it: keeping `standard` in the enum fails
`charter-mode-enum-matches-modes`, and keeping `yolo` fails criterion 4 directly.

`templates/charter.example.yaml` is NOT on
`delivery/plan/phase-declarations/m3-p3.json`. It is edited here (two values,
`standard` to `full`) because the phase cannot be delivered otherwise (SETTLED
BY CAPTURE in the claim-grep section below: the template reverted and three
existing tests observed red), and the gap is REPORTED to the orchestrator rather than fixed by widening the
declaration from inside the branch. The scope gate reads the declaration from
the MERGE BASE, so only an amendment on `main` (the shape commit c2e2009 used)
can clear it.

Second, smaller: `test/fixtures/charter-no-escalation.yaml` also carries
`delivery-mode: standard`. Its test asserts by `assert.match` on one pointer and
still passes, so nothing reddens, but the fixture stops being "the valid example
with exactly one thing changed" (section 2.3 rule 1) and now carries two
defects. `test/fixtures/` is not on the declaration either. NOT edited here;
reported.

### D3. Criterion 1's literal command and criterion 3(d)'s standing rule contradict

Criterion 1 says `tiphys validate --type assurance-modes assurance-modes.yaml`
exits 0. Criterion 3(d) says `mode-gate-sets-resolve` is run with `--context`,
and the hazard map adds "plus M3-P1 criterion 4c's standing rule that the same
check invoked WITHOUT `--context` prints `SKIPPED <check-id> no context` and
exits nonzero, so the cross-document rule cannot pass by not being run".

Both cannot hold for the same invocation. The hazard-covering half wins:
`mode-gate-sets-resolve` and `charter-mode-enum-matches-modes` both carry
`requiresContext: true`, so the bare command exits 1 with two SKIPPED lines and
the context-bearing form exits 0. Both forms are captured under criterion 1
below and both are asserted by registered tests. Nothing was softened to make
the plan's sentence true.

### D4. `charter-mode-enum-matches-modes` watches BOTH charter mode fields

Step 4 says "Add `mode` and `assurance-tier` validation to the charter schema's
enum". M3-P1 shipped the identical placeholder enum on `delivery-mode` and on
`assurance-tier`. The check compares the declared mode ids against BOTH, and
both were replaced. A check watching one of two identical lists leaves the other
free to drift, which is the hazard rather than a smaller version of it.

### D5. `full`'s merge authority is `delegated-under-conditions`, not `owner`

Blueprint section 8's table says `owner` for the full row. The shipped `full`
declares `delegated-under-conditions` with DR-0012's six conditions verbatim and
`granted-by: DR-0012`. Reasoning, in the order it decided the question:

1. Criterion 4c REQUIRES `full` to carry DR-0012's own escalation bounds. A mode
   carrying DR-0012's limits while declaring an authority regime DR-0012
   replaced is internally incoherent, and incoherence in this artifact is the
   hazard class the phase is named after.
2. DR-0015 removed the owner from the merge path for this project entirely,
   milestone boundaries included. `owner` would record a regime this project has
   left.
3. The plan's own justification for the third enum value is that "a mode
   vocabulary that cannot express the authority regime actually in force would
   force the next such grant to live outside the artifacts". The regime actually
   in force IS this one.

`owner` and `owner-approves-orchestrator-merges` both remain representable and
`local-only` still declares the second, so no other project's governance was
made unexpressible. The blueprint's value and the departure from it are stated
in a comment at the field itself, not only here.

### D6. `orchestrator-diff-review` was added to the stage vocabulary

Blueprint section 8's local-only row is "implement, orchestrator diff review,
local fast-forward". The plan enumerates twelve stages for `full` and does not
enumerate the CLOSED SET, so local-only's middle stage had no id. Two options
were considered: describe local-only as `[implement, merge-on-green]` and lose
the review, or add the id the blueprint already names. The second is faithful to
the source and the first misdescribes the mode, so there was no comparable pair
to escalate (DR-0016). The enum is thirteen ids; `full`'s pipeline is twelve.

### D7. One behavior beyond the plan's list of fifteen

The plan names fifteen new behaviors and all fifteen are registered. A
sixteenth, `role-model-config-tiers-by-risk`, is registered for the test that
asserts R-075's rule over the SHIPPED role data (which roles took which tier,
that both review roles carry a family constraint, that the implementer carries
the phase-class half). Criterion 1 only asserts that the document validates, and
the schema permits `cheaper` on any role, so without this test nothing said what
the data actually is. Registered rather than left unregistered because
CLAUDE.md requires every new behavior to be in the registry.

### D8. `strongest-for` is a field the plan's field list does not name

R-075 is phase-class scoped for the implementer ("strongest for money-path and
architecture phases ... cheaper for mechanical phases"). The plan's field list
for `role-model-config` is `{tier, charter-override, review-model-family?}`, and
a flat `tier` drops half of R-075's rule. `strongest-for` is an optional array of
phase classes, DATA only: nothing in M3 classifies a phase and no resolver reads
it. Recorded here because adding a field the plan's prose does not enumerate is a
deviation even when the requirement it serves is cited.

### D9. `charter-override: allowed` is uniform across all six roles

The plan asks for "a `charter-override: allowed` flag". Every role ships
`allowed`, so today the field discriminates nothing. It is shipped despite that
because the charter override is L4 and lands at M4 (R-075's migration-table
note), so the M4 adapter has a field to read rather than a convention to infer.
Said plainly rather than presented as if it carried information.

### One witness is not a class: the pairs, and why each pair is two things

- `mode-no-undeclared-downgrade`: (1) a mode omits a stage and declares NOTHING;
  (2) a mode declares a plausible, present, one-entry-short skips list. The
  second is the shape a real downgrade takes and the first is the one a careless
  reader would still catch. A third, the reference mode DELETED, disables the
  comparison for every remaining mode at once and is why the absent `full` fails
  closed rather than returning quietly.
- `mode-stage-order`: (1) the two stages present and INVERTED; (2) the review
  DELETED and not declared. Reordering and deleting reach the same state by
  different routes and the plan states both arms of the rule.
- `mode-gate-sets-resolve`: (1) a gate id in no registry; (2) a gate id that
  RESOLVES to a real entry whose own `modes` list excludes this mode. The second
  survives any check that only asked whether the id exists, and it is the hazard
  as the plan words it: assurance that is a name with no gates behind it.
- `charter-mode-enum-matches-modes`: (1) a mode ADDED that the enum lacks;
  (2) a mode REMOVED that the enum still offers. Different directions of the
  same equality, and only the second is reachable end to end through the command
  (the mode `id` enum is closed, so a fourth id is a schema rejection first).
- `mode-delegated-authority-requires-conditions`: (1) `conditions` emptied;
  (2) `granted-by` removed. Different keywords on different fields.
- `mode-escalation-bounds-require-response`: (1) `on-exceeded` ABSENT;
  (2) `on-exceeded` PRESENT and invented. The second is likelier in practice:
  an author who knows the field exists fills it with something.
