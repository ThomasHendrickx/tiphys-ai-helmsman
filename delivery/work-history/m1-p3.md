## Key decisions and the why that is invisible in the diff

1. The one shared mutation primitive (applyLeaseMutation in src/lock.ts) implements EXT-F-01 as: serialize through a claim file beside the lock (<lock>.mutex, O_EXCL create; FM-022's serialize-through-a-claim pattern), then inside the claim re-read the lock file, byte-compare against the observed state the mutation was decided on, apply (O_EXCL create for the absent-lock acquire per PR-006; write-temp-then-rename otherwise; unlink for release), and confirm by re-reading the mutation's unique token (FM-022 write-then-verify). Any mismatch at compare or confirm is a loss without retry, exactly the plan's wording. No steal protocol exists on purpose (FM-058): a claim file left by a crashed mutation makes later mutations fail loudly after a bounded 5s wait, naming the file for manual removal; the critical section is a few file operations, so that window is tiny and honesty beats cleverness.
2. The lease JSON carries two fields beyond the plan's named four (holderId, hostname, acquiredAt, expiresAt): token, which is the plan's own per-mutation confirmation token made visible (criterion 6 requires asserting on it), and durationSeconds, so renew defaults to the acquired duration and half-life (renewByMs, PR-203) is computable. Declared as deviation 2. No pid-like field anywhere (C-2); doctor's P2 lock check requires only holderId and expiresAt and is unaffected.
3. Holder identity transport across CLI invocations (FM-022: an identity that outlives one tool call): acquire prints "acquired <holderId> expires <ts>" and the holder passes --holder <id> to renew and release. M1-P4's spawn/teardown holdership checks will consume the same flag or the lease file.
4. Renew computes the new expiry as max(now + duration, old expiry + 1ms) so criterion 4's strict increase holds even for a sub-millisecond renew; a renew that does not extend the lease would be useless.
5. Release semantics derived from criterion 8: a matching holder may release even after expiry (cleanup of one's own expired lease is legitimate and is exactly the release-versus-takeover race the criterion stages); a non-matching holder is always refused (criterion 9), so a losing holder can never remove the winner's lease.
6. Takeover of an absent lock behaves as a plain O_EXCL acquire; a takeover whose observed lease disappeared before apply loses with "the observed lease is gone" (criterion 8's release-first outcome). Takeover of an unexpired lease is refused at decision, before any mutation (plan step 1).
7. Deterministic race witnesses: TIPHYS_LOCK_TEST_HOLD in src/commands/lock.ts is a documented hold point (the environment guidance for this phase explicitly prefers an injected hold point or the primitive's own staging over sleep-timing). When set, a mutating lock subcommand observes the lease and freezes its decision clock, writes <barrier>.observed, and waits (bounded 30s) for the barrier file before deciding and applying. This models the paused holder of DR-0007 (a reclaimed session resuming mid-operation) and lets tests interleave two real CLI invocations at the exact compare-and-swap point. Inert unless the variable is set. The lock library additionally exposes the primitive's own staging seam (an observed option on acquire/renew/release), used for the applied-order-renew-first half of criterion 6.
8. A corrupt (unparseable) lease file: status reports "corrupt" and still exits 0 (status never blocks a human); every mutation refuses with a reason naming the file. Doctor already FAILs on it (P2).
9. Pool records live beside the worktree at worktrees/<task-id>.pool.json (plain JSON per D-3), never inside it, so the record can never dirty the destroy-time cleanliness check and no exemption list is ever needed (FM-059). The record carries taskId, project, remote, branch, baseSha, branchName, offline, createdAt; M1-P4 spawn reads baseSha and offline from it for meta.json (baseSha, baseOffline).
10. Task branch name is task/<task-id>, created by git worktree add -b at the exact fetched base SHA (EXT-F-03 step 4). Task ids are validated as safe path segments; anything else is refused.
11. The fetch uses the explicit force refspec +refs/heads/<branch>:refs/remotes/<remote>/<branch> so the remote-tracking ref mirrors the remote exactly even after a remote rewind; the base SHA is then rev-parse of that tracking ref, never a local branch (criterion 11's behind and ahead cases).
12. Remote resolution: origin if configured, else the single configured remote, else refuse. Default branch: the local symbolic ref refs/remotes/<remote>/HEAD when set (no network), else the remote's advertised default via ls-remote --symref (criterion 12). With --offline and origin/HEAD unset and the remote unreachable, create fails honestly (the default branch cannot be known); observed during the criteria walk.
13. --offline authorizes the fallback, it does not skip the fetch: the fetch is always attempted; on success the fresh SHA is used and offline: false is recorded even when the flag was passed; only on fetch failure with the flag does create use the last fetched remote-tracking SHA and record offline: true. Without the flag, fetch failure creates nothing (criterion 13, both directions).
14. Parallel-safety for criterion 15: the record file is created with O_EXCL as the atomic duplicate gate, and fetch and worktree add retry up to 5 times with linear backoff when stderr matches a transient git lock-contention signature (index.lock, cannot lock ref, Unable to create .lock). Concurrent fetches of the same tracking ref can transiently contend; the retry absorbs it. Failures that do not match the signature (for example an unreachable remote) fail on the first attempt.
15. Destroy's index.lock rule (FM-036, FM-051): after retries exhaust on a lock signature, provablyStaleLock removes the lock only when it exists, its mtime age exceeds 300s, and lsof is available and provably shows no holder (exit 1, empty stdout); lsof missing, erroring, or listing anything means not stale, leave it, exit nonzero. The predicate takes an injectable lsof runner so the refusal ladder is unit-tested deterministically (fresh lock, lsof unavailable, lsof holder, lsof error, and the one provable case).
16. --duration accepts fractional seconds (parsed as a positive finite number); the default is 900 (DEFAULT_LEASE_DURATION_SECONDS). Tests use 1s leases and wait past the recorded expiresAt, so expiry is real, never mocked.

The fix is an unconditional stage removal at the top of the claim-held critical section: it runs inside the claim, so it provably cannot race a live mutation (a live one would hold the claim), and therefore needs no age threshold at all. The deliberate-failure witness below reproduces the salvaged behavior exactly and fails with "strand survived a release", which is the proof the rewrite was necessary rather than cosmetic.

### Dispositions

1. CR-201 (pool destroy leaves the task branch): FIXED. poolDestroy now deletes the branch it created after the worktree is gone, using git branch -D. Force deletion is deliberate: whether the work is landed is the teardown guard's judgement (M1-P4), which refuses before ever calling destroy, so the pool's own contract is simply that destroy leaves nothing of the task behind. When deletion fails (the branch is checked out in another worktree, for example) destroy refuses with a single reason line and keeps the pool record, which makes the refusal retryable: a re-run takes the already-removed-worktree path and retries the deletion. poolCreate additionally pre-checks refs/heads/task/<id> and refuses with a reason naming the branch, so a branch the pool did not create surfaces as a clean refusal instead of a raw git error from inside worktree add. Registered behaviors pool-destroy-then-recreate, pool-destroy-branch-refusal, pool-create-foreign-branch-refused.
2. CR-202 (stranded stage files): FIXED, design re-derived (see the salvage section). One fixed stage path plus an unconditional claim-held sweep. Chosen over sweeping unique .tx-* names by age because the claim already provides the exclusion an age heuristic would only approximate: inside the claim, any stage file present is provably not from a live mutation, so no threshold is needed and no live mutation can ever be disturbed. Registered behavior lock-stale-stage-cleaned, which plants a strand before a renew (rename branch), a release (unlink path) and an acquire (O_EXCL path) and asserts the strand is gone and the mutation unaffected in all three, and that strand bytes never reach the lease.
3. CR-203 (over-broad retry trigger): FIXED. The signature now requires an actual lock path: /index\.lock|Unable to create '[^']*\.lock'/. Empirically confirmed against git 2.43 that genuine contention always names the lock file ("Unable to create '<path>.lock': File exists.", for index locks and ref locks alike), while permanent failures do not: a directory/file ref conflict reports "cannot lock ref 'refs/x': 'refs/x/y' exists; cannot create 'refs/x'" with no lock file. Both the bare "File exists" phrase and the bare "cannot lock ref" phrase were therefore dropped, which is wider than the review's minimum and drops a second permanent case it did not name. Evidence below. Registered behavior pool-retry-signature-narrow.
4. CR-204 (stale claim reported as "lock held"): FIXED, and widened on the owner reviewer's instruction from a wording change to a classification that is propagated and consumed at every layer. The primitive classifies the failure (claimTimeout) and states the lease situation ("no lease, no live holder" or "lock held by <holder>") plus the claim path; all three lease operations (acquireLease, renewLease, releaseLease) propagate the flag to their caller instead of re-wrapping the reason as "lock held" or prefixing it with the operation name; and the CLI's one failure emitter, used by the acquire, renew and release paths, appends the claim-file remedy from the flag. The remedy text lives at the CLI on purpose: a CLI that ignored the classification would visibly lose it, which makes the propagation load-bearing rather than prose carried along for the ride, and the deliberate-failure witness below proves exactly that. Exit codes are unchanged (operational failures 1, usage errors 64). Registered behaviors lock-stuck-claim-diagnostic, lock-stale-claim-no-live-holder, lock-stale-claim-all-operations.

Contract detail found while testing CR-204 and worth recording: renew and release with no lease present refuse before any mutation is attempted, so a claim file is not what stops them and they correctly say "no lease present" rather than reporting a stale claim. The first version of the new test asserted otherwise and failed honestly; the assertion was corrected to the real contract rather than the code bent to the test. All three operations are still witnessed carrying the classification at the point where they do reach the primitive: renew (unexpired matching lease), release (matching holder), and acquire --take-over (expired lease), plus acquire on an absent lease.
