## Key decisions and the why that is invisible in the diff

1. The one shared mutation primitive (applyLeaseMutation in src/lock.ts) implements EXT-F-01 as: serialize through a claim file beside the lock (<lock>.mutex, O_EXCL create; FM-022's serialize-through-a-claim pattern), then inside the claim re-read the lock file, byte-compare against the observed state the mutation was decided on, apply (O_EXCL create for the absent-lock acquire per PR-006; write-temp-then-rename otherwise; unlink for release), and confirm by re-reading the mutation's unique token (FM-022 write-then-verify). Any mismatch at compare or confirm is a loss without retry, exactly the plan's wording. No steal protocol exists on purpose (FM-058): a claim file left by a crashed mutation makes later mutations fail loudly after a bounded 5s wait, naming the file for manual removal; the critical section is a few file operations, so that window is tiny and honesty beats cleverness.
2. The lease JSON carries two fields beyond the plan's named four (holderId, hostname, acquiredAt, expiresAt): token, which is the plan's own per-mutation confirmation token made visible (criterion 6 requires asserting on it), and durationSeconds, so renew defaults to the acquired duration and half-life (renewByMs, PR-203) is computable. Declared as deviation 2. No pid-like field anywhere (C-2); doctor's P2 lock check requires only holderId and expiresAt and is unaffected.
3. Holder identity transport across CLI invocations (FM-022: an identity that outlives one tool call): acquire prints "acquired <holderId> expires <ts>" and the holder passes --holder <id> to renew and release. M1-P4's spawn/teardown holdership checks will consume the same flag or the lease file.
4. Renew computes the new expiry as max(now + duration, old expiry + 1ms) so criterion 4's strict increase holds even for a sub-millisecond renew; a renew that does not extend the lease would be useless.
5. Release semantics derived from criterion 8: a matching holder may release even after expiry (cleanup of one's own expired lease is legitimate and is exactly the release-versus-takeover race the criterion stages); a non-matching holder is always refused (criterion 9), so a losing holder can never remove the winner's lease.
6. Takeover of an absent lock behaves as a plain O_EXCL acquire; a takeover whose observed lease disappeared before apply loses with "the observed lease is gone" (criterion 8's release-first outcome). Takeover of an unexpired lease is refused at decision, before any mutation (plan step 1).
7. Deterministic race witnesses: TIPHYS_LOCK_TEST_HOLD in src/commands/lock.ts is a documented hold point (the environment guidance for this phase explicitly prefers an injected hold point or the primitive's own staging over sleep-timing). When set, a mutating lock subcommand observes the lease and freezes its decision clock, writes <barrier>.observed, and waits (bounded 30s) for the barrier file before deciding and applying. This models the paused holder of DR-0007 (a reclaimed session resuming mid-operation) and lets tests interleave two real CLI invocations at the exact compare-and-swap point. Inert unless the variable is set. The lock library additionally exposes the primitive's own staging seam (an observed option on acquire/renew/release), used for the applied-order-renew-first half of criterion 6.
8. A corrupt (unparseable) lease file: status reports "corrupt" and still exits 0 (status never blocks a human); every mutation refuses with a reason naming the file. Doctor already FAILs on it (P2).
9. Pool records live beside the worktree at worktrees/<task-id>.pool.json (plain JSON per D-3), never inside it, so the record can never dirty the destroy-time cleanliness check and no exemption list is ever needed (FM-059). The record carries taskId, project, remote, branch, baseSha, branchName, offline, createdAt; M1-P4 spawn reads baseSha and offline from it for meta.json (baseSha, baseOffline).
10. Task branch name is task/<task-id>, created by git worktree add -b at the exact fetched base SHA (EXT-F-03 step 4). Task ids are validated as safe path segments; anything else is refused.
11. The fetch uses the explicit force refspec +refs/heads/<branch>:refs/remotes/<remote>/<branch> so the remote-tracking ref mirrors the remote exactly even after a remote rewind; the base SHA is then rev-parse of that tracking ref, never a local branch (criterion 11's behind and ahead cases).
12. Remote resolution: origin if configured, else the single configured remote, else refuse. Default branch: the local symbolic ref refs/remotes/<remote>/HEAD when set (no network), else the remote's advertised default via ls-remote --symref (criterion 12). With --offline and origin/HEAD unset and the remote unreachable, create fails honestly (the default branch cannot be known); observed during the criteria walk.
13. --offline authorizes the fallback, it does not skip the fetch: the fetch is always attempted; on success the fresh SHA is used and offline: false is recorded even when the flag was passed; only on fetch failure with the flag does create use the last fetched remote-tracking SHA and record offline: true. Without the flag, fetch failure creates nothing (criterion 13, both directions).
14. Parallel-safety for criterion 15: the record file is created with O_EXCL as the atomic duplicate gate, and fetch and worktree add retry up to 5 times with linear backoff when stderr matches a transient git lock-contention signature (index.lock, cannot lock ref, Unable to create .lock). Concurrent fetches of the same tracking ref can transiently contend; the retry absorbs it. Failures that do not match the signature (for example an unreachable remote) fail on the first attempt.
15. Destroy's index.lock rule (FM-036, FM-051): after retries exhaust on a lock signature, provablyStaleLock removes the lock only when it exists, its mtime age exceeds 300s, and lsof is available and provably shows no holder (exit 1, empty stdout); lsof missing, erroring, or listing anything means not stale, leave it, exit nonzero. The predicate takes an injectable lsof runner so the refusal ladder is unit-tested deterministically (fresh lock, lsof unavailable, lsof holder, lsof error, and the one provable case).
16. --duration accepts fractional seconds (parsed as a positive finite number); the default is 900 (DEFAULT_LEASE_DURATION_SECONDS). Tests use 1s leases and wait past the recorded expiresAt, so expiry is real, never mocked.

### V-1 (high): pool destroy destroyed committed work

What it was: the CR-201 fix ran git branch -D unconditionally. Committed but unpushed work leaves the worktree clean, so the dirty guard never fired; destroy printed "destroyed <id>", exited 0, deleted the branch, removed the worktree (taking the per-worktree reflog with it) and unlinked the pool record that named the branch. The commits survived only as dangling objects until the next gc. The safety profile was exactly inverted: the command refused to remove a worktree holding an untracked scratch file, but destroyed real commits without a word, and its own dirty-refusal message advised the operator to "commit or land them first", which after that change was the advice that destroyed the work. Reproduced independently here before fixing: commit 74e5351 destroyed, exit 0, no warning, dangling after fsck, then "could not get object info" after git gc --prune=now.

Why it happened, honestly: the justification recorded in the first round was that "the teardown guard (M1-P4) refuses before ever calling destroy". M1-P4 does not exist. I wrote a safety argument that depended on a component that had not been built, for a command that is public today, and I did not test the case the argument was protecting. The reviewer's own recommended fix for CR-201 (a create-side pre-check) closed the finding without deleting anything; I went further than the finding required and made destroy destructive.

The correction: destroy compares the branch tip against the base SHA the pool itself recorded. Tip equal to baseSha proves the branch carries no commits, so deletion is lossless and unconditional. Anything else refuses by default with one reason line naming the branch, the base and the tip, and deletes only when the new, distinct --delete-branch-force flag is passed. The flag is deliberately NOT --discard: --discard's plan-defined meaning is the dirty-tree override, and conflating them would make the scout path silently destroy committed work. Plain git branch -d is not usable as the gate, because the clone's local default ref may be behind the fetched base and a squash-landed branch is not an ancestor of anything. On the success path the deleted branch and its tip sha are printed, so a mistaken destroy still leaves a recovery handle. M1-P4 teardown passes the flag from its ship path after its landedness judgement, which makes the dependency on teardown explicit instead of assumed.

### V-2 (high): the narrowed retry signature broke parallel pool create

### V-3 (high): a refused destroy was destructive, and could permanently wedge a task id

What it was: the V-1 branch gate was evaluated AFTER the worktree had already been removed. So a refused destroy deleted the worktree it was refusing to destroy, taking every git-ignored file with it (a .env, build output: content no git object holds), and its remedy line, "land them or pass --delete-branch-force", named a place that no longer existed. Worse, with an unreadable pool record the removed worktree was the only remaining way to resolve the git context, so every subsequent destroy refused with "cannot resolve the project repository" and the task id became permanently unusable through the CLI. That is strictly worse than the U-3 behavior the previous round claimed to fix: the pre-fix wedge was escapable, this one was not.

The correction, and this is the part that matters more than the fix: I did not patch the order again. poolDestroy is now three explicit stages with the invariant written into the code, and the invariant is NO DESTRUCTIVE ACTION MAY HAPPEN BEFORE EVERY GATE HAS PASSED.

- resolveDestroy: read only. Gathers every fact a decision needs (context directory, record, worktree state, cleanliness, branch tip). Mutates nothing.
- evaluateDestroy: pure over those facts. No IO at all, so a gate cannot destroy anything even by accident. Returns a refusal reason or undefined.
- applyDestroy: destructive, reached only when evaluate returned no refusal, and therefore has no gates left to evaluate.

The point of the shape is that adding a rule means adding a fact in stage 1 and a clause in stage 2; a rule added to stage 3 is a bug by construction. A refused destroy now leaves the worktree, its registration and the record byte-identical, which is asserted directly rather than through a proxy. The "cannot resolve" refusal also now names the record file and the remedy, so even the narrow residue where stage 3 fails midway is escapable.

### V-4 (high): the commondir transient also strikes the fetch, so parallel create still failed

What it was: the previous round discovered the concurrent worktree-add collision and correctly kept it out of the shared retry signature, because a failed add leaves the branch behind and cannot be retried in place. But the same collision also strikes the FETCH, where only the shared signature applies, so concurrent pool create still failed with exactly the V-2 refusal text, and under --offline still recorded offline: true for a base that had fetched fine. V-2's failure mode reached the operator through a second door that my own round opened its eyes to and then left unguarded.

The correction: the fetch gets the shape as an explicit extra predicate, and the reason is recorded where the next maintainer will read it. The rule is now stated as an invariant rather than a case list: A SHAPE MAY BE RETRIED IN PLACE ONLY IF THE FAILED COMMAND CREATED NOTHING. The fetch has created nothing at that point (the record is written later, no branch or worktree exists), so a retry repeats a pure read. The add has created a branch, so it must roll back first. Same shape, different call site, different correct handling.

Why my round did not see it: my stress measured 90 concurrent creates as 15 rounds of 6, and six-way concurrency almost never puts a fetch and an add in the same window. The narrative then compressed that to "90 concurrent creates", which reads like 90-way. Those are not the same measurement and the difference is exactly where the defect lives. Corrected below.

The surviving general lesson is narrower: check what a failed git command left behind before adding it to a retry signature, because that determines whether a retry is safe or merely noisy.
12. New (second fix round): a safety argument that depends on a component not yet built is not a safety argument. The V-1 data-loss defect was justified by "M1-P4 teardown refuses before calling destroy" while M1-P4 did not exist and the command was public. If a guarantee lives in a future phase, the current phase must either enforce it itself or refuse by default.
13. New (second fix round): full-suite runs and --test-name-pattern runs are different concurrency configurations and can disagree. Report both when making a flake claim; a clean targeted run says nothing about the parallel-file configuration that npm test actually uses.
14. New (third fix round): ordering is not a fix, structure is. Three consecutive rounds put a new high-severity defect into src/pool.ts by getting a sequence of statements right for the case under test with no structural reason it would stay right. poolDestroy is now resolve/evaluate/apply with the invariant written down, so a gate cannot be added in the destructive stage without being obviously wrong. Prefer a shape that makes the mistake unspellable over a comment asking the next person to be careful.
15. New (third fix round): a concurrency stress figure must state its width, not just its total. "90 concurrent creates" meaning 15 rounds of 6 hides exactly the fetch-versus-add window that only appears at high width; the two numbers are different experiments and only one of them can see V-4.
16. New (third fix round): git writes .git/worktrees/<id>/locked = "initializing" during worktree add, and git worktree prune skips locked entries. A rollback that relies on prune therefore leaves its own half-created registration behind, and the subsequent branch delete fails with "used by worktree". Remove your own admin directory directly.
17. New (third fix round): node -e passes script arguments starting at process.argv[1], not argv[2]. A reader helper written the usual way silently reads undefined and reports a perfectly clean result, which is worse than crashing.
18. New (third fix round): writeFileSync with flag "wx" is not an atomic publish. It is an O_EXCL open plus a separate write, so the name is visible at length zero first. Use linkSync from a complete stage file when both exclusivity and atomic content are needed.
