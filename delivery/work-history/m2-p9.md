## 2. The mechanism the harness enforces (not a finding)

The mechanism a vacuous exit test rests on is: **reading a bundle's success
from a bare aggregate (a count, or the runner's exit code) rather than from a
per-gate comparison against a declared expected-status table.** A bare count
cannot see a gate that is silently missing, a required gate that reported
`not-applicable`, a green with zero units, or the two bundles conflated. The
harness fixes the mechanism, not an instance: one assertion program
(`scripts/m2-exit-test.sh:1`, written once to `<evidence-dir>/m2-assert.mjs` and
reused by every bundle and by the self-test) reads `summary.json` and every
per-gate `result.json`, and against an expectations document it checks, per
gate: exactly one record with the expected status; every `required` gate green;
every `green` row with units > 0; every `not-applicable` record naming its
reason AND its evaluation evidence, with the three M2-P7 states distinguishable
(precondition-unmet carries `precondition{id,met:false,reason,evidence}`;
declared-none carries a declaration path and a 64-hex merge-base blob sha256);
zero `error`; zero `vacuous`; recomputed counts equal `summary.json`; every
`absent` gate having NO record on disk; and `summary.manifestSha256` equal to a
fresh hash of the manifest. Every reported figure is re-derived from the bundle
(CR-602).

Because the assertion program is the SAME for the PR bundle, the main bundle and
the self-test, "the self-test exercises the assertion code" is literal, not a
resemblance.

### 9.3 What changed in the harness (DR-0018 points 1 and 2)

## 10. Fix round 2: the scope gate never audited a real PR in CI (HIGH)

Clean-room criteria review (reproduced three ways) found that the `scope` gate
reports `not-applicable` on EVERY CI `pull_request` run and never audits a diff,
so the exit test passed vacuously for `scope` on this and every future PR. This
is the vacuous-pass hazard M2-P9 exists to prevent, one layer up (the gate
result itself was vacuous-by-precondition, not the harness assertion).

### 10.1 The MECHANISM, not the finding

The finding is "`scope` is not-applicable in CI". The MECHANISM is: **deriving
branch identity from `git rev-parse --abbrev-ref HEAD` in a checkout whose HEAD
state (detached vs named) is chosen by the CI harness, not by this repository.**
On a `pull_request` event `actions/checkout@v4` with no `ref:` leaves a DETACHED
HEAD at the ephemeral merge commit (`refs/pull/N/merge`), so `abbrev-ref HEAD`
returns the literal string `"HEAD"`. Any code that decides "am I on the phase
branch" from that value is deciding it against `"HEAD"`, which can never match
`^(?:claude/m[0-9]+-p[0-9]+-.*)$`.

### 10.3 What the derivation did NOT cover

- `node_modules/` (third-party, not our authored tree) was excluded; a branch
  derivation there could not be a Tiphys gate's own logic.
- A gate could in principle read branch identity by a non-git means (an
  environment variable, a file). The env path is already covered by the standing
  test "no environment variable changes a production gate's reported status"
  (grep over `src/gates`); no gate reads branch identity from a file.
- The derivation is over the AUTHORED tree at this head; it says nothing about
  future gates. The two new guards in 10.5 are the standing protection.

### 10.4 The fix (Option A, the root)

`.github/workflows/gates.yml`: the `actions/checkout@v4` step keeps
`fetch-depth: 0` and ADDS `ref: ${{ github.head_ref }}`, so the head branch is
checked out BY NAME. `abbrev-ref HEAD` then returns `claude/mN-pM-...`, and both
mechanism sites see the real branch. On a `push` to `main` `github.head_ref` is
empty and checkout falls back to the pushed ref (the main bundle does not run
`scope`, so it is unaffected). Option B (threading a `--branch` into the
precondition) was rejected: it would edit `src/gates/run.ts` and/or
`src/gates/scope.ts`, which are M2-P4 files NOT on M2-P9's files-to-touch list,
so it would itself make `scope` RED on this PR; Option A edits only the
declared workflow and fixes the mechanism at its source.

Second, `scripts/m2-exit-test.sh` PR_EXPECT_JSON tightens `scope` from
`"green|not-applicable"` to `"green"`. `scope`'s precondition is branch-matches
and a PR bundle is BY CONSTRUCTION on a phase branch, so `scope` is NEVER
legitimately N/A in a PR bundle: the only N/A was the detached-HEAD artifact.
Requiring green means the exit test now genuinely REQUIRES `scope` to audit, and
any recurrence to N/A FAILS the harness instead of slipping through.
`red-witness` and `citations` stay `"green|not-applicable"` (each CAN be
legitimately N/A on a head that does not touch its trigger).
