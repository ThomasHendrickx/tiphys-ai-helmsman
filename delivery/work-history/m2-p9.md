# M2-P9 work history: the M2 exit-test harness and evidence bundle

Phase M2-P9. Branch `claude/m2-p9-exit-test` off `origin/main` at `1b6f096`
(M2-P1 through M2-P8 merged). Toolchain: the floor Node `v26.6.0`, npm
`11.18.0`.

This phase is the milestone's own falsifiability harness, and its declared
hazard class (kernel plan M2 section 3, M2-P9) is "an exit test that can pass
vacuously." The single most important property of this deliverable is that the
harness is NOT vacuous: it refuses to certify a bundle that does not match
section 1.4's expected-status table, and it proves that refusal on injected bad
bundles. That property is fully delivered and demonstrated. In the course of
running it against the real head, the harness surfaced two blockers in
already-merged code that structurally prevent a green PR or main bundle on the
M2-P9 head; those are named below with derivations, and they are the escalation
this phase carries to the orchestrator.

## 2. The mechanism the harness enforces (not a finding)

The mechanism a vacuous exit test rests on is: **reading a bundle's success
from a bare aggregate (a count, or the runner's exit code) rather than from a
per-gate comparison against a declared expected-status table.** A bare count
cannot see a gate that is silently missing, a required gate that reported
`not-applicable`, a green with zero units, or the two bundles conflated. The
harness fixes the mechanism, not an instance: one assertion program
(`scripts/m2-exit-test.sh:1`, written once to `<evidence-dir>/m2-assert.mjs` and
reused by every bundle and by the self-test) reads `summary.json` and every
per-gate `result.json`, and against an expectations document it checks, per
gate: exactly one record with the expected status; every `required` gate green;
every `green` row with units > 0; every `not-applicable` record naming its
reason AND its evaluation evidence, with the three M2-P7 states distinguishable
(precondition-unmet carries `precondition{id,met:false,reason,evidence}`;
declared-none carries a declaration path and a 64-hex merge-base blob sha256);
zero `error`; zero `vacuous`; recomputed counts equal `summary.json`; every
`absent` gate having NO record on disk; and `summary.manifestSha256` equal to a
fresh hash of the manifest. Every reported figure is re-derived from the bundle
(CR-602).

Because the assertion program is the SAME for the PR bundle, the main bundle and
the self-test, "the self-test exercises the assertion code" is literal, not a
resemblance.

## 4. BLOCKERS: two integration failures in already-merged code (escalation)

Both are outside M2-P9's files-to-touch. M2-P9 cannot fix either without a scope
widening the plan does not authorize. Neither the `suite` gate nor the `scope`
gate has ever run in CI: the interim workflow ran only `--only

### BLOCKER A: red-witness is structurally not-applicable on the M2-P9 head

`red-witness` (required) has precondition `diff-touches src/, bin/`
(`delivery/plan/kernel-plan-m2.md:76`). M2-P9's files-to-touch
(`delivery/plan/phase-declarations/m2-p9.json:3`) contain NO `src/` or `bin/`
path, so `main...HEAD` touches no source, the precondition is unmet, and
red-witness reports `not-applicable`. A required gate reporting not-applicable
makes the runner exit 20 (`requiredNotApplicable`). Section 1.4's PR-bundle
column and section 4 both require red-witness GREEN and "seven required gates
green", which the M2-P9 diff cannot produce.

Derivation (the enumeration and its scope): the changed paths are exactly the
five declared files plus the standing work-history extra; none is under `src/`
or `bin/`. What the derivation does NOT cover: it says nothing about phases that
DO touch src (their red-witness runs and is green when covered by a witness
spec, which is how M2-P2's own PR was green). It is specific to the exit-test
phase, whose legitimate diff touches no source.

Recommendation (for the orchestrator, per DR-0016): the exit test's red-witness
leg cannot be green on M2-P9's own diff, and red-witness's green path is already
proven by M2-P2's merged PR and by `test/witness.test.ts`. Either (a) correct
section 1.4's PR-bundle expectation for the exit-test head to record red-witness
as `not-applicable` for a precondition-unmet reason that is structural to this
phase's src-less diff (distinguishable and non-vacuous: the harness would then
assert red-witness is not-applicable-by-evaluated-precondition, and would still
fail if it were silently absent or errored), or (b) run the milestone exit test
on a head that carries a witness-covered representative source change. This is
recorded rather than improvised because it changes what "seven required gates
green" means, which is the plan's to decide.

### BLOCKER B: the suite gate cannot run this repository's own suite green

`suite` (required) reports RED with 19 failing tests, ALL in
`test/witness.test.ts`, while a plain `npm test` over the identical toolchain is
395 tests / 395 pass / 0 fail. The mechanism: the suite gate runs
`node --test` in place with a child-scoped custom reporter injected via
`NODE_OPTIONS` (`src/gates/suite.ts:862` builds the child env). The witness
tests spawn nested `node --test` invocations to evaluate witnesses in scratch
clones; those grandchildren INHERIT the custom-reporter `NODE_OPTIONS` and
produce output the witness harness cannot parse, so 19 witness tests fail ONLY
under the suite gate. This blocks BOTH bundles (suite is in the PR and the main
bundle).

Derivation: `npm test` exit 0 (395/395/0); the suite gate's own
`counts.json` reports `pass 376, fail 19` with every finding naming
`test/witness.test.ts`. What the derivation does NOT cover: I did not fully
isolate whether the correct fix belongs in `src/gates/suite.ts` (strip or
neutralise the custom-reporter `NODE_OPTIONS` for grandchildren) or in
`src/witness/run.ts` (sanitise the env when spawning nested `node --test`); both
are outside M2-P9's scope. I did not attempt to fix it.

Recommendation: a fix round (or a fresh phase) against `src/gates/suite.ts`
and/or `src/witness/run.ts` so the suite gate can run the kernel's own suite
green, because the M2-P9 CI wiring makes the full bundle run on every future
PR and this would otherwise red every PR.

### Minor: the scope gate takes a LOWERCASE `--phase`

`scope` reads its declaration from `<declarations>/<phase>.json` verbatim
(`src/gates/scope.ts` `loadDeclarationAtMergeBase`), and the committed
declarations are lowercase (`m2-p9.json`), while the id check uppercases
(`phase.toUpperCase() !== declaration.id`). So the exit test must pass
`--phase m2-p9`, not `M2-P9`; `test/scope-gate.test.ts` uses the lowercase form.
The plan and the dispatch brief wrote `M2-P9`. The harness derives the phase
from the branch in lowercase and the CI wiring derives it lowercase from
`github.head_ref`, so the harness is correct; this is recorded so the
orchestrator invokes the standalone exit test with `--phase m2-p9`.
