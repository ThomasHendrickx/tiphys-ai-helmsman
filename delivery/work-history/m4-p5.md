## What this phase did

`@tiphys/claude-code-plugin` now exists as a second npm package in this
repository, per
delivery/decisions/DR-0040-the-plugin-is-a-second-package-in-the-kernel-repository.md:1.
It ships a plugin manifest and one module: the executor adapter that
implements the `ExecutorAdapter` interface M4-P3 and M4-P4 delivered
(src/spawn.ts:280). The root package gained `workspaces`, an `overrides` entry
that keeps the plugin's kernel dependency resolving to the workspace, a third
project in the `tsc -b` build, and one behaviour change in
`build:runtime-deps`. Nothing in `src/` or `bin/` changed.

**THE RESTRAINT IS THE DESIGN.** Criterion 7 is "the adapter implements the
interface and nothing else". The hooks are M4-P6's (delivery/plan/kernel-plan-m4.md:882)
and the model-resolution record is M4-P7's (delivery/plan/kernel-plan-m4.md:1018),
so this adapter is the three-armed launch contract and nothing more. The only
things that make it the CLAUDE CODE adapter rather than a second copy of the
built-in one are the package it ships in and the manifest beside it, and that
is stated here rather than left for a reviewer to discover and read as an
omission.

## The manifest filename came from a measurement, not from a guess

the manifest SHAPE as **LEFT OPEN, and untouched**
(delivery/verification/m4-prototype-probes.md:319), so the shape had to be
chosen here. The FILENAME is measured, twice, in this repository:

- delivery/evidence/m4-probes/pretooluse-write-block.md:84 records a real
  `claude -p` session loading a plugin whose manifest was at
  `plugin/.claude-plugin/plugin.json`, with `--plugin-dir` pointed at the
  plugin root. The same layout is repeated at
  delivery/evidence/m4-probes/pretooluse-write-block.md:405.
- M4-P1's Q1 matrix used the same loader, and its manifest is committed
  verbatim at
  test/fixtures/harness-probe/q1-bypass-permission-mode/plugin-manifest.json.txt:1.

So the manifest is at `plugin/.claude-plugin/plugin.json`. Its CONTENT is
minimal on purpose: `name`, `version` and `description`. The probe's manifests
also carried a `hooks` pointer, and this phase ships no hooks, so declaring one
here would be a manifest field pointing at a file that does not exist. M4-P6
adds it.

**WHAT M4-P6 INHERITS FROM THIS CHOICE, stated so it is not discovered.** The
plugin's `files` array is `["dist", ".claude-plugin"]`. M4-P6 edits the
manifest to declare hooks and creates hook modules, and its files-to-touch
(delivery/plan/kernel-plan-m4.md:919) does not include `plugin/package.json`.
The compiled hook modules land under `plugin/dist/src/hooks/` and are already
covered by the `dist` entry. A hooks JSON placed beside the manifest, under
`.claude-plugin/`, is also already covered. A hooks JSON placed at
`plugin/hooks/hooks.json`, which is the layout the probes used, is NOT covered
and would need a `files` entry, which is one line on M4-P6's declaration. Two
of the three options need no scope grant; that is the whole of the
constraint this phase imposes.

**The manifest's NAME is `tiphys`, not `tiphys-claude-code`.** The host is
Claude Code, so naming the plugin after its host inside its own manifest says
nothing; and workstream 2's project-write-block hook lands in THIS manifest
rather than in a second one, so the name has to cover more than the adapter.
The npm package keeps the harness in its name, `@tiphys/claude-code-plugin`,
because THERE it is the distinguishing part: a Codex or Cursor plugin would be
a different package and the same manifest name inside its own tree.

**A test asserts the manifest parses**, that its version matches the package's,
and that it declares NO `hooks` key yet. The last one is not pedantry: a `hooks`
pointer naming a file that does not exist is a manifest-level guard that cannot
go red, and the assertion moves with M4-P6 when M4-P6 adds the hooks. The
reason a test exists at all is M4-P1's measurement that a nonexistent
`--plugin-dir` makes the harness fail OPEN at exit 0, so a manifest the harness
cannot read produces a session with no plugin and no complaint. Nothing else in
this repository reads this file.

## How the plugin reaches `@tiphys/kernel`, and why there is an `overrides` entry

The plugin imports its types from the PACKAGE NAME (criterion 6). For that to
resolve, `@tiphys/kernel` has to be findable from `plugin/src/`, and the root
package IS `@tiphys/kernel`, which npm does not link into its own
`node_modules` on its own.

**FOUR FORMS WERE MEASURED, in a scratch tree built for the purpose, node
v26.6.0 and npm 11.18.0, one variable changed at a time.** The scratch tree is
a two-file reproduction: a root package named `@tiphys/kernel` with
`workspaces: ["plugin"]`, and a workspace declaring the kernel in one of three
dependency fields.

| the plugin declares | root `overrides` | what npm produced |
|---|---|---|
| `peerDependencies` `@tiphys/kernel` `0.1.0` | none | **the REGISTRY tarball**: `node_modules/@tiphys/kernel` is a real directory and npm reported "added 12 packages" |
| `peerDependencies` | `@tiphys/kernel: file:.` | the workspace root, but with `npm warn ERESOLVE overriding peer dependency` on every install |
| `dependencies` | `@tiphys/kernel: file:.` | the workspace root, zero warnings |
| `devDependencies` | `@tiphys/kernel: file:.` | the workspace root, zero warnings |

Rows two, three and four were each run as `npm install` followed by `rm -rf
node_modules && npm ci`, and both commands produced the same tree; row one was
run as `npm install` only, because a registry fetch was already the answer and
the point of the row is that the fetch happens at all.

The first row is the trap and it is silent in the worst way: the published
`@tiphys/kernel@0.1.0` predates M4-P4, so it has no `exports` map and no
`ExecutorAdapter` to import. A build against it fails for a reason that reads
as a TypeScript problem.

**`devDependencies` is the chosen row, and the reason is that the dependency is
TYPE-ONLY.** `plugin/src/adapter.ts` imports four types and no values, and
`verbatimModuleSyntax` erases the whole statement from the emitted JavaScript,
so `plugin/dist/src/adapter.js` imports three node builtins and nothing else
and there is no kernel import for Node to resolve at run time. The DECLARATION
output keeps it, which is why `plugin/dist/src/adapter.d.ts` does carry
`@tiphys/kernel`; a declaration file is a build-time artifact and never runs,
which is exactly what makes the dependency a build-time one. A `dependencies` entry would assert a runtime need this
package does not have. M4-P6 or M4-P7 importing a kernel VALUE is what would
move it, and this paragraph is where the next implementer finds out that the
move is one line.

**The `overrides` entry is inert for consumers.** npm applies only the ROOT
project's `overrides`; an `overrides` block inside an installed dependency's
`package.json` is not read. So it changes what this repository installs and
nothing about what anyone who installs `@tiphys/kernel` gets.

## The adapter

`plugin/src/adapter.ts` is one exported object and three helpers. Its `launch`
does exactly four things, in this order, and the order is the contract:

1. **Build the launch record and write it.** `adapter` is `claude-code`,
   `launchedAt` is an ISO instant, `deadline` is present exactly when the
   request carried `deadlineSeconds`, and `requestedTier` and `requestedRole`
   are copied VERBATIM when the request carried them (M4-P3 criterion 6: what
   was REQUESTED, never what was resolved; the kernel holds no tier vocabulary
   and neither does this record). A failure here returns `launch-failed`.
2. **Refuse an empty command.** `launch-failed`, before anything starts.
3. **Spawn the payload**, without a shell, in `request.worktree`, with
   `request.env` spread rather than assigned so an undefined env means Node's
   full-inheritance form. A `spawnSync` `error` is `launch-failed`: no process
   was created. No shell, for the reason the kernel's own adapter gives: under
   one, a missing binary arrives as exit code 127 and is indistinguishable from
   a payload that ran and failed.
4. **Invoke the turn-end hook** with the payload's exit code as a STRING of an
   INTEGER, converting a signal death to 128 plus the signal number. Anything
   that goes wrong from here is `incomplete`.

`payloadExitCode` is reimplemented rather than imported, and that is a
deliberate consequence of criterion 6: the kernel does not publish it,
`src/index.ts` publishes the adapter contract and nothing else, and reaching
past the published surface for it is the climbing relative import the criterion
forbids. The duplication is four lines and it is named here so a reviewer reads
it as a decision.

The generated hook exits 64 on a non-integer argument (src/hooks.ts:47), which
`spawnTask` then reports as "the turn-end record could not be written", hiding
the real outcome behind a plumbing failure. That is M4-P6 criterion 1's
subject; this phase's contribution to it is the conversion, and nothing in this
phase drives a signal death, so the conversion is present and unwitnessed here.

### 2. `build:runtime-deps` skips workspace links, and that is trap 2 realised

The plan's packaging trap 2 is "a plugin directory that lands inside `dist/`
through the build would be published as part of `@tiphys/kernel`"
(delivery/plan/kernel-plan-m4.md:773). It happened, and it happened through a
route that is not obvious from reading `files`.

`npm run build:runtime-deps` walks `node_modules/.package-lock.json` and copies
every entry npm has not marked `dev` into `dist/node_modules`. A workspace link
is such an entry. Measured on this branch before the fix, after a plain
`npm run build`:

```
dist/node_modules/@tiphys/claude-code-plugin -> /tmp/.../w6-m4-p5/clone/plugin
dist/node_modules/@tiphys/kernel            -> /tmp/.../w6-m4-p5/clone
```

Two ABSOLUTE symlinks into the machine that ran the build, inside the directory
the package publishes. The fix is one added condition, `entry?.link === true`,
in the same filter that already skips dev entries. After it, `ls
dist/node_modules/@tiphys` reports "No such file or directory".

**Stated honestly, because the fix is belt and braces rather than the thing
that stops the leak.** `npm pack` does not list symlinks: measured by removing
`!dist/node_modules` from `files` with the link vendoring restored, the tarball
grew by 1722 `dist/node_modules/` paths and NONE of them was the plugin. So the
tarball was not carrying the plugin by this route even before the fix. What the
fix stops is a build output that points at the builder's home directory, and it
removes one of the three routes the packaging test now checks.

## The shape M4-P6 and M4-P7 inherit

Both later plugin phases create files under `plugin/`, so the layout chosen
here constrains them. It is written out rather than left to be read off the
tree.

```
plugin/
  package.json              name, type module, exports, files, devDependencies
  tsconfig.json             composite, rootDir ".", outDir "dist",
                            references ../tsconfig.src.json, include src/**/*
  .claude-plugin/
    plugin.json             the manifest the harness loads
  src/
    adapter.ts              the ExecutorAdapter implementation
    index.ts                the default export the kernel's loader requires
  dist/                     gitignored; the published code
```

Four facts a later phase needs:

1. **The default export is the loader's whole contract.** `src/adapters/load.ts`
   refuses a module with no `default`, a default that is not an object, a
   default with no `launch`, a `launch` that is not callable, and a default
   with no usable `name`. `plugin/src/index.ts` exports the adapter object
   itself, unwrapped.
2. **`exports` must offer a `require` or `default` condition.** The loader
   resolves with `require.resolve` (src/adapters/load.ts:191), which applies the
   `require` condition, and src/adapters/load.ts:170 records that a map offering
   only `import` fails with ERR_PACKAGE_PATH_NOT_EXPORTED. The plugin's map
   offers `default`, so it resolves; the file it names is an ES module and is
   imported through a file URL, which is the shape that paragraph describes.
3. **Plugin tests live under `test/`, and not under `plugin/test/`.** The
   `suite` gate runs `package.json`'s `test` script, whose glob is rooted at
   `test/`. RW2 below measures both placements with the same failing assertion:
   under `test/` it runs and fails the suite, under `plugin/test/` its name does
   not appear in the run at all. A test in this phase reddens if a
   `plugin/test/` directory appears.
4. **The kernel is a TYPE-ONLY dependency today.** A later phase importing a
   kernel VALUE has to move `@tiphys/kernel` from `devDependencies` to
   `dependencies` in `plugin/package.json`. That file is on no later phase's
   declaration, and the scope auditor admits only paths the declaration lists
   plus two standing extras (src/gates/scope.ts:978), so the move is one line
   of code and one line of declaration.

**And one thing a later phase will want that does not exist.** M4-P6 criterion
7 asks the plugin to emit status through `emitStatus` (src/status.ts:98).
`src/index.ts` publishes the adapter contract and nothing else, deliberately,
so `emitStatus` is not reachable by package name. Criterion 6 here forbids
reaching it by a relative path that climbs out of `plugin/`. Those two
constraints together mean M4-P6 either widens the kernel's `exports`, which is
a public API decision, or writes the status record itself. Neither is decided
here; it is flagged so it is not discovered at the end of that phase.

## The derivation

**The mechanism this phase had to enumerate is not "the plugin" but "a
non-dev entry of `node_modules/.package-lock.json`".** Two separate consumers
walk that file and neither of them knows what a workspace is: `npm run
build:runtime-deps` copies every such entry into `dist/node_modules`, and
`scripts/license-gate.mjs:198` inventories every such entry as a production
package. Adding a workspace adds entries, so both consumers change, and finding
one of them by tripping over it would have left the other.

The command that enumerates every entry both consumers see, and its full
output, on this head:

```
$ node --input-type=module -e "import {readFileSync} from 'node:fs'; \
  const l = JSON.parse(readFileSync('node_modules/.package-lock.json','utf8')); \
  for (const [p,e] of Object.entries(l.packages ?? {})) \
```

### Criterion 6: the plugin imports the kernel by package name

**WHAT "COMPILED OUTPUT" HAS TO MEAN HERE, and it was nearly got wrong.**
`verbatimModuleSyntax` erases an `import type` entirely, so a climbing TYPE

`adapter.js` carries three node builtins and no kernel import; `adapter.d.ts`

earlier form of `plugin/src/adapter.ts` carried the literal token in a comment
and a raw grep of the compiled output hit it. The comment was reworded and the
test was written to strip comments before matching.

adapter's specifiers. Zero climbing imports is also what a plugin that imported
nothing from the kernel would report, and an absence is only evidence beside a

### Criterion 8: the record goes down before the payload, and the arms are not transposed

Four tests, and each one asserts BOTH the arm AND whether the payload ran. An

itself and writes down what it saw; the test then asserts that what the payload
saw is byte-identical to what is on disk afterwards. That is real captured
output from the program under test rather than a string chosen to match the
implementation.

## One capture was contaminated, and how that was caught

**Recorded because the capture LOOKED fine and the arithmetic did not.** An
earlier verification pass was stopped mid-run by killing its script. Killing the
script did not kill the `node --test` CHILDREN it had spawned, and those
children kept writing to the same capture path that the NEXT pass had just
truncated. The file therefore held two runs interleaved.

What gave it away was the arithmetic rather than the tail:

```
$ grep -c '^x' final-bare-node-test.txt      # x is the transliterated U+2716
3                       # three failing test lines in the body
$ grep '^i' final-bare-node-test.txt | tail -8   # i is the transliterated U+2139
tests 1172  pass 1169  fail 1  skipped 2
```

(The two greps were run against the untransliterated capture with the real
glyphs; they are written here with the substitutions this document declares at
the end, so the commands as printed match the text as printed.)

`1169 + 1 + 2 = 1172` exactly, so the SUMMARY is one run's own and is
internally consistent; the two extra failure lines belong to a different run
and are not counted anywhere. A reader who quoted either half would have been
quoting a number no single command produced.

The fix was mechanical rather than careful: every process whose
`/proc/<pid>/cwd` is inside this clone was killed, the count re-read as zero,
the tree confirmed unchanged by `git status --short`, and the suites re-run
from a quiet tree. The numbers quoted in this document are from THAT run.

**The lesson for the next agent, and it generalises past this phase:** a
background script that spawns a test runner owns a process TREE, and stopping
it by name leaves the tree running. A capture file truncated by a later run is
then written by both, and nothing in the file says so. Redirect each run to a
UNIQUELY NAMED file, or verify the process tree is gone before starting the
next one.

## Transliteration of captured output

reporter prints three non-ASCII glyphs at the head of its summary and
result lines, so a work history pasting a real run verbatim fails the
authored-bytes check. Hand-writing the output instead is the fabrication
the red-witness rule exists to prevent, so the captures here are
TRANSLITERATED and the substitutions are named with their counts:

- U+2139 INFORMATION SOURCE, rendered `i`, 15 occurrence(s)
- U+2714 HEAVY CHECK MARK, rendered `ok`, 5 occurrence(s)
- U+2716 HEAVY MULTIPLICATION X, rendered `x`, 11 occurrence(s)

captures are shortened with an ellipsis of three ASCII dots in a few
