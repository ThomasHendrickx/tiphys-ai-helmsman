## Mechanism lookup (T-005 interim obligation)

Read MECHANISMS.md in full. Rows bearing on this phase:

1. "Parsing another program's reporter output": PIN the format as a
   controlled input rather than widening the parse. This is the core of
   step 2: the reporter is REQUESTED by name for the child, the received
   stream is validated to be that format before any count is parsed, and a
   stream in any other format is `error` naming expected and observed.
   Requires: no format-agnostic regex, no acceptance of whichever format
   arrived.
2. "Deciding what another program will do by pattern-matching the text of
   a file it consumes": the wrapper must run the suite the way the
   repository configures it (`package.json` scripts.test), and reading that
   script text is exactly this mechanism. The row's tier 2 applies: PIN the
   accepted shapes and fail closed on anything else, never widen. The
   accepted shape is declared below (see "Pinned script grammar") and any
   scripts.test outside it is `error`, never a guess at what npm would do.
3. "Reading a path whose type is not established" (M2-C-6): every path this
   gate reads that it did not create (package.json, test/behaviors.json,
   walked test files, the reporter stream file) routes through the
   delivered `classifyEntry` / `readRegularFileIfPresent` /
   `refuseOpenForWrite` from src/task.ts. No bare readFileSync on an
   externally supplied path.
4. "Classifying another program's errors" / CLAUDE.md warning 10: parse
   fixtures and format-validation fixtures must be REAL captured output
   from the pinned Node's reporters, not hand-written strings. The captured
   streams are recorded below and committed as test fixtures.
5. "Claim file": not used by this gate (the runner owns the evidence-claim
   mechanism; this gate only writes inside the directory the runner hands
   it). Noted so the absence is a decision, not an oversight.

## Step 1: reporter survey on the pinned Node (recorded BEFORE choosing)

(appended below as measured)

The survey was performed on BOTH installed toolchains before the reporter
was chosen (the phase brief's emphasis). Probe scripts and full captured
output live in the session scratchpad (probe1.sh to probe5.sh); the
load-bearing findings and the verbatim decisive excerpts are recorded
here, and the captured streams used as test fixtures are committed inside
test/suite-gate.test.ts.

Toolchains measured:
- container default: node v22.22.2 (login shell and `bash -lc` both,
  checked in the shell that ran each probe)
- floor: node v26.6.0 from the pre-fetched scratch prefix, put first on
  PATH for the floor runs

Reporter inventory (measured, not recalled): `--test-reporter=<name>`
accepts tap, junit, spec, dot, lcov on both toolchains (each ran with
exit 0/1 per test outcomes); a non-built-in name is resolved as a MODULE
specifier (`--test-reporter=bogus` fails ERR_MODULE_NOT_FOUND, exit 7),
which means the documented custom-reporter interface is itself part of
what the pinned Node emits. Machine-readable candidates: tap, junit, and
the custom-reporter event stream. spec and dot are human-facing; lcov is
coverage only.

Decisive measurements, identical on v22.22.2 and v26.6.0:

1. TAP carries NO file attribution. A two-file suite (test/a.test.ts,
   test/sub/x.test.ts) reports all tests FLAT at the top level:
   `ok 1 - alpha passes` ... `ok 6 - sub x passes`, `1..6`. No file path
   appears anywhere in the stream for a passing test (only failing tests
   carry a `location:` in their YAML block). So TAP cannot support
   criterion 2's "naming the file", nor the file-set comparison of step 3,
   at all.
2. junit carries `file="..."` ONLY for non-nested testcases. With a
   parent test carrying subtests, and with describe/it, the nested
   `<testcase>` elements have no `file` attribute (measured, fix2 probe).
   And the counterfeit raw line printed by a test body does NOT appear
   anywhere in the junit stream (measured, fix1 probe), so criterion 6's
   "captured verbatim in the evidence" is unsatisfiable from junit alone.
3. The custom-reporter event stream carries, for EVERY test at every
   nesting level, on both toolchains: `data.file` (absolute path),
   `data.name`, `data.nesting`, `data.skip` (true or the reason string),
   `data.todo`, `data.details.type` ('test' or 'suite'), and on failure
   `data.details.error.failureType`. Raw test-body output arrives as
   `test:stdout` / `test:stderr` events with the verbatim `message`
   ("pass 999\n" captured exactly). File-level synthetic entities emit
   test:enqueue/test:complete but NEVER test:pass or test:fail (verified
   by grep over the captured event streams of both fixtures), so counting
   pass/fail events with details.type === 'test' reproduces node's own
   "# tests" semantics: fix2 gave 6 by this rule and `# tests 6` in the
   TAP summary of the same run.
4. Counterfeit routing: with a tap destination file, a test body's
   `console.log("pass 999")` lands INSIDE the tap stream as the comment
   line `# pass 999`, byte-identical in shape to the REAL summary line
   `# pass 3` seven lines below it in the same capture. This is the
   measured demonstration of why a summary-line parse is banned (C-1):
   the counterfeit and the authority are the same grammar. In the event
   stream the same bytes arrive as a `test:stdout` event whose payload is
   a JSON STRING, so an injected line cannot form an event: JSON.stringify
   escapes it inside the message field. Structural immunity rather than a
   cleverer regex.
5. A `data:text/javascript,<urlencoded module>` reporter works on both
   toolchains, both as a CLI flag and via child-scoped NODE_OPTIONS
   through /bin/sh -c (all four combinations measured; the header line
   the probe reporter emitted carried process.version v22.22.2 and
   v26.6.0 respectively, proving the stream records which node actually
   ran the suite).
6. `node --test` with a pattern matching NOTHING exits 0 and reports
   `1..0` / `# tests 0` (measured on v22). An exit-code-only check passes
   on an empty suite, which is CR-604's shape; the walk plus M2-C-2
   close it here.
7. Cancellation vocabulary differs between toolchains for the same
   fixture: the never-resolving-promise test under --test-timeout=500 is
   `failureType: 'cancelledByParent'` on v22.22.2 and
   `failureType: 'testTimeoutFailure'` on v26.6.0. The did-not-run bucket
   is therefore PINNED to `cancelledByParent` (the only shape node itself
   counted under `# cancelled 1` in the same run's TAP summary), and every
   other test:fail is `fail`. This mapping is recorded in every run's
   counts.json.

REPORTER CHOSEN, after the survey and because of it: a gate-owned NDJSON
event reporter named `tiphys-suite-events-v1`, delivered as a data: URL
module embedded as a string constant in src/gates/suite.ts, requested
explicitly for the child via child-scoped NODE_OPTIONS
(`--test-reporter=data:... --test-reporter-destination=<evidence path>`),
with ambient NODE_OPTIONS deliberately dropped from the child environment
(an inherited reporter option is precisely the ambient default the pin
exists to exclude). The stream is validated as that format before any
count is parsed: header line first, every line a JSON object with a known
event field, explicit stream-end trailer last; anything else is `error`
naming the expected and the observed format. This is a DECLARED DEVIATION
from the plan's singular "chosen machine-readable reporter" being one of
the named built-ins: the measurements above show tap cannot satisfy
criteria 2 and 3 (no file attribution) and junit cannot satisfy criterion
6 (raw output dropped) or step 3 under nesting (file attribution lost),
so no single built-in satisfies the phase's criteria, and requesting BOTH
built-ins would mean two parsers and a file set that still goes dark on
nested tests. The custom-reporter interface is documented, pinned Node
behavior, measured on both toolchains; the format it emits is owned by
this gate and versioned in its name. Decided under DR-0016 (recommendation
was unambiguous) and recorded here rather than escalated.

How the suite is EXECUTED (also decided from the mechanism index): the
gate runs the repository's configured `scripts.test` from package.json
verbatim through `/bin/sh -c`, exactly as npm does, rather than parsing
the script text and re-executing a reconstruction of it. Reading the
script and re-deriving "what npm would run" is the mechanism
"Deciding what another program will do by pattern-matching the text of a
file it consumes", and the survey's sh -c + NODE_OPTIONS measurement
(finding 5) shows verbatim execution with an injected reporter works on
both toolchains. Residues, stated: npm's PATH prepending of
node_modules/.bin and npm lifecycle hooks (pretest/posttest) are not
reproduced; the kernel's test script is a bare `node --test` glob with no
lifecycle hooks, and a repository whose test script depends on either
will fail loudly (stream absent -> error), never silently pass.
