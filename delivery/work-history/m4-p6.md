## What this phase did

Three modules under `plugin/`, one manifest edit, one adapter edit, one test
file, four fixtures and eight witness specs.

- **plugin/src/hooks/turn-end.ts:1** holds the conversion from a `spawnSync`
  result to the integer the generated kernel hook demands, and the invocation
  itself. The conversion existed already, inline in M4-P5's adapter; this phase
  MOVED it into the file the plan names and gave it a witness. The move is the
  smaller half of the value: what was missing was not the arithmetic, it was
  anything that would redden if the arithmetic changed.
- **plugin/src/hooks/tool-call-observer.ts:1** is the `PreToolUse` observer. It
  appends the hook payload verbatim, plus a receipt, to
  `tasks/<id>/tool-calls.jsonl`, writes nothing to stdout, and exits 0 on every
  path including every failure path. It carries no policy and makes no safety
  claim; the write block is workstream 2's.
- **plugin/src/status.ts:1** delivers the status line through the kernel's own
  command line and holds no status path of its own.
- **plugin/.claude-plugin/plugin.json:1** declares the observer INLINE.
- **plugin/src/adapter.ts:212** emits the turn's status line and then invokes
  the turn-end hook, in that order and for a reason stated below.
- **test/plugin-hooks.test.ts:1** is the phase's eight tests.
- **test/fixtures/plugin-hook-payloads/** holds two real `PreToolUse` payloads
  projected out of M4-P1's captures and two verbatim line ranges of the shipped
  Claude Code binary's own strings. Their derivation is at
  test/fixtures/plugin-hook-payloads/PROVENANCE.md:1 and is re-run inside the
  test on every run.
- **witness/plugin-\*.json**, eight specs, sixteen dangerous-state members.

   captured verbatim. The observer was not loaded by a real Claude Code session
   in this phase, and no `claude` process was started by it at all. Specifically unestablished:
   - that a plugin manifest with INLINE hooks loads. The binary's schema strings

## The four decisions this phase took, and the evidence under each

### 1. The plugin tree is `plugin/`, and the hooks are declared INLINE

The tree was settled by M4-P5 and the plan's two later `packages/` mentions are
stale echoes of a question delivery/plan/kernel-plan-m4.md:1192 handed to the
orchestrator.

The manifest shape was NOT settled. M4-P1 built its probe plugin with
`"hooks": "./hooks/hooks.json"` and a separate file, and its own coverage table
says the M4-P5 manifest shape was left open
(delivery/work-history/m4-p1.md:879). Rather than copy a layout whose root the
probe did not pin down, the shipped binary was asked directly:

```
/opt/claude-code/bin/claude --version        # 2.1.273 (Claude Code)
strings -n 8 /opt/claude-code/bin/claude | grep -n 'hooks/hooks.json'
```

Seven of those lines are committed verbatim at
test/fixtures/plugin-hook-payloads/manifest-hooks-field.txt:1. Three of them
decide this:

- `Plugin hooks (~/.claude/plugins/*/hooks/hooks.json)`
- `. The standard hooks/hooks.json is loaded automatically, so manifest.hooks
  should only reference additional hook files.`
- `The hooks provided by the plugin, in the same format as the one used for
  settings`

So `manifest.hooks` accepts either a path to an ADDITIONAL hooks file, resolved
against the plugin root, or an inline object in the settings hooks format. The
inline form is chosen because it keeps the declaration inside the one file the
plan's files-to-touch names, which means this phase adds no undeclared file for
it. The residue is in the not-covered list above: documented is not measured.

### 2. Status delivery goes through the kernel's command line, so the plugin holds no status path

The brief warned that criterion 7 names `state/status/current.json` while
M4-P18 is moving the current document out of the gitignored `state/` prefix
under M4-D-13. The instruction was to read the constant from `src/status.ts`
rather than hard-code the plan's string.

This phase went one step further and gave the plugin NO status path in either
spelling. `deliverStatus` runs `tiphys status emit` and `showStatus` runs
`tiphys status show` (plugin/src/status.ts:163, plugin/src/status.ts:219), and
the kernel decides where both documents live. Two consequences worth stating:

- the M4-D-13 move cannot leave a stale path in this package, because there is
  no path here to go stale;
- the emit goes through `emitStatus` (src/status.ts:98) exactly as criterion 7
  requires, by way of src/commands/status.ts:138, and it is VALIDATED against
  the shipped schema before anything is written (src/commands/status.ts:127),
  which is why an invented state is refused rather than recorded.

The TEST still needs the paths in order to read the files, and it imports
`CURRENT_FILE` and `STREAM_FILE` from src/status.ts:32 rather than spelling
them. At the head this branch was cut from, `CURRENT_FILE` is
`state/status/current.json`; if M4-P18 lands first, the test follows it without
an edit.

`resolveKernelCli` locates the command line through the package name, using the
one subpath `@tiphys/kernel` publishes (`./package.json`, package.json:24), and
falls back to `bin/tiphys.ts` when the declared `bin` entry is absent. The
fallback is what makes every status test runnable in the red-witness harness's
scratch clone, which clones source and builds nothing. Without it those tests
would have to skip there, and a test that skips under the harness is a test
that cannot go red.

### 3. The observer derives its log path from the payload, because it may not be handed one

`tasks/<id>/tool-calls.jsonl` is inside the fleet home, and a `PreToolUse` hook
is a child of the agent, not of the adapter. The obvious answer is an
environment variable, and it is not available: src/exec/env.ts:69 builds the
child environment from an exact-name allowlist and plugin/src/adapter.ts:188
records that an adapter never widens it. Adding `TIPHYS_TASK_DIR` would be
precisely the widening M2-P8 forbids.

What the hook does receive is the payload's `cwd`. For a kernel-launched agent
that is the task worktree, `<fleet>/worktrees/<taskId>` (src/pool.ts:241), so
the task directory is the sibling `<fleet>/tasks/<taskId>`. The derivation is
checked rather than assumed: the parent directory must be named `worktrees` and
the task directory must already exist, and an observer that resolves nothing
records nothing and still exits 0.

### 4. Criterion 6's test compiles the plugin itself rather than reading `dist/`

The criterion asks for a test over COMPILED output. Reading `plugin/dist/`
would make the test depend on a prior `npm run build`, and standing warning 12
records what that costs: nine tests already skip silently when `dist/` is
absent, and the run still exits 0. In the red-witness harness it is worse than
silent, because a skipped test is never red and the member would pass through
looking guarded.

So the test invokes the pinned `tsc` from `node_modules` with `--noCheck` into a
temporary directory and asserts over what it emitted. Measured cost of that
compile, on the plugin's five sources:

```
$ time node node_modules/typescript/bin/tsc --noCheck --module nodenext \
    --moduleResolution nodenext --target es2024 --rewriteRelativeImportExtensions \
    --verbatimModuleSyntax --rootDir plugin/src --outDir "$OUT" \
    plugin/src/hooks/tool-call-observer.ts plugin/src/adapter.ts plugin/src/index.ts
real    0m0.114s
```

`--noCheck` is deliberate and it is what makes the two members of that witness
redden for the right reason. A mutation that introduces `readFileSync` without
importing it is a TYPE error and an ordinary compile would fail on it, which is
a red the test did not earn. With `--noCheck` the emit still happens and the
test reddens on the thing it actually asserts: a read-family call in the module
that owns the append-only log.

## The acceptance criteria, walked

### Criterion 1: the turn-end exit code is always an integer

Test: `a turn that ends with no exit code still hands the generated turn-end
hook an integer`, test/plugin-hooks.test.ts:247.

Two arms in one test. The first is the degenerate termination, both `status` and
`signal` null, which `SpawnSyncReturns` types as expressible and which no real
spawn on this platform produces; it is asserted directly against
`payloadExitCode` and `turnEndInvocation`. The second is a real turn that ends
with no exit code: the payload runs `kill -KILL $$`, so `spawnSync` reports
`status: null`.

The assertion is the OUTCOME ARM, not the file's presence. A non-integer
argument makes the generated hook exit 64 (src/hooks.ts:47), the adapter reports
`incomplete` with a plumbing reason, and the payload's real outcome is nowhere.
So `assert.equal(outcome.kind, "completed")` is the assertion that refuses the
dangerous state, and the parsed record's `Number.isInteger` is the second half.

The hook under test is the kernel's own generated text, written to the lab by
calling `renderTurnEndHook` (test/plugin-hooks.test.ts:200). It is not a
stand-in, so the exit-64 refusal this criterion turns on is the shipped one.

### Criterion 2: the second member of the class, and it is a different shape

Test: `a turn that ends by signal reports 128 plus that signal and never reports
success`, test/plugin-hooks.test.ts:314.

The two signals are PARSED out of M4-P1's own abandonment captures rather than
chosen here: `timeout -s KILL` and `timeout -s TERM` are read off the `command:`
lines of
test/fixtures/harness-probe/q2-launch-failed-vs-incomplete/D-abandon-sigkill.summary.txt:2
and
test/fixtures/harness-probe/q2-launch-failed-vs-incomplete/E-abandon-sigterm.summary.txt:2,
and the test asserts the derivation yields exactly `["KILL", "TERM"]` so a
fixture change is loud rather than silent. The expected value is
`128 + os.constants.signals["SIG" + name]`, read from the platform.

The plan's point about `status ?? 0` is exactly right and is what makes these
two members structurally different rather than two spellings of one. Measured,
by applying that member and running BOTH tests:

| member applied | criterion 1's test | criterion 2's test |
|---|---|---|
| `return status ?? 0;` | red (its unit arm asserts 128) | red (0 instead of 137) |
| `return 128 + (number as number);` | red (NaN is not an integer) | GREEN (SIGKILL is mapped) |

The second row is the one worth reading: a fix that handles only the mapped
signals passes criterion 2 and fails criterion 1, and a fix written as `?? 0`
would pass a criterion-1 test that asserted only integer-ness. Neither test
alone is the class.

### Criterion 3: the hook is invoked by the ADAPTER, not by a `Stop` hook

Test: `the turn-end record is written by a process the adapter spawned, and no
Stop hook is declared`, test/plugin-hooks.test.ts:355.

The lab's hook is the generated text with three lines APPENDED that record
`process.ppid` and `process.argv.slice(1)`. The adapter runs inside the test
process and invokes the hook with `spawnSync`, so the hook is a direct child and
its `ppid` is the test process's `pid`. The assertion is
`invocation.ppid === process.pid` plus `argv` deep-equal to `[hookPath, "5"]`,
which is the plan's "comparing the recorded path against the adapter's own
invocation log" made into a process-identity measurement.

The design half is asserted on the manifest: the declared hook events are
exactly `["PreToolUse"]`, and the declared command names the observer. A `Stop`
hook receives static JSON and has no exit code to carry
(delivery/plan/m4-intake.md:1029), so a design that routed the exit code through
one would have nothing to route.

### Criteria 4 and 5: the observer blocks nothing and summarises nothing

Tests: `the observer lets a tool call through and records it, and removing it
changes only the record`, test/plugin-hooks.test.ts:495, and `the observer's
line round-trips the captured hook payload and adds only a receipt`,
test/plugin-hooks.test.ts:572.

A real `claude` run is not available to this phase, so the tool call is PLAYED
past the hook by a driver whose rule is taken from measurement and then checked
against it before it is used:

- the exit-code half is M4-P1's matrix. `hook-exit-configured: 0` with
  `app.txt changed: YES`
  (test/fixtures/harness-probe/q1-bypass-permission-mode/bypass-exit0.summary.txt:3),
  and `hook-exit-configured: 2` with `app.txt changed: NO`
  (test/fixtures/harness-probe/q1-bypass-permission-mode/control-acceptEdits-exit2.summary.txt:3).
  The test reads both fields out of both captures and asserts its own rule
  agrees with them, so a driver that had drifted from the measurement fails
  before it is trusted.
- the stdout half is the shipped binary's documented protocol, captured verbatim
  at test/fixtures/plugin-hook-payloads/hook-json-output-contract.txt:1: a
  decision travels as `decision`, `continue` or
  `hookSpecificOutput.permissionDecision`, all on stdout. A hook that exits 0
  and writes nothing to stdout has expressed no decision at all.

Both directions of criterion 4 are asserted in the one test: with the observer
installed the write lands and one line is appended; with the observer removed
the same write lands and no line is appended. The second direction is what stops
this being green for a system in which the observer is the only thing letting
the write happen.

The payload for the live arm is the real capture with exactly two paths
relocated, `cwd` and `tool_input.file_path`, because M4-P1's scratch directory
is gone. The relocation is written into the test at
test/plugin-hooks.test.ts:529 and every other field crosses untouched.

Criterion 5's round trip uses the fixtures UNMODIFIED and asserts three things:
the record's `payload` deep-equals the fixture, the receipt hash is over the
bytes that arrived, and the record has exactly three keys. A summarised record
fails the first on `tool_input.content` and on `permission_mode`; a record whose
hash is over the re-encoded object fails the second.

The fixtures cannot drift from the captures they came from, because the test
re-runs the projection: take the summary's `--- marker.jsonl ---` section, parse
its first non-empty line, keep the five payload keys M4-P1's marker recorded.
Editing either side reddens.

### Criterion 6: nothing reads state from the log (C-1)

Test: `the compiled plugin appends to the tool-call log and never reads it`,

Four assertions over emitted JavaScript, not over source and not over a grep

### Criterion 7: status lines are delivered and are valid

Test: `an agent turn delivers a status record that validates, and the current
document is the read path`, test/plugin-hooks.test.ts:711.

A real turn through `launch` against a real fleet home. After it: the stream
holds at least one line, the current document holds the last record, its `run`
is the task id and its `state` is `done`, and
`tiphys validate --type status-line <current document>` exits 0.

C-1 is asserted in both directions and this is the part worth reading, because
only one direction is informative on its own. Appending `{not json at all` to
the stream leaves `tiphys status show` reporting exactly what it reported
before; rewriting the current document changes it. The first assertion alone
would be green for an implementation that reported nothing at all, which is why
the second is there.

### Criterion 8: status delivery does not fail the turn

Test: `a status emit that fails leaves the turn outcome unchanged and the
turn-end record written`, test/plugin-hooks.test.ts:765.

Two turns, identical but for the status target. The control runs against an
intact fleet; the broken arm runs against a fleet whose `state` directory has
been REPLACED BY A REGULAR FILE. Replaced rather than removed, because
`emitStatus` opens with `mkdirSync(directory, { recursive: true })`
(src/status.ts:100) and would quietly put a removed directory back, which would
make the arm vacuous.

Three assertions, and the third is what keeps the other two honest:

1. the broken arm's outcome deep-equals the control's, `{ kind: "completed",
   exitCode: 3 }`;
2. the turn-end record is still written and still carries 3;
3. the current status document is ABSENT in the broken arm, so the emit really
   did fail.

The ORDER in plugin/src/adapter.ts:212 is the property, not a preference: the
status emit is placed BEFORE the turn-end invocation, so an emit that threw or
returned early would take the turn-end record with it and the witness would see
it. Placed after, the same bug would be invisible to this test.

## Red witnesses

Eight specs at `witness/plugin-*.json`, sixteen dangerous-state members, two per
spec. Every spec is `class: additive`, `deterministic: true`, `repeats: 2`, and
every one declares `consumesExternalOutput`.

**Why every spec declares captures.** Rule (f) of the harness
(src/witness/run.ts:1312) derives the obligation rather than trusting the
declaration: a member touching a changed file that matches
`child_process|execFile|spawnSync|execSync` requires it. Three of the four files
these members mutate match, so six of the eight specs owe it whatever this
document says. The other two declare it because their tests genuinely consume
M4-P1's captures, and a uniform rule is easier to keep true than a per-spec one.

**One thing about rule (c) worth naming rather than leaving for a reviewer to
find.** The harness checks a cited capture's basename against the whole SOURCE
of the files holding the named tests (src/witness/run.ts:1266), not against the
test body. All eight tests live in one file, so any capture named anywhere in
`test/plugin-hooks.test.ts` satisfies the rule for every spec. That makes the
check weaker than it reads, and the `provenance` string on each spec says which
capture that spec's own test actually consumes.

### The sixteen members, and why each pair is two members rather than one

Rule (g) collapses two mutations of the same text in the same file into one
member. None of these pairs collapses, and more to the point none of them is two
spellings of one bug:

1. **always-integer.** `128 + (number as number)` lets `undefined` through, so
   the degenerate termination becomes NaN. `String(termination.status)` sends
   the literal text `null` to the hook, which exits 64. The first breaks the
   arithmetic; the second breaks the argument. A fix for either leaves the other.
2. **signal-convention.** `return status ?? 0` removes the conversion and
   reports SUCCESS for a killed agent. `64 + (number ?? 0)` keeps the conversion
   and gets the base wrong. One is a missing mechanism, the other a wrong
   constant.
3. **invoked-by-adapter.** An intermediate `node -e` process spawns the hook, so
   the record is written by a grandchild and the `ppid` claim fails; separately,
   the manifest gains a `Stop` hook. One attacks the runtime claim, the other
   the design claim, and the test asserts both.
4. **blocks-nothing.** `process.exit(2)` blocks through the exit code;
   a `permissionDecision: "deny"` on stdout blocks through the JSON protocol
   while still exiting 0. The captured contract
   (test/fixtures/plugin-hook-payloads/hook-json-output-contract.txt:1) is what
   says the second channel exists at all, and a witness that only covered the
   exit code would be green for it.
5. **records-payload-verbatim.** One member summarises the payload down to
   `tool_name`; the other keeps the payload whole and hashes the re-encoded
   object instead of the bytes that arrived. The second is the subtle one: the
   record still round-trips, and the receipt silently stops being evidence of
   what was received.
6. **log-never-read-as-state.** One member gives the observer a read API; the
   other gives the ADAPTER a read of the log. The second is the real C-1
   violation, a decision taken from the tail of an append-only file, and it
   reddens two of the test's four assertions.
7. **status-delivered.** One member removes the emit entirely; the other emits a
   state outside the kernel's closed vocabulary, which the kernel refuses
   (src/commands/status.ts:127) so that nothing is written. Silence and a
   refused write are different failures with the same symptom.
8. **status-failure-not-the-turn's.** One member makes `deliverStatus` throw
   instead of returning its failure; the other makes the ADAPTER turn a failed
   delivery into an `incomplete` turn. The first is telemetry escaping, the
   second is telemetry being obeyed.
