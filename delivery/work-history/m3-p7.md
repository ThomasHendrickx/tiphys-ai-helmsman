## The mechanism this phase ships

A checklist is a probe list plus DECLARED ENTRY POINTS, and the entry point is
the part that has value. T-001's second data point is that the M1-P4 dual
review found different defects because the two reviewers were given different
STARTING QUESTIONS, not because they were different reviewers. So `framings[]`
is a field of the artifact and `checklist resolve --framing` reorders and
re-heads the list.

**The one design decision worth stating, because criterion 4d turns on it.** A
framing's `orders-probes` names probe SCOPES (`applies-to` tokens), never probe
ids. Probes in a named scope lead, scope by scope, and inside a scope the FILE
ORDER decides. A framing that named probe ids would pin the resolved head
wherever the probe sat in the file, which is precisely the hazard class's
"ordering expressed as a comment rather than as position" wearing a schema's
clothes. With scopes, moving `fix-round-not-covered` later in
checklists/clean-room.yaml:27 changes the resolved head, which is what makes
"the reviewer's FIRST check is item 3" falsifiable.

## Declared deviations

1. **`applies-to` on a probe is a scope TOKEN, not a list of document names.**
   Step 3d describes `c2-liveness-vocabulary` as having "`applies-to` covering
   `assurance-modes.yaml`, `AGENTS.md` and the role briefs". The schema makes
   `applies-to` a `[a-z0-9-]+` token because the resolver GROUPS on it, which is
   what makes `--framing` reorder rather than decorate (criterion 4d). The three
   documents are named in that probe's own text instead, where a reviewer reads
   them. Nothing is lost except the field's shape.
2. **The Kind A witness for criterion 4(a) removes the `enum` INSIDE `then`,
   not `then` itself.** Deleting `then` while `if` remains is refused at
   COMPILATION by this validator's strict policy, captured verbatim:
   `INVALID # schema is refused by this validator's strict policy`. That is a
   refusal of the SCHEMA rather than an acceptance of the instance, so it would
   witness nothing. Removing the enum leaves a well formed `then` that
   constrains nothing, which is the defanged schema the witness needs.
3. **The verdict's rule is stated WIDER than criterion 4(a).** The criterion
   names `high`; the shipped `contains` matches `high` OR `critical`, because
   critical outranks high and a rule stopping at high would let the worse
   finding through. A registered test captures the critical case separately.
4. **The three verdict checks resolve `plan.yaml` and `work-history.yaml` by
   fixed relative path from `--context`.** The plan names neither filename. The
   shape is the one `mode-gate-sets-resolve` already uses for
   `gate-registry.yaml` at src/checks.ts:640, and the join key is the verdict's
   own `phase` field, which the schema requires for exactly this reason.
5. **The `--extra` file is a full checklist document**, kind and all, rather
   than a bespoke fragment shape. A second, weaker schema for the extension
   mechanism would defeat R-054's point that a per-phase probe set is data a
   reviewer can validate on its own.
6. **The branch is the declaration's name**, not the one in the dispatch
   message. See the first section.

## Mechanism, cause A

Not "two witnesses name tests that stay green". The mechanism is the harness's
red predicate, at src/witness/run.ts:886:

```
red: exitCode !== 0 && failed.length === tests.length,
```

A member counts as red only when EVERY test the spec names fails. So a spec
whose members map one-to-one onto its named tests, each member breaking the arm
one test covers, can never be red on any member: each member reddens its own
test and leaves the sibling green. Both failing specs had exactly that shape,
and the gate reported it as an unreached arm because redCount reached zero.
