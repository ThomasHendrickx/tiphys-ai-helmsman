## 1. The defect, restated from the code rather than from the plan

`tasks/<id>/meta.json` is TRACKED and survives a reclaim.
`worktrees/<id>.pool.json` cannot survive, because `worktrees/` is one of
the three gitignored prefixes (src/fleet.ts:28) and the record sits beside
the worktree deliberately. The module's own words for why, at
src/pool.ts:40, are that it lives there "so the record can never dirty the
destroy-time cleanliness check (FM-059: no exemption list, ever)". That is
quoted from the source rather than asserted by me.

Teardown then refuses without that record and says so in terms. The reason
line, which this phase extends rather than replaces, still reads "teardown
needs it for the project remote and default branch, and refuses rather
than guessing them" (src/teardown.ts:268). So the plan's stated fallback
of "recovery is manual teardown" does not work post-reclaim, because the
manual path is the blocked one.

**What meta.json carries and what it does not.** `TaskMeta`
(src/task.ts:230) carries `id`, `project`, `shape`, `branch`, `worktree`,
`baseSha`, `baseOffline`, `status`, `createdAt`. `PoolRecord`
(src/pool.ts:60) needs `taskId`, `project`, `remote`, `branch`, `baseSha`,
`branchName`, `offline`, `createdAt`. Six of the eight map across
directly. The two that do not are `remote` (the project clone's configured
remote) and `branch` (that remote's default branch). Those two are exactly
the fields this phase is about.

**Why those two and not any other two.** `defaultRef` is built from them
(src/teardown.ts:304), landed-ness is judged against `defaultRef`, and the
landed judgement is what passes `deleteBranchForce: true` into
`poolDestroy`. So a wrong value there is not a cosmetic inaccuracy in a
report: it is the V-1 defect, branch deletion of unlanded committed work,
reached from the reclaim side.

## 2. What I built

Four source files, all on the phase's files-to-touch list except one,
which is declared and explained in section 7.

### 2.1 `reconstructPoolRecord` (src/pool.ts)

A three-way result rather than a two-way one:

- `complete`, every field derived;
- `incomplete`, carrying the PoolRecord FIELD NAMES git could not answer
  for plus the detail;
- `absent`, no readable task meta, so there is nothing to build from.

`remote` and `branch` are re-derived by calling the SAME two resolvers
`poolCreate` uses (`resolveRemote` and `resolveDefaultBranch`), so a
reconstruction repeats the original derivation instead of remembering a
value. It reads only; it writes nothing, anywhere.

The `incomplete` arm is the design point. No default is ever filled in.
Section 5's mutant D2 is what that buys.

### 2.2 `poolList` reports reconstructed entries (src/pool.ts)

`PoolListEntry` gains `origin: "record" | "reconstructed" |
"unreconstructable"` and, for the third, the unresolved field names. The
enumeration is now a union of `worktrees/*.pool.json` and OPEN tasks under
`tasks/` with no record beside them.

Closed tasks are excluded deliberately. Including them would add one
permanent line per finished task, and a report that grows without bound is
one nobody reads.

`tiphys pool list` appends ` reconstructed` or
` unreconstructable (unresolved: ...)`. The original two-field line is
unchanged for original records, so nothing that reads this output gains a
field it did not ask for.

### 2.3 `CHECK worktrees` (src/commands/doctor.ts)

One line naming, BY ID, every pool entry with no record beside it, and
whether it is reconstructable. WARN, with the condition
`worktree-record-missing`, and NOT promoted by any profile.

That last part is a decision, so here is the reason rather than the
preference: a fleet freshly rehydrated from its remote is EXPECTED to be
in this exact state, so promoting the condition would make
`doctor --for full` unpassable on the one fleet the remedy exists for, and
an unpassable check gets switched off. That is hazard H-D, and it is the
same reasoning the plan records for M4-P17's branch check at
delivery/plan/kernel-plan-m4.md:2724.

### 2.4 `--from-reconstructed` (src/teardown.ts, src/commands/teardown.ts)

The flag authorizes exactly one thing: DERIVING the two lost fields. It is
not a destruction override, and src/teardown.ts carries a header saying so
at length, because the two flags it sits beside ARE destruction overrides
and that is the trap (section 5, mutant D1).

Two further changes fall out:

- `DestroyOptions` gains an optional in-memory `reconstructed` record.
  Without it, `evaluateDestroy`'s base-sha gate has no base and returns
  its "pool record missing or unreadable" refusal, so the post-reclaim
  path would be blocked at the one gate that was already going to behave
  correctly. Passing the reconstruction in makes that gate ABLE TO JUDGE.
  `haveRecord` still comes from `existsSync` on the FILE, so nothing is
  created and nothing is unlinked that was not there.
- The unlanded refusal now names the branch TIP SHA (criterion 5). It is
  named on every unlanded refusal, not only the reconstructed one, so
  there is one message rather than two that can drift apart.

### 5.1 Dangerous state D1: the flag read as a DESTRUCTION OVERRIDE

The plan says the flag "mirrors the existing explicit-destruction pattern"
(delivery/plan/kernel-plan-m4.md:2859). The two flags it mirrors are
`--discard`, which overrides the dirty refusal, and
`--delete-branch-force`, which overrides the unlanded refusal. So the
natural mis-implementation is to pass both through, reasoning that with no
record nothing can be checked. The mutation, applied to
`teardownTask` right after `resolveContext`:

```

    return finish(fleet, context, {
      discard: true,
      deleteBranchForce: true,
      salvaged: false,
    });
  }
```

Result:

```
$ node --test /tmp/n26-m4p19/mD1/test/teardown.test.ts
tests 21 / suites 0 / pass 18 / fail 3 / skipped 0
D1 EXIT: 1
```

The three reddened, and the mutant's own stdout is the evidence of loss:

| test | mutant printed |
|---|---|
| refuses a dirty worktree and removes nothing | `torn down t-recon-dirty` |
| refuses an unlanded branch and names its tip | `torn down t-recon-unlanded` |
| derives a non-main default branch instead of guessing | `torn down t-trunk` |

Each is exit 0 where the test expects 1. `torn down` is the success line
`cmdTeardown` prints after the destroy has completed, so in each case the
worktree is gone.

**The two members of D1 are structurally different**, which is the
requirement one witness does not meet:

- the DIRTY member loses UNCOMMITTED work, through `discard: true`,
  against the cleanliness gate;
- the UNLANDED member has a CLEAN worktree, so the cleanliness gate has
  nothing to say, and loses COMMITTED work through `deleteBranchForce:
  true` against the landed-ness gate.

An implementation passing `discard: true` alone is green on the second and
red on the first; one passing `deleteBranchForce: true` alone is the
reverse. Different gate, different thing lost, separately defeatable.

## 6. What I did NOT cover

- **The rehydration path itself.** My fixtures delete the pool record; a
  real reclaim deletes the whole `worktrees/` tree. In THAT state there is
  no worktree either, so `poolDestroy` refuses at `no pool worktree for
  task id <id>` before any of this phase's code matters, and `pool list`
  and `doctor` report the entry with `headSha` `missing`. I exercised the
  record-only-gone shape because it is the one criteria 4 and 5 describe
  and the one where destruction is possible. The whole-tree-gone shape is
  untested here.
- **The scout shape.** Every teardown test I added uses
  `--shape ship`. The scout path also reaches `resolveContext` and would
  get a reconstructed record, and its own tip-versus-baseSha check would
  then compare against a `baseSha` that came from meta.json rather than
  from the record. I believe that is correct, because meta.json's
  `baseSha` is written by spawn from the same value the record holds, and
  **I did not test it and did not verify that claim by command.** Open
  question for review.
- **Concurrency.** Nothing here was exercised with two commands running at
  once. `reconstructPoolRecord` reads and does not write, so it has no
  race of its own, but a record appearing between the `readPoolRecord` in
  `resolveContext` and the one in `resolveDestroy` would mean the two
  stages see different records. I did not measure that window.
- **A reconstruction whose `meta.project` points somewhere that is not a
  git repository but does exist.** `resolveRemote` returns its "is not a
  git repository" reason and the result is `incomplete`, by reading the
  code; no test drives it.
- **macOS.** Everything here ran on Linux only.
- **The `doctor --for <profile>` arms.** I assert that the worktrees check
  does not move doctor's exit code under the default profile. I did not
  run `doctor --for full` against a reclaimed fleet, so the claim that no
  profile promotes `worktree-record-missing` rests on reading
  `PROFILES` (src/commands/doctor.ts:43) rather than on a run.
