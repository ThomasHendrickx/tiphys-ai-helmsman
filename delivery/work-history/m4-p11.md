## What I built

### 1. `schemas/charter.schema.json`: the declaration

`review-families`, an object with `available` (array of strings, `minItems: 1`)
and `reason` (non-empty string). Both required inside it; the object itself is
OPTIONAL at the root, because an absent declaration is the normal case.

The schema does not encode the exception. Single-family is
`available.length === 1` and what that then means belongs to the check. A
closed enum of family names was rejected: no such vocabulary can be kept
current, and a stale one would refuse a true declaration.

### 2. `src/checks.ts`: the reader, with provenance

`readReviewFamilies(contextDirectory, ref = "HEAD")` reads the charter out of
the git object database, never the working tree, on the
src/gates/release.ts:817 pattern, and records `{path, ref, refSha, sha256}`.

Two details that are load-bearing rather than incidental:

- **`HEAD:./charter.yaml`, with the `./`.** Without it git resolves the path
  against the REPOSITORY ROOT, so a context directory sitting inside a larger
  checkout would silently read that checkout's charter. With it, git resolves
  relative to the directory it was run in.
- **A declaration present in the tree and absent from the commit is ERROR.**
  Not absent, which would silently impose the strict rule, and not permission.
  The distinction is what makes criterion 9 mean something: if an uncommitted
  declaration were simply ignored, a reader could not tell "this project
  declares nothing" from "this project declares something nothing can check".

Duplicate entries are REFUSED rather than deduplicated. Every other
canonicalisation in this file collapses toward MORE refusals; this one would
collapse toward FEWER, because `[Anthropic, anthropic]` would become a
single-family declaration. It is the one fail-open direction available and it is
closed by refusing.

### 3. `src/checks.ts`: the exception arm and its two falsifiers

`singleFamilyException(contextDirectory, corpus)`:

- FALSIFIER 1, contradiction by the corpus: two or more distinct canonicalised
  `produced-by` values in the committed corpus contradict a one-family
  declaration. Red, and the reason names every observed value.
- FALSIFIER 2, the name must match: a verdict whose `produced-by` canonicalises
  to anything other than the declared family. Red, and the reason names the
  declared family in BOTH the operator's spelling and the canonical form,
  because the canonical form is what was compared and the operator's is what is
  in the file they are holding.
- Otherwise `produced-by` alone is exempted from the DISTINCTNESS requirement.
  `framing` and `review-contract` are untouched.

`dualReviewDecorrelation.run` gains a `continue` for the exempt dimension and
its final REPORT names the dimensions actually compared, so the sentence
"distinct on produced-by" is never written about a pair that was not required to
differ on it. The exception's own REPORT line is printed on the RED arm too, so
a run that reddens for another reason still shows that produced-by was exempt.

### 4. `scripts/check-dual-review.mjs`: the third status

`not-applicable`, exit 20, carrying `precondition.id`
`single-family-declared`, `met: false`, a reason naming
`review-families`, and evidence carrying `declared: true`, the ref sha, the blob
sha256, the declared families and every verdict's observed `produced-by`.

**A NEW precondition id and not the existing one.** This gate already has a
not-applicable arm, for a directory carrying no verdicts, whose reason says
there is no pair of reviews to compare. Routing the exception through it would
have made the record assert something false: two verdicts were read.

**`met: false` reads oddly and is right.** The precondition of running the
cross-family comparison is that the environment has more than one family. The
declaration establishes that it does not. Evaluated and unmet, which is what
SC-011 says `not-applicable` asserts.

**How the script knows the exception was RELIED ON, rather than asserting it.**
The falsifiers live inside the derived check and each produces a violation. A
single-family declaration that survives to a zero-violation run is therefore one
whose falsifiers passed, and both of them passing requires every committed
verdict to carry the one declared family.

**That is a derivation from the code, not a measurement, so it is labelled as
one.** I did not find an input where the declaration exists, the run reports no
violation, and the exception was not the reason `produced-by` stopped mattering.
The two directions I did run are the mutants `falsifier-1-off` and
`falsifier-2-off` below, which show each falsifier really does produce a
violation, and test 17, which is the control showing the registered path
reaching `status green` with `singleFamily` set. What would break the derivation
is a future arm that suppresses a falsifier's violation without suppressing the
declaration, and the two vacuity guards are the defence that is actually
executed rather than reasoned about.

### 5. `src/gates/run.ts`: the aggregation, which is the real work

`DECLARED_PRECONDITION_EVIDENCE` (`"declared: true"`),
`isDeclaredNotApplicable()`, a `declaredNotApplicable?: boolean` on
`GateSummaryRow`, a `declaredNotApplicable: string[]` on `RunSummary`, and a
clause appended to `decideAggregate`'s reason on EVERY arm.

**Why the marker is an array element and not a field.**
`src/gates/schemas/gate-result.schema.json` is `additionalProperties: false` on
the precondition object, so a `declared` boolean there is a schema change
outside this phase's files-to-touch list. What is done instead is the narrowest
available structural thing: an EXACT element of a structured array, compared
with `===`, never a pattern over detail prose, and
`src/gates/release.ts:1050` already writes that same string for the sibling
declared-none case. A test asserts that the producer's exported constant and the
runner's exported constant are the same string, so the two ends cannot drift
apart silently. **A boolean on `PreconditionRecord` is the better home and is
declared here as residue for whoever owns that schema.**

**`decideAggregate`'s signature did not gain a parameter.** The row type gained
an optional field instead, so every existing caller in `test/gates.test.ts`
still compiles and still gets the old reason. That file is not on this phase's
files-to-touch list.

## What stops a project declaring the exception when it is not true

The dispatch asked for a concrete falsifiable check and a plain statement of
what it cannot catch. Both falsifiers above are that check, and here is the
honest limit.

**What IS caught.** A project whose own committed verdicts carry two or more
distinct families cannot claim one (falsifier 1). A project whose declaration
names a family its verdicts do not carry cannot buy the relaxation (falsifier
2). Both are evaluated over the WHOLE committed corpus rather than over the pair
under review, so a project cannot satisfy them by arranging for two agreeing
reviews in front of the check while its history says otherwise.

**What is NOT caught, stated rather than implied.** A project that HAS a second
