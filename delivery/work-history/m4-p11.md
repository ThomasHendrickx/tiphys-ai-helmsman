## What I built

### 1. `schemas/charter.schema.json`: the declaration

`review-families`, an object with `available` (array of strings, `minItems: 1`)
and `reason` (non-empty string). Both required inside it; the object itself is
OPTIONAL at the root, because an absent declaration is the normal case.

The schema does not encode the exception. Single-family is
`available.length === 1` and what that then means belongs to the check. A
closed enum of family names was rejected: no such vocabulary can be kept
current, and a stale one would refuse a true declaration.

### 2. `src/checks.ts`: the reader, with provenance

`readReviewFamilies(contextDirectory, ref = "HEAD")` reads the charter out of
the git object database, never the working tree, on the
src/gates/release.ts:817 pattern, and records `{path, ref, refSha, sha256}`.

Two details that are load-bearing rather than incidental:

- **`HEAD:./charter.yaml`, with the `./`.** Without it git resolves the path
  against the REPOSITORY ROOT, so a context directory sitting inside a larger
  checkout would silently read that checkout's charter. With it, git resolves
  relative to the directory it was run in.
- **A declaration present in the tree and absent from the commit is ERROR.**
  Not absent, which would silently impose the strict rule, and not permission.
  The distinction is what makes criterion 9 mean something: if an uncommitted
  declaration were simply ignored, a reader could not tell "this project
  declares nothing" from "this project declares something nothing can check".

Duplicate entries are REFUSED rather than deduplicated. Every other
canonicalisation in this file collapses toward MORE refusals; this one would
collapse toward FEWER, because `[Anthropic, anthropic]` would become a
single-family declaration. It is the one fail-open direction available and it is
closed by refusing.

### 3. `src/checks.ts`: the exception arm and its two falsifiers

`singleFamilyException(contextDirectory, corpus)`:

- FALSIFIER 1, contradiction by the corpus: two or more distinct canonicalised
  `produced-by` values in the committed corpus contradict a one-family
  declaration. Red, and the reason names every observed value.
- FALSIFIER 2, the name must match: a verdict whose `produced-by` canonicalises
  to anything other than the declared family. Red, and the reason names the
  declared family in BOTH the operator's spelling and the canonical form,
  because the canonical form is what was compared and the operator's is what is
  in the file they are holding.
- Otherwise `produced-by` alone is exempted from the DISTINCTNESS requirement.
  `framing` and `review-contract` are untouched.

`dualReviewDecorrelation.run` gains a `continue` for the exempt dimension and
its final REPORT names the dimensions actually compared, so the sentence
"distinct on produced-by" is never written about a pair that was not required to
differ on it. The exception's own REPORT line is printed on the RED arm too, so
a run that reddens for another reason still shows that produced-by was exempt.

### 4. `scripts/check-dual-review.mjs`: the third status

`not-applicable`, exit 20, carrying `precondition.id`
`single-family-declared`, `met: false`, a reason naming
`review-families`, and evidence carrying `declared: true`, the ref sha, the blob
sha256, the declared families and every verdict's observed `produced-by`.

**A NEW precondition id and not the existing one.** This gate already has a
not-applicable arm, for a directory carrying no verdicts, whose reason says
there is no pair of reviews to compare. Routing the exception through it would
have made the record assert something false: two verdicts were read.

**`met: false` reads oddly and is right.** The precondition of running the
cross-family comparison is that the environment has more than one family. The
declaration establishes that it does not. Evaluated and unmet, which is what
SC-011 says `not-applicable` asserts.

**How the script knows the exception was RELIED ON, rather than asserting it.**
The falsifiers live inside the derived check and each produces a violation. A
single-family declaration that survives to a zero-violation run is therefore one
whose falsifiers passed, and both of them passing requires every committed
verdict to carry the one declared family.

**That is a derivation from the code, not a measurement, so it is labelled as
one.** I did not find an input where the declaration exists, the run reports no
violation, and the exception was not the reason `produced-by` stopped mattering.
The two directions I did run are the mutants `falsifier-1-off` and
`falsifier-2-off` below, which show each falsifier really does produce a
violation, and test 17, which is the control showing the registered path
reaching `status green` with `singleFamily` set. What would break the derivation
is a future arm that suppresses a falsifier's violation without suppressing the
declaration, and the two vacuity guards are the defence that is actually
executed rather than reasoned about.

### 5. `src/gates/run.ts`: the aggregation, which is the real work

`DECLARED_PRECONDITION_EVIDENCE` (`"declared: true"`),
`isDeclaredNotApplicable()`, a `declaredNotApplicable?: boolean` on
`GateSummaryRow`, a `declaredNotApplicable: string[]` on `RunSummary`, and a
clause appended to `decideAggregate`'s reason on EVERY arm.

**Why the marker is an array element and not a field.**
`src/gates/schemas/gate-result.schema.json` is `additionalProperties: false` on
the precondition object, so a `declared` boolean there is a schema change
outside this phase's files-to-touch list. What is done instead is the narrowest
available structural thing: an EXACT element of a structured array, compared
with `===`, never a pattern over detail prose, and
`src/gates/release.ts:1050` already writes that same string for the sibling
declared-none case. A test asserts that the producer's exported constant and the
runner's exported constant are the same string, so the two ends cannot drift
apart silently. **A boolean on `PreconditionRecord` is the better home and is
declared here as residue for whoever owns that schema.**

**`decideAggregate`'s signature did not gain a parameter.** The row type gained
an optional field instead, so every existing caller in `test/gates.test.ts`
still compiles and still gets the old reason. That file is not on this phase's
files-to-touch list.

## What stops a project declaring the exception when it is not true

The dispatch asked for a concrete falsifiable check and a plain statement of
what it cannot catch. Both falsifiers above are that check, and here is the
honest limit.

**What IS caught.** A project whose own committed verdicts carry two or more
distinct families cannot claim one (falsifier 1). A project whose declaration
names a family its verdicts do not carry cannot buy the relaxation (falsifier
2). Both are evaluated over the WHOLE committed corpus rather than over the pair
under review, so a project cannot satisfy them by arranging for two agreeing

## 1. THE MECHANISM

DV-001 and DV-002 are not two bugs. They are two members of one shape, and the
round fixes the shape.

**A LOOKUP AND THE DECISION IT FEEDS ADDRESS DIFFERENT TREES, AND THE
DISAGREEMENT IS NEVER REPORTED BECAUSE THE LOOKUP ANSWERS SUCCESSFULLY ABOUT
ITS OWN TREE.** The wrong answer arrives well formed, with exit 0, so nothing
downstream has anything to object to.

"Which tree" has TWO COORDINATES, and the round's two findings are one on each:

| coordinate | the two values | the finding |
|---|---|---|
| WHICH SNAPSHOT | the commit, or the working tree | DV-001 |
| WHICH ROOT a relative path resolves against | the context directory, or the repository | DV-002 |

The dispatch offered "a probe reads a different source, or a different scope,
than the decision it feeds". That is right and it is one word short of
mechanical: SOURCE and SCOPE sound like two unrelated problems, and naming them
as two COORDINATES of one address is what makes the derivation below finite.
An addressing site is wrong when either coordinate differs from the decision's,
and it is INVISIBLE in both cases for the same reason.

There is a third way the same fault surfaces, and it is the pair collapsing
rather than a third coordinate: **a probe that could not look at all, reported
as a fact about what is there.** `git cat-file -t <sha>:./<dir>` fails
identically for a path that is not in the tree and for an object database that
cannot produce the commit, and fix round 1's listing helper returned an EMPTY

## 4. THE SITES, AND WHAT CHANGED AT EACH

Three edits in two shipped files, and one staging option in the phase's test
file. Every one of them REMOVES a second reader rather than aligning two.

### 4.1 `listCommittedDirectory` becomes `listCommittedTree`, used by BOTH corpora

Fix round 1 left two git listing idioms in one file, twelve lines apart, and
only one survived a nested context. There is now one function with a
`recursive` parameter, and it uses the PATHSPEC form both callers can share:

```
git ls-tree [-r] -z --name-only <sha> -- ./<dir>/
```

The pathspec form's output is relative to the CURRENT DIRECTORY, which is the
context directory, which is the base `readCommittedVerdicts` then uses for
`git show <sha>:./<path>`. The listing and the read therefore resolve against
one base. That is the property that broke, stated as a property rather than as
a flag.

Measured from a context directory nested one level inside its repository, one
commit, four spellings, exit code and output for each:

```
ls-tree -z --name-only $S:./delivery/review                  => exit=0 []
ls-tree --full-tree -z --name-only $S:./delivery/review      => exit=0 [a-criteria.yaml|a-hazard.yaml|]
ls-tree -z --name-only $S -- ./delivery/review/              => exit=0 [delivery/review/a-criteria.yaml|delivery/review/a-hazard.yaml|]
ls-tree -r -z --name-only $S -- ./delivery/review/           => exit=0 [delivery/review/a-criteria.yaml|delivery/review/a-hazard.yaml|]
ls-tree -z --name-only $S -- ./delivery/review               => exit=0 [delivery/review|]
```

(`|` is a rendered NUL; the commands are run with `-z` and the separator is
shown so an empty result is distinguishable from a one-entry result.)

Two things in that table decided the spelling. **The trailing slash is
load-bearing**: without it the pathspec matches the TREE ENTRY and the listing
returns the directory's own name. And `--full-tree` on the tree-ish form also
works, and was rejected: it would have left two idioms in the file, which is
the thing being removed. The sibling `loadPaperworkVerdicts` already used the
pathspec form, so the fix is the file agreeing with itself.

The non-recursive arm keeps the DIRECT-ENTRIES semantics the pair corpus had
before this round, which is a checkable statement about two implementations and
not about all of history: it was `readdirSync` until fix round 1 and
`ls-tree` without `-r` after it, and neither recursed. Measured against a
context with a subdirectory under `delivery/review/`, so the two arms are shown
to differ rather than assumed to:

```
ls-tree --full-tree -z --name-only $S:./delivery/review  => a.yaml|nested|
ls-tree -z --name-only $S -- ./delivery/review/          => delivery/review/a.yaml|delivery/review/nested|
ls-tree -r -z --name-only $S -- ./delivery/review/       => delivery/review/a.yaml|delivery/review/nested/b.yaml|
```

### 4.2 The `cat-file -t` probe stops conflating "absent" with "could not look"

`git cat-file -t <sha>:./<dir>` fails identically for a path that is not in the
tree and for an object database that cannot produce the commit, and the old
helper returned an EMPTY CORPUS for both. Absence is now established by a
SECOND probe that does not mention the path: `git cat-file -t <sha>`. If the
commit object itself is readable, the only thing the first probe can have been
reporting is that the path is not in it.

This is the round's one addition that neither reviewer nor the verifier
measured as a live defect; the verifier recorded it as an open question and
named its shape. It is fixed here rather than tracked because it arrives at the
SAME fail-open outcome as DV-002 (an empty pair corpus makes a conditional gate
report not-applicable over a committed violation), and because
`readCommittedVerdicts`, twelve lines further down, already refuses when a BLOB
it was told about cannot be read. One half of a loader fail-closed and the
other fail-open is how the open half stays unnoticed.

### 4.3 `REGIME_DOCUMENTS` and the presence probe move into `src/checks.ts`

`scripts/check-dual-review.mjs` held its own copy of the two-document list AND
its own `classifyEntry` probe of whether they were there. It now holds neither.
`missingRegimeDocument` is exported from `src/checks.ts`, uses
`contextDocumentPresentAt`, which is the same probe `establishDelegatedRegime`
uses, and takes the SOURCE AS A PARAMETER so the caller that already resolved
one passes it rather than resolving a second.

After this round `scripts/check-dual-review.mjs` addresses nothing itself:
every context read it makes goes through `loadCommittedVerdicts`,
`readReviewFamilies` or `missingRegimeDocument`. That is checkable rather than
asserted, and D6 above is the check.

**The refusal moved AFTER the declaration reading, and that is a deliberate
choice with a cost stated.** A context with nothing committed satisfies both
error conditions, so the order decides only which reason a reader is given.
DR-0038's "an exception read from an uncommitted file is error, never
permission" is the more specific of the two and names what the operator
actually did, so it goes first. The alternative was to leave the regime refusal
first and change the assertion in
`test/single-family-exception.test.ts`, which would have traded a witnessed
property for a message.

### 4.4 The report line names the source it looked in

`describeContextDocumentSource` is new and renders `in commit <sha>, resolved
from <ref>` or `in the WORKING TREE, because this context has no resolvable git
ref: <reason>`. The regime's report arm and the merge gate's refusal both use
it. "no charter.yaml" said about a directory that contains a `charter.yaml` is
unfalsifiable by the person reading it; "no charter.yaml in commit <sha>" is a
claim they can check.

### 4.5 `stage()` can build a nested context

One option, `nest`, which runs `git init` in a PARENT of the context directory
rather than in the context directory. Fix round 1's derivation named the
`test/` exclusion and DV-002 is the consequence it predicted: no arm in the
phase's test file could tell a root context from a nested one. A second option,
`regimeDocumentsUncommitted`, holds a named regime document out of the commit
and puts it back afterwards, holding it OUTSIDE the repository while it is
held so that the hold itself commits nothing.
