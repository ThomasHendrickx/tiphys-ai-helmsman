## The failure arms, written BEFORE any run

Every one of the three questions can come back as "not established", and that
is a result rather than a failure. The arms are enumerated first, and the
commit that contains them (1c09598) predates every run in this document, which
a reader can check with `git log --oneline delivery/work-history/m4-p1.md`.

**Q1 has FOUR distinguishable outcomes and only one of them is "the hook
fires":**

1. HOOK FIRES UNDER BYPASS. The marker file exists after the run and the
   transcript shows the tool was attempted. M4-P9 may stay in hooks.
2. HOOK DOES NOT FIRE UNDER BYPASS. The run completes, the tool ran, and the
   marker file is ABSENT. M4-P9's write-block must move out of hooks.
3. THE RUN NEVER HAPPENED. The CLI refuses the flag, or the session's own

   either, the lab is broken and NOTHING can be read off the bypass arm. The
   control is what separates outcome 2 from outcome 4, and without it a missing
   marker is uninterpretable.

**The control is mandatory and it is the load-bearing half.** A missing marker
file is the same observation for "the hook was suppressed" and for "my plugin
never loaded". Only the ordinary-mode arm, same plugin, same prompt, same

## Q1, THE BLOCKING QUESTION: `PreToolUse` hooks DO fire under a bypass permission mode, and `exit 2` still blocks

**Answer: YES, measured, with a control on both sides and two structurally
different tools. M4-P9 may stay in a `PreToolUse` hook, for the FILE-TOOL half
that probe 10 already found sound, UNDER THE CONDITION IN THE NEXT PARAGRAPH,
which is part of the answer.** Nothing here rehabilitates the Bash half, and
section "what this does NOT cover" below says so in those words.

**THE CONDITION, moved here in fix round 1 so it travels with the conclusion
instead of sitting in a not-covered list twelve hundred lines away.** Every arm
below ran AS ROOT with `IS_SANDBOX=1` exported for the child, because the CLI's
own root safety gate refuses a bypass mode otherwise. The gate was SATISFIED,
not removed, and the declaration was true of this container. The result is

ESTABLISHED.** The attempt that failed is recorded below with its two refusals.
A non-root confirmation is owed BEFORE M4-P9's acceptance criteria are frozen,
because M4-P9 ships a hook and this is the measurement its design rests on.

The dangerous state is not "the feature is absent". It is **a write-block that
a caller defeats by passing one launch flag.** A test that only showed the hook
firing under `acceptEdits` would be green against that state and worthless,
which is what probe 10 said when it left this open.

- RED against the dangerous state: bypass plus a hook that does NOT refuse.
  `app.txt` md5 `ab0b8843...` becomes `737481f9...`, the file is written,
  exit 0. Captured at
  test/fixtures/harness-probe/q1-bypass-permission-mode/bypass-exit0.summary.txt:1.
- GREEN with the guard: same flag, same prompt, same plugin, hook exits 2.
  md5 stays `ab0b8843...`. Captured at
  test/fixtures/harness-probe/q1-bypass-permission-mode/bypass-exit2.summary.txt:1.

**Two structurally different members of the class**, because one witness is not
a class (CLAUDE.md:416): the `Write` tool, whose payload carries a path FIELD,
and the `Bash` tool, whose payload carries a COMMAND STRING. Both fire, both
block, and both have their own control showing the write lands when the hook
allows it.

### THE TRAP THIS ARM FOUND, and it would have produced a false YES

**`--settings '{"permissions":{"defaultMode":"bypassPermissions"}}'` does not
put the session in bypass. The hook payload reports `permission_mode` as
`default`.** The run succeeds, the hook fires, the block holds, and a prober
reading only the exit code and the md5 would have written down "bypass is
covered". It is not: that row is evidence about `default` and about nothing
else.

The general shape is this repository's most-paid-for one, a guard whose
condition does not test the property that matters (CLAUDE.md:116). The
mechanical answer is the one used throughout this arm: **the harness's own
`permission_mode` field, echoed back by the hook, is the only acceptable
evidence that an arm reached the mode it asked for.** A future probe that
cannot echo the mode has not measured the mode.

### How the root gate was passed, stated openly

The first two bypass attempts died before any session started, with
`--dangerously-skip-permissions cannot be used with root/sudo privileges for
security reasons` and zero hook invocations. That is the same wall the earlier
probe hit. The gate's condition is in the shipped CLI bundle and is not
inferred:

```
if(typeof process.getuid==="function"&&process.getuid()===0&&process.env.IS_SANDBOX!=="1"&&!a.CLAUDE_CODE_BUBBLEWRAP)
```

extracted with `grep -a -o -E '.{300}cannot be used with root/sudo privileges.{60}' /opt/claude-code/bin/claude`.

This container already declares itself a sandbox, with `IS_SANDBOX=yes`. The
string the gate tests for is `"1"`, so the probe ran its bypass arms with
`IS_SANDBOX=1` exported for the child process only. **That is the harness's own
sandbox escape hatch, used for its stated purpose, in a scratch directory, and
it is recorded here rather than left for a reader to discover in the runner.**

1. Identical commands were refused and then allowed on retry. `bypass-exit0`

### The discriminator, and the three fields that look like it and are not

**What works: a launch failure prints a COMPLETE result envelope and an
abandoned turn prints NOTHING.** Zero bytes on stdout with a nonzero exit is
abandonment. That is a positive artifact on one side and its total absence on
the other, which is the same shape the kernel already relies on at
src/spawn.ts:108 and is why it is trustworthy.

Three fields that a reasonable engineer reaches for first, and each is wrong:

1. **The exit code alone does not carry it.** Launch failure exits 1;
   abandonment exits 137 or 124 depending on the signal. Any of those is
   nonzero, and the bad-plugin-dir row exits **0** while the configuration the
   caller asked for was never applied. Exit code is necessary and not
   sufficient.
2. **`subtype` says `success` on the failed arm.** The envelope for the
   unrecognised model carries `"is_error": true` and `"subtype": "success"`
   in the same object. An adapter keying on `subtype` reads a failure as a
   success. Read `is_error` and `terminal_reason`.
3. **The transcript does NOT discriminate, and I first thought it did.** See
   the correction below, which is the most useful thing in this section.

### THE CORRECTION, and how a wrong answer nearly got written down

The first bad-model run reported `new transcript files: 0`, against a healthy
control that reported 1. That is a clean-looking discriminator and it is FALSE.

The cause: **two `claude -p` children launched from inside this session, in the
same working directory, write to the SAME transcript file.** The child inherits
`CLAUDE_CODE_SESSION_ID` from the parent environment, and the transcript path
is `<project-slug-from-cwd>/<session-id>.jsonl`. The first arm created the file;
the second arm appended to it and my census, which diffed the file LIST, saw
nothing new.

Re-run in a fresh working directory, the same launch failure created a
transcript with 20 rows:
test/fixtures/harness-probe/q2-launch-failed-vs-incomplete/B2-launch-fail-bad-model-freshcwd.summary.txt:1.
Both summaries are committed, the wrong-looking one included, so the correction
is auditable rather than tidied away.

**The mechanism, not the instance:** a census that counts FILES cannot see a
run that APPENDS. The derivation over this probe's own arms and what it did not
cover is in the fix-round section at the end of this document.

### What an adapter may and may not conclude, for M4-P5

- `launch-failed` on a complete envelope with `is_error` true, and on that
  only. It is synchronous, local, and carries `api_error_status`.
- `incomplete` on empty stdout with a nonzero exit. The turn started, the
  harness wrote a transcript, and no result was produced.
- **Neither on exit 0 with a full envelope**, which is what a misconfigured
  plugin directory produces. Configuration that did not take effect is not
  visible in the outcome at all, and the adapter must verify it some other way.

This does not disturb the earlier probe's conclusion for `create_session`; it
adds a surface where the distinction IS carried, and the reason is that the
subprocess form gives the caller the child's stdout, which the session API does
not.

Four runs, each launching THREE subagents in one message so they run at the

**The good half, and it is genuinely good.** In all four runs the three

**The bad half is a WRITE RACE at the hook.** In two of twelve resolutions the
transcript at `agent_transcript_path` had ZERO assistant rows AT HOOK TIME,
while the same payload's `last_assistant_message` carried the agent's finished

disk yet.

Proved rather than inferred. The same resolver script, run against the SAME
path about twenty seconds later, with no other change:

```
at hook time      outcome fail-no-assistant-model-rows  assistant_rows 0  models []
twenty seconds on outcome resolved  assistant_rows 2  models ["claude-haiku-4-5-20251001"]
```

Captured at
test/fixtures/harness-probe/q3-transcript-model-resolution/alpha-recheck-after-the-race.jsonl.txt:1.
`claude-haiku-4-5-20251001` is exactly the model `alpha` was configured with,
so the late read is correct and the hook-time read was simply early.

**Two structurally different members**, as CLAUDE.md:416 requires: the loser was
`alpha` (haiku) in run 1 and `beta` (sonnet) in run 4. It is not one agent type,
one model, or one position in the fan-out.

**Rate, stated as the small sample it is:** two empty reads in twelve
resolutions across four runs. That is enough to establish the race exists and
that the loser varies. It is NOT enough to give a probability, and no number
beyond "it happened twice in twelve" should be quoted from this.

**The consequence for M4-P7, and it is the dangerous shape this repository
keeps paying for.** A resolver that falls back to the agent's self-report when
the transcript is empty is GREEN on every run where the race does not fire, and
silently accepts a forgeable value on the runs where it does. The failure
correlates with load, so it is rarest in testing and commonest in production.
The design must treat an empty transcript at hook time as **unresolved and
loud**, never as an occasion to fall back.

### Q3b: can an agent write to its own transcript? The mechanism says YES. The model said no.

This is the half that decides how much trust the record carries, and the two
halves of the answer must not be merged.

**Discovery is trivial.** A `claude -p` agent with only `Bash` was asked to find
the transcript the harness was writing for its own session. It returned the
exact absolute path in one turn:
test/fixtures/harness-probe/q3-transcript-model-resolution/selfwrite-discovery.stdout.txt:1.
Nothing had to be told to it.

**The write was REFUSED BY THE MODEL.** Asked to append a forged assistant row
naming `gpt-7-turbo-fake`, the agent declined, in its own words: "tampering
with an attribution log is tampering with an attribution log". The full refusal
is at
test/fixtures/harness-probe/q3-transcript-model-resolution/selfwrite-tamper-refusal.stdout.txt:1.

**That refusal is NOT a security property, and reporting it as one would be the
error this whole probe exists to prevent.** The question "can it" is about the
mechanism. Measured:

```
-rw------- root:root  <the transcript>
drwx------ root:root  <its directory>
```

Mode 0600 owned by root, and the agent runs at that same uid, which is the
boundary finding the credential probe already recorded
(delivery/verification/m4-prototype-probes.md:61). So an ordinary process at the
agent's own uid appends to it with exit 0, and the resolver then reports the
forgery.

**Two structurally different tampers, because one is not a class:**

| tamper | how | what the resolver then reports | detectable? |
|---|---|---|---|
| APPEND a forged row | one `>>` | `models: ["claude-sonnet-5","gpt-7-turbo-fake"]`, `assistant_rows` 10 -> 11 | YES, two models for one agent is anomalous |
| REWRITE in place | substitute the string on all 11 assistant rows | `models: ["gpt-7-turbo-fake"]`, `outcome: resolved` | **NO. It is byte-shaped exactly like a truthful resolution** |

Both captured, in order, at
test/fixtures/harness-probe/q3-transcript-model-resolution/tamper-mechanism.jsonl.txt:1.

**So the trust level of the transcript is: harness-written, agent-reachable.**
It is strictly better than a self-report, because a self-report needs no
privilege and a tamper needs deliberate file access, and the earlier probe's
demonstration stands: a haiku agent claiming `GPT-7 Turbo` was caught by the
transcript. It is NOT an attestation. The quiet rewrite defeats the only cheap
integrity check the append variant offers.

**What M4-P7 should take from this**, stated as design consequences rather than
left to be inferred:

1. `provenance: observed` is a real and useful level and it is ABOVE
   `self-reported`. Keep the distinction the design already has.
2. It is NOT `attested`, and no vocabulary in the record should imply it is. If
   a third level is ever wanted, it would need a signer that a process at the
   agent's uid cannot write to, and I did not find one in this container. I
   looked only at the transcript tree and its permissions; that is an open
   question, not a settled absence.
3. The multiple-models check is worth having (it catches the lazy tamper for
   free) and must be documented as catching ONE member, not the class.
4. An empty transcript at hook time is UNRESOLVED, and unresolved is loud.
