## Design, and the decisions behind it

### The split that keeps this honest: the files are cheap

The phase brief asks for this to be SAID rather than smoothed over, and it is
true. Restoring the retirement roots is one `git checkout <sha> -- <root>`
inside a guard. The interesting part is the guard, not the restore.

The AUTHORITY half is the expensive one.
delivery/decisions/DR-0036-the-harness-adapter-leads-m4-and-the-kernel-is-the-second-subject.md:15
prices the revert at "whatever phases ran under it", and the branch-protection
ruleset is owner-configured. Nothing in this phase flips authority. The code
PREPARES the request an owner acts on, and refuses rather than pretending the
preparation is the act.

### Five switches, and four of them are a file write

The five are DR-0025's retained items at
delivery/decisions/DR-0025-controlled-pre-m4-local-pilot.md:45. The table in
the document gives, per switch, how it is flipped back and how the flip is
verified. Four of the five are the same atomic file write.
`credentials-and-refs` is not, and that asymmetry is the whole reason the
switches are separate rather than one event.

### The atomic rewrite, and the mechanism it exists against

The mechanism is **writing state per item while iterating**. It does not need a
crash to hurt: any early return leaves a file that is internally valid and
factually wrong, three switches saying `kernel` and two saying `current`, which
describes a process with no owner for three of its five authorities.

`planRollback` assembles the complete next state in memory and
`publishCutoverState` writes it to a sibling temporary file, fsyncs, and
renames. The temporary name uses `randomBytes`, not the pid: C-2 forbids a pid
as an identity, and a temp-file name is an identity for as long as the rename
takes.

### Drain, and the omission is the decision

Drain counts live worktrees and open tasks with no turn-end. It does NOT count
pushed unmerged branches. That is M4-D-15, decided at
delivery/plan/kernel-plan-m4.md:3279, and the probes strengthened the reason:
delivery/verification/m4-prototype-probes.md:165 generalises the trap from
"a delete dry-run lies" to "`git push --dry-run` does not probe push
authorization at all, for any ref namespace, in either direction". A predicate
over branches therefore waits on an owner action with no local pre-check.

C-2 is load-bearing. A live worktree is a DIRECTORY. An open task is
meta.json's status plus the ABSENCE of the turn-end file. Nothing here probes a
process.

One implementation note worth a reviewer's eye: `classifyEntry` in `src/task.ts`
answers "may this be opened" and therefore classes a directory as `irregular`.
A worktree IS a directory, so `inFlightItems` uses a local `isDirectory` helper
that stats and never opens. stat(2) does not block on a FIFO the way open(2)
does, so the protection src/task.ts:118 exists to provide is not weakened.
Settled by enumerating every filesystem-reading call in the module rather than
by reading the one function:

```
$ grep -n "statSync\|readFileSync\|openSync" src/cutover.ts
45:  openSync,
49:  statSync,
229:    handle = openSync(temporary, "wx");
465:    return statSync(path).isDirectory();
```

Line 229 is the temporary file this module CREATES with `wx`, which is a path
it owns and whose type it establishes by creating it. Line 465 is the directory
test. Every other read goes through `readRegularFileIfPresent`, which is
imported rather than reimplemented, so the probe-before-open rule is a property
of the read and not of the caller.

### Two subjects, and the pilot half is somebody else's to execute

DR-0036 makes the kernel a second subject, so a failed cutover leaves a kernel
mid-adoption AND a pilot mid-flight.
delivery/decisions/DR-0037-the-kernel-is-m4s-only-subject-and-tiphys-has-no-opinion-on-project-visibility.md:19
keeps this orchestrator away from the pilot;
delivery/decisions/DR-0042-reading-the-pilot-is-allowed-and-the-pilot-can-be-rebooted.md:13
then allows READING it and records that the owner can reboot it. So each
trigger carries a `.P` step: what someone else executes, and what this side
verifies read-only.

The pilot's drain is a permanent member of the CANNOT-SEE list, which is
printed in full on every report. An absent line reads as a clean one.

### The unrehearsable steps are named, and the rehearsal refuses loudly

`--trigger freeze-point-restore` exits **3**, not 0 and not 1, and prints one
`REFUSED` line naming the property. A distinct exit code is what stops "we did
not rehearse this" being read as "we rehearsed this and it passed".

The precedent is exact and in this repository: four dry runs exited 0 and the
first real publish of 0.1.0 was refused by the registry
(delivery/tuition/T-025-the-one-path-that-cannot-be-rehearsed-is-the-one-that-failed.md:40).
The same record names the transferable practice, which is what is applied here:
write the asymmetry down BEFORE the action
(delivery/tuition/T-025-the-one-path-that-cannot-be-rehearsed-is-the-one-that-failed.md:57).

What IS rehearsed is the step's INPUT. `--trigger freeze-point-restore-input`
asserts the generated owner request is complete. It asserts the REQUEST and
never the OUTCOME, and the generated request says so in its own text.
