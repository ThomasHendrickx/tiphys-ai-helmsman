### 1. A shell write in a project clone is NOT blocked. This is measured.

Step 1 fired a `PreToolUse` hook against `Write`, `Edit` and `Bash` under
claude 2.1.273 and kept the RAW stdin bytes
(witness/captures/m4-p9-pretooluse-payloads.txt:1). The result:

| tool | what the payload carries | a resolvable write target? |
|---|---|---|
| `Write` | `tool_input.file_path`, absolute | YES |
| `Edit` | `tool_input.file_path`, absolute | YES |
| `Bash` | `tool_input.command`, a raw shell string | NO |
| `Bash`, heredoc form | `tool_input.command`, a raw shell string | NO |

Every arm also carries a top-level `cwd`. Nothing in a `Bash` payload names a
file. The plan wrote criterion 6 to be decided by exactly this measurement
(delivery/plan/kernel-plan-m4.md:1610), and the measurement says the `Bash`
arm is not covered. So:

- the hook's matcher is `Write|Edit|MultiEdit|NotebookEdit`
  (plugin/src/hooks/project-write-block.ts:75), and `Bash` is not in it;
- criterion 6 is discharged for the file-writing tools and for those only;
- an orchestrator that runs a shell redirection into `src/app.ts` inside a
  project clone is not stopped by this phase.

**THAT LAST LINE IS A MEASUREMENT, NOT A DEDUCTION, and it is in the capture so
that nobody has to take my word for it.** A fourth agent turn was run in the
same clone, the same fleet home and with the SAME INSTALLED HOOK as the two
blocked arms, differing only in the tool

The two designs that would have "covered" `Bash` were both rejected, and the

this phase exists to avoid. Parsing the shell string for redirections is
guessing, and the plan forbids guessing the payload shape.

### 2. The hook cannot tell WHO is writing.

It refuses a working-tree write in a project clone, whoever makes it. In a
fleet the orchestrator is the session standing in the fleet home, and a
dispatched implementer works in `<fleet>/worktrees/<taskId>`, which is not
under `<fleet>/projects/` and is therefore permitted. That is the whole of the
role separation this hook achieves, and it is structural rather than an
identity check. An implementer told to work directly inside a project clone
would be refused as well. Nothing in this phase distinguishes them.

### 3. Where the project roots come from is `<fleet>/projects/`, and nothing
else is a project.

`readProjectRoots` lists the direct children of `<fleet>/projects/`
(plugin/src/hooks/project-write-block.ts:420). A project clone kept somewhere
else is not a project root as far as this hook is concerned, and a write into
it is permitted as "outside every project working tree". The fleet layout is
what defines the term (src/fleet.ts:12) and this phase did not invent a second
definition, but the consequence is real and is stated rather than implied.

### The decision, and why it is shaped this way

`decideWrite(request, projectRoots, bypass, now)` at
plugin/src/hooks/project-write-block.ts:261 is PURE: no filesystem, no clock,
no environment, no log. Every criterion except the end-to-end one is stated
over it, which is what makes them falsifiable without firing a hook. `now` is
a parameter so the expiry boundary is testable at the boundary; the log is not
a parameter at all, which is the next section.

The order is: resolution failures first, then containment, then the `.git`
carve-out, then the bypass, then refuse.

**M4-D-27, the line keyed to the EFFECT.** A write resolving inside a project
working tree and outside that clone's `.git/` is refused; a write under `.git/`
is the ref update and is permitted. The `.git` test is SEGMENT-WISE and takes
the FIRST segment only (plugin/src/hooks/project-write-block.ts:162). A
substring test hands `.gitignore`, `.gitattributes` and
`src/.github/workflows/gates.yml` the release manager's carve-out, and
test/project-write-block.test.ts:382 refuses all six spellings I could think
of while permitting three real `.git` paths.

**M4-D-26, the two-file bypass.** The declaration is
`<fleet>/write-bypass.json`: current state, rewritten in place, and the only
document any decision reads. The evidence is
`<fleet>/write-bypass-evidence.jsonl`: append-only, written after a permit,
and read by nothing. C-1 forbids reading current state from the tail of an
append-only log, and the split is what makes the prohibition checkable instead
of promised.

One design point that is not in the plan and is declared here. A bypass write
whose evidence could not be appended is REFUSED
(plugin/src/hooks/project-write-block.ts:612 onward, the `appendBypassEvidence`
failure arm). A permitted-but-unrecorded bypass write is exactly the
untraceable act the split exists to prevent, so failing closed there was the
only answer I would defend. It is called out because it is a refusal the plan
does not name.

**Criterion 7, and the type that carries it.** `ProjectRoots` is
`{kind: "observed", roots}` or `{kind: "unresolved", reason}`. An empty
observed set is a fleet with no project clones, and a write outside every
project is not a project write; `unresolved` is "the fleet home could not be
read" and refuses. An implementation that passed an empty array for the second
would fail open and would not type-check. The fleet home itself is found by
walking UP from the payload's `cwd` and TESTING for the layout
(plugin/src/hooks/project-write-block.ts:385), because the kernel builds every
child's environment from an allowlist (src/exec/env.ts:69) and there is no
`TIPHYS_FLEET_HOME` to read.

**The consequence of that, stated because it is a real blast radius.** A
session whose `cwd` is under no fleet home has every `Write` and `Edit`
refused, with exit 2 and the reason `no fleet home was found at or above
<cwd>`. That is the fail-closed posture criterion 7 asks for, and it means
this plugin is for fleet work. A reviewer who thinks the trade should go the
other way is looking at the right line.

### The two dangerous states that are not mutations

Two criteria demand a dangerous state the mutation harness cannot express, and
both were built for real.

**Criterion 2, the hook ABSENT.** test/project-write-block.test.ts:214 plays
the same tool call twice by the rule M4-P1 measured: hook exit 2 leaves the file
unchanged (delivery/work-history/m4-p1.md:134) and hook exit 0 leaves it CHANGED
(delivery/work-history/m4-p1.md:135), the two BYPASS rows of that phase's
matrix. Those two line numbers are a CORRECTION of an inherited citation and it
is flagged rather than fixed silently: four merged files cite
`delivery/work-history/m4-p1.md:236` for this rule, and line 236 of that

bytes and the mtime change; with the hook the wrapper exits 2 and neither
moves. The mtime assertion spins until the millisecond clock advances rather

writes landed in one tick.

**Criterion 6, a real agent turn.** Three `claude -p` runs in a real git clone
inside a real fleet home, with the SHIPPED module installed as the plugin's
`PreToolUse` command: witness/captures/m4-p9-end-to-end-agent-turn.txt:1. The
two blocked arms leave `git status --porcelain` empty and every tracked file's
bytes identical. The third arm is the CONTROL, the same prompt and the same
tool with no plugin at all, and it changes the file. A blocked arm on its own
is a test of a path where nothing was going to happen.

That capture carries a correction I made and declared rather than quietly
fixed. The first pair of runs derived "tracked file shas" from
`git ls-files -s`, which reports the INDEX sha and does not move for an
unstaged edit, so the control arm read `unchanged: YES` while `git status`
reported ` M src/app.ts`. The check was reading a number that could not
distinguish the two arms. All three arms were re-run hashing the bytes on disk.

**Criterion 3, a real merge.** test/project-write-block.test.ts:272 creates a
repository, clones it into `<fleet>/projects/`, advances the upstream, runs a
real `git merge --ff-only`, and asserts the ref MOVED by comparing

against a list of strings that look like refs.

**Criterion 5, C-1 made falsifiable.** test/project-write-block.test.ts:525

## Hazard self-review

The class, in one sentence: **this component CERTIFIES that a project clone was
not written to, so the question is whether it can pass while the thing it
guards is broken.** What I attacked, including the attacks that found nothing:

| attack | result |
|---|---|
| a substring `.git` test hands `.gitignore` the carve-out | FOUND in design; the test refuses six spellings and the segment test is first-segment-only |
| a symlink outside a project pointing into one evades containment | FOUND in design; `canonicalisePath` resolves the longest EXISTING ancestor and re-appends the rest, because a `Write` names a file that does not exist yet |
| the hook permits when the fleet home is missing | refused, and it is the reason criterion 7 has an end-to-end arm |
| the hook permits when `projects/` cannot be listed | refused, and the arm was FORCED rather than reasoned about: probe C at witness/captures/m4-p9-settling-probes.txt:1 chmods `projects/` to 000 and runs the wrapper at an unprivileged uid, giving exit 2 and `projects could not be listed: Error: EACCES`. The root control exits 0, because root ignores the mode bits and the listing succeeds, which is why the arm needs a second uid to reach at all |
| a malformed bypass declaration reads as "no bypass" | refused instead: `invalid` is not `absent`, and the wrapper exits 2 naming the document |
| a bypass permits a write whose evidence could not be recorded | refused, declared above as a design point the plan does not name |
| a bypass path list of `/` covers the whole fleet | refused: a listed path must lie inside the declared project, asserted at test/project-write-block.test.ts:472 |
| an expiry that is not a readable instant reads as far future | refused: `instantOf` returns undefined and the refusal says so |
| the manifest matcher and the module's tool list drift apart | caught by test/project-write-block.test.ts:812, which compares them by name |
| a nested submodule's `.git` gets the carve-out | not reachable: the test is on the FIRST segment relative to the project root, so a deeper `.git` is refused. I did not find a case where that is the wrong answer, and I looked at the worktree case specifically |

| two project roots nest, and the outer one's `.git` rule applies to the inner | `containingProjectRoot` takes the LONGEST match, so the nearer root wins |
| a `Write` to a path that is a directory | not attacked. The hook decides on the path, and what the tool then does with a directory is the tool's. No defect found and none looked for |
