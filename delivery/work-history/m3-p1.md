### 1.4 HALT CHECK (a): does M2's validator as delivered emit
`INVALID <json-pointer> <message>` with deterministic ordering?

**TRUE.** Two sites, both read from the delivered source.

`src/gates/validate.ts` line 90 (the string is the module's public contract):

```
$ grep -n 'return `INVALID' src/gates/validate.ts
90:  return `INVALID ${diagnostic.pointer} ${diagnostic.message}`;
```

The ordering is a FINAL SORT applied to the collected list, so it is a
property of the contract and not of the traversal. `src/gates/validate.ts`,
`validate()`:

```
  collected.sort((a, b) => {
    if (a.pointer !== b.pointer) {
      return a.pointer < b.pointer ? -1 : 1;
    }
    if (a.message === b.message) {
      return 0;
    }
    return a.message < b.message ? -1 : 1;
  });
```

The module header states the same rule in terms and states WHY it is a final
sort: "The final sort is what makes the order a property of the CONTRACT
rather than of the traversal, so an engine that walks differently still emits
the same lines in the same order." That sentence is the one that makes DR-0013
clause 6 mechanically keepable, and it is in the delivered artifact.

The message texts these tests assert are not "Ajv's wording versus M2's
wording": they are the entries of `DIAGNOSTIC_MESSAGES`, which the module's
own header declares to be the contract, with the stated purpose of giving "a
future engine one table to map onto instead of a search through call sites".
Asserting on them is asserting on the contract. Halt check (b) is therefore
satisfied and the phase PROCEEDS.

**The residue, stated because it is the thing that could still turn the
retirement into a rewrite.** Five of the nine assertion groups above are about
`loadSchema`, which is M2's CLOSED KEYWORD SET policy (M2-D-04), not about
validation semantics. `oneOf` is legitimate Draft 2020-12 and Ajv compiles it;
Draft 2020-12 APPLIES keywords beside a `$ref` and Ajv does too. So if the
retirement replaced `loadSchema` with an Ajv compile, those tests would fail
and the only way to make them pass would be to EDIT them, which the phase's
third standing prohibition forbids outright.

DR-0013 clause 7 is what makes this resolvable without an edit, and it says so
in terms: "If the project later wants to prohibit otherwise-valid but
unapproved JSON Schema keywords, that is a small schema-aware POLICY LINTER,
never a reimplementation of keyword semantics." M2's `loadSchema` already IS
that policy linter. The retirement therefore retires the ENGINE (`validate`),
which is what DR-0013 clause 6 names, and keeps `loadSchema` as the policy
linter over M2's gate schemas. That is the design this phase implements, and
the criterion that proves it is DR-0013 criterion 10: M2's tests re-run
UNCHANGED and pass. Whether they do is executed later in this document, not
asserted here.
