## 17:33 PROBE: can criterion 5(b) be written as `if`/`then` on `minItems`?

Criterion 5(b) (delivery/plan/kernel-plan-m3.md:3146) asks for a finding set
with `findings: []` and no `no-findings-statement` to be REJECTED, and its
parenthetical says the mechanism is "`if`/`then` on `minItems`". I could not
write that, and here is the measurement rather than the assertion.

The obligation is "empty array IMPLIES a sibling property is required". `if`
must therefore match on EMPTINESS. The closed authoring vocabulary
(schemas/README.md:36, src/validate.ts:111) is `$ref additionalProperties const
contains enum if items minItems minLength oneOf pattern properties required
then type uniqueItems`. There is no `not` and no `maxItems`. `minItems: 1` and
`contains` both match the NON-empty case, which is the wrong polarity, and
`then` cannot remove an obligation. So the `if`/`then` form has no way to
express the condition.

`oneOf` is in the vocabulary and does express it. Probe, run from the
repository root on node v22.22.2 against ajv 8.20.0 with the DR-0013 clause 4
options copied from src/validate.ts:526:

```
$ node ./probe-raw.mjs
## oneOf both COMPILE ERROR: strict mode: required property "no-findings-statement" is not defined at "https://tiphys.dev/schemas/probe-oneOf-both.json#/oneOf/1" (strictRequired)
## oneOf, branch2 declares property COMPILED
   empty, no statement -> invalid
   empty, statement -> VALID
   one finding, no statement -> VALID
   one finding, statement -> invalid
```

Three things that output settles, none of them assumed:

1. A `oneOf` branch carrying `required` MUST also declare that property in a
   sibling `properties` at the SAME level, or the schema does not compile at
   all under `strict: true`. That is `strictRequired`, and the first variant is
   the captured proof.
2. With the property declared, the construct rejects exactly the dangerous
   instance criterion 5(b) names.
3. It ALSO rejects `one finding, statement`, a set that carries findings AND a
   no-findings statement. That is a second rejection the criterion did not ask
   for, and it is the same both-directions property M3-P4's report schema
   reaches with a derived check. I am recording it as a consequence rather than
   claiming it was intended.

An earlier form of the same probe, through this repository's own
`validateToLines`, first reported `INVALID # schema uses keyword minItems
without declaring type array, which this validator's strict policy requires`,
which is a fourth measured fact: inside a `oneOf` branch the `type` must be
restated. Both probe scripts are kept at
delivery/work-history/m3-p5.md (this file) and their output is above verbatim.

Three design decisions, each with the reason, because each is a place a
reviewer will ask why:

1. **The clause round trip runs inside `tiphys validate --type role-brief` and
   reads the INCLUDE-EXPANDED body.** Criterion 1 says the body is not parsed
   and criterion 6b says deleting a clause heading makes THIS COMMAND exit
   nonzero naming the orphaned id. Both are satisfied by splitting the two:
   the SCHEMA sees the frontmatter alone (criterion 1's parenthetical), and a
   separate round trip reads the body. It must expand the include, because the
   two dispatch-contract clauses live in exactly one file that all five briefs
   include, so a round trip that did not expand would report every brief as
   orphaning both ids.
2. **The anchor form is explicit: `## clause <id>: <title>`.** An anchor rule
   that guessed (a heading whose text looks like an identifier) would classify
   `## Scope` as an anchor and redden any brief with an ordinary heading.
3. **`mandated-reading` resolves against the KERNEL ROOT, not the cwd**, which
   constrains a brief to mandate only what `package.json`'s `files` ships. That
   is why the three briefs mandate `roles/_shared-dispatch-contract.md`,
   `schemas/*.json`, `templates/plan.example.yaml` and `gate-registry.yaml`,
   and why none of them mandates anything under `delivery/`, which is not
   shipped. M3-P6's criterion 8 mandates `tuition/mechanism-index.yaml`, also a

### Step 1: THE MECHANISM behind D-1, named before anything is edited

The FINDING is "the comment on test/roles.test.ts:154 claims a forward property
the test does not have". Deleting the comment would close the finding and leave

THE MECHANISM: **a test asserts over a set whose membership lives OUTSIDE the
test file and GROWS as later phases ship, using a copy of that membership
written inside the test.** The copy is correct on the day it is written and
silently incomplete from the next phase onward. CLAUDE.md's append-only-registry
rule is this mechanism one level down: it says assert BY NAME and never BY
COUNT, and a hand-written membership list is a count wearing names.

That definition is what makes the enumeration mechanical, because the property
"lives outside and grows" is testable against the tree instead of judged.

### Step 4: D-3, decided rather than noted, and the decision is to normalise

The finding: mandated-reading entries were compared as raw strings by
`outputContractDiagnostics` and resolved with `join` by
`resolveMandatedReading`, so `./schemas/report.schema.json` COMPOSED cleanly
and was REFUSED by `tiphys validate --type role-brief`. The verifier called it
LOW and fail-safe, and explicitly left the decision open.

DECISION: normalise, through ONE exported function both call
(`canonicalReadingEntry`, src/roles.ts:292). The reason is the round's own
argument, turned on the round's own work: REASON 1 for rejecting the injection
alternative was that it would leave `validate` and `brief compose` holding two
opinions about one property, and "this repository has paid repeatedly for
exactly that shape". An argument that is good enough to reject an alternative
is good enough to apply to what was built instead. Leaving it would also leave
a M3-P6 author a refusal they fix by deleting two characters, and the message
they get says nothing about path form (it is quoted in the claim-grep
settlement below, so a reader can judge that for themselves).

WHY A SHARED FUNCTION RATHER THAN A SECOND NORMALISATION AT THE COMPARISON
SITE: a second `normalize` call at the check site would make the two commands
agree TODAY by coincidence of two implementations, which is the same shape one
level down. There is now one definition of what an entry means, and both sites
ask it.

MEASURED, BOTH DIRECTIONS. Four spellings of one document, each written into
`roles/investigator.md` in a lab copy, each put through both commands:
