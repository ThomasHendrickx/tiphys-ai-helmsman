## Step 0: how the gate learns the event, and how it separates own from stored (read before any change)

### The event

It does NOT learn it today. The runner's gate subprocess contract
(src/gates/run.ts:67-75) is `<command...> --result <path> --evidence <dir>`
plus one `--<name> <value>` per parameter the gate DECLARES, and the declared
set is `RunParameter = "base" | "head" | "phase"` (src/gates/manifest.ts:53).
The argv is built at src/gates/run.ts:1588-1591 from `requiredParameters`
(src/gates/run.ts:729-739). `--event` (src/gates/run.ts:169-172,
`RunOptions.event`) is used ONLY to select registry entries
(`selectsEvent`, src/gates/run.ts:380-382) and is never handed to a gate. The
registry entry (gate-registry.yaml:85-100) declares `parameters: [base, head]`
and `events: [pull_request]`, so the gate never ran on push at all.

The two channels considered, and why one is excluded:

- An environment variable set by the runner. EXCLUDED by an existing binding
  test: test/gate-registry.test.ts:1625, "no environment variable changes a
  production gate's reported status (grep over the gate sources)", with an
  empty allowlist since M6-P3. A gate reading `process.env.X` in src/gates/
  is red there, and the event does steer what the gate evaluates.
- A declared run parameter `event`, handed as `--event <value>` exactly like
  `--base`. This is the contract's own mechanism. Chosen.

DEVIATION FROM THE FILES-TO-TOUCH LIST, flagged for the orchestrator: the
registry is validated against `schemas/gate-registry.schema.json`
(src/gates/run.ts:456-466), whose `parameters` enum is
`["base", "head", "phase"]` (schemas/gate-registry.schema.json:204). The M6-P8
section lists `src/`, `test/`, `witness/`, `delivery/`, the workflow and the
registry, not `schemas/`. Declaring `event` needs one word added to that enum.
The alternative channel is the forbidden one above, so the choice is between
this one-word schema change and not doing step 3.

### Own and stored

src/gates/red-witness.ts:300-301 (at base): `own` is every spec whose FILE
(`witness/<id>.json`) is in the phase diff; `stored` is every other spec. The
phase diff is `computePhaseDiff` (src/witness/run.ts:311), which is
`git diff -z --name-status --no-renames base...head`, a merge-base diff, so a
rename is a D of the old path plus an A of the new path.

At base the gate ALREADY narrowed stored specs:
src/gates/red-witness.ts:355-361, `triggeredStored` is a stored spec any of
whose members' `memberTouchedFiles` (src/witness/spec.ts:541: a mutation's
`file`, a patch's `diff --git` / `+++` / `---` paths, nothing for a
baseline-ref) is in the diff. So on PR #229 the 164 stored evaluations were
all triggered by that diff (M6-P3 merged 334 files), not an unconditional
sweep. What was missing, against DR-0066:

1. A test file the spec runs (`resolveNamedTests`, src/witness/run.ts:750,
   head-state `test/**/*.test.ts` sources containing the test name) did NOT
   trigger re-evaluation. A diff that edits only a witness's test was skipped.
2. There was no push arm: the entry declared `events: [pull_request]`.
3. The skipped stored specs were not counted; the detail line named only the
   evaluated ones.

A failed diff already reached `error` before any selection
(src/gates/red-witness.ts:199-202), never a skip.
