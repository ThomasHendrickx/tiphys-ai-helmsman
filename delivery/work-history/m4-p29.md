# M4-P29: three gate CLIs stop truncating their own reports

Branch `claude/m4-p29-gate-cli-exit`, cut from `origin/main` at
45c312ef70a58c464bd7de5b218038e6fc68a332. Plan section at
delivery/plan/kernel-plan-m4.md:3789.

## 1. What the phase was, in one paragraph

Three shipped gate modules ended their CLI with `process.exit(main(...))`. A
gate runs as a subprocess, so its stdout and stderr are buffered streams the
parent owns, and a write to one of those is QUEUED rather than completed.
`process.exit` ends the process without draining that queue, so everything past
the buffer is discarded while the exit code survives. So in every arm this
phase measured the verdict was right and the EVIDENCE was silently short; the
walk of those arms is section 9.3, and it is a measurement of four statuses
across three gates rather than a claim about arms nobody ran. All three entry
points now assign `process.exitCode`, which lets the process end normally, and
the queue drains first.

Two further items came with the dispatch and are not in the plan: the
`credential-scrub` gate's verdict inversion that M4-P8 measured, and M4-P8's
missing witness specs. Section 6 reports on both, including the half of each
that this phase did NOT do and why.

## 3. The measurement that corrected the plan's framing, and it matters

The plan section says the registry invokes these gates as subprocesses "so
their stdout is a PIPE". That is the right mechanism and the wrong word, and
the difference is a factor of two in the threshold.

`spawnSync` is how the registry runner invokes a gate (src/gates/run.ts:1528),
and `spawnSync` does NOT hand a child pipes. It hands it SOCKETPAIRS. Measured
by asking a child what fd 1 is:

```
$ node -e 'const {spawnSync}=require("node:child_process");
  const r=spawnSync(process.execPath,["probe-fdtype.mjs"],{encoding:"utf8"});
  console.log(r.stderr.trim());'
{"kinds":["fd1=.../socket:[26987185]","fd2=.../socket:[26987187]"],...}

$ node probe-fdtype.mjs 2>&1 >/dev/null | cat
{"kinds":["fd1=.../pipe:[26989757]",...],...}
```

A socket send buffer here is 212992 bytes (`/proc/sys/net/core/wmem_default`)
against a pipe's 65536, so the runner's own path loses nothing until the report
passes roughly 146 KiB, while a shell pipeline, a `tee` or a CI log collector
loses everything past 64 KiB.

This is why the FIRST version of this phase's tests would have been worthless.
A 131,143-byte report measured through `spawnSync` at the PRE-FIX commit
arrived complete, five runs out of five, because it fit in the socket buffer.
Read without the fd probe that is indistinguishable from "the defect does not
exist on this path". The full table, every row a real run at the pre-fix parent
commit and again after the change, same invocation, only the reader changed:

| gate | stream | reader | wrote | pre-fix | post-fix |
|---|---|---|---|---|---|
| red-witness | stdout | regular file | 176510 | 176530 | 176530 |
| red-witness | stdout | shell pipe (`\| cat`) | 176510 | 65536 | 176530 |
| red-witness | stdout | `spawnSync` | 434510 | 146176 | 434530 |
| suite | stdout | `spawnSync` | 451014 | 182750 | 451014 |
| credentials | stderr | regular file | 130143 | 130143 | 130143 |
| credentials | stderr | shell pipe (`\| cat`) | 130143 | 65536 | 130143 |

The "wrote" column is the length the gate recorded in its OWN result file, or,
for the credentials usage refusal which writes no result file, the length
delivered to a regular file. **A regular file did not truncate in either arm
measured**, which is the two `regular file` rows above and is exactly why this
defect survived casual testing. That is two instances and not a proof about
every filesystem; the settling command for the first of them is:

```
$ node src/gates/red-witness.ts --result R --evidence E --base B --head H > f
$ wc -c < f
176530
$ node -e 'console.log(require("R").detail.length)'
176510
```

The exit code was correct in every row of the table before and after, which is
why the loss was silent.

The whole table plus the reproducing commands is committed as a capture at
`witness/captures/m4-p29-gate-cli-stdio.txt`, and the three entry-point
comments carry the rows that belong to them.

## 4. What changed, and the reasoning that is invisible in the diff

### 4.1 The three entry points

Each of `src/gates/credentials.ts`, `src/gates/red-witness.ts` and
`src/gates/suite.ts` now assigns `process.exitCode` in place of calling
`process.exit` with a computed status. The assignment is the last statement of
the module in all three, so nothing runs after it.

**The second layer that `src/gates/scope.ts` and `src/gates/gate-classes.ts`
carry was deliberately NOT added.** Those two wrap the call in a try/catch that
turns an uncaught throw into `EXIT_GATE_ERROR` instead of exit 1. That is a
real improvement and it is a DIFFERENT change: it alters the uncaught-throw arm,
and criterion 3 requires the exit code to be unchanged in every arm. The
minimal shape here matches `src/gates/citations.ts`, which is already a bare
`process.exitCode = main(...)`. Extending the crash discipline to these three
is worth doing and is not this phase's to do.

**The comment in each module names the measured numbers for its own gate.** The
first draft of the credentials comment carried 131,187 bytes, a number nothing
had produced; re-measuring gave 130,143 and the comment was corrected before
the first commit. A plausible number in a comment is indistinguishable from a
measured one after the fact.

### 4.2 The egress tripwire in `credential-scrub`

See section 6.1. In the diff it is one derived constant
(`EGRESS_ENV_VOCABULARY`), one predicate (`isEgressEnvName`), and one branch of
the environment probe placed ABOVE the stray check so it fires on a permitted

### W3a: the first bundle found W3 flaky, and the cause is worth carrying

The first full bundle run reddened `red-witness` with exactly one reason:

```
gates: red-witness: red: 15 witness(es) evaluated (5 own, 10 stored re-evaluated in 97009ms);
witness gate-cli-credentials-report-survives-pipe: red: member 0 (mutation of src/gates/credentials.ts):
red in 1 of 2 repetitions where deterministic true requires every repetition red
```

One repetition of the mutant did NOT redden the test, although the same
command truncated 12 times out of 12 when run by hand:

```
$ for i in $(seq 1 12); do node src/gates/credentials.ts credential-scrub     --result /dev/null --evidence /dev/null "$BIG" 2>&1 >/dev/null | cat | wc -c; done   | sort | uniq -c
     12 65536
```

**The cause is libuv's write loop, and it makes a DRAINING reader the wrong
instrument.** `uv__write` calls `writev` in a loop until it gets EAGAIN, so a
reader that happens to be scheduled mid-loop lets the child push a second
buffer out before it exits. Whether that happens depends on machine load, so
the arm was a coin flip weighted by how busy the box is, which is the worst
kind of witness: green often enough to look fine.

The instrument is now a reader that provably is not reading while the child
writes, `| { sleep 0.5; cat; }`. The pipe fills, the remainder is queued, and
the pre-fix entry point discards it. It is also the more faithful shape: a
`tee` or a CI log collector that is briefly busy is exactly this.

Measured after the change, on a 4-CPU box (`nproc` reports 4) carrying six
background processes spinning on the CPU, which is heavier than the harness
ever is. Twelve runs of the MUTANT:

```
i tests 1|i pass 0|i fail 1|x failing tests:|   (x12, identical)
```

and four runs of all six CLI tests at HEAD under the same load:

```
run 1 exit=0   i pass 6  i fail 0  i skipped 0
run 2 exit=0   i pass 6  i fail 0  i skipped 0
run 3 exit=0   i pass 6  i fail 0  i skipped 0
run 4 exit=0   i pass 6  i fail 0  i skipped 0
```

**W1 and W2 were red in both repetitions in that same bundle run**, which is
why only this arm changed. Their margin is the reason: their reports are about
three times the socket buffer, so a spare loop iteration does not bridge the
gap, while this one was only twice the pipe buffer. The capture file's
`shell pipe (\| cat)` rows remain the real measurement that was taken with a
plain `cat`; the test now uses the stricter reader.

## 6. The two dispatch items that are not in the plan

### 6.1 The `credential-scrub` verdict inversion: the half that is fixed

delivery/verification/m4-prototype-probes.md:46 recorded that this gate reddens
`GIT_CONFIG_*`, which in that container bought only URL rewriting, and greens
`HTTPS_PROXY`, which bought full GitHub reach. M4-P8 measured the same thing
from the other side, four arms through `spawnTask` differing only in the
allowlist extension: delivery/work-history/m4-p8.md:116 is arm B, ten variables
plus `HTTPS_PROXY`, HTTP 200 from `api.github.com/user`, against arm A's ten
variables and HTTP 403.

**What is fixed.** The environment probe carries a THIRD allowlist-independent
tripwire, `EGRESS_ENV_VOCABULARY`, walked from the proxy variables curl(1),
git(1) and wget(1) document, in both the upper-case and lower-case spellings
those pages carry. It sits ABOVE the allowlist-dependent stray check, so it
still fires on a name the DEFAULT allowlist has been widened to carry, which is
the "allowlist widened by an implementer to turn a red gate green" hazard the
module's own comment declares. That widening now costs a red.

**What is NOT fixed, and this is the larger half.** The case M4-P8's arm B
actually used is a PER-INVOCATION `extraAllowlist`, an argument of one spawn.
This gate probes the constructed DEFAULT child, and no probe of a default can
see an argument a caller has not passed yet. Closing that half means auditing
the extension record a task writes into its `meta.json`, which is a different
gate, a different declaration and a different phase. Stated plainly: after this
change the gate still reports green while a task launched through the audited
route carries `HTTPS_PROXY` into its child.

**Two names are deliberately absent and both absences are measured.**
`NO_PROXY` and `no_proxy` NARROW a child's reach, so listing them would redden
a child that is strictly less capable. `CURL_CA_BUNDLE` is a TLS-trust channel
and not an egress grant: delivery/work-history/m4-p8.md:117 is arm C, which
adds it on top of arm B and measures the same HTTP 200 arm B already had, and
its node-side sibling `NODE_EXTRA_CA_CERTS` is already in
`DANGEROUS_ENV_VOCABULARY`.

**The egress walk is a SEPARATE list from `DANGEROUS_ENV_VOCABULARY`, and that
was the decision of the round.** `src/exec/env.ts` imports `isDangerousEnvName`
and REFUSES an allowlist extension naming any member of it. Folding the proxy
names in would therefore have refused M4-P8's one audited, reasoned extension
as a side effect of a data edit in a file this phase does not touch, and it
would have done so on the strength of ONE container's proxy topology, which
M4-P8's own work history warns against generalising. Whether an egress name may
ever cross into a child is a kernel design question with an owner-facing cost;
taking it by accident from inside a phase about `process.exit` would be the
wrong way to decide it. A test asserts the two vocabularies stay disjoint, so a
later editor moving a name between them has to face that consequence.

**No gate ARM was added, so `gate-registry.yaml` and `gates.manifest.json` are
untouched.** The change is to an existing gate's implementation, under its
existing id, unit label and applicability, so no registry row and no manifest
row changes. The dispatch asked for both drift checks to be run and pasted
whether or not the vocabulary moved, and they were:

### 6.2 M4-P8 shipped no witness spec: what could and could not be done

This phase ships FIVE specs, and the `red-witness` gate reports `5 own` rather
than the `0 own` M4-P8 reported.

**M4-P8's own behaviours could NOT be given specs from here, and the refusal is
structural rather than a judgment.** Rule (d) requires a member THIS PHASE
AUTHORED to intersect THIS phase's diff, and for a mutation the located text
must fall inside a CHANGED HUNK. M4-P8's credential refusals live in
`src/exec/env.ts`, which this phase does not change, so a spec added here whose
member mutates that file is refused with "rule (d): declared dangerous state
does not intersect the phase diff", whatever the quality of the witness. The
one exemption rule (d) grants is `kind: baseline-ref`, which for M4-P8's
behaviours would be the bare absent-feature baseline T-003 exists to forbid.

The correct home for those specs is a round that changes `src/exec/env.ts`, or
a deliberate decision to relax rule (d) for retrospective coverage. Neither is
this phase's to take. Recorded here rather than silently skipped.

## 7. Hazard self-review

**Hazard class.** These three modules CERTIFY something (a gate verdict) and
CONSUME another program's output, and this phase changes how they hand their
certification to a reader.

- **Can it pass while the thing it guards is broken?** This is the question that
  found the shape of the whole round. The first design of W1 and W2 used
  `spawnSync` with a 131 KiB report, which fits in a socket buffer: the tests
  passed at the PRE-FIX commit. That is the "exercises a path where the hazard
  cannot occur" failure exactly, and it was caught by measuring the truncation
  point rather than assuming it. Every oversize test now asserts its own
  fixture is oversize before asserting anything else, so a future edit that
  shrinks the fixture fails loudly instead of passing vacuously.
- **Can the change hang instead of exiting?** `process.exit` terminates whatever
  is pending; `process.exitCode` lets the process end normally, so a lingering
  handle would HANG rather than exit. Attacked directly: every arm of all three
  round-trip tests asserts `child.signal === null` under a `spawnSync` timeout,
  so a hang is a signal and a failure rather than a slow pass. Nothing was
  found; all three modules use `spawnSync` for their children and hold no
  timers or sockets.
- **Does the verdict change?** Attacked and nothing found. The round-trip tests
  assert the observed exit code against the SHIPPED table
  (`exitCodeForStatus`/`statusForExitCode`) rather than against copied
  literals, walking green, red, not-applicable and error.
- **Does the new tripwire false-positive on a real run?** Attacked. This
  container has both `HTTPS_PROXY` and `https_proxy` set in the parent
  environment, which is the worst case available. The real gate run is green
  with 7 units, because neither name is on the default allowlist and
  `buildChildEnv` therefore drops both. Capture in section 9.
- **Is the capture a real capture?** Attacked. Each of the three oversize tests
  reproduces its own recorded block LIVE before asserting anything about
  report size, so a change in the gate's rendering fails at the reproduction
  rather than silently changing what the comparison means.

## 8. What this phase did NOT cover

A reviewer's first check. Written before the gate evidence below.

1. **`scripts/*.mjs` was not examined**, exactly as the plan's own not-covered
   list says. The derivation for the entry-point mechanism was
   `grep -n 'process.exit' src/gates/*.ts bin/*.ts src/*.ts`, whose full output
   is section 8.1. It covers `src/` and `bin/` and nothing else. The 40-odd
   script gates may carry the same pattern and this phase claims nothing about
   them.
2. **Two of the eight registered behaviours carry no witness spec**, and it is
   the same three round-trip tests in different files:
   `gate-cli-red-witness-exit-codes-round-trip`,
   `gate-cli-suite-exit-codes-round-trip` and
   `gate-cli-credentials-exit-codes-round-trip`. They assert that this phase
   changed NOTHING, so no mutation inside this phase's diff reddens them and
   rule (d) refuses any spec that tries. They are controls, and a control is
   not a guard.
3. **`isAuditedSource` was not touched and its scope is narrower than the
   gate's precondition.** The `red-witness` precondition in
   `gates.manifest.json` lists `src/`, `bin/` AND `plugin/` after T-032, while
   `isAuditedSource` in `src/gates/red-witness.ts` still returns true only for
   `src/` and `bin/`. So a diff touching only `plugin/` RUNS the gate and takes
   no coverage obligation from it. This phase neither narrowed nor widened
   that; it is named here because this phase is the one editing that file and
   a later reader should not have to rediscover it.
4. **The uncaught-throw arm of all three entry points is unchanged**, so a
   throw escaping `main` still exits 1, which is EXIT_RED and is
   indistinguishable from a real red verdict to a consumer reading only the
   exit code. `src/gates/scope.ts` and `src/gates/gate-classes.ts` carry the
   second layer that fixes this. Extending it here would change an arm
   criterion 3 requires unchanged, so it is named rather than done.
5a. **The load sensitivity was characterised, not eliminated in general.** The
    credentials arm is now deterministic because its reader waits. W1 and W2
    still rely on a margin, a report about three times the buffer, rather than
    on a reader that withholds its read. **I did not find a way to delay the
    parent's read under `spawnSync`**, which is a statement about my search and
    not about the API: the search was reading the documented option set
    (`input`, `stdio`, `env`, `cwd`, `timeout`, `maxBuffer`, `killSignal`,
    `shell`, `encoding`), none of which is a reader-side hook, and I did not
    try routing the child through an intermediate process the way the
    credentials arm does. That remains open and a later round may close it.
    W1 and W2 were red in 2 of 2 repetitions in every bundle run here; that is
    a measurement, not a proof. A machine with a much larger socket buffer, or
    a much faster drain, could weaken them. Raising their fixtures further
    costs test wall time and was not done.
5. **The measurement is one container, one day, one operating system.** The

#### 12.4.2 Dynamic derivation: falsify the whole suite against a deliberately dirty machine

The static walk is a reading. This one is an experiment, and it does not know

### 12.5 What the derivation did NOT cover

The reviewer's first check, and it is stated before any result above is relied
on. Seven exclusions, each with why.

1. **Only the three test files this branch changes were enumerated
   statically.** The diff also carries three `src/` files and five witness
   specs. The `src/` edits are the `process.exit` to `process.exitCode`
   change and carry no assertions, which the enumerator confirms by finding
   fifty of them and none in `src/`. The witness specs are JSON data with no
   assertion text at all, so the static enumerator has nothing to say about
   them and the dynamic one is what reaches them: section 12.6 runs the
   `red-witness` gate, which evaluates every spec including the five this
   branch adds.
2. **The dirt is MY CHOICE OF DIRT.** `dirty-on.sh` stages the seven sources
   named in `CREDENTIAL_SOURCES`. An ambient dependency on something outside
   that list is outside the experiment: a different git version, a different
   libc, a case-insensitive filesystem, macOS spawn buffer sizes, System
   Integrity Protection, a different default shell, an ambient `NODE_OPTIONS`.
   The experiment answers "does anything here depend on ambient CREDENTIAL
   state", not "is anything here machine-dependent".
3. **It ran on Linux only.** A darwin-only code path is invisible to it. One
   exists in this file, the `process.platform === "darwin"` block inside the
   sibling green test, and it is PRE-EXISTING rather than added by this
   branch. Its behaviour on the failing runner is read from the macOS job log
   in section 12.1, not from any run performed here.
4. **`command -v` presence assertions are outside the absence filter by
   construction.** Row 982 is in the output only because `assert.notEqual` is
   in the pattern. A test that requires an ambient program without using a
   negative matcher would not appear. Grepping the added lines for the other
   shapes an expectation can take returned nothing:

   ```
   $ git diff -U0 origin/main...HEAD -- 'test/*.test.ts' | grep '^+' | grep -nE '\bthrow\b|\bexpect\(|\.strict\b'
   (no hits)
   ```

5. **The static enumerator's paren matching is naive.** It counts `(` and `)`
   without excluding string and template literals, so an assertion containing
   an unbalanced paren inside a string could be truncated early and its later
   arguments not searched. The dynamic derivation does not share this
   weakness, which is the reason both were run.
6. **Pre-existing tests OUTSIDE the three changed files were not enumerated
   statically**, only executed. Section 12.6 runs the whole suite under the
   dirty machine, which covers them by execution; a pre-existing absence
   assertion over ambient state that the dirty machine happens not to touch
   stays unfound.
7. **The macOS arm itself was not run.** Nobody on this round has a macOS
   runner. Section 12.7 says exactly which half of the result is demonstrated
   and which is reasoned.

### 12.6 The fix

The instance would go away by adding `GIT_CONFIG_NOSYSTEM: "1"` to `base`. That
is the fix this contract exists to refuse: it closes the two git probes and
leaves the shape intact, so the eighth probe source someone adds later reopens
it silently. The round fixes the shape.

The control exists to make the three members ATTRIBUTABLE to the one added
variable, and attribution is a DELTA. Two assertions replace the one absolute,
and both are pure functions of the names in `env`:

1. **The delta.** Every source other than `environment` is compared
   `deepEqual` between the control walk and the member walk. Whatever the
   machine contributes it contributes to both sides, so it cannot account for
   the difference. If adding a proxy variable ever DID move another source,
   this reddens, which is correct: the member would no longer be attributable.
2. **The shipped fold, scoped to the source under test.** `verdictFromProbes`
   is called over the environment probe ALONE, green for the control and red
   for each member. That is the resolvable-implies-red arm the old whole-walk
   assertion was reaching for, asserted over a one-element list the test
   fully determines.

The whole-walk `red` assertion is kept, at test/credentials-gate.test.ts:1218,
with a comment saying in the file that it is not attributable on its own,
because a machine with a resolvable source of its own would redden it
regardless. It stays because it is the call the gate main actually makes.

The two new assertions are at test/credentials-gate.test.ts:1178 and
test/credentials-gate.test.ts:1212, and the delta comparison at
test/credentials-gate.test.ts:1202.

No witness spec changed. The defangs in witness/credential-scrub-egress-tripwire.json
make the environment probe report `clean` where the member requires
`resolvable`, so the assertion that carries the red witness is untouched by
this edit, and the `red-witness` gate re-evaluates it below.
