**A deviation from the brief's list, decided and stated.** The brief lists
`Read, Glob, Grep, Write, Edit`. Line 331 says a path-less rule "matches that
rule at the tool level everywhere", so bare `Write` and `Edit` would
pre-approve writes OUTSIDE the review worktree, which the grant forbids
(DR-0065: "write inside its own review worktree"). The mapping therefore
anchors the file rules at the working directory, which is the review
directory: `Read(./**)` and `Edit(./**)` (an `Edit` path rule governs the Write
tool too, line 331). `Glob` and `Grep` are not listed: reads inside the
working directory need no approval, and Read rules apply to them. And since
line 555 means acceptEdits alone leaves WebFetch reaching a preapproved set of
domains, "no network tools" is mapped to an explicit deny of `WebFetch` and
`WebSearch`, and "no push" to a deny of `Bash(git push *)`. Both changes make
the flags narrower than the brief's literal list: they take approvals away
from it and add none. Neither was made to get past a classifier, and the edit
was not refused (commit `dc2b97f`).

### Item 4: the known limit

The allow-list bounds the harness's own tools, not what an allowed program
does: `Bash(node *)` admits `node -e`, which can start any process, including
`git push`. The scrubbed environment removes `GH_TOKEN`, but the agent proxy in
this container supplies credentials on the way out (CLAUDE.md standing warning
6), so a push through it is not stopped by the scrub. The grant bounds an
honest reviewer, not a hostile one; branch protection on `main` is what keeps
`main` safe. Nothing was changed for this; DR-0065 records it.

### Open questions and observations

- Whether a `--allowedTools` rule pre-approves a write to a protected path is
  not settled by what I read. permission-modes.md:619 says allow rules "in
  settings files do not pre-approve protected-path writes", and the table
  above it says acceptEdits prompts for them; it does not say the same of
  rules passed as flags. I did not probe it, because the only real CLI call
  was the smoke.
- The review worktree has no `node_modules`, so `npm run build` there needs
  dependencies the grant does not let it install (`npm ci` is not granted).
  A reviewer that must build will fail until the dispatch provides them.
- The dispatch builds the argv after it adds the review worktree
  (src/review.ts:388 follows the `git worktree add`), so an executor that
  throws for a grant it cannot map leaves the worktree registered and the task
  directory in place. The order predates this round and was not changed.
- The child loaded the project's own `.claude/skills` from the worktree (the
  init row's `skills` list names them). Recorded, not acted on.
