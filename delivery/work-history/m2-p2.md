## Decisions taken inside this phase

- D-P2-1 (pin bracketing under the five-field pin). The delivered pin
  includes ctimeMs, which userspace cannot restore, so start/end pins taken
  AROUND a mutate-restore cycle are unequal by construction and the plan's
  literal step 3 ordering cannot yield criterion 1's "both pins recorded and
  equal". M2-C-5's stated property is "a run that cannot name what it
  executed is not evidence": the pin must certify the tree a TEST RUN
  actually ran on. Resolution: pins bracket each test execution, not the
  mutate-restore cycle. Per member, the red runs are bracketed by a start and
  end pin over the dangerous tree (which is the tree those runs execute), and
  the green head run is bracketed by its own start and end pin over the head
  tree. Each pair must be equal or the record is `error` naming the paths and
  fields. Criterion 1's "both pins recorded and equal" is discharged by both
  pairs being recorded and each pair being equal; criterion 7's in-harness
  hook rewrites a file between the green run's pins and must produce `error`
  naming the path and mtimeMs. This follows the delivered module's own
  instruction (pin.ts header: read M2-P2 criterion 7 against five fields).
- D-P2-2 (coverage semantics for step 7's "source changed with no witness
  spec covering it"). A changed file under src/ or bin/ is covered when at
  least one witness spec declares a patch or mutation member that touches it
  (mutation: the member's file field; patch: the paths named in the patch's
  diff headers). baseline-ref members cover no specific file: they assert an
  absent-feature baseline, not a file-level dangerous state. Files DELETED by
  the diff are exempt (there is nothing at head for a member to touch;
  rule (d) requires members to touch head-state files). Both choices are
  recorded here because the plan states the rule at file granularity without
  fixing the mapping; each is the deterministic reading that fails closed on
  the files that still exist. Witnessed by the tests
  `witness-coverage-red` (a changed source with no covering member is red
  naming it) and `witness-harness-green-end-to-end` (a covering member
  admits green).
- D-P2-3 (derived-class grep granularity, rule (e)). "A witness whose named
  tests invoke a command on destructiveCommands" is derived by searching the
  FULL SOURCE of every test file containing a named test for any
  destructiveCommands entry as a substring. This over-approximates (a fixture
  string elsewhere in the same file counts), which is the fail-closed
  direction: an over-derived class forces `destructive`, which only tightens
  rule (a) and does not weaken a witness: `grep -n "spec.class"
  src/witness/run.ts` shows the class is consulted at exactly two places,
  rule (a) (which the destructive class can only ADD a refusal to) and rule
  (e) itself. The alternative, extracting the named test's body from TS
  source, would be a parser whose failure modes are silent
  under-derivation.
- D-P2-4 (rule (f) scope). The spawn-grep (`child_process`, `execFile`,
  `spawnSync`, `execSync`, `exec(`) runs over the CHANGED files of the diff;
  the capture obligation binds every witness one of whose patch or mutation
  members touches a changed file that the grep matched. A witness with no
  member touching a spawning module is not "in that state".
- D-P2-5 (baseline-ref member application). Applying a baseline-ref member
  checks out the resolved baseline sha and then restores the named tests'
  FILES from head (`git checkout <head> -- <test files>`), because the
  head-authored test is the thing that must be red against the baseline
  (blueprint section 4: red on baseline, green on head). A named test that
  cannot RUN at the baseline (import crash aborts the file) does not count as
  red: the member requires each named test individually reported failing,
  which is T-003's dangerous-state discipline, not a convenience.
- D-P2-6 (repeats on kernel-corpus witnesses). The kernel's own witness
  specs declare `repeats: 2`. The plan makes repeats a spec field with
  default 5; 2 is chosen for the shipped corpus because every member costs a
  clone plus repeats+1 test runs inside CI's gate bundle, and criterion 9's
  five-minute ceiling governs the whole corpus. The 3/5 determinism fixture
  of criterion 4 uses the default 5, where the measured M1 rate lives.

## CI depth requirement (documented, not assumed; STATE CR-902 carry-forward)

The red-witness gate requires, in the repository it audits:

1. `--base` and `--head` resolvable to commits in the local object store,
   with their merge history present, because the phase diff is
   `git diff base...head` (three-dot: merge-base diff). A shallow clone
   (`fetch-depth: 1`) fails this and the gate reports `error` naming the
   missing revision rather than guessing an empty diff (M2-C-3; witnessed
   by the tests `red-witness-shallow-error` and
   `red-witness-base-absent-error`, plus defang D13 below).
2. The repository to be UNSHALLOW for witness evaluation, because the
   harness creates scratch clones of it and `git clone` from a shallow
   source is refused by git. The gate probes `git rev-parse
   --is-shallow-repository` up front and reports `error` naming
   `fetch-depth: 0` as the requirement rather than failing obscurely later.
3. On pull_request events the checkout HEAD is the synthetic merge commit.
   When `--head` is supplied it is authoritative for the diff, for
   `git show` reads and for the scratch-clone checkout; the CI invocation
   supplies it explicitly (`--head ${{ github.event.pull_request.head.sha
   }}`, .github/workflows/gates.yml), and the runner passes it to this gate
   because the manifest entry declares `parameters: ["base", "head"]`. A
   direct invocation that omits `--head` audits the checkout's HEAD, which
   is the documented local-use default, not the CI shape.

The workflow edit that satisfies 1 and 2 (`fetch-depth: 0` on
actions/checkout) is owned by the gates.yml owner (M2-P9 per the phase
declarations; the workflow's own comment names the coupling). Until it
lands, the M2 gate bundle step on a pull request will report `error` for
`red-witness` (its `diff-touches` precondition needs the base commit, which
the shallow checkout lacks). Flagged in the final report for the
orchestrator's merge sequencing.

## Harness environment finding (recorded because it cost a round of red)

A child `node --test` spawned from inside a running `node --test` process
inherits `NODE_TEST_CONTEXT` and refuses to run any file, printing
"run() is being called recursively within a test file. skipping running
files." while exiting 0 with an EMPTY stdout. To the reporter pin that
reads as a non-tap stream. The harness scrubs every `NODE_TEST*` variable
from the child environment (src/witness/run.ts, runNamedTests) and the
parse-failure diagnostic now carries the child's exit code and stderr.

## Pre-submit hazard self-review (M2-D-18; the phase's declared hazard class)

The declared hazard: "a guard that judges guards, so a defect here is
invisible in every other phase's evidence." Each named hazard, walked:

1. "A dangerous state weaker than the state the behaviour actually defends
   against." Mechanized as refusal rules (a) and (d): a bare absent-feature
   baseline is refused for destructive and classification witnesses citing
   T-003 (test `witness-refusal-baseline-destructive`), and a member that
   does not intersect the phase diff is refused naming the member (test
   `witness-diff-intersection`). The V-1 shape specifically: a witness whose
   test destroys a branch carrying nothing is caught not by a rule but by
   execution, 0-of-n red (test `witness-v1-green-against-danger`). Residue,
   stated: a member that intersects the diff and reddens the test can still
   be weaker than the defended state; no script judges semantic strength,
   and section 1.5 of the plan says so (rows the gate does not cover).
2. "A class witness that reddens under one member and is green under the
   rest." The witness is green only when EVERY member was red (evaluateWitness
   loop; tests `witness-text-preserving-member` red direction and
   `witness-text-behavior-green` green direction).
3. "An assertion over a document's TEXT that survives an edit inverting its
   meaning." Rule (g) strong form: derived text-assertion detection, the
   mechanical preservation check, and the CR-661 fixture with the measured
   mutation (exit 1 to exit 0, every asserted string surviving). Tests
   `witness-text-single-member-collapse`, `witness-text-preserving-member`,
   `witness-text-same-line-collapse`. Residue, stated: the detection is
   syntactic (READ-call literals plus four assertion forms); a test that
   reads a document through an aliased callee or asserts through a helper
   escapes it. The self-guard test `witness-test-file-not-text-asserting`
   keeps the kernel's own test file honest against the detection, and the
   limits are recorded here rather than papered over.
4. "A stored witness that has silently gone green since it was written."
   Step 6 re-evaluation, tests `witness-stored-reevaluation-red` and
   `witness-stored-reevaluation-green` (the N-401 shape).
5. "A determinism claim asserted rather than measured." Every member runs
   `repeats` times and the rate is carried on the record; deterministic
   true requires n of n (tests `witness-determinism-rate-red`,
   `witness-determinism-rate-green`, staged as the real 3-of-5 stage-path
   collision).
6. "A re-evaluation pass whose cost makes an implementer narrow it
   quietly." The cost is measured and recorded per run (reEvaluationMs in
   the evidence record and the gate detail line); the dogfood measurement
   is in this file, and the five-minute stop rule of plan step 6 is
   restated here as the operative ceiling rather than silently rescoped.
