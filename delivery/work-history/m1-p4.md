## Key decisions and the why that is invisible in the diff

1. meta.branch is the TASK branch (task/<id>), which is deliberately not what the pool record calls "branch" (the project's default branch; the pool's task branch field is branchName). Teardown judges the task branch, so meta records the branch the task works on. Both names are documented at their definitions so the mismatch cannot be read as a bug.
2. baseSha and baseOffline are COPIED from the pool record poolCreate returned. baseOffline is never recomputed from spawn's own --offline flag, because pool create attempts the fetch even under --offline and records offline false when it succeeds. A recomputing spawn would mark a perfectly fetched base as offline whenever a contended fetch succeeded on retry, which is the exact provenance inversion measured as V-2 in M1-P3. Witness W2 below is red against that dangerous state, not against an absent field.
3. Holdership uses M1-P3's transport unchanged: lock acquire prints the opaque holderId, the operator carries it, and it arrives as TIPHYS_HOLDER_ID. No second identity mechanism was invented, nothing is derived from the running program (C-2), and the check is a read of the lease FILE through the merged leaseStatus. Both tests parse the holder id out of lock acquire's real captured stdout rather than asserting a hand-written string.
4. The holdership check runs BEFORE pool create even though the plan's prose introduces it later in the step, because criterion 12 requires the refusal to create nothing. Witness W8 (check moved after pool create) is red 3/3 with "the refusal created a worktree".
5. checkHoldership lives in src/task.ts. The files-to-touch list has no shared-guard module, and the rule is a precondition of every task mutation, so the task-state module is the least-bad home for it; spawn and teardown share one implementation rather than two copies of a security-relevant rule.
6. The fleet's own lease being ABSENT is a pass (the plan's M1 test contexts). Corrupt, expired, or held-by-another all refuse: fail closed, because each of those states means the caller cannot prove it is the one orchestrator.
7. The executor seam is ExecutorAdapter with exactly the plan's contract (write tasks/<id>/executor.json at launch, launch the payload in the worktree, ensure the turn-end file is written with the payload exit code). Everything crosses the boundary as files and exit codes; nothing inspects a terminal (FM-055, FM-060). M1 ships one adapter, subprocess.
8. The subprocess adapter runs the payload WITHOUT a shell. Under a shell a missing payload binary arrives as an ordinary exit code 127, indistinguishable from a payload that ran and failed, and spawn's rollback rule turns on exactly that distinction (criterion 5). The cost is that --exec is tokenised on whitespace with no quoting; that is documented at the parser and is an adapter's business later, not a string this kernel should re-parse.
9. The payload runs to completion before spawn returns (C-3). Witness W1 (payload backgrounded and detached) is red 3/3 with "spawn returned before the payload had exited", so the no-backgrounding property has a real guard rather than a comment.
10. A NONZERO payload exit is not a failed spawn. The payload's outcome lives in the turn-end record, which with meta.json status is the single current-state authority (C-1); spawn exits 0 and reports the code on stdout. Rolling back a worktree because the payload failed would destroy the work an operator needs to inspect, which is M1-P3's V-1 defect in a new place. Witness W7 makes that concrete: making a nonzero payload trigger the rollback turns the turn-end test red 3/3.
11. Rollback scope, stated narrowly on purpose. Before pool create: nothing is removed because nothing was created, and in particular nothing under tasks/<id>/ is written until the create has succeeded, so a duplicate id leaves a pre-existing task byte-identical (criterion 4, PR-005). After pool create and before the payload starts: exactly the files this invocation wrote, the task directory only if this invocation created it, and the pool worktree through poolDestroy WITHOUT --discard and WITHOUT --delete-branch-force, so a worktree that is somehow not pristine refuses and survives rather than being destroyed by a cleanup path. Once the payload has started: nothing is ever rolled back. CORRECTION TO THIS ENTRY, per F-3 and the two clean-room reviews: as first written this entry stated the contract unconditionally ("everything or a clean rollback") while only the RETURNED failure shapes had been exercised. Every step in that window signals failure by RAISING, not by returning, and an unwrapped raise walked past the rollback entirely (F-2), so the claim was broader than the code. The fix round closes the gap and the claim now holds for both shapes; the measured scope is stated in the fix-round section, not here.
12. The turn-end hook is a generated .mjs script in the TASK directory, never in the worktree (FM-059, absolute invariant), taking the payload exit code as its single argument with the turn-end path baked in. The .mjs extension makes it parse as ESM regardless of the fleet home's package.json, and the adapter invokes it with process.execPath rather than relying on a node shebang resolving on PATH.
13. Brief assembly appends the fleet's warnings.md verbatim, with a single newline inserted only when the brief does not already end in one, and writes nothing else. With no warnings file present, brief.md is byte-identical to the brief file (asserted directly, not by substring).
14. Teardown reads the pool record for the project, remote and default branch rather than re-deriving them, so EXT-F-03's remote resolution has one implementation. A missing or unreadable record refuses rather than guessing.
15. Teardown's git runner is local to src/teardown.ts rather than an export added to src/pool.ts, because src/pool.ts is explicitly out of this phase's edit scope. It has no contention retry: nothing in M1 runs teardown concurrently with anything (parallelism is off until M5), and adding retry machinery for a state M1 never reaches is the shape that cost M1-P3 four rounds.
16. Landedness is is-ancestor first, then the merge-tree tree-equality procedure against the FETCHED default ref, fail-closed on anything inconclusive (an unexpected exit from either git command refuses). Conflicts (merge-tree exit 1) are a plain unlanded verdict. Witnesses W3 (judge against the stale local ref) and W4 (ancestor only, no merge-tree) are each red 3/3.
17. THE SALVAGE COMMIT HAPPENS AFTER THE LANDED CHECK, and this is the one place where the plan's step ordering and its own criteria pull in different directions. Step 5's prose introduces the salvage inside the dirty-refusal clause ("unless --salvage: commit leavings ... then proceed"), before the landed clause. But a salvage commit is by construction NOT landed: it introduces content the default branch does not have, so a merge-tree comparison after it can never be a no-op. Committing first would make criterion 8's final requirement ("after the branch is landed ... teardown --salvage exits 0") unsatisfiable for every salvage. Deciding first and acting afterwards also bounds what a nonzero exit can leave behind. CORRECTION TO THIS ENTRY, per CR-302: as first written this said "every refusal is a true no-op: a refused teardown never commits, never pushes and never removes", and the reviewer falsified it in under a minute by pointing the push URL at a nonexistent repository. The true claim is narrower and is what the code and the module doc now say: EVERY REFUSAL THAT PRECEDES THE SALVAGE STEP is a true no-op, and the one nonzero exit that can leave a change behind is a salvage whose push fails, which commits the leavings locally, destroys nothing, and says exactly that in its reason line. The criteria therefore fix the meaning, and the code follows the criteria. Witness W5 (salvage moved before the check) is red 3/3, and the assertion that catches it is that the branch tip and the remote were unchanged by the refusal.
18. The scout path passes --discard and NOT --delete-branch-force. --discard's plan-defined meaning is the dirty-tree override; conflating it with branch deletion would make a scout that committed to its scratch branch lose those commits silently, which is precisely M1-P3's V-1. A committed scout is refused by the pool's own branch gate, with the commit intact. This is a live decision, so it has its own test. CORRECTION TO THIS ENTRY, per N-401: as first written this said "witness W9 (scout path forcing the delete) is red 3/3", and that stopped being true the moment the fix round added the CR-304 pre-check. The pre-check refuses a committed scout before pool destroy is ever called, so the inner flag's value is no longer observable at runtime and W9 measured GREEN 3/3 against the fixed source (measured by the delta reviewer, and re-measured here). What is true now: the decision is defended by TWO gates, the outer one (the pre-check) is the behaviourally witnessed one (FW5, red 3/3), the inner one is defence in depth and is guarded STRUCTURALLY by the registered behavior teardown-scout-never-forces-branch-delete, modelled on the C-2 structural test in test/lock.test.ts, red 3/3 against the dangerous edit (NW1). W9 as originally shaped is retired, and the combined dangerous edit (pre-check removed AND the flag forced) is red 3/3 as NW2.
19. The ship path passes --delete-branch-force after its landedness judgement, which is exactly the dependency src/pool.ts documents as coming from here. After a salvage the branch carries the WIP commit, which has been pushed, so removing the local branch loses nothing.
20. Teardown never re-frames a destroy failure. M1-P3's destroy has two failure kinds that mean opposite things: a stage-2 refusal is a true no-op, a stage-3 partial failure has already removed the worktree and enumerates the survivors. Teardown passes the destroy's own reason through verbatim, prefixed only with "pool destroy did not complete:" and suffixed with the one thing this layer knows for certain ("task <id> stays open"). Witness W6 (the failure dressed up as "teardown refused: nothing was changed") is red 3/3.
21. The salvage commit sets command-scoped GIT_AUTHOR_* and GIT_COMMITTER_* to the machine identity exported by src/commands/init.ts (one authority for that constant), because CI runners have no git identity and the fleet never reads or writes user or global git configuration (EXT-F-02 option B).
22. The liveness-guard seam is a documented no-op function called in the right position, so M1-P5 adds a body rather than a new call site in the middle of the spawn sequence.
23. A payload terminated by a signal has no exit code; the turn-end record uses the shell convention 128 + signal number. M1 never drives that path, and this is recorded as an interpretation rather than left as a guess in the code.

## Deviations from the plan's letter

The plan's step 4 enumerates spawn's flags without it, but this phase's named inherited obligation is that a worktree created under --offline reaches meta.json as baseOffline true, and spawn is the only command that creates the worktree a task's meta describes: without the flag the obligation is unwitnessable in the true direction. Declared because "present and correct" in criterion 11 does not itself decide the units; the test asserts the exact relationship.

## Simplicity, and what was deliberately NOT built

The standing lesson from M1-P3 (five rounds, each hardening machinery for a scenario M1 never enters) was applied as a filter. Left out on purpose, each with the reason:

- No contention retry in teardown's git calls: M1 never runs teardown concurrently with anything.
- No automatic repair of a partial destroy: the destroy already prints the exact command that finishes the job, and re-implementing that decision one layer up is how the last phase grew defects.
- No rollback after the payload has started, and no force flags on the rollback path: a cleanup that can delete real work is the defect, not the protection.
- No exec-less spawn, no daemonize flag, no background mode: PR-013 and C-3.
- No second identity mechanism, no pid, no process probing: C-2.

### The shared root cause, and the one pattern that closes it

F-1 and F-2 are the same defect in two places. These modules were written
as an ok/reason result type end to end, and the Node fs calls underneath
them are not: writeFileSync and mkdirSync RAISE. Every returned failure was
handled correctly and every thrown one walked straight past the handler,
out of the command, and onto stderr as a stack trace, taking spawn's
rollback and teardown's state update with it. My tests only ever drove the
returned shapes (a duplicate id, an ENOENT exec), so the suite was green
over a hole, which is exactly the T-003 blind spot: the tests tested the
paths I had thought of.

The fix is one wrapper, `runStep(what, fn)` in src/task.ts, which folds a
raised error into the same `{ok:false, reason}` every other step returns.
It never swallows: the caller still gets a reason naming the step and still
decides what to do with it. Applied at every write in spawn's post-create
window (task directory, brief, meta, hook), around the adapter launch, at
the adapter's own launch-record write, and around teardown's meta write.

Where the wrapper alone would not be enough, the decision is explicit:

- The subprocess adapter classifies its own failures by whether the payload
  has started. A raised launch-record write is a launch failure (safe to
  roll back, the payload never ran); anything raised after the payload has
  run is reported as incomplete, which never rolls back.
- A THROW out of `adapter.launch` itself cannot be classified, because a
  foreign adapter that raised has told us nothing about whether the payload
  started. Rolling back would destroy a worktree that may hold real work,
  which is M1-P3's V-1 defect with a different trigger, so spawn refuses to
  guess: it leaves everything in place and enumerates it in the reason.
- Teardown's meta write happens after the worktree and branch are already
  gone, so its failure is not a refusal. It is reported in M1-P3's existing
  partial-failure vocabulary ("partial teardown of task id <id>: worktree
  ... HAS BEEN REMOVED ... but meta.json could not be marked closed ...
  repair that file and set status closed by hand"), which is the shape the
  destroy contract already defines for exactly this class of outcome.
