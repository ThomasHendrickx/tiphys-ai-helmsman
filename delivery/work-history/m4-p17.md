## WHAT WAS BUILT

### The mechanism behind criteria 1 and 2: a second copy of one comparison

had TWO implementations of "has this lease expired", one in the lock module and
one inside doctor, and the second could differ from the first without any test
noticing. Correcting only the verdict would have left that.

not have one: it reads the lease file defensively and holds only `holderId` and

diagnosis. That is why the copy existed. The comparison now lives once, at
src/lock.ts:170, behind `expiryHasPassed`, and `isExpired` delegates to it.

### Criterion 5: CHECK branches

Implementation at src/commands/doctor.ts:1255. A branch is PUSHED when a
remote-tracking ref exists for it, which is the only local evidence that it is
somewhere other than this disk, and UNMERGED when `git merge-base
--is-ancestor <ref> <trunk>` exits 1.

IT REPORTS EVERY PUSHED REF RATHER THAN FILTERING TO A NAMING PATTERN, and that
is a decision. At least two spellings are in use across the repositories this
kernel runs over: the pool names task branches `task/<id>` (src/pool.ts:54) and
this project's own delivery names phase branches with a harness prefix and a
milestone-and-phase segment. A filter written for either is blind to the other.
A superset prints rows a reader can skip; a filter that misses a branch prints
nothing at all, and nothing is what a healthy fleet prints too.

THE FIRST FULL SUITE RUN FOUND A REAL DEFECT IN THAT COMMENT, and it is
recorded rather than quietly fixed. The first draft spelled the delivery
prefix out inside the header of `checkBranches`. test/schemas.test.ts:800 walks
`src/`, `bin/`, `schemas/` and `roles/` and asserts BY NAME which shipped files
carry that harness-derived prefix, existing to stop the set growing; the comment
added `src/commands/doctor.ts` to it:

```
+   'src/commands/doctor.ts',
    'src/gates/run.ts',
```

1161 tests, 1158 pass, 1 fail, 2 skipped, exit 1. The fix was to take the
spelling out rather than to widen the allowed set: the spelling belongs in a
delivery process, not in a kernel that reports over any of them. The corrected
comment says so, so the next person to reach for the literal gets the reason
without reading the test.

WARN, and no profile promotes it. The reason is the measured one the plan gives:
remote ref deletion is refused in this container and `git push --dry-run
--delete` exits 0 whether deletion is allowed or not (CLAUDE.md:1090), so a
promotable branch check would make `tiphys doctor --for full` unpassable on the
kernel's own fleet with no action its operator could take, and an unpassable
check is one that gets switched off. The test walks every profile in `PROFILES`
rather than naming `full`, so a profile added later cannot promote it by
accident, and that test is demonstrated red below under two different promotions.

### Criterion 6: CHECK remote fetches

Implementation at src/commands/doctor.ts:318. The old check listed the
configured remotes and printed PASS whenever the list was non-empty. That
condition is true of the dangerous state in two ordinary ways: a fleet whose
history has never been pushed, and a fleet whose remote URL points at nothing.
Both printed `CHECK remote PASS remote configured (origin)`. Nothing the check
did could have told either from a healthy fleet, because `git remote` reads a
config file.

THE FETCH IS BOUNDED, AND THAT IS A DEPARTURE FROM THE CLASSIFICATION M4-P19
WROTE. test/pool.test.ts:1564 executes a table that leaves object transfers
(`clone`, `fetch`, `pull`, `push`) unbounded, on the reasoning that a legitimate
transfer's duration is set by how much data there is, so a wall-clock bound
would kill real work. That reasoning is right where it was written and it does
not reach here: this fetch moves no work an operator asked for, it is a probe
inside a report. Killing it costs one diagnostic line; not killing it costs the
whole diagnosis, and M4-P19 measured `doctor` still running at 25 seconds
against a remote that accepts and says nothing. The bound reads the same
`TIPHYS_GIT_NETWORK_TIMEOUT_MS` override the pool's ref probe reads, so a test
can shorten it.

That table scans `src/pool.ts` and `src/teardown.ts` only, so this new call is
outside it and produces no red there. Stated as an omission rather than left to
be found: extending the scan to `src/commands/doctor.ts` would be an edit to
test/pool.test.ts, which is outside this phase's declaration.

A FETCH THAT DID NOT RUN IS FAIL. The plan asks for "a third status naming the
fetch failure and never PASS", and the status vocabulary here has exactly three
words, so the third one is FAIL. It is also what this command already does
everywhere else an input could not be established: an unreadable lease and an
undecodable charter are both FAIL today. The alternative I weighed and rejected
was a WARN with a non-promoted condition, on the grounds that an operator
offline would then see doctor exit 1; I rejected it because an unreachable push
target is exactly the SC-002 state this check exists to report, and because the
plan's words allow only three readings and two of them are PASS-adjacent.

The check also reports, without printing PASS, three states it cannot compare
in: outside a fleet home, on a detached HEAD, and where the remote carries no
ref for the current branch.

The second is in the test. The assertion pinned a literal TOTAL over a set the
fixture does not own. git maintains `refs/remotes/<name>/HEAD` on its own
account, and `CHECK remote` runs the fetch that makes it do so immediately
before `CHECK branches` runs.

**THE CONFIG KEY IS NAMED PRECISELY HERE BECAUSE THE FIRST DRAFT NAMED IT
WRONGLY, and the wrong name would have sent the next reader to a setting their
git does not have.** The draft said `fetch.followRemoteHEAD`, which is what
current git's `Documentation/config/fetch.adoc` on `master` calls it. That
spelling is in NO RELEASED GIT. Probed against the git project's own tags, the
released key is `remote.<name>.followRemoteHEAD`:

| tag | `config/fetch.{txt,adoc}` mentions it | `config/remote.txt` mentions it |
|---|---|---|
| v2.47.0 | no | **no** |
| v2.48.0 | no | **yes, line 105** |
| v2.49.0 to v2.55.0 | no | yes |

The v2.48.0 release note names the same change ("git fetch honors
`remote.<remote>.followRemoteHEAD` settings to tweak the remote-tracking HEAD in
`refs/remotes/<remote>/HEAD`"), and the v2.48.0 entry itself says: "The default
value is create, which will create `remotes/<name>/HEAD` if it exists on the
remote, but not locally, but will not touch an already existing local
reference."

runs 2.43.0 and knows NEITHER spelling, which is why the fixture has one ref

### THE FIX, AND WHY IT IS TWO CHANGES

**The kernel, at src/commands/doctor.ts:1290.** `checkBranches` now asks for
`--format=%(refname)%09%(symref)` and filters on the FULL refname plus the
symref target: a row is a branch only when its refname starts `refs/remotes/`,
it does not end `/HEAD`, and it carries no symref target. The short name is then
recovered by stripping the prefix, which is what `%(refname:short)` does for
every ref that is not a HEAD. Both halves are load-bearing and neither is
redundant, which the matrix below measures rather than argues.

**The test, at test/doctor.test.ts:1401.** The end-to-end test no longer pins the
total. `branchLineWithoutTotal`, at test/doctor.test.ts:1128, renders it `<total>` and is applied to BOTH the
live line and the recorded capture line, so the rest of the line is still
compared byte for byte: the status token, the wording, the trunk name, the count
of UNMERGED branches, and the branch name itself. The helper asserts that its own
replacement changed something, so a later wording change cannot quietly turn it
into an identity and restore the pin.

The count did not disappear. It moved to a test that owns its input, at
test/doctor.test.ts:1491. That test calls `checkBranches` directly rather than through the CLI, so nothing fetches
and no git version can add a ref behind its back, and it deletes any ref it did
