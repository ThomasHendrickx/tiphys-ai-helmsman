### Mechanism

A safety check read a probe it could not complete as the harmless answer.
`pool destroy` asks git which worktrees have the task branch checked out, and
it read that list only when git exited 0; any other exit left the list empty,
and an empty list means "no other worktree holds the branch", which is the one
answer that lets the branch be deleted. So a failed probe granted the
destructive step instead of withholding it (fail open).

Round 3 made the failure reachable on ordinary machines by adding a flag
(`worktree list -z`) without checking which git releases accept it. git before
2.36 exits 129 with `error: unknown switch `z'`, so on Ubuntu 22.04 (git
2.34.1) the probe failed on every run and the check was silently off.

Two things are therefore fixed: the fail-open read (a failed or unreadable
listing now refuses, naming why) and the flag (git that rejects `-z` is asked
again without it). Derivation A enumerates the first mechanism across `src/`
and `plugin/src/`; derivation B enumerates the second across every git flag
M6-P3 added.

CR-M6P3A-08 is a different, smaller mechanism in the same family round 3
fixed: a `+++` header line whose form the reader did not recognise left the
previous file current, so the hunk was credited to the wrong file. A header
carrying both C-quoting and git's trailing TAB was that form.

```
# Derivation A, compact form. Every call site in src/ and plugin/src/ at a
# commit of spawnSync( or of a wrapper named on the command line. One row per
# site: file:line, the call collapsed to one line (up to its closing paren or
# 160 chars), and the first following line (within 14) that reads the result's
# status, ok flag or error, which is where a failure is decided.
import re, subprocess, sys
rev, repo = sys.argv[1], sys.argv[2]
wrappers = sys.argv[3].split(",")
files = subprocess.run(["git", "-C", repo, "ls-tree", "-r", "-z", "--name-only", rev, "--", "src/", "plugin/src/"],
                       capture_output=True, check=True).stdout.decode().split("\0")

n = 0
for f in files:
    src = subprocess.run(["git", "-C", repo, "show", f"{rev}:{f}"], capture_output=True, check=True).stdout.decode()

        depth, i, text = 0, m.end() - 1, []
        while i < len(src) and len(text) < 400:
            c = src[i]
            text.append(c)
            if c == "(":
                depth += 1
            elif c == ")":
                depth -= 1
                if depth == 0:
                    break
            i += 1

        if len(head) > 160:

            if decide.search(lines[k]) and k >= line - 1:
                first = f"{k+1}: {lines[k].strip()}"
```

### What the derivations did not cover

- Only `src/` and `plugin/src/` TypeScript at ea3edb3. Not `bin/`,
  `scripts/`, `.claude/`, `test/`, and not the shell scripts under `bin/`.
- A2 reads each result up to the first line that tests it (14 lines); where
  the decision is further away, or in a consumer of a returned value, it was
  read by hand, and the notes table names the consumer lines read. The `R`
  rows were classified by that reading, not by a test that makes each one
  fail.
- Second-level wrappers other than `gitValue`, `runGitRetrying` and
  `destroyGitStep` were not enumerated by a command. Those whose failure
  value is a negative answer were followed through their callers by hand:
  `contextDocumentPresentAt`, `resolveCorpusSource`, `blobAt` (both),
  `readReviewFamilies`, `slugFromGit`, `resolveHeadFlag`, `currentBranch`,
  the red-witness patch readers, `readDocumentAtHead`, `provablyStaleLock`,
  `landedness`.
- The `A` rows assume absence is the only failure git gives there. The
  failures I did not force: an object git cannot read (a damaged store, a
  partial clone whose promisor is unreachable) and a blob larger than the
  256 MiB `maxBuffer` of src/witness/run.ts:201, which Node reports as a
  spawn error, not a git exit.
- B2 sees only argv written as array literals at a call site; B1 is the
  backstop for flags added anywhere in the diff, and it lists option-shaped
  string literals only (a flag assembled from pieces would not show).
- B3 dates documentation, bracketed by the tags fetched (v1.0.0, v1.4.4,
  v1.5.0, v2.6.0, v2.7.0, v2.35.0, v2.36.0); it does not bisect between
  them, and only `worktree list -z` has a release note behind it.
- B4 runs each argv once, on a small repository, on two gits, both Linux.
  Apple's git and the git of the macOS runner were not run.
- The fallback's refusal of a newline listing (below) tests each line
  against the attribute shapes git 2.34.1 prints. A worktree path whose
  continuation after a newline itself begins `worktree `, `HEAD `,
  `branch `, `locked ` or `prunable `, or is empty, passes that test; I did
  not construct one.
- A different mechanism, not searched: `git config` values and `git`
  behaviour that depend on the user's own configuration (for example
  `diff.noprefix`, `core.quotePath`), which change the text the readers
  parse without any failure.
