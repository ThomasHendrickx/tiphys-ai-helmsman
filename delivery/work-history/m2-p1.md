## Deviations from the plan's letter, declared rather than silent

Three, each with the reason and what would falsify it.

### D1. One manifest field the plan does not list: `parameters`

Step 7 requires that "a gate whose command requires `--phase` reports `error`
when that parameter is absent". The runner can learn that in exactly two ways:
the gate declares it, or the runner pattern-matches the gate's command line.
`MECHANISMS.md`'s row "Deciding what another program will do by
pattern-matching the text of a file it consumes" records four M1-P6 rounds
paid for the second option, and its rule is to PIN the accepted shapes and
fail closed. So `gates[].parameters` is a closed enum (`base`, `head`,
`phase`), validated by the schema, read by the runner, and passed through to
the gate's argv. Falsifier: if a reviewer can show a way for the runner to
derive the requirement without reading either a declaration or the command
text, this field is unnecessary.

### D2. One result field the plan does not list: `vacuous`

Step 8 requires the summary to count `vacuous` as a strict subset of `error`.
After the M2-C-2 rewrite has fired, a vacuous error and an ordinary error have
the same status, so the runner would have to recover the distinction from the
detail TEXT of a record another program wrote. Same mechanism row, same rule.
`vacuous` is therefore an optional boolean on the record, set only by the two
places that perform the rewrite.

### D3. `manifest-self-check` is a subcommand, `tiphys gates self-check`

The plan names the gate and requires it to validate every schema document and
the manifest, but does not say where it lives. It lives in
`src/commands/gates.ts`, which is on the files-to-touch list, rather than in a
new script, which is not.

Two readings recorded so a reviewer is not left to guess whether they were
noticed:

- **Criterion 5's fixture carries a second, applicable gate.** Read with a
  single-gate manifest, criterion 5's `conditional` direction ("the runner
  exits 0") and criterion 9 ("a manifest whose every gate is not-applicable
  exits nonzero with reason `no applicable gate`") contradict each other.
  Criterion 9 is the aggregate rule and names its authority (M2-C-2 at the
  aggregate level, M2R-012), so criterion 5's manifest must contain something
  applicable. It does.
- **"No record is written for a gate that was not executed" (step 8) means
  not REACHED, not "did not run its command".** Criterion 2 requires four
  records including the `not-applicable` one, and a precondition that was
  evaluated and found unmet is a measurement. The runner writes a record for
  every gate it evaluated, and none for a gate excluded by `--only`.

## Pre-submit hazard self-review (binding)

**The plan's declared hazard class for M2-P1:** the spine every later record
rests on, so a defect here is invisible in every gate downstream. Named
shapes: a runner that writes a record for a gate it did not execute; a counter
whose buckets double-count or hide one another; a pin that passes a tree that
changed; a status that can be constructed as green with nothing examined; and
a configured path that is not a regular file and blocks the runner instead of
reporting.

The question the brief calls the highest-yield one in this repository, asked
of this component: **can the runner report a green bundle while the gates it
reports on are broken?** Five attacks, and what each found.

### Attack 1: can a green bundle be produced with nothing examined?

Attacked at three levels because M2-C-2 has three of them.

- Gate level, constructor: `makeGateResult` with green and units 0. FOUND
  NOTHING WRONG, and the arm had no test; one was added (W2). Also probed
  negative and fractional unit counts, which are now folded to zero rather
  than accepted as a smaller measurement.
- Gate level, ingest: a fixture gate that does not use the constructor and
  writes green with units 0 by hand. FOUND NOTHING WRONG (W1).
- Bundle level: a manifest with zero gates, and a manifest whose every gate is
  not-applicable. FOUND NOTHING WRONG (W6).

**Scope of the negative:** these three are the enforcement points that exist.
A gate that reports units 1 having examined nothing is NOT caught by anything
here. **Restated as an open question rather than as an impossibility:** I did
not find a way for the runner to audit a gate's own unit count without redoing
the gate's work, since `units` is the gate's claim about its own labour and the
runner has no independent view of it. If a reviewer finds one, that is a
finding against this design. The residue as it stands belongs to each gate's
own criteria.

### Attack 2: can a record exist for a gate that did not run?

The runner writes a record for every gate it EVALUATED and none for a gate
excluded by `--only`. Attacked by defanging the write so a not-applicable gate
leaves no record (W9, RED) and by making the `applicable` counter increment
unconditionally (W8, RED). Also checked by hand that `--only` naming an
unknown id is an error rather than a silently smaller run, and that
`counts.declared` is the SELECTED set with `manifestGates` recorded alongside
it so a reader is not left to infer which one a count refers to:

```
$ node bin/tiphys.ts gates run --manifest gates.manifest.json --evidence /tmp/ev3
$ node -e 'const s=require("/tmp/ev3/summary.json"); console.log(JSON.stringify({manifestGates:s.manifestGates, declared:s.counts.declared, only:s.only}))'
{"manifestGates":1,"declared":1,"only":[]}
```

**Scope of the negative:** a gate that writes a record and then crashes before
exiting reddens the exit-code/record consistency check, witnessed at W10 in
the table above (defang: `if (false && exitCode !== expected)`, result RED,
exit 1). A gate
that writes a record for a DIFFERENT gate id is refused, and that arm is
reached only by the gate-id check, which has no test of its own. **Stated as
an unwitnessed arm rather than as a covered one.**

### Attack 3: can the pin pass a tree that changed?

The T-004 shape is a byte-identical rewrite. `pin-mtime-only-difference`
stages exactly that, asserts the content hash is UNCHANGED across the rewrite
(so the witness is a witness and not a restatement of "the file changed"), and
W18 shows that dropping `mtimeMs` from the comparison makes it green.

**Scope of the negative:** the pin has one-second-resolution exposure it does
not have here (mtimeMs is milliseconds on this filesystem, measured by the
test passing), and a filesystem with coarser mtime granularity could produce a
rewrite the pin cannot see. Not reproduced, not refuted: **UNPROVEN on other
filesystems.** The pin also does not follow directory symlinks, so a tree
whose contents change behind a symlinked directory is outside every pin taken
here, by design and stated rather than discovered later.

## Open questions and forward warnings for M2-P2 to M2-P9

1. **`fetch-depth` for `diff-touches` gates.** The workflow's checkout is
   `actions/checkout@v4` with no `fetch-depth`, so it is shallow. This phase's
   only gate has no precondition and needs no history, so nothing is broken
   today. **The first phase to register a gate whose precondition is
   `diff-touches` (M2-P2, M2-P5) will need `fetch-depth: 0`**, and without it
   the `git diff base...head` in `evaluatePrecondition` will exit nonzero and
   the gate will report `error`, which is the correct failure but an
   avoidable one. Not fixed here because the workflow edit would be a change
   with no gate to justify it.
2. **Three precondition kinds ship unwitnessed**: `branch-matches`,
   `file-absent`, and the `modes` reserved field. Their consumers are M2-P4
   and M2-P6; those phases should treat them as unproven rather than
   delivered.
3. **The gate subprocess contract** is documented at the top of
   `src/gates/run.ts` and is what every later gate must obey: argv gains
   `--result` and `--evidence` plus one flag per declared parameter, the gate
   writes exactly one record to `--result`, and its exit code must AGREE with
   its record's status or the runner reports `error`.
4. **`--only` has no test.** It is implemented and refuses an unknown gate id.
5. **The claim grep is worth running early, not at the end.** Three of its
   nine hits in this phase were genuine overstatements that had already been
   written down as settled facts.
6. **The red-witness campaign found three green witnesses**, and each was a
   test that guarded a property some other guard was also holding. The cheap
   way to find them is to defang the mechanism rather than delete the feature,
   which is what the strengthened red-witness rule already says.
