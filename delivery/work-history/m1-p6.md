## What was built

**`sandbox/`**: the toy project. Dependency-free on purpose, so a clone
passes `npm ci` and `npm test` on a machine with only git, Node and npm
and with no registry reachable. Its README carries the exit-test log
lines the stub payload appends; that append is the whole "trivial
change" the milestone exit condition asks a task to land.

**`scripts/seed-sandbox.sh --remote <url>`**: pushes the seed content to
a git remote. Idempotent by construction: the content is copied over a
fresh checkout of the target branch and, when the resulting tree is
identical to what the branch already carries, it commits nothing, pushes
nothing, and exits 0. It handles a remote with no HEAD yet (the fresh
scratch bare repo of local mode, and a just-created sandbox repository)
by leaving the branch unborn rather than cloning an empty repository.

**`scripts/stub-payload.sh`**: the deterministic payload `tiphys spawn`
execs in the task worktree. Appends one line to the toy README, commits,
pushes the task branch, and in full mode opens the PR with `gh` and
prints its URL. It refuses to make an empty commit and refuses a working
directory that is not a git worktree, rather than reporting success on a
run that did nothing.

**`scripts/m1-exit-test.sh`**: section 4's procedure, with its staging
kept intact. Stage A (A1 to A8) and stage C (C1 to C3) are scripted;
stage B is not. Full mode runs stage A, records what the owner must do
as a `pending-owner-action` evidence record naming the exact commands,
and is re-run as `--stage c --approval <file>`. Local mode substitutes a
stub squash merge for stage B and runs everything in one invocation. The
step registry (`--list-steps`, and `step-map.json` in every evidence
bundle) names every section 4 step, its stage, and its local-mode
disposition (`both`, `local-substitute`, `full-only`).

**`.github/workflows/gates.yml`**: one step added to the existing `test`
matrix job. The `gates` fan-in job is untouched: still non-matrixed,
still `needs: test`, still failing unless `needs.test.result == success`,
so the required check context keeps both its name and its semantics and
a failing harness cannot report green.

## Key decisions and the why that is invisible in the diff

1. **Full mode is two invocations, not one.** Section 4 stages the exit
   test precisely so that the owner authorization is not a script step.
   A single-invocation full mode would have had to either block on a
   human or fake the approval. `--stage a` ends by recording what the
   owner must do; `--stage c --approval <file>` resumes from a
   `session.json` written at the end of stage A. Local mode has no human
   in it and therefore runs `--stage all`, which is the only stage value
   it accepts.

2. **The payload reports its facts to a file, not through spawn's
   stdout.** The harness needs the task branch and the payload commit.
   Reading them from `tiphys spawn`'s captured output would have assumed
   that spawn forwards the payload's stdout, which the plan does not
   state anywhere. The harness passes `TIPHYS_EXIT_TEST_REPORT` and the
   payload writes the same lines there. spawn's own output is still
   captured as evidence either way. This is the one place where the
   harness would otherwise have invented an M1-P4 contract.

3. **`doctor --for full` in local mode is a strengthened substitution,
   not a skip.** A2 requires `tiphys doctor --for full` to exit 0. The
   `full` profile promotes `gh-missing` and `remote-missing` to FAIL,
   and criterion 2 requires local mode to pass on a machine with only
   git, Node and npm, which has no `gh`. The harness therefore runs the
   command in both cases and asserts differently: with `gh` present it
   requires exit 0; with `gh` absent it requires a nonzero exit whose
   FAIL lines are exactly one and are exactly `CHECK gh FAIL`. That is a
   stronger local witness than skipping, because it proves the
   `remote-missing` promotion did NOT fire, which is the whole point of
   provisioning the fleet's throwaway `file://` remote (PR-210). The
   plan's local-mode mapping list does not cover this step; the
   substitution is recorded in the evidence like every other one.

4. **The harness runs the three kernel gates itself.** A1 says the
   preconditions include `npm ci && npm run build && npm test`. In CI
   that duplicates the three steps the job just ran. The duplication is
   deliberate: criterion 2 requires the harness to pass standalone on a
   bare machine, so it cannot rely on a caller having built anything.
   The alternative, a `--skip-preconditions` flag, is exactly the silent
   green path this phase is supposed to be free of.

5. **The falsifiability guard points at the real behavior.** With
   `TIPHYS_EXIT_TEST_SKIP_STAGE_B=1`, C1 records the missing merge as a
   `skipped-override` observation and does not fail there, so the run
   proceeds to C2 and fails where teardown correctly refuses a task
   whose branch never landed. Failing at C1 would have been easier and
   would have witnessed nothing about teardown.

6. **The harness owns the resident watcher and waits on files.** Section
   4 A5 says the harness, not the kernel, owns that process (C-3). The
   wait for the wake is file-based (the watcher's own captured stdout),
   not a process probe; the only signal the harness sends is a watchdog
   `kill` against its own child so a watcher that printed but never
   exited fails the run instead of hanging CI.

7. **The harness identity is duplicated in three scripts on purpose.**
   M1-P6's files-to-touch list contains no shared shell library and
   inventing one would have put a file outside the declared scope. The
   duplication is guarded by a test that reads all three scripts and
   fails on drift.

## Red witnesses

Each test was demonstrated red against a DANGEROUS state, not merely
against an absent feature (CLAUDE.md red-witness rule, tuition T-003).
All witnesses were reverted; the tree at `d890cc7` is the unmutated one.

1. **Seed commit without command-scoped identity** (`git_identified` in
   `seed-sandbox.sh` replaced by plain `git`): `seeding a sandbox remote
   is idempotent and commits as the harness identity` went red, 0 pass 1
   fail. Dangerous state: a seeder that only works where an ambient git
   identity happens to exist. This witness is only meaningful because
   every test runs with `HOME` empty and `GIT_CONFIG_GLOBAL` and
   `GIT_CONFIG_SYSTEM` pointed at nonexistent paths; this environment has
   a real global identity configured, so without that neutralization the
   mutated script would have committed happily and the test would have
   stayed green.
2. **Seeder idempotency short-circuit removed** (`if git diff --cached
   --quiet` forced false): same test red, 0 pass 1 fail. Dangerous state:
   every re-seed rewrites the remote head, which would make A1 a moving
   target for anything that recorded the seeded sha.
3. **Stub payload commit without command-scoped identity**: `the stub
   payload appends, commits as the harness identity, and pushes the task
   branch` red, 0 pass 1 fail. Same failure class on a clean runner.
4. **Stub payload push removed** (`git push` replaced by `true`): same
   test red, 0 pass 1 fail. Dangerous state: a payload that commits
   locally and never pushes, which would make A6's branch evidence
   vacuous while spawn still exited 0.
5. **Step A7 deleted from the harness registry**: `the harness step
   registry covers every section 4 step exactly once` red, 0 pass 1 fail.

6. **The `--mode full --stage all` guard disabled**: `the harness rejects

7. **Harness email drifted in `stub-payload.sh` only**: `the three

8. **The toy sandbox's only test file removed**: `a clone of the seeded

## Contracts this harness assumes from M1-P4 and M1-P5

These are the exact assumptions the validation pass must check. Each is
taken from the plan; where the plan is silent it is called out.

1. Every fleet-scoped command is run with the fleet home as the working
   directory (as `lock` and `pool` already are).
2. `tiphys spawn --task <id> --project <path> --brief <file> --shape ship
   --exec <cmd>` exits 0 and runs the payload to completion (plan M1-P4
   step 4). The harness does NOT assume spawn forwards the payload's
   stdout: see key decision 2.
3. `TIPHYS_HOLDER_ID` carries the holder identity for spawn and teardown
   (PR-203). The harness parses it from `lock acquire`'s stdout line
   `acquired <holderId> expires <ts>`, which is the shipped M1-P3 format.
4. `tiphys teardown --task <id>` exits nonzero with a reason line naming
   the branch while unlanded, and exits 0 after a squash merge; the
   worktree is at `<fleet>/worktrees/<task-id>` and `tasks/<id>/meta.json`
   carries `status: "closed"` afterwards.
5. `tiphys watch --once` exits 3 when there is nothing to surface; the
   resident `tiphys watch` writes `state/watcher.beacon` and exits 0
   printing exactly `signal <task-id> turn-end`.
6. **Not specified by the plan, and worked around:** the watcher's base
   interval and poll interval have no named flag, so the harness cannot
   configure the cadence and waits on fixed upper bounds instead
   (`BEACON_TIMEOUT_SECONDS=120`, `WATCHER_WAKE_TIMEOUT_SECONDS=180`). If
   M1-P5 ships flags for the base interval, tightening these is a
   one-line change and would shorten every CI run.

## Environment warnings (inherited plus new, for future phases)

1. Inherited and confirmed: local Node is v22.22.2 against the ">=26"
   floor; EBADENGINE warnings on every npm operation; floor untouched.
   Confirmed the M1-P2 warning that any `doctor` exit-0 assertion is
   floor-dependent: the exit-test harness fails at A2 on this machine for
   exactly that reason, and that is the expected local behavior, not a
   harness defect. Anything that drives `doctor` end to end needs Node 26
   or a floor gate.
2. New: a nested `node --test` inherits `NODE_TEST_CONTEXT` from the
   parent runner and silently switches to its child-of-a-runner
   protocol, printing nothing recognizable on stdout. A test that spawns
   another project's `npm test` must strip `NODE_TEST*` from the child
   environment, or it will assert against an empty string. This cost one
   confusing red where `npm test` exited 0 with no output at all.
3. New: under `set -euo pipefail`, the idiom `[ cond ] && var=value`
   aborts the whole script when the condition is false, because the list
   returns nonzero. Seven of these were written and all seven were
   converted to `if ... then ... fi`; in a harness they would have
   produced a silent early exit with no diagnostic, which is exactly the
   failure mode a harness must not have.
4. New: assembling JSON by hand in `awk` produced an invalid evidence
   file the moment a description contained a quote character. Every JSON
   the harness writes now goes through `JSON.stringify` in a `node -e`
   helper. Node is a guaranteed dependency here, so there is no reason to
   hand-roll escaping.
5. Confirmed (M1-P3 warning 17): `node -e` script arguments start at
   `process.argv[1]`, not `[2]`. The harness's JSON helpers use
   `process.argv.slice(1)`.
6. New: `shellcheck` is not installed in this environment; `bash -n` is
   the only shell lint available. If CI or a later phase adds shellcheck,
   these three scripts have not been through it.
7. New: a witness that makes a script do MORE work (rather than fail
   fast) cannot be scored by a normal test run. Witness 6 above had to be
   bounded with `--test-timeout` and paired with a direct observation of
   the exit code, because the dangerous state's signature is that the
   harness starts running the exit test instead of refusing.
8. New: the local-mode harness step adds a second `npm ci`, `npm run
   build` and `npm test` to every CI run (A1's preconditions), on top of
   the job's own three. Budget roughly two extra minutes per leg. This is
   deliberate (key decision 4) and should not be optimized away by
   teaching the harness to skip its preconditions.
