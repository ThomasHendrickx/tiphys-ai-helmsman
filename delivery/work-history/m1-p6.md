## What was built

**`sandbox/`**: the toy project. Dependency-free on purpose, so a clone
passes `npm ci` and `npm test` on a machine with only git, Node and npm
and with no registry reachable. Its README carries the exit-test log
lines the stub payload appends; that append is the whole "trivial
change" the milestone exit condition asks a task to land.

**`scripts/seed-sandbox.sh --remote <url>`**: pushes the seed content to
a git remote. Idempotent by construction: the content is copied over a
fresh checkout of the target branch and, when the resulting tree is
identical to what the branch already carries, it commits nothing, pushes
nothing, and exits 0. It handles a remote with no HEAD yet (the fresh
scratch bare repo of local mode, and a just-created sandbox repository)
by leaving the branch unborn rather than cloning an empty repository.

**`scripts/stub-payload.sh`**: the deterministic payload `tiphys spawn`
execs in the task worktree. Appends one line to the toy README, commits,
pushes the task branch, and in full mode opens the PR with `gh` and
prints its URL. It refuses to make an empty commit and refuses a working
directory that is not a git worktree, rather than reporting success on a
run that did nothing.

**`scripts/m1-exit-test.sh`**: section 4's procedure, with its staging
kept intact. Stage A (A1 to A8) and stage C (C1 to C3) are scripted;
stage B is not. Full mode runs stage A, records what the owner must do
as a `pending-owner-action` evidence record naming the exact commands,
and is re-run as `--stage c --approval <file>`. Local mode substitutes a
stub squash merge for stage B and runs everything in one invocation. The
step registry (`--list-steps`, and `step-map.json` in every evidence
bundle) names every section 4 step, its stage, and its local-mode
disposition (`both`, `local-substitute`, `full-only`).

**`.github/workflows/gates.yml`**: one step added to the existing `test`
matrix job. The `gates` fan-in job is untouched: still non-matrixed,
still `needs: test`, still failing unless `needs.test.result == success`,
so the required check context keeps both its name and its semantics and
a failing harness cannot report green.

## Key decisions and the why that is invisible in the diff

1. **Full mode is two invocations, not one.** Section 4 stages the exit
   test precisely so that the owner authorization is not a script step.
   A single-invocation full mode would have had to either block on a
   human or fake the approval. `--stage a` ends by recording what the
   owner must do; `--stage c --approval <file>` resumes from a
   `session.json` written at the end of stage A. Local mode has no human
   in it and therefore runs `--stage all`, which is the only stage value
   it accepts.

2. **The payload reports its facts to a file, not through spawn's
   stdout.** The harness needs the task branch and the payload commit.
   Reading them from `tiphys spawn`'s captured output would have assumed
   that spawn forwards the payload's stdout, which the plan does not
   state anywhere. The harness passes `TIPHYS_EXIT_TEST_REPORT` and the
   payload writes the same lines there. spawn's own output is still
   captured as evidence either way. This is the one place where the
   harness would otherwise have invented an M1-P4 contract.

3. **`doctor --for full` in local mode is a strengthened substitution,
   not a skip.** A2 requires `tiphys doctor --for full` to exit 0. The
   `full` profile promotes `gh-missing` and `remote-missing` to FAIL,
   and criterion 2 requires local mode to pass on a machine with only
   git, Node and npm, which has no `gh`. The harness therefore runs the
   command in both cases and asserts differently: with `gh` present it
   requires exit 0; with `gh` absent it requires a nonzero exit whose
   FAIL lines are exactly one and are exactly `CHECK gh FAIL`. That is a
   stronger local witness than skipping, because it proves the
   `remote-missing` promotion did NOT fire, which is the whole point of
   provisioning the fleet's throwaway `file://` remote (PR-210). The
   plan's local-mode mapping list does not cover this step; the
   substitution is recorded in the evidence like every other one.

4. **The harness runs the three kernel gates itself.** A1 says the
   preconditions include `npm ci && npm run build && npm test`. In CI
   that duplicates the three steps the job just ran. The duplication is
   deliberate: criterion 2 requires the harness to pass standalone on a
   bare machine, so it cannot rely on a caller having built anything.
   The alternative, a `--skip-preconditions` flag, is exactly the silent
   green path this phase is supposed to be free of.

5. **The falsifiability guard points at the real behavior.** With
   `TIPHYS_EXIT_TEST_SKIP_STAGE_B=1`, C1 records the missing merge as a
   `skipped-override` observation and does not fail there, so the run
   proceeds to C2 and fails where teardown correctly refuses a task
   whose branch never landed. Failing at C1 would have been easier and
   would have witnessed nothing about teardown.

6. **The harness owns the resident watcher and waits on files.** Section
   4 A5 says the harness, not the kernel, owns that process (C-3). The
   wait for the wake is file-based (the watcher's own captured stdout),
   not a process probe; the only signal the harness sends is a watchdog
   `kill` against its own child so a watcher that printed but never
   exited fails the run instead of hanging CI.

7. **The harness identity is duplicated in three scripts on purpose.**
   M1-P6's files-to-touch list contains no shared shell library and
   inventing one would have put a file outside the declared scope. The
   duplication is guarded by a test that reads all three scripts and
   fails on drift.

## The floor defect found before any criterion could be walked

`npm test` at `6ff149b` on Node 26 exited **1**: 153 tests, 152 pass,
1 fail. Captured, at `test/exit-test-local.test.ts:260`:

```
not ok 5 - a clone of the seeded sandbox passes npm ci and npm test with at least one test
  error: |-
    no pass count in npm test output:
    ...
    ok greet returns a greeting for a name (0.674488ms)
    [info] tests 2
    [info] pass 2
    [info] fail 0
```

(the two glyphs the spec reporter actually emits are a check mark and an
information sign; they are transliterated here because authored files in
this repository are pure ASCII.)

The toy sandbox was NOT broken. Its own suite passed 2 of 2 in that very
output. The harness test failed to PARSE the result, because lines 281
and 287 asserted `/^# pass (\d+)$/m` and `/^# fail 0$/m`, which is the
Node 22 default TAP reporter, and Node 26's default reporter is `spec`.

Measured, all four cells, on the pre-fix assertion and the fixed one:

| toolchain | pre-fix assertion | post-fix assertion |
|---|---|---|
| Node v22.22.2 (container default) | `ok 1`, pass 1 fail 0 | `ok 1`, pass 1 fail 0 |
| Node v26.6.0 (declared floor) | `not ok 1`, pass 0 fail 1 | `ok 1`, pass 1 fail 0 |

That table is the defect: the assertion was green only on a toolchain
BELOW the declared `>=26` floor. It is a false witness in the family
tuition T-003 names: an assertion coupled to another program's output
format, written against the format that happened to be ambient, rather
than against captured output from the toolchain the contract names.

The consequence for CI is an INFERENCE from two measurements, and is
labelled as one rather than reported as an observation: the workflow's
matrix is `node: [26]` and nothing else, and the assertion is measured
red on Node 26.6.0. Nobody has watched this test fail in GitHub Actions,
because no PR has been opened. What was measured is the local Node 26
red; that CI would reproduce it follows from the matrix, and the
orchestrator's PR observation is what would turn it into a sighting.

### The fix, and why this approach rather than the other one

Two approaches were on the table. **Chosen: pin the reporter.** The
sandbox suite is now invoked with `NODE_OPTIONS=--test-reporter=tap`
scoped to that one child, so the output format is a CONTROLLED INPUT the
test asks for rather than an ambient default it inherits.

Rejected: make the parse reporter-agnostic (accept `# pass N` or
`[info] pass N`). It would fix today's red and would not fix the defect
class. A reporter-agnostic regex is a union of the formats the test
author happens to know about on the day. Measured here: the default
already differs between the two toolchains this project runs on, which is
the whole incident, so the union is at least two wide today and there is
nothing in the test that would notice a third. The next default would
fail the test the same way, with the same misleading message ("no pass
count in npm test output") pointing at a healthy sandbox. Pinning removes
the ambient input entirely.

The property the test exists to guard is that a genuinely failing or
genuinely empty sandbox suite is detected. That was not assumed. It was
constructed, twice, on both toolchains (see the red witnesses below).

Both failure modes of the pin itself are loud, which is why it is safe.
This was CONSTRUCTED rather than reasoned about, because "the failure
mode of my safety net is loud" is exactly the coverage claim tuition
T-006 says a record may not contain without the command that produced it:

## CR-605: guarding the guard, and why not the obvious way

The reviewer's suggested fix, a registered test that runs the harness
with `TIPHYS_EXIT_TEST_SKIP_STAGE_B=1`, cannot be implemented as written.
Two reasons, both MEASURED against a real evidence bundle rather than
reasoned about, because a claim about what would happen is exactly what
T-006 forbids:

1. **Recursion.** Harness step A1 runs `npm test` with the live
   repository root as cwd (record `001-A1.json`, `003-A1.json`,
   `cwd` = the repo root). The captured output of `003-A1.out` contains
   the titles of tests defined in `test/exit-test-local.test.ts` and
   reports `tests 153`: A1 runs this very file. A test here that invoked
   the harness would be re-entered by the harness it invoked.
2. **Concurrent destruction.** A1's first step is `npm ci` in that same
   live repository root. `node --test` runs test files in parallel, so
   the nested `npm ci` would remove and reinstall `node_modules` under
   the other files of the running suite.

So the property is guarded in three places instead, at two levels:

**a. The real red path, in CI.** A new `gates.yml` step runs the harness
with the skip override and fails the job if it exits 0, then checks that
the failure landed at C2 on a nonzero teardown, so an unrelated early
abort cannot masquerade as the guard firing. This is the only place the
end-to-end red path runs automatically. It costs a second full harness
run per leg and the workflow comment says not to delete it for minutes.

**b. `exit-test-step-failure-is-fatal`** (registered, fast): a failing
step must abort the run, name the step, and leave a record with outcome
`fail`. The failure is induced from OUTSIDE the harness, by pointing it
at a repository root whose `npm ci` cannot succeed, so the test guards
the harness as shipped rather than an edited copy.

**c. `exit-test-falsifiability-guard-wired`** (registered, fast): the
workflow still contains the step, still fails the job when the harness
exits 0, and still checks the C2 record.

**Red witnesses, each against the state it is supposed to catch.**

| # | Dangerous state constructed | Result |
|---|---|---|
| W1 | `run_step` forced to score every step `pass` | `exit-test-step-failure-is-fatal` red, 0 pass 1 fail |
| W2 | the `die` on a failed step replaced by `true` | same test red, 0 pass 1 fail |
| W3 | the CI falsifiability step deleted from `gates.yml` | `exit-test-falsifiability-guard-wired` red |
| W4 | the CI step kept but defanged to `... \|\| true` | same test red |
| W7b | `run_step` AND `assert_step` both forced green | sabotaged harness exits **0** on the red path; the CI step's exit-code arm fires, and its C2-record arm independently reports `no C2 record showing a nonzero teardown exit with outcome fail` and exits 1 |

**W7, the witness that did NOT fire, recorded because a failed
construction is evidence too.** The first attempt sabotaged only
`run_step`. The harness still exited nonzero, at C2's
`the worktree is removed` assertion. That is not a weakness: it means the
harness has two independent failure paths, `run_step` and `assert_step`,
and defeating one is insufficient. W7b had to defeat both before the
regression could be reproduced at all. Had W7 been written up as "the CI
step catches an always-green harness" it would have been a coverage claim
with no construction behind it.
