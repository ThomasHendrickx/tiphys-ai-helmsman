## What was built

**`sandbox/`**: the toy project. Dependency-free on purpose, so a clone
passes `npm ci` and `npm test` on a machine with only git, Node and npm
and with no registry reachable. Its README carries the exit-test log
lines the stub payload appends; that append is the whole "trivial
change" the milestone exit condition asks a task to land.

**`scripts/seed-sandbox.sh --remote <url>`**: pushes the seed content to
a git remote. Idempotent by construction: the content is copied over a
fresh checkout of the target branch and, when the resulting tree is
identical to what the branch already carries, it commits nothing, pushes
nothing, and exits 0. It handles a remote with no HEAD yet (the fresh
scratch bare repo of local mode, and a just-created sandbox repository)
by leaving the branch unborn rather than cloning an empty repository.

**`scripts/stub-payload.sh`**: the deterministic payload `tiphys spawn`
execs in the task worktree. Appends one line to the toy README, commits,
pushes the task branch, and in full mode opens the PR with `gh` and
prints its URL. It refuses to make an empty commit and refuses a working
directory that is not a git worktree, rather than reporting success on a
run that did nothing.

**`scripts/m1-exit-test.sh`**: section 4's procedure, with its staging
kept intact. Stage A (A1 to A8) and stage C (C1 to C3) are scripted;
stage B is not. Full mode runs stage A, records what the owner must do
as a `pending-owner-action` evidence record naming the exact commands,
and is re-run as `--stage c --approval <file>`. Local mode substitutes a
stub squash merge for stage B and runs everything in one invocation. The
step registry (`--list-steps`, and `step-map.json` in every evidence
bundle) names every section 4 step, its stage, and its local-mode
disposition (`both`, `local-substitute`, `full-only`).

**`.github/workflows/gates.yml`**: one step added to the existing `test`
matrix job. The `gates` fan-in job is untouched: still non-matrixed,
still `needs: test`, still failing unless `needs.test.result == success`,
so the required check context keeps both its name and its semantics and
a failing harness cannot report green.

## Key decisions and the why that is invisible in the diff

1. **Full mode is two invocations, not one.** Section 4 stages the exit
   test precisely so that the owner authorization is not a script step.
   A single-invocation full mode would have had to either block on a
   human or fake the approval. `--stage a` ends by recording what the
   owner must do; `--stage c --approval <file>` resumes from a
   `session.json` written at the end of stage A. Local mode has no human
   in it and therefore runs `--stage all`, which is the only stage value
   it accepts.

2. **The payload reports its facts to a file, not through spawn's
   stdout.** The harness needs the task branch and the payload commit.
   Reading them from `tiphys spawn`'s captured output would have assumed
   that spawn forwards the payload's stdout, which the plan does not
   state anywhere. The harness passes `TIPHYS_EXIT_TEST_REPORT` and the
   payload writes the same lines there. spawn's own output is still
   captured as evidence either way. This is the one place where the
   harness would otherwise have invented an M1-P4 contract.

3. **`doctor --for full` in local mode is a strengthened substitution,
   not a skip.** A2 requires `tiphys doctor --for full` to exit 0. The
   `full` profile promotes `gh-missing` and `remote-missing` to FAIL,
   and criterion 2 requires local mode to pass on a machine with only
   git, Node and npm, which has no `gh`. The harness therefore runs the
   command in both cases and asserts differently: with `gh` present it
   requires exit 0; with `gh` absent it requires a nonzero exit whose
   FAIL lines are exactly one and are exactly `CHECK gh FAIL`. That is a
   stronger local witness than skipping, because it proves the
   `remote-missing` promotion did NOT fire, which is the whole point of
   provisioning the fleet's throwaway `file://` remote (PR-210). The
   plan's local-mode mapping list does not cover this step; the
   substitution is recorded in the evidence like every other one.

4. **The harness runs the three kernel gates itself.** A1 says the
   preconditions include `npm ci && npm run build && npm test`. In CI
   that duplicates the three steps the job just ran. The duplication is
   deliberate: criterion 2 requires the harness to pass standalone on a
   bare machine, so it cannot rely on a caller having built anything.
   The alternative, a `--skip-preconditions` flag, is exactly the silent
   green path this phase is supposed to be free of.

5. **The falsifiability guard points at the real behavior.** With
   `TIPHYS_EXIT_TEST_SKIP_STAGE_B=1`, C1 records the missing merge as a
   `skipped-override` observation and does not fail there, so the run
   proceeds to C2 and fails where teardown correctly refuses a task
   whose branch never landed. Failing at C1 would have been easier and
   would have witnessed nothing about teardown.

6. **The harness owns the resident watcher and waits on files.** Section
   4 A5 says the harness, not the kernel, owns that process (C-3). The
   wait for the wake is file-based (the watcher's own captured stdout),
   not a process probe; the only signal the harness sends is a watchdog
   `kill` against its own child so a watcher that printed but never
   exited fails the run instead of hanging CI.

7. **The harness identity is duplicated in three scripts on purpose.**
   M1-P6's files-to-touch list contains no shared shell library and
   inventing one would have put a file outside the declared scope. The
   duplication is guarded by a test that reads all three scripts and
   fails on drift.

## The floor defect found before any criterion could be walked

`npm test` at `6ff149b` on Node 26 exited **1**: 153 tests, 152 pass,
1 fail. Captured, at `test/exit-test-local.test.ts:260`:

```
not ok 5 - a clone of the seeded sandbox passes npm ci and npm test with at least one test
  error: |-
    no pass count in npm test output:
    ...
    ok greet returns a greeting for a name (0.674488ms)
    [info] tests 2
    [info] pass 2
    [info] fail 0
```

(the two glyphs the spec reporter actually emits are a check mark and an
information sign; they are transliterated here because authored files in
this repository are pure ASCII.)

The toy sandbox was NOT broken. Its own suite passed 2 of 2 in that very
output. The harness test failed to PARSE the result, because lines 281
and 287 asserted `/^# pass (\d+)$/m` and `/^# fail 0$/m`, which is the
Node 22 default TAP reporter, and Node 26's default reporter is `spec`.

Measured, all four cells, on the pre-fix assertion and the fixed one:

| toolchain | pre-fix assertion | post-fix assertion |
|---|---|---|
| Node v22.22.2 (container default) | `ok 1`, pass 1 fail 0 | `ok 1`, pass 1 fail 0 |
| Node v26.6.0 (declared floor) | `not ok 1`, pass 0 fail 1 | `ok 1`, pass 1 fail 0 |

That table is the defect: the assertion was green only on a toolchain
BELOW the declared `>=26` floor. It is a false witness in the family
tuition T-003 names: an assertion coupled to another program's output
format, written against the format that happened to be ambient, rather
than against captured output from the toolchain the contract names.

The consequence for CI is an INFERENCE from two measurements, and is
labelled as one rather than reported as an observation: the workflow's
matrix is `node: [26]` and nothing else, and the assertion is measured
red on Node 26.6.0. Nobody has watched this test fail in GitHub Actions,
because no PR has been opened. What was measured is the local Node 26
red; that CI would reproduce it follows from the matrix, and the
orchestrator's PR observation is what would turn it into a sighting.

### The fix, and why this approach rather than the other one

Two approaches were on the table. **Chosen: pin the reporter.** The
sandbox suite is now invoked with `NODE_OPTIONS=--test-reporter=tap`
scoped to that one child, so the output format is a CONTROLLED INPUT the
test asks for rather than an ambient default it inherits.

Rejected: make the parse reporter-agnostic (accept `# pass N` or
`[info] pass N`). It would fix today's red and would not fix the defect
class. A reporter-agnostic regex is a union of the formats the test
author happens to know about on the day. Measured here: the default
already differs between the two toolchains this project runs on, which is
the whole incident, so the union is at least two wide today and there is
nothing in the test that would notice a third. The next default would
fail the test the same way, with the same misleading message ("no pass
count in npm test output") pointing at a healthy sandbox. Pinning removes
the ambient input entirely.

The property the test exists to guard is that a genuinely failing or
genuinely empty sandbox suite is detected. That was not assumed. It was
constructed, twice, on both toolchains (see the red witnesses below).

Both failure modes of the pin itself are loud, which is why it is safe.
This was CONSTRUCTED rather than reasoned about, because "the failure
mode of my safety net is loud" is exactly the coverage claim tuition
T-006 says a record may not contain without the command that produced it:

## CR-605: guarding the guard, and why not the obvious way

The reviewer's suggested fix, a registered test that runs the harness

at a repository root whose `npm ci` cannot succeed, so the test guards
the harness as shipped rather than an edited copy.

## CR-681: what the class is, and what closes it

I named `continue-on-error` and treated it as the class. It was one
member. This is the third time in this milestone that an instance was
closed and the mechanism left open, so the answer is not two more
assertions.

**The class:** an edit to `gates.yml` that leaves the step's `run:`
script intact and extractable, so every behavioural probe still passes,
yet stops the step's failure from failing the required check.

A step's failure reaches that check only if EVERY link holds, so the
class is exactly "break any one link without touching the script":

1. the workflow runs on the event that gates a pull request
2. the step executes (no step-level `if:`)
3. its failure fails the step (no step-level `continue-on-error:`)
4. that fails the job (no job-level `if:` / `continue-on-error:`)
5. the job's result is consumed (the `gates` fan-in needs it)

**Behavioural versus structural, enumerated rather than implied.** The
executed probes witness link 3's shell half by running the script. NO
exit code from that script can witness links 1, 2, 4 or 5, because those
are properties of the YAML around it. Those four are asserted
structurally. That is a claim about the whole YAML class, which is the
correction asked for; last round I made the same claim about one key.

**Links 2, 3 and 4 use a WHITELIST, not a denylist.** The step must
declare exactly `name` and `run`; the `test` job exactly `runs-on`,
`strategy`, `steps`. A denylist needs re-extending every time someone
finds another key. A whitelist fails on a key nobody thought of, which is
what closing a class means rather than enumerating members.

## The shape chosen, and why not the other two

Three shapes were available. I am recording the two I rejected, with the
reason, because the next person to look at this will reach for one of
them.

**Rejected: extend the whitelist and add the three missing nodes.** This
is what rounds 2 and 3 did and it is what produced CR-720 to CR-724. It
also cannot fix CR-724 at all: a whitelist's whole mechanism is refusing
keys nobody enumerated, and "keys nobody enumerated" is where the
legitimate edits live too. There is no length of whitelist at which
`permissions:` is allowed and an unknown neutralising key is not.

**Rejected: parse the YAML properly.** This project takes no
dependencies, so it would mean writing a YAML parser inside a test file,
whose failure mode is exactly CR-722 one level up: a hand-rolled parser
silently mis-reads a shape it does not know. And it would not help,
because a correct parse still leaves the question "which parsed keys
change GitHub's evaluation", which is the part that was actually wrong.

**Chosen: state the boundary and enforce inside it.** Three tiers, each
labelled in the test by what enforces it, and an honest residual.

- **TIER 1, BEHAVIOUR.** Unchanged from round 2 and still the only tier
  that measures meaning: the step's `run:` script is extracted and
  EXECUTED against five stub harnesses. One assertion added (below).
- **TIER 2, PINNED STRUCTURE.** The guard step exists exactly once, is
  INSIDE the `test` job, the `gates` fan-in NAMES that job, and the
  `pull_request:` trigger is unfiltered. The reader that establishes
  these PINS the shapes it accepts and FAILS LOUDLY on anything else.
  That is not a new idea here: `MECHANISMS.md` already carries "PIN the
  format as a controlled input rather than widening the parse", paid for
  by this same phase's floor defect. Pinning is what closes CR-722,
  because a quoted key is no longer invisible, it is either recognised
  or it reddens the test with the line quoted.
- **TIER 3, A DERIVED DENYLIST.** Refused keys, and why a denylist is
  defensible here when round 3 argued it never is.

### Why a denylist, when round 3 argued for a whitelist

Round 3's sentence was: *"a whitelist fails on any key nobody thought of,
which is the only shape that closes a class instead of enumerating
members."* It is a good argument and it is wrong here, for a reason that
is measurable rather than rhetorical: the whitelist did not close the
class (CR-720, CR-721, CR-722 all walked past it) and it did reject four
legitimate edits (CR-724). It paid the whitelist's cost and did not
collect the whitelist's benefit.

The benefit was not collected, and CR-720, CR-721 and CR-722 are three
measured reasons why: a whitelist closes a class only when the property
is "nothing else may be here on the nodes I inspect", and that is not the
property. The property is "nothing here may decouple a failing guard from
a failing required check", and most keys cannot do that.

What makes a denylist defensible here specifically: **GitHub's workflow
syntax is a CLOSED, DOCUMENTED vocabulary.** So the enumeration is
finite and can be walked once. I walked it. Every documented step key and
every documented job key, each asked one question:

**Step keys** (`jobs.<id>.steps[*]`):

| Key | Can it decouple a failing guard from a failing check? |
|---|---|
| `if` | YES, the step does not run. **REFUSED** |
| `continue-on-error` | YES, the failure does not fail the step. **REFUSED** |
| `working-directory` | YES, differently: the step runs against another tree, so it can certify a harness that is not this repository's. **REFUSED** |
| `shell` | YES, if it is a custom command TEMPLATE (`bash -c "exit 0" {0}`), which decides whether the script runs at all. **REFUSED in template form only**, see below |
| `run` | it IS the script; tier 1 executes it |
| `uses` | mutually exclusive with `run`; the workflow does not validate, so not a green defang |
| `id`, `name`, `env`, `with`, `timeout-minutes` | no. A timeout makes the step FAIL, which is the safe direction |

**Job keys** (`jobs.<id>`):

| Key | Can it decouple? |
|---|---|
| `if` | YES, the job is skipped. **REFUSED on `test`**; on `gates` it is pinned to `always()` instead, since `always()` is documented as what makes the fan-in run after a failed job (documented, not measured here: see "did NOT cover" item 5) |
| `continue-on-error` | YES. **REFUSED on both** |
| `defaults` | YES, via `defaults.run.shell`, the same hole one level up. Covered by the file-wide shell rule |
| `uses` (reusable workflow) | it replaces `steps:` entirely, so the guard step ceases to exist and the step scan reddens |
| `strategy` | no. `fail-fast: false` still fails the job when a leg fails |
| `needs`, `runs-on`, `name`, `permissions`, `env`, `outputs`, `concurrency`, `environment`, `timeout-minutes`, `container`, `services`, `with`, `secrets` | no |

`shell` is asserted once over EVERY `shell:` in the file at any indent,
rather than three times, because the same key sits at the step, at a
job's `defaults.run` and at the workflow's `defaults.run`, and a rule
attached to two nodes is how CR-720 and CR-721 happened. The assertion
refuses only a value containing `{0}`, the placeholder Actions
substitutes the script path into, so a plain `shell: bash` stays green.

**Two of those four refused keys were not in the review.**
`working-directory` and the `shell` template came out of walking the
vocabulary, not out of CR-720 to CR-725. That is the difference between
answering a review and closing a mechanism, and it is the thing rounds 2
and 3 did not do.

## What REMAINS UNGUARDED, and what enforces it instead

This is the part rounds 2 and 3 got wrong, twice, and it is the reason
this section is here rather than a claim that the class is closed. **The
class is NOT closed. It is BOUNDED, and here is the bound.**

**R1. Which check branch protection REQUIRES.** Not readable from the
tree. It is GitHub repository configuration, DR-0004's territory, and it
is already active on this repository. If `gates` is dropped from the
required set, every assertion in this file still passes and no pull
request is gated by anything. *Enforced by:* the branch-protection
settings themselves, and by whatever process changes them.

**R2. The test file itself.** Every assertion described above can be
deleted in one commit. Adding a layer that guards this file only moves
the regress. *Enforced by:* the pull-request diff and the scope audit. I
did not add a guard-on-guard-on-guard and I do not think one should be
added.

**R3. A neutralising key outside the four refused.** The denylist rests
on the vocabulary walk two sections up. That walk is over GitHub's
DOCUMENTED workflow syntax and was not measured on a runner. If Actions
grows a key with this power, or has one that is undocumented, this test
does not see it. *Enforced by:* nothing in the tree. This is the honest
cost of choosing a denylist, and it is the cost I chose over CR-724.

**R4. Actions' `needs` semantics.** Tier 2 asserts the fan-in NAMES the
job the guard is in. That naming it means consuming its result, and that
`needs.test.result` reports `failure` when a step in it failed, are read

**R5. `runs-on`, and the runner itself.** A self-hosted or substituted

**R6. `working-directory` at the JOB's `defaults.run`.** Refused at the

## An environment observation, recorded because it cost me a stage A

My first full-mode stage A failed at A1 "seeded project npm ci" with
`npm error code EUSAGE ... can only install with an existing
package-lock.json`, and the seeded project DOES carry one
(`git ls-files sandbox/` lists `sandbox/package-lock.json`). The cause
was my own scratch remote: `git init --bare` under git 2.43 writes
`ref: refs/heads/master` into `HEAD`, the seeder pushed `main`, and
`git clone` of a remote whose `HEAD` names an unborn branch produces a
worktree containing only `.git`. Fixed with
`git init --bare --initial-branch=main`.

Worth writing down for two reasons. The harness's diagnosis pointed at
`npm ci` when the fact was an empty clone six steps earlier; and a
GitHub-hosted remote advertises a default branch, so I do not expect this
state there, though I did not verify the sandbox repository's `HEAD` and
did not reference it at all. I did NOT change the harness for it: it is outside this round's
findings, it is not reachable through the documented path, and adding an
unrequested check in a fourth fix round is how rounds get longer.
