## What this phase is, and the one thing it deliberately does not do

The hazard the plan names is **a credential reaches a project payload and no
artifact says so**. The answer is not a wider allowlist, and this phase builds
no part of one: `DEFAULT_CHILD_ENV_ALLOWLIST` gains no name and is
byte-identical to its merge-base form. What is built is the ROUTE around it:
who may ask for the escape hatch, what a per-invocation widening costs, what a
widening leaves behind for a reader, and how a widening applied AFTER the
kernel handed the environment over is detected.

## The decisions that are invisible in the diff

### Step 4's question: import the vocabulary, do not move it

The plan offers two shapes and requires the choice be recorded. **The
vocabulary stays in src/gates/credentials.ts and `src/exec/env.ts` imports
it.** `GH_TOKEN_VARIABLES`, `DANGEROUS_ENV_VOCABULARY` and
`isDangerousEnvName` were already exported, so the gate module's only change is
a comment saying who else reads them now. A copy was never an option: two lists
drift, and they drift toward the permissive side.

That import makes the two modules a cycle. Before choosing it, the existing
graph was measured rather than assumed:

```
$ node -e '<walk every relative import under src/, report cycles>'
cycles: 13
cli.ts -> commands/doctor.ts -> cli.ts
...
spawn.ts -> adapters/load.ts -> spawn.ts
```

Thirteen cycles already, one of them inside the spawn path itself. So this is
the repository's existing shape rather than a new hazard class. The rule the
cycle DOES impose is real and is now mechanical rather than remembered: nothing
in `src/exec/env.ts` may read an imported binding at module-evaluation time.
The eighth test imports the two modules in both orders, in a fresh child per
order, and the mutation that breaks the rule is captured below.

### `meta.json` has no schema, and this phase does not give it one

The plan asks this be verified in step 1 rather than assumed. Measured:

```
$ ls schemas/ | wc -l
17
$ grep -rln 'meta.json\|task-meta\|taskMeta' schemas/ ; echo "exit=$?"
exit=1
```

`schemas/executor-record.schema.json` exists and covers `executor.json`, a
different document. `meta.json` is validated by nothing, and the plan says in
terms not to create a schema in this phase. Recorded, not fixed.

**That absence had one design consequence.** The adapter's report of what it
launched with is carried on the `LaunchOutcome` return value and NOT on
`ExecutorRecord`, because `executor.json` has a shipped schema with
schemas/executor-record.schema.json:7 set to `false` for additional
properties, and that schema is not this phase's to edit.

### The step-5 refusal cannot appear in `meta.json`, and the record says so

Step 6 asks that the refusal be recorded in `meta.json` "if one fired". Step 5
asks that the escape-hatch refusal happen "before the worktree is touched".
Those two cannot both be satisfied for the SAME refusal: a spawn refused before
pool create has no task directory, so there is no `meta.json` to write into,
and creating one would undo the property that a refused spawn creates nothing.

The resolution, stated in the type rather than left implicit: the recorded
`refusal` field is for refusals that fire AFTER the record exists, which is the
criterion-6 handover refusal. The step-5 refusal's artifact is its reason line
plus the measurable absence of a task directory and a worktree, which is what
the first test asserts.

### `handover` is absent until the launch has reported

`meta.json` is written BEFORE the payload starts, which is what makes a failure
to write it safe to roll back. At that moment no adapter has launched anything,
so `handover` is optional and its absence is a fact rather than an omission,
the same reason `ExecutorRecord` carries no resolved model.

## What this phase did NOT cover

A reviewer's first check, and this section is written to be checked rather than
believed.

1. **The boundary is still environment-only, and the environment is not the
   boundary.** The M4 probes measured that the real credential boundary here is
   the uid and the filesystem: a scrubbed child runs at the same uid and keeps
   READ access to an absolute credential path outside `$HOME`. Nothing in this
   phase changes that, and the step-1 probe reproduces it: the scrubbed child
   authenticated to the model with ten variables. **No evidence in this phase
   should be read as saying a project payload cannot reach a credential.** It
   says the ENVIRONMENT route is audited.
2. **The `credential-scrub` gate's inverted verdict is NOT fixed here.** Probe
   item 2 recorded that the gate greens `HTTPS_PROXY`, which grants real GitHub
   reach, and reddens `GIT_CONFIG_*`, which grants only URL rewriting. This
   phase measured the same thing from the other side (arm B took `HTTPS_PROXY`
   through the audited route and got HTTP 200, and the gate stayed green), and
   deliberately did not change it: the brief makes `src/gates/credentials.ts`
   edit-to-export-only, and a new gate arm would be an escalation rather than a
   quiet registry edit. Recorded as an open item for whoever owns that defect.
3. **A dishonest adapter is not caught by the kernel.** Criterion 6 compares
   what the adapter REPORTS. An adapter that widens the environment and reports
   the kernel's set passes that comparison, by construction, and the
   criterion-5 test carries exactly such an adapter to prove it. The
   child-written probe is what settles it, and that probe is a TEST payload, not
   something the kernel runs on every spawn. A kernel that verified every launch
   from inside the child is a different design and is not in this plan section.
4. **No witness spec was added under `witness/`.** That directory is not on this
   phase's files-to-touch list. The `red-witness` gate is green and selected 15
   stored specs against this diff, so the coverage rule is satisfied by existing
   specs; the red witnesses for the new behaviour are the captures above, each
   reproducible from an isolated worktree.
5. **`meta.json` is still unvalidated.** The new `credentials` record has a
   TypeScript shape and no schema, so a hand-edited or foreign-written
   `meta.json` can carry any credentials block it likes and `readTaskMeta` will
   accept it. `readTaskMeta` deliberately does not require the field, so an
   older record still reads; the cost is that a consumer cannot rely on its
   presence. Giving the document a schema is explicitly out of scope per the
   plan.
6. **The name list is one container, one day.** See the caveat under step 1.
   Nothing was measured on a second runner, and the probe could not distinguish
   "this list is the general answer" from "this list is what this proxy
   requires".
7. **`extraAllowlist` has no CLI surface.** It is reachable only from the
   library seam, which is where the plugin sits. That is deliberate for this
   phase (the CLI would need a flag whose reason argument an operator would
   type, and a typed reason is not an audited one), and it means the arms in
   step 1 were driven through `spawnTask` directly rather than through
   `tiphys spawn`.
8. **The bare-string extension form still accepts an entry with no reason.** It
   is refused for a dangerous NAME exactly as the object form is, so the safety
   half is whole, but a bare string carries no reason and nothing demands one of
   it. It survives because the kernel's own tests model a widened allowlist with
   that shape and that file is not this phase's to edit. The audited route
   cannot produce one: `SpawnOptions.extraAllowlist` is typed to the object form
   and a string does not typecheck there.
9. **Not measured on macOS or on the Node floor's lower bound.** Everything
   above is node v26.6.0 on Linux in this container.
