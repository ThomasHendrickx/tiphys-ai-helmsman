## What this phase had to make true

Two facts, measured in the plan's grounding and re-measured here, are one
phase because either alone delivers nothing:

- `tiphys spawn` could reach exactly ONE adapter. `grep -rn '"--adapter"' src/
  bin/` exited 1 on `main`, and the only callers that ever passed an adapter
  were tests.
- `@tiphys/kernel` published no `main`, no `exports`, no `types` and had no
  `src/index.ts`, so a separately published plugin could not import
  `ExecutorAdapter` at all.

A flag with no importable type, or a type nothing can select, is not half a
seam; it is no seam. M4-D-03 recommends exactly this shape
(delivery/plan/m4-intake.md:743).

## The property that made it more than a flag

Loading an adapter EXECUTES THIRD-PARTY CODE inside the orchestrator process,
which is the process holding delegated merge authority under DR-0012.
DR-0029 Part 2c's untrusted-project-content boundary does not exist and
M4-D-23 recommends it is not built in M4, so the only mitigation available is
the RESOLUTION ROOT:

- the FLEET HOME is owner-controlled and already pins `@tiphys/kernel`
  exactly;
- the PROJECT CLONE is the thing under review and may carry anything a
  contributor pushed, `node_modules/` included.

So resolution is rooted at `<fleet home>/package.json` with
`createRequire`, at src/adapters/load.ts:188, and nothing in the loader ever
consults the project clone, the kernel's own checkout, or `process.cwd()`.

## Decisions taken here, with the reasoning that is invisible in the diff

**D-M4P4-1. The fleet-home field is `tiphys.adapter`.** The plan says "a
fleet-home `package.json` field" and does not name it. The kernel's own
`package.json` already namespaces its configuration under a `tiphys` object,
so a fleet home carrying kernel configuration uses the same namespace rather
than inventing a second convention. `src/commands/init.ts` is NOT on this
phase's files-to-touch list and was not edited, so `tiphys init` does not
write the field; its absence is the built-in default, which is criterion 6's
first arm.

**D-M4P4-2. Precedence is flag, then fleet-home field, then built-in.** A
flag is a per-spawn instruction and a fleet-home field is a standing one, so
the narrower statement wins. The opposite order would make `--adapter`
unusable on any fleet that declared a default.

**D-M4P4-3. A directly supplied `options.adapter` object short-circuits the
whole selection, including the fleet-home read.** The kernel's own tests hand
an object across this seam. Without the short-circuit, a test fleet that
happened to declare a default would silently change which adapter those tests
exercised.

**D-M4P4-4. `BUILT_IN_ADAPTER_NAME` lives in `src/adapters/load.ts`, not in
`src/spawn.ts`.** The runtime import edge then runs ONE way: `src/spawn.ts`
imports the value, and the loader imports only a TYPE back, which is erased. A
value-level cycle between the launch module and the loader would evaluate one
inside the other's temporal dead zone the first time an import order changed,
and nothing in the suite would predict that.

**D-M4P4-5. A fourth shape check the criterion does not name: `name` must be a
non-empty string.** Criterion 4 names three shapes and criterion 5 refuses one
particular NAME. A loaded adapter with no name would write `undefined` into
the launch record's `adapter` field, which defeats criterion 5 entirely: a
guard on the VALUE of a field that may be absent cannot go red for the absent
case. Declared here rather than smuggled in.

**D-M4P4-6. The entry point publishes two VALUES as well as the four types.**
`requirableRequestFields` and `BUILT_IN_ADAPTER_NAME` (src/index.ts:37). An
adapter author has to answer two questions that types cannot answer at
runtime: which names may legally appear in `requires`, and which name is
reserved. Publishing the answers is cheaper than publishing a document that
drifts from them. It is also what makes `src/index.ts` observable at all from
a test: a file of pure `export type` compiles to an empty module, so a witness
member mutating it could not redden anything.

**D-M4P4-7. The `exports` map has no wildcard and an explicit
`"./package.json"` entry.** Measured refusals are in "Criterion 8" below.

## The release question, NOT decided here

Adding `exports` is a public API commitment. The plan says this phase must not
decide the release alone and recommends ONE 0.2.0 cut after the last kernel
API phase of workstreams 1 and 2, with this phase landing the `exports` map
unreleased. Nothing here bumps `version`, which stays `0.1.0`. Recorded as an
open question for the orchestrator rather than settled.

## WHAT THIS PHASE DID NOT COVER

A reviewer's first check. Each item is a region deliberately outside this
work, not a region searched and found empty.

1. **The loader's own supply chain.** A legitimate fleet-home adapter that is
   later compromised is not defended against by anything here. This phase
   MOVES the trust boundary to the fleet home; it does not defend inside it.
   That is M4-D-23's residue, and the plan's own hazard table records it as
   having NO criterion.
2. **The resolved module is imported directly.** `loadAdapter` hands the
   resolved path to `import()` without classifying the file first, so the
   FIFO discipline applied to the fleet-home `package.json` is not applied to
   the adapter's own entry file. An irregular file at a resolved module path
   inside the fleet home is unmeasured here. It is inside the boundary this
   phase draws, which is why it was not treated as blocking, and it is stated
   rather than left to be discovered.
3. **Resolution walks UP from the fleet home.** `createRequire` performs
   ordinary Node resolution, so `<fleet>/node_modules`, then the fleet home's
   PARENT directories, are searched. In the fixtures the project clone is
   below the fleet home, so no upward walk from the fleet home reached it in
   any fixture used here, which is what the tests assert. A fleet home whose
   PARENT carries a `node_modules` is not exercised by any test here, and I
   did not find a way to reach the project clone from the fleet home by that
   walk in this layout; whether some other layout allows it is open.
4. **An absolute or relative `--adapter` specifier.** `--adapter
   /abs/path.js` or `--adapter ./x.js` resolves against the fleet home (a
   relative one) or to itself (an absolute one), which escapes the fleet home
   by the operator's own instruction. No test covers either form, and the
   loader does not refuse them. Whether an absolute specifier should be
   refused is a design question this phase did not settle; the flag is
   operator input at the same authority level as the command itself.
5. **The `require` condition.** `require.resolve` applies an `exports` map
   under the `require` condition, so a package offering ONLY an `import`
   condition does not resolve here. Measured on node v26.6.0, 2026-09-17:
   `ERR_PACKAGE_PATH_NOT_EXPORTED`. `import.meta.resolve(specifier, parent)`
   was measured as an alternative and SILENTLY IGNORES its second argument
   without `--experimental-import-meta-resolve`, resolving from the caller's
   file instead, which is the opposite of what this phase needs. The refusal
   message names the limitation. It constrains M4-P5's packaging and is raised
   with the orchestrator rather than decided here.
6. **No adapter is shipped.** This phase builds selection and the seam. The
