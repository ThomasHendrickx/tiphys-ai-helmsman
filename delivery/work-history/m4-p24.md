## The design decisions that are invisible in the diff

### The exit code is three-valued, and `unknown` sits on the work side

Criterion 1 asks for exit 3 while any in-flight item exists and 0 only when every
category is empty. The third state this command can be in is neither: a category
it FAILED TO READ. That state is counted as work remaining, not as empty, and the
reason is the tuition this phase was told to read first.

delivery/tuition/T-036-the-stop-condition-reported-a-finished-milestone.md:1
records a stop condition that printed `24/24 phases merged` while six phases had
not been started, because a source it could not see contributed zero. So
`exitCodeFor` at src/commands/next.ts:411 sums the in-flight items AND the
unreadable categories, and `nextAction` at src/commands/next.ts:362 puts
`MEASURE` first, ahead of every real item.

### The T-036 question, asked of every category, and the answer is uncomfortable

The brief asks: for every category counted, does its source exist before the work
starts, or only after? Measured against this command's three categories:

| category | source | exists from |
|---|---|---|
| task | `tasks/<id>/meta.json` with status `open` | the dispatch that wrote the record |
| worktree | a pool record, or an open task with none beside it | pool create |
| branch | a ref in a project clone | branch create |

**All three are traces that work leaves BEHIND.** A fleet home carries no
artifact that names work before anyone starts it: `backlog.md` exists in the
layout (src/fleet.ts:22) and has no defined item grammar, so inventing one here
would be improvising a format the plan is silent on.

This is not fixable inside this phase and it is therefore REPORTED. The fourth
entry of `CANNOT_SEE` at src/commands/next.ts:74 says in the command's own output
that an empty report cannot tell "nothing left to do" from "nothing started". The
shape T-036 names is a DENOMINATOR that grows; this command prints no fraction at
all, which removes the specific false green T-036 measured and does not remove the
general limit.

### The delivered-elsewhere predicate is three arms, and two of them are load bearing

`git branch --merged` is the naive implementation and delivery/STATE.md:54 names
it as a stop condition that cannot go green. Measured on a repository built to
the plan's own shape (witness/captures/next-delivered-elsewhere-git.txt, git
2.43.0):

```
$ git branch --merged main
  feat-c
* main
```

Member A (`feat-a`, squash-merged) and member B (`feat-b`, whose only commit
landed inside `feat-c`'s pull request) are BOTH absent from that list. The same
capture records how each arm answers:

| branch | `--is-ancestor` | `merge-tree --write-tree` | `cherry` | verdict |
|---|---|---|---|---|
| feat-a | exit 1 | main's own tree | `+`, `+` | delivered, by CONTENT |
| feat-b | exit 1 | exit 1, add/add conflict | `-` | delivered, by PATCH ID |
| feat-open | exit 1 | a different tree | `+` | open |

**Neither arm subsumes the other, and the capture is what settles it.** A squash
collapses N commits into one whose patch id equals the COMBINED diff, so
`git cherry` sees `+` for every individual commit of `feat-a` and answers open.
And once `main` edits the same region again after a branch's commit has landed
through somebody else's pull request, the three-way merge of that branch
CONFLICTS, so the content arm answers open for `feat-b` while its patch is
demonstrably upstream.

Arms 1 and 2 are not reimplemented: `deliveredElsewhere` at
src/commands/next.ts:151 calls `landedness` at src/teardown.ts:123, which is the
predicate `tiphys teardown` already refuses on. Arm 3 is the new one.

### A project directory that is not its own repository, found by the test

This was a defect in the first version of this command, found when the
criterion-1 test for an unreadable category reported `unknown: 0` and exit 0.

A fleet home IS a git repository. So `git -C projects/foo rev-parse --verify
refs/heads/main` inside a directory that is not a clone resolves against the
FLEET's repository: the base ref verifies, the branch walk lists the fleet's own
branches, and a project nobody could read reports nothing in flight. That is the
T-036 mechanism with a different source.

src/commands/next.ts:307 now requires the directory to be the top level of its
own git work tree, compared with `pathsIdentifySameObject` because git
canonicalises the path it prints. It is member 1 of the
`next-unreadable-category-is-not-empty` witness, so the defect stays closed.

### Where the pull-request capability's decisions live, and why

`plugin/src/pr.ts` spawns nothing. Every arm that can refuse is a pure function
over a supplied environment and an argv; `plugin/src/pr-main.ts` is the only file
that owns a child process. The reason is measurable rather than stylistic: `gh` is
absent from this container by default (CLAUDE.md standing warning 6), and a
refusal arm exercisable only where the tool is installed is a refusal arm nobody
exercises.

The credential is READ from a supplied environment and never written into
`process.env`. The convenient alternative, assigning the token into the ambient
environment so a child inherits it, is the exact defect criterion 5 forbids,
because the kernel's adapter launches payloads out of that same process.

## What this phase did NOT cover

A reviewer's first check. Every item here is a limit of what was measured, not a
list of things left to do later.

1. **`gh` is never invoked by any test, so the credential-PRESENT arm of
   `pr open` and `pr merge` is unexercised.** Both commands build an argv and hand
   it to an injected executor; the shipped executor in
   plugin/src/pr-main.ts:1 calls `spawnSync("gh", ...)`. That call has not been
   run anywhere. What IS asserted is the refusal arm, the argv builders, and the
   environment handed to the child. Whether `gh pr create` and `gh pr merge`
   accept the argv this builds is an open question here, and the plan's own
   boundary means no test in this repository may answer it by opening a real pull
   request.
2. **"The network is unreachable" is a git reachability distinction, not a
   severed interface.** The reachable arm of the criterion-4 test is a bare
   repository on local disk, because nothing in this container answers an
   outbound git URL. The unreachable arms are a remote path that does not exist
   and a TCP endpoint that refuses the connection. A third shape, a remote that
   accepts the connection and then hangs, is NOT covered, and it is the shape a
   proxy failure most often takes here.
3. **The branch category reads LOCAL branches only.** `refs/remotes/*` is not
   walked. A phase branch that exists only on the remote is invisible to this
   command, which matters because that is the normal state after a clone. The
   cannot-see list does not name this, and naming it would be an improvement a
   later round could make.
4. **The exit code does not distinguish how much work remains.** Exit 3 is the
   same for one stale worktree and for twenty undelivered branches. That is the
   criterion as written, and a caller wanting the count parses the report.
5. **Nothing here retires `.claude/orchestrator-next.mjs`.** The script is
   untouched and still runs. Criterion 2 says the script is being retired; this
   phase builds its kernel destination, and removing the harness script is the
   cutover, which this phase does not perform.
6. **The delivered-elsewhere predicate is not tested against a repository whose
   base ref has been force-pushed or rewritten.** Every scenario is
   append-only history. A rebased base could make the patch-id arm answer
   `delivered` for a branch whose content is no longer on the base.
7. **The retirement inventory rows this phase moved to PORTED are a
   classification, and a classification is a judgment.** Three of nine rows moved;
   six kept their absence claim with a widened block. The six reads are argued in
   the JSON and a reviewer who disagrees with any of them is disagreeing with a
   sentence, not with a measurement.
8. **`poolList` and the open-task walk overlap.** An open task with no pool
   record beside it appears in both categories, so the in-flight COUNT is not a
   count of distinct work items. The report names each item with its category, so
   nothing is hidden, and no assertion anywhere depends on the total.
9. **The criterion-6 grep reads `src/` and `bin/` only.** `scripts/`, `.github/`
   and `.claude/` are not walked, so a harness script naming the plugin's
   commands would not be caught by it. The criterion names those two trees and
   this is a statement of what that means, not a complaint about it.

## Acceptance criteria, walked

### Criterion 1: one next action, exit 3 while anything is in flight, 0 only when empty

Guarded by "next exits 3 while an in-flight item exists and 0 only when every
category is empty" and "next prints exactly one next action line in every state".

The empty fleet exits 0 and reports `in flight: 0` and `unknown: 0`. One open
task record makes it exit 3. Outside a fleet home the same binary exits 1 with
`not a fleet home` on stderr, which is the assertion that makes the three codes
distinct rather than merely declared distinct.

Witness `next-one-next-action-line`, two members: a second `next action:` line
pushed by the renderer, and a `next action:` smuggled inside the empty-state
reason string. The second is structurally different because it produces two lines
from ONE push, which a renderer-side check would miss.

### Criterion 3: the delivered-elsewhere predicate, two structurally different members

The captures are in the red-witness section below. The premise is measured
INSIDE each test before the predicate is exercised: the recorded
`git branch --merged` block is parsed out of
witness/captures/next-delivered-elsewhere-git.txt, the freshly built repository
is required to reproduce it, and the test asserts that the member's branch is not
in it. If a future git ever reported a squash-merged branch as merged, these
tests would say so rather than quietly asserting something about a state that no
longer exists.

Member B's test additionally asserts that `git merge-tree --write-tree` EXITS 1
for it, which is what makes it structurally different from member A rather than a
second instance of the same thing.

The control is its own test: `feat-open` is reported open, and `tiphys next`
names it while naming neither delivered branch. Without it, a predicate that
answered `delivered` for everything would pass both member tests.

Guarded by "next prints the whole cannot-see block and the same exit code when

### Criterion 5: the plugin refuses without a credential, and the kernel process never gets one

Guarded by "pr open and pr merge each exit nonzero with exactly one line when the
credential is absent" and "the pull-request credential never reaches a kernel
adapter child, probed from inside the child".

The refusal test asserts exit 65, exactly one stderr line, and an empty stdout,
and then requires the live run to reproduce
witness/captures/pr-refuses-without-credential.txt byte for byte on both streams
and on the exit code. The capture is a real run of both subcommands with every
credential name removed from the environment.

The boundary test is the one that matters and its ORDER is the assertion. The
child-written probe runs FIRST, through `claudeCodeAdapter.launch` on
scripts/credential-witness.mjs, on two arms: `inherited`, a launch with no env
option at all, which is Node's full-inheritance form; and `scrubbed`, the
environment the kernel's own `buildChildEnv` returns. The in-process read of
`process.env` follows as a second and weaker statement.

**Two defects in this phase's own test were found by that reordering, and both
are recorded because neither would have been visible from reading it.** The first
is the order itself: with the in-process read first, the mutant reddened on a
statement made in the parent and the child-written file was decorative. The
second is worse. The helper that removes the credential names for the duration
was written synchronously:

```
  try {
    return body();
  } finally {
    restore();
  }
```

With an async body that restores at the body's FIRST SUSPENSION POINT, not at its
end. Half the arms therefore ran with the ambient environment back in place and
passed anyway, because `claudeCodeAdapter.launch` happens to spawn synchronously
before it ever suspends. A guard that holds by the callee's internal scheduling
rather than by its own construction is green and worthless. The helper is now
`async` and awaits the body; the green control below was taken in a process where
`GH_TOKEN` is genuinely set, so it is a measurement rather than a tautology.

### Criterion 6: no kernel code path invokes either command

Guarded by "no kernel code path under src or bin names either plugin pull-request
command". The test walks every `.ts` file under `src/` and `bin/`, greps for
`PR_OPEN_COMMAND`'s and `PR_MERGE_COMMAND`'s VALUES and for the module specifier,
and requires zero hits. It also asserts the walk found files at all, so an empty
walk cannot pass as an empty result.

Witness `pr-commands-uninvoked-by-the-kernel`, two members: a kernel command
source naming `pr open`, and the dispatch table gaining a `pr merge` row. Two
different ways a kernel path could come to name the capability.
