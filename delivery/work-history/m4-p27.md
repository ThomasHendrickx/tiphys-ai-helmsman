## 2. The dangerous state, and the three shapes it takes

The brief names it: **a trigger that reports READY when it is not.** Everything
below is organised around the three concrete shapes of that, because a design
built against "be careful" is a design built against nothing.

1. **A check greens because it could not reach the thing it checks.**
2. **A check greens on an EMPTY result**, so zero rows reads as zero bad rows.
3. **A check treats an OWNER step as done.**

### The four-arm classifier, and why two states are wrong

Both scripts classify every question into exactly one of four words:
`satisfied`, `not-yet`, `unreachable`, `refused`. The measured reason a
two-state answer is wrong is at delivery/verification/m4-prototype-probes.md:153:
a nonzero exit does NOT mean the condition is false, because a transport
failure exits nonzero too.

Exit codes carry the distinction rather than burying it: 0 satisfied, 1 a real
negative, 3 indeterminate, 64 usage. `unreachable` and `refused` DOMINATE
`not-yet` in both scripts, so "I could not tell" is never reported as "the
answer is no".

### The owner step is structurally not computable

`scripts/check-cutover-entry.mjs` prints the step-3 HALT on EVERY run,
including the run where all four computed arms are satisfied. Its overall
vocabulary is a closed three-word set and no member means ready. The
all-satisfied fixture is the dangerous input for this property, and it is the
one the witness uses.

### 3.2 The REST path is refused and the git path is not

### 3.3 The design change this forced

The probe's FIRST version returned on the first non-satisfied source. Against
the real pilot that reported `refused` and threw away the `ls-remote` read that
had SUCCEEDED. That is the same defect as a precondition checker that
short-circuits on its first failing arm, one layer down.

The probe now reads THREE sources per target (the REST repository record, the
REST newest-commit listing, and `git ls-remote HEAD`), keeps a verdict per
source, and takes the WORST as the target's verdict. The evidence document
carries the per-source breakdown, so a reader can tell "nothing could be read"
from "one transport is refused and another is not".

That reordering is also what makes criterion 3's second assertion non-vacuous:
if the probe invoked git NOWHERE, "the only git operations it invokes are
`ls-remote` and `clone --depth 1`" would be true of a program that invokes no
git at all, which is the guard-that-cannot-go-red shape.

### 3.4 ONE RUN CONTRADICTS THE OTHERS AND IS RECORDED AS UNEXPLAINED

One probe run during the same session read the REST path successfully for both
targets, reporting heads `d4e491b` and `7656f67`, exit 0. Every attempt before
it and every attempt after it was refused, including three bare `fetch` calls
and fifteen `curl` calls.

This is NOT averaged away and it is NOT explained. What is established:

- the REST path is refused far more often than not in this container today;
- the head `d4e491b` that the single 200 reported is corroborated by the git
  protocol, which is the one cross-check available.

What is NOT established: why that run succeeded. The operational consequence is
the one standing warning 6 already states for a different pair of signals, and
the measurement extends it: REST reachability here varies WITHIN a session, not
only between sessions, so probe it rather than assuming it in either direction.

## 4. Two defects this phase found in its own guards

Both were found by running the thing rather than reading it, and both are the
repository's recurring shape: a guard whose condition does not test the
property that matters.

### 4.1 `# pass 1` does not mean a test ran

Arm b's anti-vacuity condition was "the exclusion suite reports a pass count
above zero", because a suite that runs zero tests exits 0. That condition is
itself vacuous. Measured on node v22.22.2:

```
$ printf '// a file that registers no tests at all\n' > fx/test/vacuous.test.ts
$ node --test --test-reporter tap .../fx/test/vacuous.test.ts
TAP version 13
# Subtest: .../fx/test/vacuous.test.ts
ok 1 - .../fx/test/vacuous.test.ts
1..1
# tests 1
# suites 0
# pass 1
# fail 0
...
EXIT=0
```

**The runner reports the FILE as a passing subtest when nothing inside it ran.**
So "pass count above zero" was green on a file asserting nothing, inside the
arm written to catch exactly that.

The condition is now "at least one passing subtest whose NAME is not the file's
own path", at scripts/check-cutover-entry.mjs:339. The pass-count check stays as
a second, weaker layer rather than being replaced.

### 4.2 A nested `node --test` run silently does not run

The checker spawns `node --test` for arm b. Run from inside the phase's own test
file, that child inherited `NODE_TEST_CONTEXT` and did not run at all:

```
$ NODE_TEST_CONTEXT=child-v8 node --test fx/test/cross-environment.test.ts
(node:32185) Warning: node:test run() is being called recursively within a test
file. skipping running files.
```

Exit 0, no counts, nothing executed. The arm FAIL-CLOSED to `unreachable`
("reported no pass/fail counts; exit 0 alone establishes nothing"), which is how
this was found: the backstop caught it before a reader did. But an arm that can
never be satisfied when run from inside a test is not usable, so the child
environment now drops `NODE_TEST_CONTEXT` and pins the TAP reporter
(scripts/check-cutover-entry.mjs:240). The missing-counts backstop is kept.

### 4.3 The test harness blocked its own event loop

The first version of the probe tests used `spawnSync` to run the probe while a
stub HTTP server lived in the test process. `spawnSync` blocks that process's
event loop, so the server never accepted a connection and every stub-server arm
failed with a fetch timeout that had nothing to do with the subject. Captured
from that run, verbatim:

```
- `owner/name`: unreachable. record unreachable: transport failure reading
http://127.0.0.1:44163/repos/owner/name: TimeoutError: The operation was aborted
due to timeout; commits unreachable: transport failure reading
http://127.0.0.1:44163/repos/owner/name/commits?per_page=1: TimeoutError: The
operation was aborted due to timeout
```

(the line is wrapped here for width; nothing else is changed.)

Fourteen of thirty-one tests failed and every stub-server one failed for that
reason. That exact harness defect is on the record at
delivery/verification/m4-prototype-probes.md:286, and it was reproduced here
before being recognised. `runProbe` is asynchronous now, and the probe's own
four-arm classifier is what made the cause legible: it reported `unreachable`
with the transport reason rather than a bare nonzero exit.

## 6. The derivation, and what it did NOT cover

### 6.1 The MECHANISM, not the findings

The mechanism is not "a check returns the wrong answer". It is:

**A PREDICATE WHOSE FALSE CASE AND UNKNOWN CASE ARE COLLAPSED INTO ONE VALUE.**

Every shape in section 2 is an instance. A two-state predicate has nowhere to
put "I could not tell", so it puts it in one of the other two, and whichever it
picks is wrong somewhere. The empty-result family is the same mechanism with the
unknown arriving as an absence rather than as an error.

The derivation is therefore an enumeration of every site in this phase's two
scripts where a verdict is DECIDED, and a check that each one sits in the closed
four-word vocabulary.
