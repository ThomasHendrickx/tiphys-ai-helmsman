## 2. The specification this implements, and it is not this phase's invention

AGENTS.md's `fleet-resume-specification` clause is a SPECIFICATION and says so
at AGENTS.md:295. It fixes three obligations, and this phase owns the first two
(the third is M4-P17's):

- what must survive a reclamation, AGENTS.md:302: everything committed and
  pushed, and nothing else;
- what is REBUILT rather than restored, AGENTS.md:306: worktrees, evidence
  directories, build output and leases. Rebuilt, not restored, is deliberate
  there: a lease held by a session that no longer exists must expire rather
  than block.

`resume` therefore creates empty directories and NEVER carries content forward.
It does not write a lease, it does not invent a worktree, and it does not
fabricate durable content. The test at test/resume.test.ts:516 asserts that the
rebuilt `state/` is empty, so an implementation that "helpfully" seeded it
reddens.

## 4. The design decisions, and why each one

**D1. A new command, not a flag on `init`.** The plan recommends this at
delivery/plan/kernel-plan-m4.md:2634 and the reason holds under inspection:
`init` requires a fleet home to be ABSENT and `resume` requires one to be
PRESENT. Two opposite preconditions inside one entry point is the shape that
produces a destructive mis-invocation. Recorded rather than escalated, per
DR-0016.

**D2. The ephemeral set is DERIVED from `FLEET_IGNORED`, never listed twice.**
src/fleet.ts:167 maps the gitignore constant at src/fleet.ts:29 and strips the
trailing slash. A second hand-written list would be a second thing to keep in
step, and the first divergence would be silent: resume would rebuild one set
while `.gitignore` ignored another, leaving something git ignores permanently
missing or creating something git tracks. The derivation is asserted by a test
at test/resume.test.ts:240 and reddens under two different mutations of it
(section 6, M6 and M7).

**D3. Two preconditions, not one, and they are different failures.**

- `.git` absent means "this is not a clone of anything", src/commands/resume.ts:91.
- Durable content absent means "this is a git repository, but not a fleet
  home", src/commands/resume.ts:108.

The second exists because the first is not sufficient. A clone of ANY other
repository passes the `.git` test, and a resume that stopped there would create
three directories inside a stranger's repository and exit 0. That is the
dangerous state the dispatch names as "greens on a directory that is not a
fleet clone at all", and it is not the same failure as running resume in an
empty directory.

Durable content is never fabricated. It comes back by fetching from the remote.
A resume that created `charter/` to make the layout check pass would be
reporting a recovered fleet while the fleet's actual content was gone, which is
the other dangerous state the dispatch names.

**D4. The whole plan is decided before anything is created.**
`planRebuild` at src/commands/resume.ts:54 classifies all three entries and
returns either a complete plan or one refusal. A refusal discovered halfway
through a creating loop has already changed the tree, and criterion 2's
"creates nothing" would then be false of exactly the paths that matter. The
test at test/resume.test.ts:551 blocks the SECOND ephemeral entry with a file
and asserts the FIRST one was not created.

**D5. Per entry, never all-or-nothing.** Criterion 5's half-rebuilt state is
what an interrupted resume leaves, and it is a common case rather than an edge.
src/commands/resume.ts:132 carries the reasoning.

**D6. stdout carries the `REBUILT` lines and nothing else.** Criterion 1 pins
stdout to exactly three lines, so a summary line mixed in would make "exactly
three lines" a claim about a format that varies with the fixture. On a complete
fleet home stdout is empty, asserted at test/resume.test.ts:483.

**D7. Paths are classified before they are used.** src/fleet.ts:130 lstats
first, then stats, so a symlink is seen as a symlink and a dangling one is
reported rather than read as absent. This is the same mechanism
`classifyEntry` in `src/task.ts` exists for; it is a separate function because
that one answers "may this be opened as a REGULAR FILE" and therefore calls a
directory irregular, which is the wrong answer for a layout entry. C-2 is
untouched: nothing here probes a process, and rehydration is a statement about
a tree.

### 6.5 The witness specs this phase ships

Five, at `witness/resume-*.json`, plus one patch at
`witness/patches/resume-destroy-and-recreate.patch`.

| spec | class | members | named test |
|---|---|---|---|
| `resume-refusal-is-a-class` | classification | 2 mutations (M4, M5) | the class test |
| `resume-rebuilds-only-what-is-absent` | destructive | 1 patch (M1) + 2 mutations (M2, M3) | criterion 5's |
| `resume-leaves-a-live-fleet-untouched` | destructive | 1 patch (M1) + 1 mutation (M3) | criterion 4's |
| `resume-layout-sets-partition` | additive | 2 mutations (M6, M7) | the partition test |
| `resume-command-registered` | additive | 1 mutation | the registration test |

**Why M1 is a PATCH member and not a mutation.** A mutation member is a literal
find-and-replace inside ONE region of one file. Destroy-and-recreate needs two
regions: `rmSync` must be added to the import line AND called in the rebuild
loop. A mutation that adds only the call produces a `ReferenceError`, which is
red for the wrong reason and would be a fabricated witness. The patch kind
exists for exactly this and carries both hunks.

**Every spec's named tests are red under EVERY one of its members**, which is
what the harness requires (src/witness/run.ts:932 records a member red only when
`failed.length === tests.length`). That constraint is why criterion 4's and
criterion 5's witnesses are separate specs rather than one: M2 reddens criterion
5's test and leaves criterion 4's green, which is the correct behaviour of an
all-or-nothing resume and not a weakness of the test.

## 9. What this phase did NOT cover

Stated as residue rather than left to be discovered.

1. **`tiphys resume` does not reconcile task state.** It rebuilds the layout
   only. Which tasks were in flight, which leases are expired and who held
   them, and which phase branches are unmerged are M4-P17's report and
   M4-P19's reconstruction (delivery/plan/kernel-plan-m4.md:2687). A fleet that
   `resume` has rehydrated is structurally valid and has had nothing said about
   its contents.
2. **The `init` remedy behaviour has a manual red witness (M8) and no machine
   witness spec.** The reason is mechanical: any spec whose members touch
   `src/commands/init.ts` inherits rule (f)'s capture obligation, because that
   file spawns `git` and the spawn grep at src/witness/run.ts:319 matches it.
   The only honest capture available is the existing git-bootstrap exit-code
   capture, which has nothing to do with a remedy token, and citing it would be
   a rule satisfied by a document that does not support the claim. Coverage of
   `src/commands/init.ts` for the gate is provided by the pre-existing
   `witness/init-writes-kernel-pin.json`, which this phase does not change.
   The gap is the machine RE-verification of M8 on future heads, and it is real.
3. **No test here exercises a symlinked ephemeral entry.** src/fleet.ts:130
   classifies a symlink-to-directory as a directory and a dangling symlink as
   `other`, and the `other` arm is exercised by a regular file
   (test/resume.test.ts:551), not by a dangling symlink. The two reach the same
   refusal through the same branch, so I judged a second fixture to add nothing;
   that is a judgement, not a measurement, and a reviewer may disagree.
4. **Concurrency: a window exists in the code, and I did not manage to force
   it.** `planRebuild` classifies every entry and the rebuild loop then calls
   `mkdirSync` without `recursive`, so two processes that both classify an
   entry as absent before either creates it would leave the second one throwing
   `EEXIST`. I tried to force that:

   ```
   $ bash .../scratchpad/m4p16/race.sh
   iterations 25; iterations with a nonzero exit: 0
   ```

   Twenty-five forced races, two `node bin/tiphys.ts resume` processes started
   together in one freshly cloned fleet home, zero nonzero exits and zero
   stderr. **That is not evidence that the window is closed.** The likeliest
   reading is that node process startup is far longer than the interval between
   planning and creating, so the second process reliably plans AFTER the first
   has finished. A faster caller, or an in-process caller, would not have that
   protection. I am recording this as an open question rather than as a
   property.

   What the throw WOULD do, if forced, is measurable without the race: the
   top-level handler at `bin/tiphys.ts` turns any thrown error from a
   subcommand into one diagnostic line and exit 1, never a stack trace. So the
   outcome would be an ugly refusal rather than a crash or a corrupted tree,
   and `mkdirSync` does not destroy the directory it fails to create. I did
   not add contention handling, because the phase section does not ask for it
   and AGENTS.md's clause says nothing about concurrent resume.
5. **`resume` is not wired into any exit test or CI bundle beyond the standard
   suite.** Nothing in `scripts/` was touched.
6. **Windows path behaviour is not exercised.** The digest helper normalises
   separators (test/resume.test.ts:114) but the suite runs on Linux here and on
   macOS in the portability job; no Windows arm exists in this repository.
