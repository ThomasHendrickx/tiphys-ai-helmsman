## 1. What shipped

DR-0029 part 2a left a vocabulary with no mechanism behind it. M4-P13 moved six
migration rows onto that vocabulary, so until this phase the re-disposition was
a promise. This phase is the mechanism.

Two new gates, one new source module, one schema field.

| thing | where | what it does |
|---|---|---|
| `gateClasses` | src/gates/schemas/phase-declaration.schema.json | the field a phase declares its classes in |
| `gate-classes` gate | src/gates/gate-classes.ts | the check: one gate per required class, or a declared escape |
| `typecheck` gate | src/gates/gate-classes.ts | R-041, delivery/requirements/migration-table.md:75 |

The three required classes are DR-0029's own, at
delivery/decisions/DR-0029-the-ownership-boundary-and-the-applicability-envelope.md:65:
`correctness`, `scope`, `review`. The requirement attaches to the PHASE and not
to the project
(delivery/decisions/DR-0029-the-ownership-boundary-and-the-applicability-envelope.md:70),
so a greenfield phase 1 can satisfy it on its first commit.

A class is satisfied one of three ways. It names one or more gate ids that this
repository's registry declares. Or it declares `not-applicable` carrying a
`reason`. Or it declares `not-yet-establishable` carrying `establishedBy`, a
phase id. The second and third are DR-0029's escapes
(delivery/decisions/DR-0029-the-ownership-boundary-and-the-applicability-envelope.md:78),
and the property they protect is at
delivery/decisions/DR-0029-the-ownership-boundary-and-the-applicability-envelope.md:83:
quoting that line, "you can start from nothing; you can never SILENTLY have
nothing". That sentence is DR-0029's, not this phase's claim about its own code;
what this phase can show by command is that the green arm prints the escape
rather than absorbing it:

```
$ node src/gates/gate-classes.ts gate-classes --declarations declarations \
    --registry registry.yaml --result out.json --phase m2-p4
gate-classes: green (3 declared gate classes checked)
phase M2-P4 declares all 3 required gate class(es) in declarations/m2-p4.json: correctness: asserted by suite; scope: asserted by scope; review: DECLARED not-applicable, reason: M2-P4 is a harness-only change reviewed under the M2 exit test; 1 class(es) satisfied by a DECLARED ESCAPE rather than a gate, which a reviewer signs off rather than the gate refusing: review
EXIT=0
```

That is the whole of the disclosure, and it is the same trade
src/gates/scope.ts makes for a declaration addition under M3-P11 change B
(src/gates/scope.ts:110): a control the gate no longer refuses becomes a line a
reviewer has to read. A reviewer who does not read the line gets nothing from
it.

## 3. Three design decisions, and the reasoning for each

### 3a. A new gate rather than an arm of `scope`

The plan allowed either. A separate gate was chosen for three reasons. The
classes are a different question from "the change is the change that was
promised". A separate gate produces its own `units`, and folding the check into
`scope` would have made `scope`'s unit label (`changed paths audited`) describe
a count that also included class judgements. And DR-0029's anti-vacuity contract
at
delivery/decisions/DR-0029-the-ownership-boundary-and-the-applicability-envelope.md:89
is per gate, so a gate that asserts one thing reports one honest number.

### 3b. The class-to-gate map lives in the PHASE DECLARATION, not on registry entries

**This is a declared deviation from the plan's files-to-touch list and it is
also an escalation. Read section 8.**

Plan section 3.3.2 asks for "the class field on existing entries" in
`gate-registry.yaml`. That field is refused by the shipped registry schema.
Measured, on a scratch copy of the real registry with `class: correctness` added
to its first entry:

```
$ node bin/tiphys.ts gates run --registry <scratch>/reg.yaml --mode local-only \
    --evidence <scratch>/ev --base origin/main --head HEAD
gates: run c6f58fcc028c861454cff6ef
tiphys gates run: registry <scratch>/reg.yaml is not a valid gate registry
INVALID #/gates/0/class property class is not permitted here
```

`schemas/gate-registry.schema.json` sets `additionalProperties: false` on
`gateShape`, so admitting the field is an edit to `schemas/` at the repository
root. That path is not on this phase's files-to-touch list, and the dispatch
brief names `schemas/` as one of four trees to stop and escalate about rather
than edit. So it was not edited.

What shipped instead: the declaration names the gate ids that satisfy each
class, and the gate resolves every named id against the registry. A class
naming an id the registry does not declare is red:

```
$ node src/gates/gate-classes.ts gate-classes --declarations declarations \
    --registry registry.yaml --result out.json --phase m2-p4
gate-classes: red (3 declared gate classes checked)
phase M2-P4 fails 1 of 3 required gate class(es) in declarations/m2-p4.json: correctness: names gate id(s) a-gate-this-registry-does-not-declare that this repository's gate registry does not declare, so nothing runs for this class
```

**What that does not reach, stated rather than left to be found.** With the
class on the registry entry, a phase declaring `correctness: [citations]` would
be red because `citations` is not a correctness gate. Without it, that
declaration is green. The gate checks that a named id EXISTS, not that it is of
the class it was named under. Closing that is the registry field, and the
registry field is the escalation.

### 3c. Two gate ids out of one module

The plan authorises one new source file, `src/gates/gate-classes.ts`. The
`typecheck` gate is a command that produces a GateResult with a derived unit
count, and that is code rather than a shell one-liner. `src/gates/credentials.ts` already ships two gate ids
behind one entry point (`credential-scrub` and `credential-token`, dispatched on
the first positional argument), so this follows the delivered precedent rather
than widening the declaration to a second file. The alternative would have been
a second source file and a scope deviation; this way there is no deviation on
that axis at all.
