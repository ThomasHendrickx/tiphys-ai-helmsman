# M4-P7: the model-resolution record, all four parts

Branch `claude/m4-p7-model-resolution`. The phase's contract is its section of
the M4 plan, which begins at delivery/plan/kernel-plan-m4.md:1018, with the
files-to-touch line at delivery/plan/kernel-plan-m4.md:1049 and the acceptance
criteria at delivery/plan/kernel-plan-m4.md:1058.

## What was built, and the one sentence that shapes every part of it

M4-D-06 has four parts: SHAPE, TIMING, VOCABULARY OWNERSHIP and LOCATION
(delivery/plan/m4-intake.md:746). They ship together because a schema with no
writer asserts nothing and a writer with no consumer is a file nobody reads,
which is DR-0031's rule that a pull request is a unit of self-contained value.

The sentence that shapes all of it: **a record written at launch can only carry
what was REQUESTED, so it is a restatement of the request wearing the word
`resolved`.** Everything below is arranged so that the restatement is
unrepresentable rather than merely discouraged.

### The seven files

- `schemas/model-resolution.schema.json` (new). The Kind A contract. Three of
  its decisions are load-bearing rather than shape-keeping:
  - `turnEnd` is REQUIRED. A record written at launch has no turn-end file to
    echo, because the generated hook has not run, so the dangerous state cannot
    be expressed as a valid document at all.
  - `resolved` is a three-branch `oneOf` on `provenance`. The `observed` branch
    requires an `observation`; the `unresolved` branch requires a `reason`.
  - `resolution.observation` carries `consulted`, and the `consulted: false`
    branch may cite no configuration path. A harness with no tier-policy
    document in front of it has not observed a permission, and reporting one
    would be the same laundering the record exists against, one field over.
- `src/model-resolution.ts` (new). The kernel-side reader. It holds NO
  vocabulary: no tier-to-model table, no model-to-family table, no vendor name.
- `src/checks.ts` (edit, DECLARED ADDITION, see below). One derived check,
  `model-resolution-subject-echo`, for the three sibling-field agreements no
  keyword reaches.
- `src/commands/validate.ts` (edit, DECLARED ADDITION, see below). The type
  row. One row serves the `--type` table AND the `auto` resolver, because
  `resolveAutoType` answers `--type auto` by looking the instance's `kind` up
  in that same map, and this record carries a required `const` kind.
- `plugin/src/vocabulary.ts` (new). The tier-to-model and model-to-family
  tables, in the only package where a vendor name is allowed to be.
- `plugin/src/model-resolution.ts` (new). The writer, the charter-override
  resolver for R-075, and the transcript observation resolver.
- `plugin/src/adapter.ts` (edit). The record is written after
  `invokeTurnEndHook` returns `ok`, which is the one point in `launch` where
  the turn-end record is known to exist on disk.

## Deviations, declared

### 1. Two files added to the declaration: `src/commands/validate.ts` and `src/checks.ts`

The plan's files-to-touch line names `src/validate.ts` "(edit: type table and
`auto` resolver)". Measured: `src/validate.ts` holds neither. The type table is
`TYPE_TABLE` in `src/commands/validate.ts`, and `resolveAutoType` is in the
same module. `src/validate.ts` is the Ajv wrapper and the YAML decoder, and I
did not touch it.

```
$ grep -rn "executor-record" --include=*.ts src/
src/commands/validate.ts:129:  ["executor-record", "executor-record.schema.json"],
```

`src/checks.ts` is the second addition and it follows from criterion 1 plus a
rule the repository already has. Criterion 1 requires `tiphys validate --type
model-resolution <file>` to exit nonzero on "a subject echo that does not match
the request field by field". That compares two sibling fields of one document,
and schemas/README.md:70 says such a property is Kind B and "live in
`src/checks.ts` as named derived checks (kernel plan M3 section 2.3, DR-0013
clause 8). They are never encoded as Ajv extensions." So the criterion cannot
be met inside the schema, and the repository's own rule names the file it must
be met in. The declaration entry `src/validate.ts` was left in place rather
than removed, because the scope gate refuses a REMOVAL outright.

Both additions are entries inside an existing declaration, which the scope gate
allows and PRINTS by name for sign-off (the correction CLAUDE.md records for
DR-0031, from src/gates/scope.ts:110).

### 2. An eleventh behavior: `model-resolution-empty-observation-is-unresolved`

The plan lists ten new behaviors. This is an eleventh, and it discharges a
finding of the prototype this phase is blocked on rather than inventing scope.
M4-P1's amendment measured the observation channel's write race and stated the
consequence as a requirement:

> **Consequence: a resolver that falls back to the self-report on an empty
> transcript is green whenever the race does not fire and silently accepts a
> forgeable value when it does.** The failure correlates with load, so it is
> rarest in testing. An empty transcript at hook time must be UNRESOLVED and
> LOUD.

That is at delivery/verification/m4-prototype-probes.md:432. A behavior with no
registered id has no witness spec and is therefore not re-evaluated by the
`red-witness` gate on later runs, which is the whole reason this repository
ships specs rather than captures. `test/behaviors.json` is append-only and a
phase may extend it.

### 3. `provenance` carries THREE values, not two

The plan's criterion 6 names `observed` and, by implication, a non-observed
level. The schema ships `observed`, `self-reported` and `unresolved`, for the
reason in deviation 2: "nobody looked" and "somebody looked and saw nothing
usable" are different facts, and collapsing them is the measured failure. The
probe's own words, same citation: "So `observed` is a real level ABOVE
`self-reported` and BELOW attested... What must not be written into M4-P7 is
any vocabulary implying attestation." No such level is shipped.

### 4. The observation channel is INJECTED, not discovered, and the first draft was wrong

This one was found by the suite rather than by reading, and it is worth the
space.

M4-P1 established that every hook payload carries `transcript_path` and that
the transcript is harness-written with `message.model` on every assistant row
(delivery/verification/m4-prototype-probes.md:209). M4-P6's tool-call observer
already writes every hook payload VERBATIM to an append-only log in the task
directory. So the first draft of the writer read that log to find a transcript
path, which made `provenance: observed` reachable from the adapter with no new
hook and no new dependency.

The full suite reddened `the compiled plugin appends to the tool-call log and
never reads it` in test/plugin-hooks.test.ts:631, which asserts that exactly
ONE compiled plugin module names that log:

```
AssertionError [ERR_ASSERTION]: 2 compiled modules name the log:
  /tmp/tiphys-p6-hooks-0pS6aD/emit/hooks/tool-call-observer.js,
  /tmp/tiphys-p6-hooks-0pS6aD/emit/model-resolution.js
2 !== 1
```

The failing assertion is the symptom and the mechanism is a rule: plan
constraint C-1 forbids reading current state from the tail of an append-only
log, and M4-P6's single-owner assertion exists because one owner is what keeps
the append-only discipline checkable. A value taken from the tail of a log by a
second module is the shape both of those exist against, whatever the value
happens to be, and the draft's own comment arguing that a transcript path is
not "current state" is exactly the kind of argument the rule is there to stop.

The fix was not to narrow the read. `observeServedModel` now takes the
transcript path as an ARGUMENT, so a caller that HAS a hook payload passes one
in and nothing goes looking. The consequence is stated rather than dressed up:
**the adapter has no hook payload, so the record it writes today ranks itself
`self-reported`.** That is the state M4-D-06 was designed to survive, and the
plan's own hazard table says whether the identity is observable at all is
something "NO CRITERION CAN SETTLE" (delivery/plan/kernel-plan-m4.md:1136).
`observed` is reachable, tested against the probe's real captured transcript
shape, and guarded; wiring a hook to it is a later phase's.

## What this work did NOT cover

A reviewer's first check is this section, so it is written before the evidence.

1. **NO HOOK IS WIRED TO `observeServedModel`, so no shipped code path
   produces `provenance: observed`.** The resolver is exercised only by
   `test/model-resolution.test.ts`. Everything the adapter writes in production
   today is `self-reported`. This is deviation 4 above and it is the largest
   gap in the phase.
2. **The charter override has no production reader.** `resolveTier` is a pure
   function and is complete in both directions, but nothing in the shipped
   adapter parses `role-model-config.yaml` or a charter to fill its `policy`
   argument, so every record the adapter writes carries
   `resolution.observation.consulted: false`. The reason is mechanical: the
   plugin's only declared dependency is `@tiphys/kernel`, which publishes the
   adapter contract and nothing else, so the plugin has no YAML parser, and
   adding one is a `plugin/package.json` and lockfile change outside this
   phase's files. The record's `consulted` field exists so that this state is
   recorded rather than inferred.
3. **No charter document carries a role tier today.** schemas/charter.schema.json:7 closes the document with
   `additionalProperties: false` and it has eleven top-level properties and `additionalProperties: false`, and none
   of them is a per-role model tier. `resolveTier` therefore takes the
   charter's tier as data rather than parsing a charter, and which charter
   field will carry it is not settled by this phase.
4. **The transcript REWRITE tamper is not detectable here and is not claimed to
   be.** M4-P1 ran two structurally different tampers and reported that an
   APPENDED forged row makes a resolver see two models, which the writer treats
   as unresolved, while a REWRITE in place is "byte-shaped exactly like the
   truth". Nothing in this phase detects the second.
5. **One environment.** Every measurement quoted here is from this container on
   node v26.6.0. The probe's own limits carry forward: one account, one CLI
   build, one day.
6. **The consumer side is a reader, not a gate.** `src/model-resolution.ts`
   exports the acceptance and comparison functions; no gate calls them yet, and
   `check-dual-review` still compares `produced-by` strings. Criterion 8 puts
   the family token where a verdict carries it and asserts the copy is exact;
   it does not change how the decorrelation check reads that field.
7. **No end-to-end launch test.** The adapter's write site is exercised through
   the writer's own functions and the real generated turn-end hook, not through
   a full `claudeCodeAdapter.launch` with a payload child. The existing
   adapter tests in `test/plugin-adapter.test.ts` are not on this phase's
   files-to-touch list and were not extended.
8. **`npm audit` reports issues on this lockfile.** Pre-existing, untouched,
   and out of scope.

## The acceptance criteria, walked

### 1. (a) SHAPE

`tiphys validate --type model-resolution <file>` exits 0 on a record the plugin
ACTUALLY WROTE: every instance comes from the writer's own
`buildModelResolutionRecord` and is then damaged one field at a time, because a
literal here would test the schema against the schema author's idea of the
writer. Real captured output of all eight cases is committed at
`witness/captures/m4-p7-model-resolution-cli.txt`, and the test asserts against
lines taken FROM that capture through a helper that fails first when the
capture does not carry the line at all.

| case | exit | diagnostic |
|---|---|---|
| the record as written | 0 | (no output) |
| no subject echo | 1 | `INVALID #/subject required property subject is missing` |
| echo that does not match the resolution field by field | 1 | `INVALID #/resolution/role ... so this record resolves a different subject than it claims (check: model-resolution-subject-echo)` |
| no `vocabulary` identity | 1 | `INVALID #/resolved/vocabulary required property vocabulary is missing` |

The echo is compared BEFORE the outcome is read, in both places it is compared.
In the derived check the role and tier comparisons run before anything reads
`resolved`; in the kernel-side reader the four refusals are ordered contract
version, subject echo, vocabulary identity, provenance, and the ordering is
commented at the function rather than left to be inferred. That mirrors
src/gates/release.ts, where `validateAdapterResponse` compares the subject echo
against the subject the KERNEL holds before the outcome is read at all.

### 2. (b) TIMING

MET. The record is written after `invokeTurnEndHook` returns `ok` and nowhere
else. The test renders the SHIPPED hook with `renderTurnEndHook`, runs it as a
real child, reads the `endedAt` the child wrote, and asserts
`writtenAt >= endedAt`, so the instant compared against is one the shipped
generator really produced.

Two refusals, because the dangerous state has two shapes:

- a record whose `writtenAt` precedes `turnEnd.endedAt` is refused at
  `#/writtenAt` by the derived check;
- a record with NO `turnEnd` at all, which is what a launch-time writer would
  actually produce because the file it must echo does not exist yet, is refused
  at `#/turnEnd` by the schema.

### 3. (c) VOCABULARY, and the kernel refuses to compare across one

MET. `compareResolvedFamilies` refuses two records naming different
`vocabulary.id` values with a reason naming BOTH ids, and compares two naming
the same one. The refusal is tested under two structurally different members:
tokens that DIFFER across vocabularies, and tokens that are EQUAL across
vocabularies. The second is the one most likely to be waved through, because
"they match, so the reviews are correlated" reads as the conservative answer
and is in fact unfounded.

### 4. (c) continued: no vendor name enters `src/`

MET. M4-P3 criterion 7's test is `no vendor model name appears in the kernel's
shipped source, schemas, roles or configuration`, and it walks `src/`, `bin/`,
`schemas/`, `roles/` and the root YAML at run time. It passes at this head, run
on its own with the TAP reporter so the capture is pure ASCII and needs no
transliteration:

```
$ node --test --test-reporter tap --test-name-pattern '^no vendor model name appears in the kernel.s shipped source, schemas, roles or configuration$' test/schemas.test.ts
ok 1 - no vendor model name appears in the kernel's shipped source, schemas, roles or configuration
# tests 1
# pass 1
# fail 0
# skipped 0
exit=0
```

The kernel-reads-identity-only assertion is MECHANICAL rather than by
inspection. The grep above reads the BYTES of `src/`, so a vendor name that
arrives at run time as data the plugin handed in is not among those bytes; a
reader that reaches INTO a vocabulary is therefore outside what that grep
covers. So the test hands the reader a `Proxy` whose
`get` trap records every property name, with content keys planted on the target
that a careless reader would reach for, and asserts the recorded set:

```
assert.deepEqual(touched, ["id", "version"], ...)
```

### 5. (d) LOCATION and the absent-record rule

MET. `modelResolutionPath` composes the path from the shipped `taskDir`
helper, so the record lands in the fleet home under `tasks/<id>/` and never
inside the worktree. src/task.ts:31 records why that invariant is absolute.

The absent-record rule is NOT reimplemented and its wording is NOT copied. The
test DRIVES `src/gates/release.ts` with a stub adapter that exits 0 writing
nothing, captures the verdict reason that program really produced, extracts the
rule clause from the capture with a regular expression, and asserts the
kernel-side reader's own reason carries the same clause:

```
const clause = /exit 0 with no \S+ is error, not success/.exec(capturedReason);
const expected = (clause as RegExpExecArray)[0].replace("response", "record");
```

src/gates/release.ts:609 is the line that produces it. An absent record is
`kind: "error"`; there is no arm that returns a read, a green, or a
not-applicable.

### 6. Provenance cannot be laundered

MET, both members, and they are guarded by two independent mechanisms.

- MEMBER ONE, a missing field: `resolved.provenance: "observed"` with no
  observation fails the schema's `oneOf` and exits 1. The kernel-side reader
  refuses it too, which matters because the schema cannot run inside a consumer
  and the consumer never shells out to `tiphys validate`.
- MEMBER TWO, present but inconsistent: an observation about ANOTHER task, and
  an observation naming a DIFFERENT model than the record claims. Both
  documents VALIDATE, which the test asserts explicitly before exercising the
  reader, so the record shows that a schema-only guard passes this member
  green. Both are refused by `acceptModelResolution`.

Two sibling launderings the same reader closes: a record that ranks itself
`self-reported` while carrying an observation, and a record that reports the
identity `unresolved` and names a family or a model anyway.

### 7. The charter override is resolved, not assumed

MET for the resolver, in both directions, and NOT wired in production (see
"what this did not cover", item 2).

| role permission | charter names a tier | resolved tier | `overrideApplied` | charter echoed |
|---|---|---|---|---|
| `allowed` | yes | the CHARTER's | true | path and tier |
| `forbidden` | yes | the config's | false | nothing |
| anything else | yes | the config's | false | nothing |
| `allowed` | no | the config's | false | nothing |

The third row is the fail-closed direction on the one field that gates an
override. The override CONDITION is two document reads, so it is recorded as
`observed` with the path and the verbatim permission; when no document was read
the observation says `consulted: false` and cites no path at all.

A record claiming an override while its observed permission is `forbidden` is
refused at `#/resolution/observation/configPermission` by the derived check.

### 8. Closeout copies the family token into the verdict

MET. `producedByFromRecord` returns `resolved.family` verbatim. The test
compares the copy and the record's own field AS BYTES, not as strings, because
a copy that trimmed, lowercased or prefixed the token would satisfy every prose
reading of "reaches the verdict" and break the one comparison the token exists
for. The verdict carrying it is validated against the shipped
`schemas/verdict.schema.json`. A record whose identity is `unresolved` yields
`undefined` rather than an empty string that would validate.
