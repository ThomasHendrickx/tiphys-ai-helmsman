### Criterion 2: the output exists and the gate is EVALUATED

The release job declares

```
    outputs:
      publish: ${{ steps.decide.outputs.publish }}
```

at .github/workflows/release.yml:133, and the tag job's condition at
.github/workflows/release.yml:352 compares it by exact string equality.

Both are COMPILED AND RUN by test/license-gate.test.ts:1862, not matched as
text. The evaluator (test/license-gate.test.ts:1771) accepts exactly two
shapes, a bare reference and a reference compared to a single-quoted literal,
and `assert.fail`s on everything else. That refusal is the design and not a
limitation: `always()`, a negated comparison, a boolean operator chain and a
bare literal are all ways to make a repository write reachable on a dispatch
that published nothing, and an evaluator that returned `undefined` for them
would be green over every one.

The condition is run against seven rows (`yes`, `no`, empty, absent, `YES`,
` yes`, `true`) plus an absent `needs` context, the output is run against four
values plus an absent decide output, and then the two are COMPOSED end to end,
so the assertion is "a rehearsal does not tag" rather than two assertions about
two expressions that might not be connected.

One consequence worth naming because a text assertion cannot reach it:
`if: ${{ needs.release.outputs.publish }}` (a bare reference, no comparison)
would pass any grep for the output's name and would RUN on `publish=no`,
because GitHub treats a non-empty string as truthy. The table reddens on it,
since a bare reference returns the string `no` where the row expects `false`.

## What I decided about a tag write that fails after a successful publish

The spec leaves this open at delivery/plan/m3-p12-phase-spec.md:88 and requires
the choice to be stated. **The tag job fails loudly and the published version
exists with no tag. Nothing retries and nothing forces.**

The reasoning, and it follows from DR-0032 rather than from taste. The state
DR-0032 forbids is an anchor pointing at NOTHING. A missing anchor is not that
state: it is a visibly missing one, with a red job on the run page naming it. A
retry or a force is how a half-made anchor becomes a confidently wrong one, and
`--force` on a tag is the single operation that could destroy the anchor for a
version that really was published.

What the job does instead is make the recovery cheap. Every refusal prints the
tag name and the commit sha in the same line, so the manual repair is a copyable
pair of facts rather than an investigation.

**What I did NOT establish, and it is the interesting half.** GitHub's "re-run
failed jobs" would in principle re-run only the tag job and carry the release
job's stored outputs forward, which would be a repair that cannot republish. I
did not verify that, because verifying it needs a dispatch and this phase must
not dispatch. It is written here as an open question, not as a property. The
repair that needs no such assumption is the manual one above.

## Where the derivation was scoped, and what it does NOT cover

Stated before the results rather than after, because a search whose scope is
wrong returns an empty result indistinguishable from an absence of defects.

The subject of every new assertion is EVERY JOB OF EVERY WORKFLOW FILE under
`.github/workflows/`, and every selection goes through the round-2 `exactlyOne`
helper. Enumerated at this head:

```

```

What that scope does NOT cover:

- **The repository or organisation DEFAULT grant.** A job declaring no
  `permissions:` at either level inherits a setting that lives in no file here.
  Exactly one such job exists (`gates.yml job gates`) and the test ENUMERATES it
  by name rather than passing over it, so a new one reddens where a reviewer
  will read the reason.
- **Reusable workflows called through `jobs.<id>.uses:`** and **composite
  actions**, whose grants and steps live elsewhere. This repository has none.
- **Workflow files outside `.github/workflows/`**, which GitHub does not read
  either, so this is GitHub's scope and not a gap in the walk.
- **Anything a `run:` body INVOKES.** The predicates read the body, not what it
  calls. `npm run release` or a shell script would be invisible to all of them.
- **`GITHUB_TOKEN` reaching a step through some other route.** The token
  assertions inherited from M3-P10 cover the release workflow's text; nothing
  here covers a credential arriving another way.

One gap in the INHERITED predicate was closed rather than described, because
this phase made it real. `PUBLISH_COMMAND`'s own comment lists "a publish
written with the command split across a line continuation" as an exclusion, and
the tagging command IS written with continuations. Continuations are now joined
before every publish scan (test/license-gate.test.ts:1803). Joining widens the
search and narrows nothing, measured at this head:

```

```

A measured near-miss worth recording, because the obvious predicate is wrong.
`/^\s*git\b.*\btag\b/m` matches `git rev-parse -q --verify "refs/tags/${tag}"`,
since `${tag}` is delimited by non-word characters on both sides. Two of the
three git lines in the step would have been candidates and `exactlyOne` would
have reported the wrong count for the right reason. The predicate at
test/license-gate.test.ts:1814 anchors on the git SUBCOMMAND instead, allowing
only repeated `-c` flags between.

## One design point that is mine and is worth attacking

The tagging step uses `set -eu` where the neighbouring `decide` step uses
`set -u`. That difference is deliberate and it was found by construction rather
than by taste: this script WRITES, and under `set -u` alone a rejected
`git push` would fall through to the closing `echo` and the step would exit 0,
reporting a tag that is not there. The remote probe is written as
`git ls-remote ... || probe=$?` so that `set -e` does not abort on the "absent"
answer, which is exit 2 and is the normal case.

## What a reviewer should attack first

DR-0032:76 says the second job is the security-relevant change and should be
attacked first. Three places I would look:

1. **A third gate.** The spec says the two conditions each cover a failure the
   other does not, and does NOT claim they are sufficient. The case I could not
   close is a dispatch whose release job publishes and whose tag job then runs
   against a DIFFERENT commit; `github.sha` and the release job's checkout are
   the same ref on a `workflow_dispatch`, and I assert the version agreement
   from `package.json` in the tag job's own checkout, but I have not shown the
   two checkouts cannot diverge.
2. **The evaluator's grammar.** It is deliberately tiny and refuses everything
   else. If GitHub accepts a form that is semantically equivalent to the
   accepted one and this refuses it, the failure is loud and cheap. The opposite
   direction, a form it accepts and mis-evaluates, is the one worth hunting.
3. **The stub `gh`.** It records argv and exits 0. It does not model gh's own
   failure modes, so nothing here establishes what the step does when
   `gh release create` fails; under `set -eu` the step exits nonzero, which is
   the intended direction, and that arm is reasoned about rather than run.
