## Design, decided before code

Three measured facts shaped it.

1. `check-dual-review` is NOT a gate in gates.manifest.json
   (`git show origin/main:gates.manifest.json | grep -c '"id": "check-dual-review"'`
   prints 0; its one mention, at line 247 on this branch, is inside
   merge-preconditions' precondition command), so the runner does not
   execute it in CI; CI runs it only through a legacy workflow step that
   passes no `--base` (the step is not on this phase's declaration).
   `merge-preconditions` IS in the manifest, and the harness row for it in
   scripts/m2-exit-test.sh:226 is `green|not-applicable`, so a red from it
   fails the pull-request bundle. It is therefore the gate that can make a
   shipped-code pull request fail in CI.
2. Both gates' precondition today is `check-dual-review --precondition .`,
   which exits 1 when no verdict document exists, so on a branch with no
   verdict the runner reports not-applicable WITHOUT spawning either gate.
   That precondition is the review-gate-never-runs mechanism, and it is the
   thing that has to change.
3. Adding `check-dual-review` to the manifest is refused by the harness: a
   manifest gate with no row in scripts/m2-exit-test.sh is asserted
   required-green, so every paperwork-only pull request would fail.

The review budget is DR-0027's table, read literally
(delivery/decisions/DR-0027-reviews-target-shipped-value-not-ceremony.md:36):
row 3 (`delivery/`, `CLAUDE.md`, `.claude/`) and row 2 (`scripts/`, `test/`,
`.github/`, `gate-registry.yaml`, `gates.manifest.json`) are below the
dual-review tier; every other path is held to row 1, fail closed. The
classification is one exported function in src/gates/merge-preconditions.ts
and both gates call it.

The DR-0027 table itself is at
delivery/decisions/DR-0027-reviews-target-shipped-value-not-ceremony.md:38 (the

## Declared deviations

- D-1 (additive grants). test/dual-review-head-anchor.test.ts and
  test/gates.test.ts pinned `check-dual-review`'s parameters as `[head]`; both
  now expect `base` too. Witness specs and captures under `witness/`, two
  stored witnesses re-anchored because this phase re-indented or re-signed the
  lines they mutate (merge-preconditions-no-verdict-at-head-is-not-applicable,
  merge-preconditions-unreachable-api-is-error), and .github/workflows/gates.yml
  (D-3). All are additive entries in the declaration; nothing was removed.
- D-2 (in-flight rule). Once verdicts are committed, the pull-request run
  evaluates merge-preconditions INSIDE the `gates` check run for the head
  condition 4 asks about, and that check run is `in_progress` because it is
  this run. Judged as before, condition 4 would be red on every reviewed head
  forever. So a `gates` check run for exactly this head that has not completed,
  with every review row green, makes the gate not-applicable with precondition
  `merge-preconditions-ci-concluded-for-this-head`, whose evidence carries the
  in-flight run and every ESTABLISHED row. A refusing review is still red; an
  in-flight run for another head is not counted. Witnessed on a REAL captured
  in-progress response (witness/captures/m5-p3-github-check-runs-in-flight.json).
  Consequence: CI is not expected to turn this gate green, because during
  the run its own `gates` check run is in progress by construction; the orchestrator's pre-merge run
  after CI concludes does.
- D-3 (API token). Measured here, 2026-09-23, with Node's `fetch` (which does
  not use the agent proxy): unauthenticated `GET /repos/{slug}` answered
  `403 {"message":"API rate limit exceeded for 146.148.98.137. ...`, and the
  same request with a bearer token answered 200. Before M5-P3 the precondition kept the gate
  off the network on any branch without a verdict document (design fact 2); from M5-P3 it does on every reviewed shipped-code
  head. So merge-preconditions takes `--token-env <NAME>` (a declared flag,
  not an ambient read, asserted by the token-env test's no-flag arm, which
  observes no authorization header; a value that is not a variable name is a usage error),
  the registry and manifest commands declare `--token-env GH_TOKEN`, and the
  pull-request M2 exit step in .github/workflows/gates.yml sets
  `GH_TOKEN: ${{ github.token }}`. The token value is never written anywhere,
  asserted by test.
- D-4 (review of the pair-arm checks by manual witness). The FIX-ROUND-NEEDED
  and correlated-pair refusals are decided in src/checks.ts, which this phase
  does not change, and red-witness rule (d) refuses a stored member outside the
  phase diff. So the runner-level pair-arm test is witnessed by hand, below,
  and the stored witnesses cover the arms whose code this phase owns.
- D-5 (row 2 is not enforced). DR-0027 row 2 (`scripts/`, `test/`, `.github/`,
  the two registries) owes ONE review round. The gate classifies it as tier
  `single` and reports not-applicable, the pre-M5-P3 behaviour, because the
  plan asks only for the two-verdict rule on the shipped tree. Open question 2.

- D-6 (retirement inventory). The suite's retirement-inventory tests
  (test/retirement-inventory.test.ts:134) derive every rule anchor from
