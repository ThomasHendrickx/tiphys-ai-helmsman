## Four things the real data settled, and three of them changed the code

### 1. The wire names are camelCase, and the plan spells them with hyphens

Criterion 4 names `flipped-at`, `flipped-by`, `reason` and `restore-to`. The
document M4-P26 already writes and reads spells them `flippedAt`, `flippedBy`,
`reason` and `restoreTo` (src/cutover.ts:101 declares the interface,
src/cutover.ts:152 validates it). A schema pinning the hyphenated spelling
would refuse every document the shipped writer produces, so the schema pins
what the document uses, and the plan's spelling is read as prose naming four
fields rather than as their serialised keys. Both spellings are stated in the
schema's own `$comment` and in a test, so the next reader meets the difference
instead of discovering it.

### 2. The inventory's `negative-witness` is an OBJECT, not an argv array

`RetirementRow` declares `negativeWitness` as an argv ARRAY. The shipped M4-P23
inventory writes `negative-witness` as an OBJECT carrying a SHELL STRING and a
recorded exit. Measured before anything was written:

```

  const p=j.rows.filter(r=>r.disposition==="PORT");

Handing a shipped row straight to `evaluatePortRow` therefore returns

The adapter at src/cutover.ts:1678 is what fixes it, and the test
`a shipped inventory row is unported without the adapter and ported with it`
asserts BOTH sides so the adapter cannot quietly stop mattering.

### 4. A nonzero exit is not the same thing as a red witness

`grep` exits 1 when it searched and found nothing and 2 when it could not
search at all. Accepting any nonzero status reports a row as `ported` on the
strength of an error message, which is a guard that fails open when its own
tool fails, one level below the vacuous green criterion 6 names. The row's own
`negative-witness.exit` is what it recorded when it was written, so when a row
declares one it is now required to match. Same rule and same reason as
scripts/check-retirement-inventory.mjs:628 applies to its widening grep.

Measured over the shipped inventory before the rule was added, so that the
change is known to alter no verdict today:

```
$ node -e '... spawnSync("sh",["-c",r["negative-witness"].command]) for every PORT row ...'
exit distribution: { '1': 199 }
```

All 199 exit exactly 1. None of them errors, so none was a vacuous red, and the
rule is a guard against the day one of them starts erroring rather than a
correction of a present fault.

### The comparison is content to content, and the mtime version was measured wrong

The criterion says the capture must not be OLDER than the most recent switch
write. An mtime does not survive the journey. Measured:

```
$ git clone -q --no-local <repo> c && cd c

## Criterion 1: the output shape, and what exit 0 means

`tiphys cutover status --fleet <dir> [--repo <dir>] [--json]` prints exactly
five `SWITCH <name> current|kernel` lines, in the closed order of
src/cutover.ts:73, then one `DRAIN clean|<n> in flight` line. The test asserts
the five as an EQUALITY against `CUTOVER_SWITCHES`, never as a subset: "at
least five" would stay green if a sixth appeared, and the closed list is what
every rollback trigger enumerates.

Exit 0 requires all five `kernel` AND a clean drain AND a satisfied
precondition. The other codes are distinguished on purpose:

| code | meaning |
|---|---|
| 0 | the condition is met |
| 3 | the question was answered and WORK REMAINS |
| 1 | the command refused to answer |
| 64 | usage error |

3 is the code `tiphys next` already uses for the same meaning
(delivery/plan/kernel-plan-m4.md:3234). A cutover that has not completed is not
a failure of this command, and a caller that cannot tell those apart cannot
script anything.

**A fleet with no `cutover.json` reports five `current` lines and exits 3.**
That is the ORIGINAL state rather than an undecidable one, and the reasoning is
in the code at the site: nothing creates the file at init, so its absence means
no switch has ever been written. This is deliberately NOT the reading
`inFlightItems` gives an absent `worktrees/`, where absence IS undecidable
because the fleet had the directory when it was loaded.

**One reading had to be settled and it is stated rather than smoothed over.**
Criterion 5 says no switch may REPORT `kernel` while the capture is absent, and
criterion 1 pins the third token of a SWITCH line to `current|kernel`. Printing
anything else there would break criterion 1; printing `current` for a switch
the file says is `kernel` would be a lie. So the command prints the recorded
state, adds one `REFUSED <name> ...` line per switch that reads `kernel`, and
exits 1. One refusal line per switch rather than one for the table, because a
reader who greps for a switch name must not see `kernel` and nothing else.

## Criterion 4: the schema is what refuses the write

`schemas/cutover-state.schema.json` requires `state`, `flippedAt`, `flippedBy`,
`reason` and `restoreTo` on every switch record, and `publishCutoverState`
validates the whole document against it BEFORE the temporary file is opened, so
a refused write leaves the destination byte-identical and leaves no temporary
behind. The test asserts the byte comparison and the directory listing, not the
exception alone.

**That the SCHEMA is what refuses is demonstrated by defanging the schema, not
by reading the code.** With `restoreTo` removed from `required`, the same
document validates; with it present, it does not. A dangerous-state member does
exactly that mutation, so the claim is re-evaluated by the gate on every later
run rather than read once.

**The document stays EXTENSIBLE at both levels, and that is a decision.**
`schemas/README.md` prefers `additionalProperties: false` at every object
level. M4-P26 registered a rollback that CARRIES document keys it does not own,
at the document level and inside a switch record
(test/cutover.test.ts:974 asserts it), so closing either level would make the
shipped writer refuse its own preserved keys. The half that IS closed is the
switch NAME list, which is the vocabulary that has to be closed, and a sixth
name is refused with a named diagnostic. The deviation is recorded in the
schema's `$comment` at the site rather than left for a reviewer to infer, and
six of the eight schemas already on `main` carry open object levels, so this is
within the shipped practice rather than a new liberty.

## Criterion 6: both halves, and the two vacuous verdicts

`tiphys cutover status --retirement` prints one `PORT <id> ported|unported
<reason>` line per PORT row and exits 3 while any row is unported. A row is
`ported` only when every artifact its `destination` names exists AND its
`negative-witness` command is red under the new artifact with the exit it
recorded.

Four refusals guard the two vacuous verdicts:

1. the destination does not exist: `unported`, whatever the witness did;
2. the witness exits 0: `unported`, because a probe that discriminates nothing
   under the new artifact means the artifact is WEAKER than the rule it
   replaced (M4-P26's rule, unchanged);
3. the witness exits something other than what the row recorded: `unported`,
   because it failed rather than searched;
4. an inventory with zero PORT rows refuses outright, because `unported === 0`
   over an empty list is the vacuous green one level up.

The rows are DATA FROM A FILE, so every command is screened on the executable
position of each segment before anything spawns it, against an allowlist of
tools with no option for writing a file. A test compares that list with the one
the inventory's own checker applies to the same rows and requires this one to be
no wider, because the kernel cannot import that script (DR-0029 keeps
`scripts/` on the project's side) and two lists screening one document must not
drift apart. The screen is a TOOL allowlist and not a sandbox: the child still
runs with this process's privileges and can read what it can read.

## Criterion 7: nothing is mutated, asserted per invocation

A sha256 over the whole fixture tree, every path, its entry type and the bytes
of every regular file, is taken BEFORE and AFTER every invocation in every
criterion above rather than once at the end. A single end-of-suite comparison
cannot say which invocation moved something, and a command that wrote and then
restored a file would pass it. `.git` is inside the digest, because the command
shells out to the version-control program and a digest that excluded the
directory it writes into would be blind to the side effect the fixture exists
to detect.

## Criterion 8: read as a constraint on a LATER pull request

Criterion 8 says deletion of retired artifacts ships in ONE pull request with
its replacement. **Nothing is deleted in this phase**, and that is the
criterion being met rather than missed. It is recorded here so that a reviewer
does not read the absence of deletions as an unmet criterion. `main` must not
assert evidence for code it does not contain nor carry code its evidence does
not cover (DR-0031), and the phase that performs a deletion is the one that
owes both halves in one unit.
