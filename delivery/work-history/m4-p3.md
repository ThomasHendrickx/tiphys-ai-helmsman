# M4-P3 work history: the request contract widens, and executor.json gets a schema

remainder, pull request #165). Plan section: delivery/plan/kernel-plan-m4.md:456.

## What this phase changed, and why

`ExecutorRequest` had seven fields and none of them was the brief, although the
brief is an agent payload's entire input and the call site already held its
path. `ExecutorRecord` had three fields and was validated by nothing. This
phase adds the four fields M4-D-05 names, gives the record a schema, and adds
the mechanism that turns a missing field into a REFUSAL rather than an
`undefined` an adapter reads silently.

The mechanism is the part that is not just four fields. Adding optional fields
creates a new dangerous state: an adapter that needs the brief path, gets
`undefined`, and launches an agent with no input. The kernel cannot fix that
per adapter, so the ADAPTER declares what it needs and the kernel refuses
BEFORE it creates anything. The precedent is already in this repository and it
is exact: the `--deadline` parse-time rejection at src/commands/spawn.ts:104
carries the comment "a usage error creates nothing", written after an
unrepresentable value used to raise INSIDE the adapter once a worktree, a
branch and a pool record existed.

### The design decisions that are invisible in the diff

**`briefPath` is not optional and the three others are.** src/spawn.ts:103.
`assembleBrief` has already produced the path by the time the request is built,
so an optional `briefPath` would be an optionality the kernel never exercises:
every production path supplies it, and no test could construct the absent case
without inventing one. That is a field that cannot go red. `role`,
`declaredTier` and `phaseId` are `string | undefined` for the opposite reason:
nothing in the kernel produces them.

**One source for the requirable field names.** `requestFieldPresence` in
src/spawn.ts answers, for every field, whether the kernel can fail to supply
it, and `requirableRequestFields` at src/spawn.ts:165 reads the NAME list back
out of the same function. A list of legal names maintained beside a separate
list of presence tests is two things that drift, silently, in the direction
that matters. A registered test then derives the comparison from the request an
adapter is ACTUALLY handed, so a field added to `ExecutorRequest` and not to
the presence map reddens.

**The order of the two checks is load-bearing, and the code says so.**
src/spawn.ts:196 answers "is this a field at all"; src/spawn.ts:242 answers "is
this field absent". An unknown key is also absent, so a single check written as
`request[name] === undefined` would answer an adapter DEFECT with a message
about a missing flag, sending an operator to look for a `--modelName` the
kernel can never accept. The contract check therefore runs first, and one of
the red witnesses is the ORDER SWAP rather than a deletion.

**A non-array `requires` is refused rather than raised.** From M4-P4 the
adapter is resolved from the fleet home, so `requires` arrives from a module
the kernel did not write and the TYPE IS A PROMISE. `adapter.requires.filter`
on `undefined` would be a TypeError raised out of `spawnTask` with no reason
line, which is the same "refusal arriving as a crash" shape the check exists to
prevent, one level lower. This is a content-level addition the plan does not
name; it is declared as DEVIATION 4.

**No resolved model in the launch record, and no `phaseId` either.** The record
is written BEFORE the payload starts, which is the whole basis of the
launch-failed-versus-incomplete distinction, while a harness that requests one
model and is served another resolves mid-turn. A resolved model here would be a
value nobody could have observed at the moment it was written. M4-P7 carries
the resolved half. The record's key set is pinned by a registered test, so a
field arriving here reddens.

**The tier and the role cross verbatim.** The kernel holds no tier vocabulary
and no role vocabulary, so there is nothing here it could legitimately validate
against; a kernel that normalised either value would be holding one. The test
uses `Strongest-Available` and `clean-room-Reviewer`, mixed case and hyphens,
for exactly that reason.

## Acceptance criteria, walked

### Criterion 1: the four request fields

`briefPath: string` at src/spawn.ts:103, then `role`, `declaredTier` and
`phaseId`, each `string | undefined`. Walked by the test
"the executor request carries the assembled brief path, and the adapter reads a
real file at it", which asserts the file AT the path (not the path's shape),
asserts it is not the hook path, and asserts the three optional values cross
verbatim. PASS.

### Criterion 2: a declared requirement that is unmet creates nothing

`readonly requires: readonly string[]` at src/spawn.ts:294. The test
"an adapter requirement the spawn cannot meet refuses before a worktree, a
branch, a task directory or a pool record exists" asserts all four
post-conditions, because exiting nonzero is compatible with having created
three of them, plus a fifth (the adapter was never reached). The other
direction is in the same test: the same declaration with `role` supplied
reaches launch. PASS.

Two of the four post-conditions are not files. They are `git worktree list` and
`git branch --list`, so they are asserted against real captured output at
witness/captures/spawn-requirement-refusal-git-state.txt:1 rather than against
a hand-written string. Two details in that capture would have been got wrong by
hand, and both are recorded there: `git worktree list` RE-PADS its first column
when a longer path joins, and a branch checked out in another worktree is
printed by `git branch --list` with a `+` marker rather than `*` or a bare
indent.

### Criterion 3: an unknown field is refused at load, not at launch

The test "an adapter requiring a field the request contract has no name for is
refused as a contract defect, not as a missing value" asserts that the two
refusals SAY DIFFERENT THINGS, in both directions: the unknown-field reason
must not contain "supplied no value" and the absent-value reason must not
contain "has no field for". A conflated implementation exits nonzero on both
and is red here. The refusal also names the requirable fields, so the adapter
author can fix the defect from the message. PASS.

### Criterion 4: the record validates through the CLI

The test
"the launch record a real spawn wrote validates under --type executor-record,
one missing adapter is refused naming the field, and --type auto cannot resolve
it" runs a real `tiphys spawn` and validates the record THAT SPAWN produced,
never a fixture. Exit 0 on the real record, exit 1 with
`INVALID #/adapter required property adapter is missing` on a copy with the
field deleted. The wording is read out of
witness/captures/executor-record-validate-cli.txt:1 rather than retyped. PASS.

### Criterion 5: Kind A dangerous-instance on additionalProperties

The test "an executor record carrying an undeclared model field is refused, and
is accepted once additionalProperties is removed" lifts the REAL record out of
the capture, asserts `INVALID #/model property model is not permitted here`,
then deletes the keyword from the schema object and asserts the SAME instance
becomes accepted. That is the dangerous state, and it is a future one: nothing
in the document knows the word `model`, so `additionalProperties: false` is the
whole of what stops a later adapter smuggling a vendor model name into the
launch record. PASS.

### The members are dangerous states, not absent features

Each pair is two structurally different members of one class, which is the
"one witness is not a class" rule:

| witness | member 0 | member 1 |
|---|---|---|
| brief path | the path exists and is the WRONG FILE (the hook path), which a test asserting only `typeof` or `existsSync` would pass | the field is omitted, which is the `undefined` an adapter would launch on |
| unmet requirement | the derivation is emptied, so the check runs and finds nothing | the derivation is intact and the refusal is downgraded to a stderr warning, so the kernel knows and proceeds |
| unknown field | the contract check is deleted, so an unknown name is reported as a missing value | both checks remain and their ORDER IS SWAPPED, which destroys the distinction while both still refuse |
| echoed tier | the flag parses and its value is dropped at the CLI boundary | the request carries the value and the adapter does not copy it into the record |
| record validates | the type row is removed, so the type is unnameable | the row remains and points at another shipped schema, so the type is nameable and means the wrong thing |
| vendor names | a vendor token enters a source comment | a vendor token enters the shipped schema as an enum value |

The seventh behavior, `executor-record-rejects-undeclared-fields`, carries its
red witness INSIDE its own test rather than as a spec: the test removes
`additionalProperties` from the schema object and asserts that the same
smuggled record becomes ACCEPTED, then restores it. That is the Kind A
dangerous-instance form test/schemas.test.ts already uses for the four M3-P1
instances, and a spec-level mutation would be a second copy of it.

## The pre-submit hazard self-review

The hazard class: **a widened contract whose new fields are read as
`undefined` and proceed**, **a refusal that arrives after state exists**, and
**a vendor name entering `src/` and closing off every other harness**. What was
attacked, including the attacks that found nothing:

**"Can this pass while the thing it guards is broken?"** The unchanged-state
assertions in criterion 2's test compare two readings of the same two git
listings. A kernel that created nothing, ever, would satisfy them. That is a
guard that cannot go red, so the test carries a control arm: a SUCCESSFUL spawn
in the same test, whose listings must DIFFER from the baseline in the exact
shapes the capture records. This was found by asking the question, not by a
failure.

**A non-regular path at `briefPath`.** The brief path is produced by
`assembleBrief`, which the kernel owns, and the adapter reads it. This phase
does not add a read of an operator-supplied path. The test reads the file with
`readFileSync`, which is a test reading a file the test's own spawn created.
Nothing found.

**The adapter declaration as foreign input.** Found something, and it is
DEVIATION 4: `adapter.requires.filter` on a missing declaration is a TypeError,
not a refusal. Fixed before submitting.

**Requiring a field that is always supplied.** An adapter may declare
`requires: ["taskId"]`, which can never be unmet. That is not a defect: it is a
truthful declaration that happens to be always satisfiable, and the brief-path
witness's adapter declares exactly `requires: ["briefPath"]` for that reason.
What it means is that `requires` on a kernel-supplied field is documentation
rather than a guard, which is stated at the presence map rather than left for a
reader to discover.

**Could the two checks be reordered without any test noticing?** No: that is
witness member 1 of `spawn-adapter-requirement-unknown-field-refused`, measured
red above.

**Could a resolved model be added to the record without a test noticing?** No:
the key set is asserted with `assert.deepEqual` in criterion 6's test.

**Does the vendor-token test cover `bin/`?** Yes, `bin/` is walked. It does NOT
cover `templates/`, `checklists/`, `scripts/`, `test/` or `delivery/`, which is
stated in the non-coverage section rather than implied.

## WHAT THIS WORK DID NOT COVER

A reviewer's first check.

1. **The CLI cannot select an adapter, so criterion 2's literal sentence was
   not executed.** The criterion says an adapter declaring `requires: ["role"]`
   spawned without `--role` makes `tiphys spawn` exit nonzero. `tiphys spawn`
   reaches exactly one adapter until M4-P4 ships `--adapter`, and the shipped
   one declares `requires: []`. Both requirement tests therefore drive
   `spawnTask` through the `ExecutorAdapter` seam, which is the same seam every
   M4-P2 criterion used and for the reason that file's own section comment
   gives. What is NOT covered is the CLI's exit code and stderr on this path.
   DEVIATION 3.
2. **The vendor-token derivation covers five trees and no others.** `src/`,
   `bin/`, `schemas/`, `roles/` and root-level `*.yaml`. It does not read
   `templates/`, `checklists/`, `scripts/`, `tuition/`, `test/` or `delivery/`.
   The intake's property is about the shipped kernel surface, and `test/` in
   particular MUST be excluded: this phase's own witness spec
   witness/kernel-carries-no-vendor-model-names.json contains vendor tokens by
   construction, as the mutation text.
3. **`claude` is not in the token list, deliberately.** The intake states that
   the wider zero-vendor-NAMES property is NOT true and names two shipped
   schemas carrying a vendor-derived branch prefix. A list including `claude`
   would assert a property this repository does not have. The branch prefix has
   its own baseline in the same test, named file by file, whose job is to stop
   the set growing rather than to empty it. What is NOT covered: a vendor name
   that is neither one of the eleven tokens nor the branch prefix, for example
   a new vendor whose model family nobody has heard of yet. The constant is the
   place to add it.
4. **The schema is not exercised against a record any adapter other than
   `subprocessAdapter` wrote,** because no other adapter exists. The first one
   that does is M4-P5's plugin adapter, and nothing here forces it to write a
   record this schema accepts: the kernel does not validate `executor.json`
   after an adapter writes it. That is a real gap and it is not this phase's to
   close; the plan puts validation in the operator's hands (`tiphys validate`),
   not in the launch path.
5. **`--type auto` on an executor record is a usage error, not a resolution.**
   An executor record carries no `kind` field, because criterion 6 fixes the
   record's fields and `kind` is not among them. The type must be NAMED. This
   is asserted rather than left in a comment, so a later phase that gives the
   record a `kind` reddens. See DEVIATION 5 for why the alternative was
   rejected.
6. **No CI arm was observed.** Everything above is local, on the toolchain
   named below. The `push`-event arm of the `gates` workflow runs a different
   bundle from the `pull_request` arm (T-009) and neither was witnessed by this
   implementer.
7. **The scope gate cannot pass on this branch as things stand,** because the
   declaration is not on `main` at the merge base. DEVIATION 1.
8. **Concurrency, races and the watcher are untouched.** This phase adds no
   lease, no retry and no wait. The `requires` checks are pure functions over
   an options object and an adapter object, evaluated once, before any I/O.
9. **The three new flags are not validated against any vocabulary,** by
   design. `--tier bananas` is accepted and recorded. A kernel that refused it
   would be holding the tier vocabulary the plugin owns. What is NOT covered is
   therefore a caller who misspells a tier: nothing in the kernel will tell
   them, and M4-P7 is where a mapping could.
