## Change 1: a crash is not a skip (src/gates/run.ts)

### The mechanism, not the instance

The finding named `check-dual-review`'s precondition. The MECHANISM is:
**a verdict inferred from an exit code that two different situations produce
identically.** The evaluator's only "could not run" test was `spawnSync`'s
`error` field, which reports the LAUNCHER failing to spawn and nothing else.

### Derivation: measured, not predicted

Four commands, one `spawnSync` each, node v26.6.0, on this machine:

```
{"name":"missing script","status":1,"signal":null}
{"name":"node -e exit 1","status":1,"signal":null}
{"name":"non-executable","status":null,"signal":null,"error":"Error: spawnSync ./noexec.sh EACCES"}
{"name":"bad interpreter","status":null,"signal":null,"error":"Error: spawnSync ./badinterp.sh ENOENT"}
{"name":"absent launcher","status":null,"signal":null,"error":"Error: spawnSync definitely-not-a-command ENOENT"}
```

Rows one and two are indistinguishable to `spawnSync` and opposite in
meaning. Rows three, four and five ALREADY reached `error` before this
phase, because `spawnSync` sets `error` for them; they are regression
guards here, not the new behaviour. That is stated rather than smoothed
over, because criterion 4 names exactly those two and a reader would
otherwise assume they were newly fixed.

### What the derivation did NOT cover

- A script that EXISTS and whose own body throws still exits 1 and is still
  read as unmet. Nothing outside the script separates that from a deliberate
  refusal, and this phase does not try.
- An interpreter invoked as `node --flag script.mjs` puts the script after an
  option, and probe rule 4 skips it deliberately (see below).
- An operand named through an environment variable, or produced by a shell,
  is invisible to a probe over argv.
- The probe does not cover `kind: file-exists`, `file-absent`,
  `branch-matches` or `diff-touches`; those already fail closed on an
  unexaminable path and were not part of this finding.

### The fix

`probeCommandRunnable` establishes runnability BEFORE the spawn, so
"could not run" is a fact about the filesystem rather than an inference from
a number. The four-part path-operand rule and its residues are documented in
the block comment at src/gates/run.ts:629. It is applied in two places: the
`command-exit-zero` precondition evaluator, and the gate's own command.

### False-positive check against every real command in this repository

The probe was run over every `command` and every `precondition.command` in
`gates.manifest.json` AND in `gate-registry.yaml` (mode full), 30 commands.
Full output is in this history's appendix; the summary line is
`total 30 not-runnable 0`. `credential-token`'s precondition, whose inline
`node -e` code is exactly the shape rule 4 exists to protect, probes zero
elements.

## Change 2: a phase's own evidence is a standing extra (src/gates/scope.ts)

The rule and its three parts are documented at src/gates/scope.ts:512. Two
points that are decisions rather than mechanics:

**The prefix list is derived, and it is DELIBERATELY SHORTER than what is in
use.** `clean-room-`, the empty prefix and `arbitration-` come from the
spec's own list and from criterion 8; `verification-` comes from CLAUDE.md's
durability table, which names `delivery/review/verification-<phase>-fix-round.md`
as a required artifact. Names in use on `main` and NOT covered:
`final-review-<phase>.md`, `open-call-<phase>-*.md`. Nothing binding
requires those, so a phase that needs one declares it. That is a limit, not
an oversight, and it is written here so a later reviewer does not have to
guess which it was.

**The prefix boundary is load-bearing.** `m3-p1` is a proper string prefix
of `m3-p11`. A `startsWith` with no boundary hands every M3-P11 review
document to the M3-P1 branch, which is the exact cross-phase leak criterion
8's second arm refuses. It is witnessed as its own arm, on those two ids.

**Directory nesting is refused.** `delivery/review/evidence/` exists on
`main`; a path one level deeper is NOT a standing extra, whatever its
basename says, because a directory prefix would otherwise sweep in a whole
subtree. Witnessed as arm 4.

## Change 3: the declaration is read from BOTH sides (src/gates/scope.ts)

Additions are allowed and PRINTED by name; removals are red; a head that
deletes the declaration outright is red. `id` and `branch` are compared as
scalars and any difference counts as a removal, because they are the two
fields every anti-widening cross-check is anchored to.

### THIS WEAKENS AN EXISTING ACCEPTANCE CRITERION, AND IT IS SAID PLAINLY

M2-P4's criterion 5 is the anti-widening property, and its witness was the
test `a declaration widened on the head branch to add an undeclared touch
does not change the verdict`. That criterion is deliberately narrowed here,
on the authority of delivery/plan/m3-p11-phase-spec.md:156. What survives:
the merge base is still the yardstick for `id` and `branch`, the record
still pins the merge-base blob's sha256, and a REMOVAL is still refused.
What is traded away: an addition at the head is no longer refused, and the
only protection left against it is the printed line and a reviewer who reads
it.

### The masked pass, found by running the old test rather than reasoning about it

With change 3 in place, the old anti-widening test STILL PASSED, and it
passed for a different reason than the one it named. Its branch touched
`src/c.ts` AND `delivery/plan/phase-declarations/m2-p4.json`; the head
declaration authorized the first, so the violation became the declaration
FILE, and `src/c.ts` matched the test's assertion only through the new
amendment note. A test passing for a reason other than the one it names is
the shape this repository keeps paying for, so it was restated with both
reasons separated into two arms rather than left green.

A consequence worth stating because it is the mechanism that keeps this
honest: **a phase amending its own declaration must also authorize the
declaration FILE, and the only way to do that is to add its path at the
head, which is itself printed.** So every amendment is named twice.

### What change 3 does NOT do

- It does not let a phase reach a path that is on neither declaration. A
  changed path outside the union is still red.
- It does not make the printed line enforceable. A reviewer who ignores it
  gets no protection at all. This is a process control, not a gate.
- It does not touch how `--phase`, `--base` or `--head` are cross-checked.

## The chicken-and-egg: this phase cannot use its own change

The scope gate reads the declaration and the standing-extras list from the
MERGE BASE, which for this branch is `main` BEFORE change 2 lands. So during
M3-P11 itself, evidence about M3-P11 still cannot sit on the M3-P11 branch
without reddening the gate: the running code is the merge base's, not this
branch's. Change 2 was therefore built and tested against staged fixtures
and NOT used to carry this phase's own reviews. The asymmetry is expected
and is not a defect; the first phase that benefits is the one after this one.

## Residues, open questions, and what this phase did not do

Stated as open questions where they are open, not as settled facts.

1. **Criterion 1's stdout half is not delivered**, for the scope reason given
   above. `src/commands/gates.ts` is the file that would carry it.
2. **Spec step 3 asks for "an evaluated precondition record on EVERY path",
   and the could-not-run path deliberately carries none.**
   `src/gates/result.ts:99` documents `PreconditionRecord.met === false` as
   meaning EVALUATED AND UNMET, and says in the same sentence that an
   evaluation which could not conclude produces no record at all. Attaching a
   record with `met: false` to a crash would make the record say the opposite
   of what happened, and correcting that comment means editing
   `src/gates/result.ts`, which is not on this declaration. The reason is
   carried in the gate result's `detail` instead, and the presence or absence
   of the `precondition` field is itself the discriminator: `not-applicable`
   plus a record is a skip, `error` plus no record is a crash. Whether the
   record should be added, with the comment corrected, is an open question for
   the orchestrator.
3. **The path-operand rule has four stated limits** (an operand after an
   option is skipped; an operand carrying whitespace is skipped; an operand
   with no `/` is skipped; a launcher resolved through `PATH` is left to
   `spawnSync`). Each was chosen to protect a real declaration in this
   repository, and each is a place a genuinely unrunnable command would still
   be read as unmet. They are documented at the rule rather than only here.
4. **A script that exists and throws is still read as unmet.** I did not find
   a way to separate that from a deliberate refusal without changing the
   precondition contract, which the phase spec does not authorize and which
   would break `credential-token`'s declared `node -e` precondition. That is
   what I looked at and did not solve, stated as an open question rather than
   as an impossibility.
5. **No survey of historical `not-applicable` lines was run.** The spec says
   explicitly that this phase does not re-audit past evidence, and it has not
   been done here either. The claim that the verdict was unreadable follows
   from the code path plus the two-arm capture, not from a census.
6. **The eleven gates whose commands name unshipped paths are not fixed.**
   They now report `error` honestly instead of the old mixture, which is the
   point: the packaging defect becomes visible. It belongs to M4 under DR-0029.
7. **`final-review-<phase>` and `open-call-<phase>` are not standing extras.**
   Deliberate; see change 2.
8. **The declaration-addition rule is self-authorizing for the declaration
   file itself.** A branch adds `delivery/plan/phase-declarations/<phase>.json`
   to its own head declaration in order to touch it. That is visible (both the
   addition and the path are printed) but it is not refused. Whether that
   should be a standing extra instead is a question for the orchestrator; the
   spec does not say.
9. **The `citations` gate did not run on this branch** (its precondition is
   diff-touches over six `delivery/` locations, none of which this branch
   changes), so nothing mechanically checked this work history's `path:line`
   citations. They were checked by hand against the branch's own tree, and the
   two that pointed at the wrong line in `src/gates/run.ts` and
   `src/gates/scope.ts` were corrected in commit ef559ad before this section
   was written.
