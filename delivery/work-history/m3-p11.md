## Change 1: a crash is not a skip (src/gates/run.ts)

### The mechanism, not the instance

The finding named `check-dual-review`'s precondition. The MECHANISM is:
**a verdict inferred from an exit code that two different situations produce
identically.** The evaluator's only "could not run" test was `spawnSync`'s
`error` field, which reports the LAUNCHER failing to spawn and nothing else.

### Derivation: measured, not predicted

Four commands, one `spawnSync` each, node v26.6.0, on this machine:

```
{"name":"missing script","status":1,"signal":null}
{"name":"node -e exit 1","status":1,"signal":null}
{"name":"non-executable","status":null,"signal":null,"error":"Error: spawnSync ./noexec.sh EACCES"}
{"name":"bad interpreter","status":null,"signal":null,"error":"Error: spawnSync ./badinterp.sh ENOENT"}
{"name":"absent launcher","status":null,"signal":null,"error":"Error: spawnSync definitely-not-a-command ENOENT"}
```

Rows one and two are indistinguishable to `spawnSync` and opposite in
meaning. Rows three, four and five ALREADY reached `error` before this
phase, because `spawnSync` sets `error` for them; they are regression
guards here, not the new behaviour. That is stated rather than smoothed
over, because criterion 4 names exactly those two and a reader would
otherwise assume they were newly fixed.

### What the derivation did NOT cover

- A script that EXISTS and whose own body throws still exits 1 and is still
  read as unmet. Nothing outside the script separates that from a deliberate
  refusal, and this phase does not try.
- An interpreter invoked as `node --flag script.mjs` puts the script after an
  option, and probe rule 4 skips it deliberately (see below).
- An operand named through an environment variable, or produced by a shell,
  is invisible to a probe over argv.
- The probe does not cover `kind: file-exists`, `file-absent`,
  `branch-matches` or `diff-touches`; those already fail closed on an
  unexaminable path and were not part of this finding.

### The fix

`probeCommandRunnable` establishes runnability BEFORE the spawn, so
"could not run" is a fact about the filesystem rather than an inference from
a number. The four-part path-operand rule and its residues are documented in
the block comment at src/gates/run.ts:629. It is applied in two places: the
`command-exit-zero` precondition evaluator, and the gate's own command.

### False-positive check against every real command in this repository

The probe was run over every `command` and every `precondition.command` in
`gates.manifest.json` AND in `gate-registry.yaml` (mode full), 30 commands.
Full output is in this history's appendix; the summary line is
`total 30 not-runnable 0`. `credential-token`'s precondition, whose inline
`node -e` code is exactly the shape rule 4 exists to protect, probes zero
elements.

## Change 2: a phase's own evidence is a standing extra (src/gates/scope.ts)

The rule and its three parts are documented at src/gates/scope.ts:512. Two
points that are decisions rather than mechanics:

**The prefix list is derived, and it is DELIBERATELY SHORTER than what is in
use.** `clean-room-`, the empty prefix and `arbitration-` come from the
spec's own list and from criterion 8; `verification-` comes from CLAUDE.md's

`final-review-<phase>.md`, `open-call-<phase>-*.md`. Nothing binding
requires those, so a phase that needs one declares it. That is a limit, not
an oversight, and it is written here so a later reviewer does not have to
guess which it was.

**The prefix boundary is load-bearing.** `m3-p1` is a proper string prefix
of `m3-p11`. A `startsWith` with no boundary hands every M3-P11 review

8's second arm refuses. It is witnessed as its own arm, on those two ids.

**Directory nesting is refused.** `delivery/review/evidence/` exists on
`main`; a path one level deeper is NOT a standing extra, whatever its
basename says, because a directory prefix would otherwise sweep in a whole
subtree. Witnessed as arm 4.

## Divergence from a WRITTEN spec step, taken deliberately

Spec step 3 (delivery/plan/m3-p11-phase-spec.md:80) says: "Emit an evaluated
precondition record on every path, so the reason is DATA and a reader never
has to guess which of the three happened." That sentence is quoted verbatim
from the cited line and is the spec's wording, not a claim of this document.
**This phase does not do that on the could-not-run path, and that is a
departure from a written step of the spec, not an oversight and not an
interpretation.**

The reason is a constraint the spec could not have seen, because it lives in a
file the spec does not cite. `src/gates/result.ts:99` defines
`PreconditionRecord` and documents, in the same sentence, that `met: false`
means EVALUATED AND UNMET and that an evaluation which could not conclude
produces no record at all. Attaching a record with `met: false` to a command
that did not run would therefore make the record assert the opposite of what
happened, in a field a consumer is invited to trust. Correcting that
definition means editing `src/gates/result.ts`, which is on no part of this
phase's declaration and which the orchestrator has ruled should be left alone.

What is delivered instead, and it satisfies the step's STATED PURPOSE without
the lie: the reason is data in the gate result's `detail`, and the presence or
absence of the `precondition` FIELD is itself the discriminator. The three
outcomes are distinguishable from the record alone, by this table, and the
worked instance is the two-arm capture at
witness/captures/gate-precondition-crash-vs-skip.txt:1, whose four quoted
records are one of each shape:

| outcome | `status` | `precondition` field |
|---|---|---|
| ran, precondition met | the gate's own verdict | ABSENT |
| ran, precondition unmet | `not-applicable` | present, `met: false` |
| could not run | `error` | ABSENT |

**ROW ONE SAID "present, `met: true`" UNTIL FIX ROUND 1, AND THAT WAS FALSE
(finding C-3).** No such record is produced anywhere: `precondition:` is set
at exactly ONE site in `src/gates/run.ts`, inside the unmet branch, and the
string `met: true` occurs nowhere in that file. On the met path the runner
ingests the gate's own record verbatim and adds nothing to it, so a green
gate's record carries no `precondition` key at all. A clean-room reviewer
measured that directly against a gate whose precondition exits 0.

The DIVERGENCE'S SUBSTANCE IS UNAFFECTED, and saying so is not a softening:
the three outcomes are still distinguishable from the record alone, because
`status` alone already separates them (`error`, `not-applicable`, and the
gate's own verdict). What was wrong is the specific MECHANISM the document
offered as the replacement for the record the spec asked for, and a work
history is the artifact a later reviewer trusts. The corrected table makes
`status` the discriminator and the `precondition` field a corroborating
detail on the one row that has one, which is what the code actually does.

The met-path gap is PRE-EXISTING (this phase's diff does not touch that path)
and is not attributed to this phase. It is also not a defect to fix here:
adding a record on the met path would be a change to a shipped type's
observable output, on a file this declaration does not carry.

The orchestrator accepted this and asked that the divergence be recorded
plainly. It is recorded here as a divergence, and it is also listed in the
deviations section, so a reader who reads only one of the two still finds it.

## Mechanism 1: runnability was established by testing a PROPER SUBSET of what running actually requires

### The mechanism, not the finding

H-1 is a finding: "an unreadable operand is reported runnable". The MECHANISM
is that the probe decided "this command can run" from a proper subset of the
conditions running actually needs, and then let an exit code decide the rest.
It has two independent halves, and fixing either alone leaves the other.

**HALF A, the CONDITIONS tested per examined element were incomplete.**
`classifyEntry` answers "does it exist" and "is it a regular file". It does
not answer "may this process OPEN it". A `chmod 000` script is present and
regular; the probe passed it; `node` launched fine so `spawnSync`'s `.error`
stayed undefined; the open failed with EACCES; the exit was 1; and 1 meant
unmet. Existence and type are two of the three conditions for an open, and
permission was untested.

**HALF B, the SET of examined elements was a proper subset of the path-shaped
ones.** The four-part rule skips an operand after an option and one carrying
whitespace. The hazard reviewer confirmed BY EXECUTION, through the packed
CLI, that both produce the same wrong verdict rather than merely a worse
message.

### The fix, and why the two halves are fixed in two different places

Half A is closed by asking the COMPLETE question. A path can be opened for
reading exactly when `access(R_OK)` succeeds, which resolves every path
component's traversal permission and the file's own mode in one call, for the
CALLING PROCESS. That last clause is the whole reason it is the right
primitive: the process running the probe is the process that will spawn the
command, so the calling uid is the uid to ask about. The launcher keeps its
pre-existing UID-INDEPENDENT mode-bit test and gains `access(X_OK)` as well,
because those answer two different questions and the original comment was
right about its own one. All of it now lives in a single function,
`probeOpenable`, so there is one enumeration of "what opening a file
requires" rather than one per call site.

Half A alone does NOT close the mechanism, and this is the part a fix limited
to the named finding would have missed.

I did not find a way to close half B by widening the pre-spawn rule, and I am
stating that as a search result rather than as an impossibility. What I
looked for was a test that separates an option's VALUE from an operand, and
every candidate I could construct required knowing the launcher's own flag
grammar, which is the trap the runner's own header already forbids (`node
--no-warnings x.mjs` and `node -e x.mjs` differ in nothing a general rule can
read). So half B is closed instead on the OTHER SIDE OF THE SPAWN, where the
cost of being wrong has flipped:

> A nonzero exit is evidence about a command's own semantics only if
> everything the command needed in order to reach its own logic was
> available.

After a nonzero exit, `attributionGaps` scans EVERY argv element containing
`/`, at any position, whitespace or not, launcher included, and any element it
fails to open makes the exit UNATTRIBUTABLE, which is `error`, not
`not-applicable`. It runs on the nonzero arm ONLY: an exit of 0 is its own
proof that the command ran, so no declaration that succeeds can be touched by

## THE MECHANISM, not the instances

The verifier reported two instances (an inline `node -e` existence check, and a
self-deleting one-shot script). They are not two variants of one bug. They are
two mechanisms, and fixing either alone leaves the other:

**MECHANISM A, THE WRONG ELEMENTS.** A verdict was decided by a SHAPE TEST over
a string: `element.includes("/")` was used as a proxy for "this element is a
path the command needed". The proxy is neither necessary nor sufficient.

- NOT SUFFICIENT: inline code, a URL, an `--opt=/value` pair, a date, a regex
  and plain division all contain `/` and none of them is a path.
- NOT NECESSARY: `node check.mjs` names a real script with no `/` in it. This
  is verifier finding 1, and it is the SAME mechanism as finding 2 seen from
  the other side, which is why one change closes both.

**MECHANISM B, THE WRONG MOMENT.** The scan ran AFTER the spawn and probed the
filesystem then. The question it answers ("did this command have what it needed
in order to run") is a question about the state the command was launched into.
Reading it afterwards reads the command's own effects back as evidence about
its inputs, so a script that legitimately decides "unmet" and removes one of
its own argv paths as an ordinary last act is reported `error`. Deterministic,
no timing window.

**MECHANISM C, found by the derivation rather than reported by the verifier.**
The scan asked "is this a readable REGULAR FILE" when the question is "is this
path there and usable". A directory operand is a legitimate path. Found by
enumerating this repository's own declarations: see the derivation below.

Why any of this is worse than the defect it replaced: `decideAggregate` checks
`counts.error > 0` FIRST, before red and before required-not-applicable, so ONE
false error on ONE merely-conditional gate fails the ENTIRE bundle. A silent
skip is wrong and quiet; this was wrong and total.
