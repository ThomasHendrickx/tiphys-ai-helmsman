## What this phase is, and what it deliberately is not

Tests and a probe only. No mechanism, no new command, no change to
`src/lock.ts`, no new export from `src/`. Nothing under `src/` or `bin/` is
touched at all.

The ordering is the point. The red-witness rule's stronger form says a test
must be red against the DANGEROUS STATE rather than against an absent feature.
The dangerous state here exists today and is reachable, so the witnesses are
built now, against today's code, before any exclusion layer exists to make them
green for the wrong reason. `src/lock.ts` is not defective: src/lock.ts:63
declares its exclusion domain as one filesystem and one clock and explicitly
does not claim the cross-environment case.

### 1. Criterion 1's refusal signature is taken from the wrong line

The criterion asks for `B refuse <first line of git stderr>`. Measured: this
container's global git config sets `push.negotiate` true
(`git config --show-origin --get-all push.negotiate` reports

`push.negotiate=false` command-scoped so the capture is a property of git
rather than of one machine. Nothing is hand-written, so T-003 still holds.

## The design decision the dispatch asked me to make and justify

**The two property witnesses (single holder across environments) are RED
against today's code. I gated them and I am saying so explicitly.**

The options I considered and why I rejected the others:

- **Leave them failing.** A red branch cannot be reviewed or merged, and the
  suite gate reports `failing test:` as a finding. Rejected.
- **`todo` rather than `skip`.** The suite gate counts todo separately and it
  reads as "someone meant to write this", which is the opposite of the truth
  here: they ARE written and they DO run.
- **Invert them so they assert the dangerous state.** That is a real technique
  and I used it, but ONLY as group 2. On its own it loses the statement of
  what must become true.
- **Gate on the mechanism's presence, with a self-expiring guard.** Chosen.

**The trade-off, stated rather than buried: a skipped test is a guard that
cannot go red.** That is the exact shape T-008's postscript records, and the
same shape as the ASCII check that could not see NUL. Two things bound it, and
neither alone is enough.

1. **Group 2 asserts the dangerous state directly** (both environments acquire,
   with both holder ids, both files on disk and both leases unexpired). Those
   tests go RED the day the dangerous state goes away, so the transition is
   detectable from the other side without the gate being involved at all.
2. **Group 4 makes the gate SELF-EXPIRING.** One test asserts that
   `src/exclusion.ts` is still absent. The day M4-P21 adds it, that test goes
   red and names, in its own failure message, the three edits required. The
   skip therefore cannot outlive the thing it waits for.

**A third thing was needed and is easy to miss: the gated witnesses could be
red because their assertion is UNSATISFIABLE rather than because the mechanism
is missing, and I did not find a way for a reader to tell those two apart from
the skip line alone.** So there is an
anti-vacuity control, `the at-most-one-live-lease assertion is satisfiable
within one fleet home`, which runs the SAME `exactly one winner` assertion
against two acquires on ONE lock path, where `lock.ts` already excludes. It is
green. So the assertion is satisfiable by real code and what the gated
witnesses wait for is the mechanism.

**The hole I did NOT close, stated as an open question.** If M4-P21 names its
module something other than `src/exclusion.ts`, the gate keys off a file that
never appears, the two witnesses skip indefinitely and the expiry guard stays
green. I did not find a way to key the gate on something M4-P21 is structurally
forced to touch, because the plan's M4-P21 files-to-touch list does not include
`test/cross-environment.test.ts` at all. That is recorded below as the scope
gap it is, rather than as something I solved.

the same shape:

```
Error: pattern ^(?:M([0-9]+))$ did not complete within 250ms against a value of length 2 (possible catastrophic backtracking)
    at boundedExec (file:///tmp/m4p20-base/src/gates/coverage.ts:260:11)
```

A two-character value against a trivial anchored pattern. That is a
WALL-CLOCK budget losing to CPU starvation, not backtracking.

**The control that settles it:** the same file, same head, same interpreter,
same build state, run ALONE at load average 18.50:

```

```

exit 0. So the failures are a property of the CONTAINER'S LOAD, not of the
base commit.

**I am not claiming the branch is immune to the flake.** Two clean branch runs
against two dirty base runs is a small sample, and the flaky file is one this
phase does not touch. The honest reading is that the flake is real, is in
`test/coverage-gate.test.ts`, is load-driven, and happened not to fire in
either branch run.

**The consequence, and it is for every wave-1 implementer, not just me.**
Standing warning 12's last paragraph says a red on the default toolchain is no
longer proof of a red branch. This adds an axis to that: **a red under load is
not proof of a red branch either, and unlike the interpreter axis it does not
reproduce**, which runs 3 and 4 show directly by failing DIFFERENT tests at the
same head. Re-reading the assertion does not settle it, because the assertion
is right in both runs and the value it is fed is two characters long. What
settled it here was running the suspect file alone, at a recorded load, and
getting 17 of 17. Every suite number in this document carries its load.
