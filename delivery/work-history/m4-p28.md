## 1. The mechanism, not the instance

The finding is "the coverage gate reddens on patterns that cannot backtrack".
The MECHANISM is **a guard whose condition measures elapsed wall clock and
reports the result as a property of the thing it was timing.** Elapsed time is
work divided by available CPU, so such a condition reddens whenever the machine
is busy, and the message it prints names a cause that is not the cause.

The instance sat at src/gates/coverage.ts:235 on the base commit:
`REGEX_EXEC_TIMEOUT_MS = 250`, handed to `vm` as a wall-clock `timeout` at
src/gates/coverage.ts:257, with an interruption reported at
src/gates/coverage.ts:261 as

```
pattern <source> did not complete within 250ms against a value of length <n>
(possible catastrophic backtracking)
```

The word "complete" is the substitution: elapsed time presented as evidence
about the regex.

### What the derivation did NOT cover

Read this before any row below; it is the reviewer's first check.

- **`scripts/*.mjs` and `.github/workflows/`.** The grep was scoped to `src/`
  and `bin/`, which is the shipped surface DR-0027 blocks on. A script gate or
  a workflow step carrying a wall-clock budget would not appear. The plan's own
  "what this revision did NOT cover" names the same gap for a different
  pattern (delivery/plan/kernel-plan-m4.md:3830).
- **The grep's own blind spots, which are real.** It matches four written
  forms: `timeout: `, `setTimeout(`, `Date.now() - `, and `performance.now()`.
  An elapsed-time comparison written any other way is invisible to it, and at
  least three such forms exist in this language: `Date.now() >` against a
  stored deadline, `process.hrtime.bigint()`, and a subtraction whose operands
  are on different lines. Lease expiry in `src/lock.ts` is deadline arithmetic
  of exactly that kind. It was NOT enumerated and it is not claimed to be
  clean; it is, however, a case where elapsed time is the actual subject
  (C-2 makes liveness lease freshness on purpose), which is the opposite of
  this mechanism.
- **The eleven subprocess deadlines were classified by reading, not by
  execution.** Each was read at its call site and each names the timeout in
  what it returns. None was forced to time out and observed. The witness
  harness row is the exception: its `error` behaviour was observed in this
  phase by accident.
- **The other patterns the coverage gate compiles.** Carried forward from the
  verification document unchanged: nobody has shown that every pattern in
  `KERNEL_COVERAGE_CONFIG` is free of catastrophic backtracking. The new
  instrument makes that question answerable without noise; it does not answer
  it.
- **Whether this defect has ever reddened a CI run here.** No run was checked
  for the signature. Everything below is about the mechanism, not about damage
  already done.
- **`test/` and the harness.** Only shipped source was enumerated. A test
  asserting on elapsed time is a different problem (a flaky test rather than a
  wrong verdict) and one such assertion was REMOVED by this phase, see
  section 3.

## 2. What was rejected

**Raising the constant.** The plan names this as out of scope
(delivery/plan/kernel-plan-m4.md:3784) and the verification document names it
as the wrong fix. It keeps the instrument and only moves the load at which the
instrument lies. Nothing in this phase raises it; the CPU budget is the SAME
number, 250, now applied to a different quantity.

**Deleting the bound.** CR-991 put it there because a catastrophic match never
returns, and removing it would restore a hang. The wall-clock interrupt is kept
for exactly that reason and demoted from a verdict to patience.

**Strengthening the static shape screen instead.** `catastrophicShapeReason`
(src/gates/coverage.ts:415 at the head) already refuses the nested-quantifier
family at config time. Extending it to alternation ambiguity would refuse some
legitimate patterns and would still be incomplete, and it does not address the
mechanism at all: the false red came from the EXECUTION bound. The screen is
untouched by this phase.

## 3. What changed

`src/gates/coverage.ts`, one function and its constants.

**The verdict instrument is `process.threadCpuUsage()`.** It reports the CPU
time this thread has consumed. A busy neighbour does not add to it, because a
descheduled thread consumes no CPU while it is not running. The regex executes
on this thread inside `runInContext`, so the delta across that call is the work
the regex did.

**The wall-clock interrupt survives as PATIENCE.** One attempt runs with a
`vm` timeout, now 500ms, twice the CPU budget. Whatever the outcome, the CPU
consumed is added to a running total:

- total CPU at or above 250ms: `RegexBoundExceededError`, a verdict about the
  pattern. A busy machine cannot cause this.
- the match finished: return the result.
- interrupted with the total still far below budget: the machine was busy.
  Double the patience and try again, up to four attempts.

**A second error class, `RegexBudgetUndeterminedError`**, for four exhausted
attempts. It names the CPU consumed, the wall clock spent and the load average,
and says in words that no verdict about the pattern was reached. Under M2-C-3 a
check that cannot reach a verdict reports error, and the gate's existing
top-level catch at src/gates/coverage.ts:1039 already turns any throw out of
`checkCoverage` into an `error` record rather than a red one. It is
deliberately NOT a subclass of `RegexBoundExceededError`, so a `catch` meaning
"the pattern is dangerous" cannot swallow "the machine was busy".

**A non-timeout throw out of `runInContext` is now undetermined too.** The old
code funnelled every throw into the catastrophic-backtracking message, which is
the same substitution one cause over.

**An optional third argument** lets a caller override the CPU budget, the
patience and the attempt count. The witness test varies the PATIENCE only; the
verdict instrument stays at its shipped default, so the test cannot pass by
weakening the thing under test.

**`REGEX_EXEC_TIMEOUT_MS` is gone.** It was exported, and `src/index.ts` does
not re-export this module and `package.json`'s `exports` map publishes only
`.`, so nothing outside the repository could see it. The only other reference
was the test.

**One test assertion was removed rather than ported.** The old test asserted
`elapsedMs >= REGEX_EXEC_TIMEOUT_MS` and `elapsedMs < ... + 2000`. Those are
assertions ABOUT WALL CLOCK inside the suite, which is the same instrument this
phase is removing from the gate; keeping them would have left the suite
load-dependent for the same reason the gate was. The replacement asserts on the
reported CPU figure and on the error class.

**One import was moved.** `import { cpus, loadavg } from "node:os";` sits BELOW
the `node:vm` import, not above it. The stored witness
`coverage-gate-main-module-guard-survives-a-symlink` carries a patch member
whose first hunk's context is lines 1 to 5 of this file; adding a line above
made that hunk fail to apply and turned the `red-witness` gate into an `error`.
Captured, before the move:

```

coverage-gate-main-module-guard-survives-a-symlink: error: member 1 (patch
witness/patches/m4-p2-normalise-but-still-compare-strings.patch): patch ...
```

### Criterion 3: the two members are structurally different

`(a+)+b` is a NESTED UNBOUNDED QUANTIFIER: a group whose body ends in `+`,
itself quantified with `+`. `(a|a)+b` has no nested quantifier at all; the
blow-up comes from two alternatives matching the same text, so every position
splits the search.

The difference is asserted mechanically rather than argued. The test asserts
that the static shape screen is BLIND to the second one before running it:

```
assert.equal(coverageModule.catastrophicShapeReason("(a|a)+b"), undefined);
```

Measured directly: `catastrophicShapeReason('(a+)+b')` returns a reason,
`catastrophicShapeReason('(a|a)+b')` returns undefined. So the screen catches
member 1 and cannot catch member 2, which is the sharpest available evidence
that they are not one pattern twice, and it also proves that the EXECUTION
bound and not the screen produced member 2's verdict. MET.

  moves in steps of roughly 1ms: twenty back-to-back measurements of a 20,000
  iteration loop returned 0 microseconds sixteen times and 1051 to 2290
  microseconds four times. Against a 250ms budget that is 250 steps of
  resolution, which is ample, but on a platform with coarser accounting the
  budget could be reached in fewer steps than it looks. No other platform was
  measured.
- **The `process.cpuUsage()` fallback was not exercised.** It is there for an
  interpreter without `process.threadCpuUsage` (absent on node v20.20.2, which
  a stripped environment here resolves; present on v22.22.2 and v26.6.0). The
  package floor is 26, so the fallback should be unreachable in practice, and
  no test forces it. It is process-wide, so it OVER-estimates and cannot let a
  catastrophic pattern through, but that is an argument and not a measurement.
- **The worst-case wall clock grew.** A pattern that really backtracks now runs
  for up to 500ms instead of 250ms before it is reported, and an undetermined
  result costs up to 7.5 seconds of patience across four attempts. Nothing
  measured the gate's total runtime under sustained heavy load with a hostile
  config, and under such load a benign pattern that is repeatedly interrupted
  now retries where it used to throw. That is slower, and the slowness is the
  price of not lying.
- **No CI run has been checked for the old signature**, so whether this ever
  reddened a real pull request here is still unknown. Carried forward from the
  verification document unchanged.
- **The other patterns `KERNEL_COVERAGE_CONFIG` compiles** were not analysed

- **The macOS arm.** The new test spawns `sleep` through `spawnSync`. `sleep`
