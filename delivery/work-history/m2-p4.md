## Real captured git output the parser is pinned against

Captured with a scratch repo (own GIT_AUTHOR_*/GIT_COMMITTER_* env, no
global config touched), covering modify, add, delete and rename in one
diff:

```
$ git diff --name-status <base> <head>
M	src/a.ts
A	src/fresh.ts
R100	src/old.ts	src/new.ts
D	src/todelete.ts
```

And the two `git show <sha>:<path>` outcomes that distinguish "declaration
absent at the merge base" (RED) from any other git failure (ERROR):

```
$ git show <sha>:nope.json
fatal: path 'nope.json' does not exist in '<sha>'
(exit 128)

$ git show <sha>:a.txt
hi
(exit 0)
```

And an unresolvable ref for `git merge-base`, which must be ERROR (a merge
base that cannot be resolved means the gate cannot reach a verdict, never a
guessed red or green):

```
$ git merge-base <sha> nosuchref
fatal: Not a valid object name nosuchref
(exit 128)
```

The parser recognizes "does not exist in" and "exists on disk, but not in"
as the RED-classifying git message and treats every other nonzero exit from
`git show` as ERROR. Only the first pattern was reproduced above; the second
is git's own message for a path that exists on disk in the working tree but
not in the named commit. It was not independently reproduced in this
container and is included on the strength of git's own source text alone.
Recorded as a derivation gap rather than asserted as covered: if it never
fires, the affected input degrades to ERROR rather than a wrongly-guessed
RED, which is the fail-closed direction (M2-C-3), not the dangerous one.

## Step 3 and 4: `src/gates/scope.ts`

Built as a STANDALONE script, not a `tiphys gates` subcommand. This phase's
declaration (`delivery/plan/phase-declarations/m2-p4.json`) does not list
`src/cli.ts` or `src/commands/gates.ts`, and none of the seven concurrent
M2-P2 to M2-P8 declarations lists those two files either (checked directly:
`grep -l 'cli.ts\|commands/gates.ts' delivery/plan/phase-declarations/*.json`
matches nothing), so the manifest's `scope` entry invokes
`node src/gates/scope.ts` directly, the way `manifest-self-check` invokes
`bin/tiphys.ts` for the one gate M2-P1's own file list owns. The module
exports `main(argv)` and only calls `process.exit` when
`pathToFileURL(process.argv[1]).href === import.meta.url`, so a test can
`await import(...)` it for its pure helpers without triggering the CLI (the
same computed-URL import pattern as `test/doctor.test.ts`, CLAUDE.md warning
4) while a direct `node src/gates/scope.ts ...` invocation still runs it.

The anti-widening mechanism (criterion 5): `git merge-base --base --head` is
resolved first (error if unresolvable), then the declaration is read with
`git show <mergeBaseSha>:<declarationsDir>/<phase>.json`, which reads the git
OBJECT DATABASE and never opens the working tree at that path, so an edit to
the declaration committed on the audited branch cannot be seen by this read.
Diffs are computed with `git diff --name-status <mergeBaseSha> <head>`, never
`<base> <head>` directly and never against `main`'s current tip, per the
hazard class's fourth item.

`gates.manifest.json`'s new `scope` entry declares `"parameters": ["base",
"head"]` in addition to the `phase` requirement `branch-matches` already
implies, so the runner ALWAYS forwards the caller's real `--head` (see step 1:
without this, on a `pull_request` event the gate would silently default to
bare `HEAD`, the synthetic merge commit CR-902 warns about).

`--phase`'s value convention: this build assumes `--phase` is the lowercase
hyphenated form that already names both the declaration file
(`delivery/plan/phase-declarations/<phase>.json`) and the work-history
standing extra (`delivery/work-history/<phase>.md`), for example `m2-p4`.
The plan does not spell this convention out explicitly for the `--phase`
CLI value (only for file names), so this is a DEVIATION worth naming rather
than silently assuming: it is the only convention consistent with the
existing eight declaration filenames and the eight work-history filenames on
`main`, and the branch-matches precondition's own token substitution
(`{phase}`) is documented as a literal string substitution into the branch
name, which for this repository's branches is exactly this lowercase form
too (`claude/m2-p4-scope-auditor`).

## Pre-submit hazard self-review (SHARED-BRIEF, before final gates)

Plan section 3's M2-P4 hazard class, walked item by item:

1. **"A declaration widened on the branch being audited."** Closed by
   reading the declaration through `git show <mergeBaseSha>:<path>`, never
   the working tree and never `--head`. Red-witnessed as the dangerous state
   (Defang 1 above): patching the read to use `head` instead of `mergeBase`
   turns the anti-widening test red. Evidence: criterion 5's test and its
   defang, and the "F" manual scenario, both above.
   **CORRECTION, fix round 1 (CR-1046):** the paragraph above is true only
   when `--base` itself is honest (a ref reachable from the real trunk).
   Clean-room hazard CR-1045's witness W2 falsified the stronger claim this
   document originally made (see the correction at the claim-grep entry
   below): `--base` naming a commit on the audited branch itself (for
   example `HEAD~1` after a self-widening commit) makes the object-database
   read resolve the BRANCH's own widened blob, not main's, because the
   merge base computed from a caller-forged `--base` can itself sit on the
   audited branch. This round adds a second, independent check (the merge
   base must be an ancestor of the configured trunk) so the property now
   holds for the reason stated here PLUS that check together, not from the
   object-database read alone. See fix round 1's own section below for the
   derivation and red witnesses.
2. **"A branch name that does not match the phase pattern, which is the one
   path by which source can reach a pull request unaudited."** This is named
   in the plan as a residual property of the DESIGN (a phase branch is
   audited only when it matches the pattern; non-matching branches are the
   paperwork-branch case CLAUDE.md's own standing extras rule already
   assumes), not a defect this gate is meant to close on its own: closing it
   fully would need branch-naming ENFORCEMENT (a different mechanism, likely
   DR-0004's ruleset or process discipline, not a files-scope auditor). What
   this phase DOES contribute: a non-matching branch reports `not-applicable`
   cleanly (never silently green, never error), so the residual risk is at
   least OBSERVABLE in every run's summary rather than hidden inside a
   passing bundle. Evidence: criterion 6 direction 2 in the test suite.
   OPEN QUESTION, not asserted as closed: whether any mechanism outside this
   phase's files-to-touch list actually prevents a real PR from using a

### The mechanism (not the three instances)

**The scope gate forwarded `--phase`, `--base` and `--head` verbatim and
never cross-checked any of them against a property of the branch under
audit.** `declaration.id` and `declaration.branch` were loaded and

- W3 (CR-1045): set `--head` to an ancestor of the real tip, hiding a

The fix cross-checks every one of the three caller-supplied selectors
against a value this process establishes independently:

1. `--phase`, case-normalized to uppercase, must equal the loaded

   forked onto the audited branch is never reachable from the real trunk
