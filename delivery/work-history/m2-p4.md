## Step 1: M2-C-1 verification of delivered M2-P1 contracts

Verified against the actual merged code at 4c9bfbc, not assumed from the
plan text:

- `src/gates/result.ts` exports `makeGateResult`, `renderGateResult`,
  `exitCodeForStatus`, `GateResultFields`, `GateStatus` exactly as the
  plan's gate-result shape describes: four statuses, `units` coerced with
  the M2-C-2 vacuous-green rewrite applied inside the ONE constructor.
  Confirmed by reading src/gates/result.ts lines 1-197.
- `src/gates/manifest.ts` exports `GateEntry`, `PreconditionKind`,
  `RunParameter`, `loadManifest`. `PreconditionKind` is exactly
  `file-exists | file-absent | branch-matches | diff-touches |
  command-exit-zero`, matching plan section 1.4. `RunParameter` is
  `base | head | phase`, matching the plan's parameter vocabulary.
- `src/gates/run.ts`'s `requiredParameters` merges `entry.parameters` with a
  kind-derived requirement: `diff-touches` implies `base`; `branch-matches`
  implies `phase` UNCONDITIONALLY, even when the pattern does not use
  `{phase}` (a deliberate strict reading per its own comment). This is
  divergent from a naive reading and worth recording rather than silently
  working around: the runner forwards to a gate's argv ONLY the parameters
  in `requiredParameters(entry)`, so a parameter the gate needs but the
  manifest entry does not declare in `parameters` is simply never passed,
  silently. Consequence for this phase: `--head` is NOT automatically
  forwarded to `scope` unless the manifest entry explicitly declares
  `"parameters": ["base", "head"]`. This matters because STATE.md's
  carried-forward CR-902 note records that on `pull_request` events the
  checked-out SHA is a synthetic merge commit, so a gate that silently
  defaulted to bare `HEAD` when the caller actually supplied `--head` would
  silently audit the wrong commit. Resolution: `gates.manifest.json`'s
  `scope` entry declares `"parameters": ["base", "head"]` explicitly, so the
  runner always forwards the caller's real `--head` rather than letting the
  gate fall back to a local default. `scope.ts` still defaults `--head` to
  `HEAD` when invoked directly without the flag (parity with the runner's
  own `diff-touches` default), which only matters for direct/manual
  invocation, never for a `gates run` bundle, because the manifest
  declaration always supplies it there.
- `src/task.ts` exports `classifyEntry`, `readRegularFileIfPresent`,
  `refuseOpenForWrite`, `runStep`, `singleLine` exactly as M2-C-6 assumes:
  lstat then stat then open only a regular file; `EntryClass` kinds
  `absent | dangling | regular | irregular | unexaminable`.
- `src/gates/validate.ts` exports `loadSchema`, `validate`, `validateToLines`,

## Real captured git output the parser is pinned against

Captured with a scratch repo (own GIT_AUTHOR_*/GIT_COMMITTER_* env, no
global config touched), covering modify, add, delete and rename in one
diff:

```
$ git diff --name-status <base> <head>
M	src/a.ts
A	src/fresh.ts
R100	src/old.ts	src/new.ts
D	src/todelete.ts
```

And the two `git show <sha>:<path>` outcomes that distinguish "declaration
absent at the merge base" (RED) from any other git failure (ERROR):

```
$ git show <sha>:nope.json
fatal: path 'nope.json' does not exist in '<sha>'
(exit 128)

$ git show <sha>:a.txt
hi
(exit 0)
```

And an unresolvable ref for `git merge-base`, which must be ERROR (a merge
base that cannot be resolved means the gate cannot reach a verdict, never a
guessed red or green):

```
$ git merge-base <sha> nosuchref
fatal: Not a valid object name nosuchref
(exit 128)
```

The parser recognizes "does not exist in" and "exists on disk, but not in"
as the RED-classifying git message and treats every other nonzero exit from
`git show` as ERROR. Only the first pattern was reproduced above; the second
is git's own message for a path that exists on disk in the working tree but
not in the named commit. It was not independently reproduced in this
container and is included on the strength of git's own source text alone.
Recorded as a derivation gap rather than asserted as covered: if it never
fires, the affected input degrades to ERROR rather than a wrongly-guessed
RED, which is the fail-closed direction (M2-C-3), not the dangerous one.
