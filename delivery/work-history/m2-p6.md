## Mechanism lookup (T-005 interim obligation, MECHANISMS.md)

Rows that bear on this phase:

- **"Reading a path whose type is not established"**: M2-C-6 binds this
  phase. The coverage gate reads three configured paths (inventory,
  coverage table, and an optional `--config` document) that it did not
  create, so every read goes through `readRegularFileIfPresent` /
  `classifyEntry` from `src/task.ts`. Verified directly rather than
  asserted:
  ```
  $ grep -n "readFileSync\|writeFileSync" src/gates/coverage.ts
  1:import { writeFileSync } from "node:fs";
  584:        writeFileSync(
  647:    writeFileSync(resultPath, renderGateResult(result)),
  ```
  No `readFileSync` import exists in the module at all (every read is
  `readRegularFileIfPresent`); both `writeFileSync` call sites (lines
  584 and 647) are immediately preceded by a `refuseOpenForWrite` guard
  (the write-side half of M2-C-6, lines 581 and 641).
- **"Parsing another program's reporter output"**: not directly applicable
  (this gate parses markdown tables it is itself the sole consumer of, not
  another program's structured output), but the spirit carries: the
  markdown-table parse is PINNED to an explicit row/cell shape (a line
  starting and ending with `|`, separator rows skipped, first cell tested
  against a configured `idPattern`) rather than a permissive scrape that
  would silently absorb unrelated table rows from other documents.
- **"Deciding what another program will do by pattern-matching the text of
  a file it consumes"**: the closest analogue here, because this gate is
  a regex classifier over prose documents by construction (the coverage
  table's "Bucket" column). The plan accepts this for M2 (the milestone
  IS the arithmetic-over-two-documents checker); the mitigation taken is
  full-string anchoring of every bucket-kind pattern (`^(?:pattern)$`), so
  a bucket kind cannot silently absorb a value it was not written for, and
  an unrecognized value is a named finding (`unknown-kind`) rather than a
  guess.
- **"Claim file"**, **"Lease compare-and-swap"**, **"Atomic file
  replacement"**, **"Worktree removal and force branch delete"**,
  **"Append-only log"**, **"A guard's own failure path"**: none of these
  mechanisms is exercised by this phase (no claim, no lease, no atomic
  rename, no destructive git operation, no log tail read, no bespoke
  failure path beyond the shared `makeGateResult`/`refuseOpenForWrite`
  primitives already governed by their own rows).

## Design decisions (step 2, config shape)

- `bucketKinds` is modeled as an ARRAY of `{kind, pattern, requiresNote}`
  rather than an object keyed by kind name, because the closed keyword set
  (`src/gates/validate.ts`) has no `patternProperties`, and an array with
  `items` expresses the same information inside that set.
- "a milestone extraction (a capture group)" is not a separate config
  field: each `bucketKind`'s own `pattern` carries its capture group
  (`M([0-9]+)-P[0-9]+` for phase, `M([0-9]+)` for milestone), read as
  `match[1]` when the match used it. `decision` and `parked` carry no
  group, exactly as the plan states them verbatim, so a row of those kinds
  is bucketed in the per-milestone view by the KIND's own name (this is
  why `parked` appears as a key in `perMilestone` rather than as an `Mn`
  value, and is exercised by the parked-note test, both directions).
- **The kernel config is a plain exported TypeScript constant**
  (`KERNEL_COVERAGE_CONFIG` in `src/gates/coverage.ts`), not a checked-in
  data file. This phase's files-to-touch list
  (`delivery/plan/phase-declarations/m2-p6.json`) names the module, its
  schema and its test, and no separate configuration document; a
  committed config file at a path outside that list would fail the scope
  audit. A `--config <path>` flag exists on the CLI for a caller that
  wants a different pair (used by every fixture test in
  `test/coverage-gate.test.ts`, and validated against
  `coverage-config.schema.json` when supplied), and the kernel config
  itself was checked to conform to that same schema:

  ```
  $ node --input-type=module -e '
  const { loadSchema, validate } = await import("./src/gates/validate.ts");
  const { KERNEL_COVERAGE_CONFIG } = await import("./src/gates/coverage.ts");
  const fs = await import("node:fs");
  const schemaDoc = JSON.parse(fs.readFileSync("src/gates/schemas/coverage-config.schema.json","utf8"));
  const loaded = loadSchema(schemaDoc, "coverage-config.schema.json");
  const diags = validate(loaded.schema, KERNEL_COVERAGE_CONFIG);
  console.log("diagnostics:", JSON.stringify(diags));
  '
  diagnostics: []
  ```
- A bucket value matching MORE THAN ONE declared kind is resolved by
  taking the first match in declaration order rather than reported as a
  distinct "ambiguous" finding. No acceptance criterion requires the
  ambiguous case (the four real bucket-kind patterns are mutually
  exclusive once anchored full-string, verified by the real-pair test
  producing zero `unknown-kind` findings and the exact stated per-kind
  split), and adding an untested branch no criterion drives is the kind
  of extra surface the fix-round contract's "one witness is not a class"
  spirit warns against. Stated here as an open design choice rather than
  a silent one.
- **Registered `unitLabel` is `"finding ids checked"`**, matching section
  1.4's manifest table verbatim (not the acceptance-criteria prose
  "inventory ids checked", which is the semantic paraphrase); the
  manifest entry in `gates.manifest.json` uses the section 1.4 string.
- The `coverage` gate's manifest `precondition` is `file-exists` on
  `delivery/requirements/migration-table.md` (the inventory document),
  matching section 1.4's "`file-exists` inventory config" cell. This is a
  DIFFERENT dangerous state than criterion 7's empty inventory: the
  precondition covers the file being entirely ABSENT (structural,
  `not-applicable` if unmet, evaluated by the runner before this gate is
  even spawned), while criterion 7 covers the file being PRESENT but
  producing zero id rows (an `error`, evaluated inside this gate). Kept
  separate deliberately so neither can mask the other.
- The gate additionally writes `evidence/counts.json` (the full per-kind,
  per-milestone and findings breakdown as structured JSON) when
  `--evidence` is supplied, referenced in the record's `evidence` array.
  Not required by any criterion; added because criterion 1 asks for "two
  different views, both recorded", and a structured file is a more
  durable record of that than parsing the `detail` prose string. Declared
  here as an addition beyond the plan's literal step list, in the same
  spirit as M2-P1's declared `vacuous` field addition.

## Hazard-class self-review (T-007, pre-submit, per the shared brief)

Hazard class: "arithmetic over two documents that can drift, where a
total can add up while a row is lost." Named defeaters, each walked:

1. **"a renumbering that leaves a bucket row pointing at an id that no
   longer exists"** , the PHANTOM check (`checkCoverage`'s second pass,
   `src/gates/coverage.ts`), independent of the orphan check (the first
   pass, over inventory ids). Evidence: `test/coverage-gate.test.ts`
   test "a coverage-table row whose id is absent from the inventory is
   red naming it phantom" (green), plus the orphan test staged against
   the REAL appendix with `R-050a` deleted from a mutated copy of its
   text (green both directions: red when deleted, green when restored).
2. **"a bucket value matching no declared kind, silently uncounted"** ,
   every `bucketKinds[].pattern` is compiled anchored
   (`^(?:pattern)$`); an unmatched value is the `unknown-kind` finding,
   named by id and the literal observed value (`JSON.stringify`d into the
   detail string so an empty or whitespace value is visibly distinct from
   a missing one). Evidence: test "a phase bucket value is counted under
   its milestone and kind, and an unrecognized bucket value is red naming
   the row" (green), fixture value `"TBD"`.
3. **"an empty inventory producing a green with nothing examined"** ,
   `main()` in `src/gates/coverage.ts` computes `status: "green"` when
   `totalInventoryIds === 0` REGARDLESS of any findings, so the shared
   `makeGateResult` constructor's own M2-C-2 rewrite (not a second
   implementation of that rule) turns it into `status: "error"`,
   `vacuous: true`. Evidence: test "an empty inventory is error with
   units 0 and the vacuous flag set, never green", run through the real
   CLI entry and real file reads (not a unit call), exit code 21,
   `record.status === "error"`, `record.vacuous === true`.
4. **"a milestone extraction that cannot produce the totals the plan
   states, so the two views agree only because one is never computed"**
   , `perKind` and `perMilestone` are two INDEPENDENT tallies filled in
   the same loop from the same classification, and the real-pair test
   asserts BOTH against the plan's stated numbers in the same test run
   (`perKind.phase === 11`, `perKind.milestone === 104`, and all five
   `perMilestone` entries), so neither total can pass by only one of them
   being computed.
5. **"a finding whose outcome cell is present but empty"** ,
   `checkFindingOutcomeParity` distinguishes MISSING (no row for the id)
   from EMPTY (a row exists with `outcome === ""`) as two different
   result buckets, never conflated. Evidence: test "a finding report
   missing an id, carrying an empty outcome, or fully covered, is red,
   red, and green respectively naming the id", three directions, `missing
   = ["F-6"]` in direction 1 and `empty = ["F-3"]` in direction 2 (not the
   other bucket in either case).

### Mechanism 5 (CR-990/991/992, taken together as instructed): config strings reaching RegExp unvalidated and unbounded

**The mechanism.** Every config-supplied pattern (`inventory.idPattern`,
`coverageTable.idPattern`, every `bucketKinds[].pattern`) was compiled
with a bare `new RegExp(...)` and executed with a bare `.test()` /
`.exec()`. The schema constrained these to `"type": "string"` only. Three
consequences, one root cause:

- CR-990: a syntactically malformed pattern throws a `SyntaxError` out of
  `extractIdRows`, which escapes past every `emit()` call site (none of
  which is on the stack yet) to the top-level handler, which writes NO
  result record.
- CR-991: a syntactically valid but catastrophic pattern (`(a+)+b`
  against an adversarial input) never returns; nothing bounds the
  execution.
- CR-992: a value matching more than one declared kind resolved by
  breaking on the first match, so a second kind's `requiresNote` was
  never consulted, with nothing said about the ambiguity.

**Fix, two layers (validate AND bound, as instructed):**

1. **Validate.** `validateConfigPatterns(config)` runs once, in `main()`,
   before ANY pattern is compiled elsewhere. For every `idPattern` and
   every `bucketKinds[].pattern` it: (a) attempts `new RegExp(pattern)`
   in a try/catch, turning a `SyntaxError` into a named config error
   with a written record; (b) rejects a pattern matching
   `catastrophicShapeReason`'s static heuristic, a parenthesised group
   containing `+`/`*` immediately followed by another `+`/`*`
   (`/\([^()]*[+*][^()]*\)[+*]/`), which is exactly the shape the
   review's own `(a+)+b` witness is.
2. **Bound.** `boundedExec(compiled, value)` runs `compiled.exec(value)`
   inside a reused `node:vm` context with a 250ms `timeout`. `node:vm`'s
   timeout interrupts synchronous execution including regex
   backtracking (V8 checks for the termination request during a
   backtrack, not only between statements), which is why this stops a
   hung match where a plain try/catch around a synchronous call could
   not (a catastrophic match never throws on its own). EVERY execution
   of a config-supplied pattern in `extractIdRows` and `checkCoverage`'s
   bucket-kind loop now goes through this function; this is the backstop
   for whatever the static heuristic in layer 1 does not recognise
   (documented residue below).
   CR-992 is folded into the SAME fix because it is the same "a config
   string is trusted further than its syntax justifies" mechanism one
   property over: `checkCoverage` now tests EVERY declared bucket kind
   (never breaking on the first match) and pushes an `ambiguous-kind`
   finding naming every kind that matched when more than one does.
