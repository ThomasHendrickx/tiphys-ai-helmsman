## Design decisions taken inside the plan's space (recorded before code)

D-p7-1. **Declaration path is `release-verification.json` at the repository
root.** The plan names "the release-verification declaration" without a path;
the manifest precondition needs a literal one. Root-level mirrors
`gates.manifest.json` (the other per-repository declaration M2 ships). The
gate entries and the manifest precondition share the one constant, exported
from `src/gates/release.ts`.

D-p7-2. **The gate reads the declaration from a committed ref, never from the
working tree.** `--base <ref>` when supplied (the anti-widening read, criterion
9), else `HEAD`. Read via `git show <ref>:release-verification.json`; the
record carries the sha256 of the blob bytes read. A working-tree read would
let an uncommitted edit change the verdict, which is the widening attack.

D-p7-3. **Adapter responses may carry an optional `units` field** (integer >=
0): criterion 7 requires the migrations gate green with `units` 2 when two
migrations were compared, and the kernel cannot know the count without the
adapter saying it. Absent, a satisfied verification counts 1 (the plan's
"units 1 per verification satisfied"). Declared here because the
investigation's response sketch (section 2.5) does not list the field.

D-p7-4. **Criterion 10's "the record states that this is structural"** is
carried in the manifest precondition `id` string (see 1b), because the
runner, not the gate, authors the not-applicable record for an unmet
precondition, and the id is the only manifest-authored text that reaches the
record verbatim. The id used:
`release-verification-declared (unmet is structural in any pre-merge bundle: release verification runs post-merge, plan M2 section 1.4)`.

D-p7-5. **Attempt-level fail-closed violations are terminal.** A misbehaving
adapter (any of the seven rules) ends the loop with verdict `error`
immediately; only `pending` and `absent` loop. This follows criterion 4
("each produces `error` naming the rule and the field") over the
investigation's guarantee-3 phrasing ("error at the attempt level and red at
the deadline"), because the plan's criteria govern and fail-closed is the
stricter reading: a broken adapter cannot reach a verdict, and M2-C-3 says
that is `error` now, not red later.

D-p7-6. **Missing applied migrations are `pending`; superset and checksum
drift are `failed`.** The incident is "migrations skipped by a flake": a
not-yet-applied migration may still be applied by a queued job, so it is
`pending` and becomes red at the deadline naming the missing ids (criterion 7
direction 1 via the deadline conversion; investigation section 1.2). An
applied migration the repository does not have, or an id whose checksum
differs, will never become right by waiting: terminal `failed` naming it.

D-p7-7. **Credential handling in this phase**: the declaration lists NAMES;
an unresolvable name is `error` before any adapter spawn; resolved VALUES are
redacted from every captured adapter stream before it is written under the
evidence directory (criterion 11's mechanical form). No allowlist extension,
no injection, no M2-P8 module is consumed (plan step 8; the adapter child
inherits the parent environment exactly as the delivered `subprocessAdapter`
does today, and the scrub that changes that is M2-P8's, then M4's).

D-p7-8. **Fixture honesty.** Appendix A transcribes verbatim FIELD NAMES and
observed VALUES, not complete raw bodies, for Vercel and GitHub Actions; the
Supabase response IS a complete body. The fixtures therefore carry every
captured field name and captured value byte-for-byte, carry NO field and NO
status value that appendix A does not attest, and use clearly-marked
placeholder strings only for identity handles appendix A truncated
(deployment ids, which the parser treats as opaque). `test/fixtures/release/PROVENANCE.md`
states this per file, per field. No failure vocabulary appears anywhere.

## Pre-submit hazard self-review (M2-D-18)

The declared hazard class: **a verifier that can be fooled while reporting
an observation.** Each named member, walked against the implementation:

1. *An adapter that verified a different subject and was believed.* The
   subject echo is compared field by field before the outcome is read
   (rule 3); witnessed red under two structurally different defangs (R3a,
   R3b).
2. *A commit sha matched without a target, so a preview build answers for
   production.* The http-json locate takes a conjunction of match rules;
   the test stages the REAL captured pair (one sha on both a preview and a
   production deployment) and the H-sha-only-match defang reddens it.
3. *A release object created before the merge, so the previous release
   answers for this one.* Recorded as the older-than-merge flag on the
   attempt record, deliberately an observation and not an error (plan step
   3; investigation section 8 item 8); witnessed in both directions.
4. *A pending or absent state read as a pass.* pending and absent are loop
   states in one total mapping; the deadline conversion is the only exit
   and produces red with distinct reasons; DEADLINE-pending-pass and
   H-absent-as-pending redden their witnesses.
5. *An expired or unresolvable credential producing a permanent soft
   state.* An unresolvable declared name is error before any spawn; an
   HTTP 401 at the adapter is error, never pending; both witnessed.
6. *An adapter that hangs and takes the kernel with it, or owns its own
   timeout.* The per-attempt bound is spawnSync timeout+killSignal in the
   kernel; the adapter has no clock at all (no sleep, no loop, no
   scheduling in either reference adapter); HANG-no-timeout reddens the
   witness by genuinely blocking.
7. *An adapter whose only observation is that the deploying command exited
   0.* Not expressible in the shipped adapters: http-json reads a
   platform response over HTTP, migrations-command reads an applied
   inventory. The hazard remains OPEN for third-party adapters, where it
   is a documentation obligation: release.ts's module doc states the
   authority must be independent of the deploying process (guarantee 4).
   A kernel cannot verify that property mechanically from the response
   alone; recorded as a residue, not claimed closed.
8. *A verification switched to none inside the branch that needed it on.*
   The declaration is read from the committed governing ref; the
   flipped-on-head test reddens under WIDEN-head-read; the record carries
   the merge-base blob sha256 so a reviewer sees which text authorized any
   skip.

Open residue from this walk, stated rather than absorbed: member 7 above
(third-party adapter independence is not machine-checkable here), and the
locate rule quality is only as good as the project's match configuration;
a project that configures matching on sha alone has reintroduced member 2
for itself, and nothing in M2 lints a project's locate rules. Both belong
to M4's pilot wiring and the M3 charter coherence checks.

## CR-P7H-3 (MEDIUM): encoded credential forms are redacted, with the residue disclosed

### Mechanism

redactSecrets removed only the verbatim bytes (text.split(value).join(...)),
so a credential emitted in a common single-step encoding survived. A base64
Authorization Basic header and a percent-encoded URL query each leaked a
trivially reversible copy into the evidence. The fix broadens redaction to the
enumerable single-step encodings the kernel can derive from the value alone:
secretForms (src/gates/release.ts) returns the verbatim value, its standalone
base64, and its encodeURIComponent form, and redactSecrets splits on each.

### Derivation

Command: grep -n 'redactSecrets|secretForms' src/gates/release.ts confirms
redaction is applied at every evidence write: stdout (:543 arg), stderr (:550
arg), and the response body before it is parsed (:625), so records built from the
parsed body inherit the redaction. secretForms is the single enumeration of
forms; adding a form there covers all evidence at once.

### What the derivation did NOT cover (stated precisely, never softened)

Redaction covers the value and its own single-step base64 and percent encodings.
It does NOT cover forms that fold in bytes the kernel does not hold: base64 of
"user:" + value for a full HTTP Basic credential PAIR (the username is the
project's, not the kernel's), nor a value re-encoded by a transport the kernel
never sees (gzip, hex, a double base64 round). Those are residue the reference
adapters do not produce; a third-party adapter that composes a credential with
unknown surrounding bytes owns that redaction. This scope is recorded in the
secretForms/redactSecrets doc comments so the guarantee is auditable rather
than overstated.

### Red witness (>= 2 structurally different members)

Dangerous state: an adapter emitting the credential ONLY in encoded forms
(never the raw bytes) into stdout, stderr and the response record, including a
realistic Basic-auth header. Out-of-band probe (pre-fix release):

```
PRE-FIX release:  ANY_LEAK=true
   LEAK in deploy-attempt-1-stderr.txt base64=false url=true  raw=false
   LEAK in deploy-attempt-1-stdout.txt base64=true  url=false raw=false
   LEAK in deploy-response-1.json      base64=true  url=true  raw=false
POST-FIX release: ANY_LEAK=false
```

Two structurally different members (base64 and percent-encoding), using the real
bytes the adapter emitted; both present pre-fix and absent post-fix. The value
carries characters (space, /, +, :) that make its percent encoding genuinely
differ from the raw bytes, so the url member is not a re-test of the verbatim
path. Permanent guard: test
"release encoded credential forms are redacted from every file under the
evidence directory" (test/release-contract.test.ts). Behavior
release-encoded-credential-redaction.
