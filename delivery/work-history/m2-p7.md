## Step 1: M2-C-1 verification of delivered contracts (before any code)

All checks run in the phase worktree at 4c9bfbc, login shell, node v22.22.2.

1a. **Gate invocation contract** (`src/gates/run.ts:703-711`): the runner
spawns `entry.command[0]` with
`[...entry.command.slice(1), "--result", recordPath, "--evidence", gateDir]`
plus `--<name> <value>` for each of `requiredParameters(entry)`. Required
parameters are the union of the entry's `parameters` declaration and the
precondition kind's needs (`run.ts:366-376`); `file-exists` adds none. A gate
therefore receives `--result` and `--evidence` always, and anything else only
if declared. Matches the plan's assumption that the two release entries can be
registered `conditional` + `file-exists` and never require `--base` in a
bundle.

1b. **Precondition evaluation** (`run.ts:416-440`): `file-exists` goes through
the delivered `classifyEntry` (M2-C-6 already applied by M2-P1), unmet yields
status `not-applicable` with a `PreconditionRecord {id, met:false, reason:
"<path> does not exist", evidence:[path]}` and detail
`precondition <id> evaluated and unmet: <reason>` (`run.ts:640-655`). The
precondition `id` is a free string in the manifest schema
(`src/gates/schemas/gate-manifest.schema.json`, `$defs/precondition/id`,
type string, no pattern), which is the mechanism this phase uses to make the
runner-built record STATE that pre-merge not-applicable is structural
(criterion 10); recorded as a deviation-free design choice below.

1c. **Result record contract** (`src/gates/result.ts`): four statuses, the
M2-C-2 vacuous rewrite in the only constructor, exit-code table
0/1/20/21/64. `GateResult.precondition` is optional and schema-validated
(`gate-result.schema.json` `$defs/precondition`). Gates write their own
record via `--result` and exit with `exitCodeForStatus` (observed pattern:
`src/commands/gates.ts` `emit()`).

1d. **Ingestion fail-closed** (`run.ts:746-800`): exit 0 with no record is
`error` ("exited 0 without writing a result record"), record read through
`classifyEntry` + `readRegularFileIfPresent`. The release contract applies the
SAME rule one level down at the adapter boundary (fail-closed rule 1), which
is a deliberate echo, not a reimplementation: the runner's rule is about gate
records, this phase's is about adapter responses.

1e. **Validator** (`src/gates/validate.ts`): closed keyword set
`type, required, properties, additionalProperties, enum, items, minimum,
minItems, pattern, const, $ref` plus annotations
`$schema, $id, title, description, $defs`. Diagnostic contract
`INVALID <pointer> <message>` with deterministic (pointer, message) ordering.
Both new schema documents are authored inside this set; kind-specific
conditional requirements (which would need `if`/`then`) are checked in code
emitting the same diagnostic shape, exactly as `src/gates/manifest.ts:140-173`
already does for precondition kinds.

## Design decisions taken inside the plan's space (recorded before code)

D-p7-1. **Declaration path is `release-verification.json` at the repository
root.** The plan names "the release-verification declaration" without a path;
the manifest precondition needs a literal one. Root-level mirrors
`gates.manifest.json` (the other per-repository declaration M2 ships). The
gate entries and the manifest precondition share the one constant, exported
from `src/gates/release.ts`.

D-p7-2. **The gate reads the declaration from a committed ref, never from the
working tree.** `--base <ref>` when supplied (the anti-widening read, criterion
9), else `HEAD`. Read via `git show <ref>:release-verification.json`; the
record carries the sha256 of the blob bytes read. A working-tree read would
let an uncommitted edit change the verdict, which is the widening attack.

D-p7-3. **Adapter responses may carry an optional `units` field** (integer >=
0): criterion 7 requires the migrations gate green with `units` 2 when two
migrations were compared, and the kernel cannot know the count without the
adapter saying it. Absent, a satisfied verification counts 1 (the plan's
"units 1 per verification satisfied"). Declared here because the
investigation's response sketch (section 2.5) does not list the field.

D-p7-4. **Criterion 10's "the record states that this is structural"** is
carried in the manifest precondition `id` string (see 1b), because the
runner, not the gate, authors the not-applicable record for an unmet
precondition, and the id is the only manifest-authored text that reaches the
record verbatim. The id used:
`release-verification-declared (unmet is structural in any pre-merge bundle: release verification runs post-merge, plan M2 section 1.4)`.

D-p7-5. **Attempt-level fail-closed violations are terminal.** A misbehaving
adapter (any of the seven rules) ends the loop with verdict `error`
immediately; only `pending` and `absent` loop. This follows criterion 4
("each produces `error` naming the rule and the field") over the
investigation's guarantee-3 phrasing ("error at the attempt level and red at
the deadline"), because the plan's criteria govern and fail-closed is the
stricter reading: a broken adapter cannot reach a verdict, and M2-C-3 says
that is `error` now, not red later.

D-p7-6. **Missing applied migrations are `pending`; superset and checksum
drift are `failed`.** The incident is "migrations skipped by a flake": a
not-yet-applied migration may still be applied by a queued job, so it is
`pending` and becomes red at the deadline naming the missing ids (criterion 7
direction 1 via the deadline conversion; investigation section 1.2). An
applied migration the repository does not have, or an id whose checksum
differs, will never become right by waiting: terminal `failed` naming it.

D-p7-7. **Credential handling in this phase**: the declaration lists NAMES;
an unresolvable name is `error` before any adapter spawn; resolved VALUES are
redacted from every captured adapter stream before it is written under the
evidence directory (criterion 11's mechanical form). No allowlist extension,
no injection, no M2-P8 module is consumed (plan step 8; the adapter child
inherits the parent environment exactly as the delivered `subprocessAdapter`
does today, and the scrub that changes that is M2-P8's, then M4's).

D-p7-8. **Fixture honesty.** Appendix A transcribes verbatim FIELD NAMES and
observed VALUES, not complete raw bodies, for Vercel and GitHub Actions; the
Supabase response IS a complete body. The fixtures therefore carry every
captured field name and captured value byte-for-byte, carry NO field and NO
status value that appendix A does not attest, and use clearly-marked
placeholder strings only for identity handles appendix A truncated
(deployment ids, which the parser treats as opaque). `test/fixtures/release/PROVENANCE.md`
states this per file, per field. No failure vocabulary appears anywhere.
