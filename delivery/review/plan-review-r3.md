### PR-202

- Severity: medium
- Claim in the plan: P3 step 1 specifies atomic acquire (O_EXCL) and atomic takeover (temp file plus rename), and criterion 3 witnesses concurrent acquire; renew is specified only as "lock renew extends expiresAt by the lease duration and fails when the caller's holderId does not match the file" (lines 162, 169-174).
- Why it is wrong: renew and takeover lack the atomicity treatment acquire got, and the lease design makes their races likely rather than exotic. Renew as written is read-check-write: if a takeover lands between renew's read and its write (exactly the expiry boundary where both happen), renew clobbers the new holder's lease and two orchestrators hold simultaneously. Two concurrent takeovers on an expired lease both write temp files and both rename; rename is atomic but not exclusive, so both exit 0 and the loser never learns it lost. The scout's harvested protocol names the fix (FM-022: write-then-read-back verification), and the plan cites it for the acquire flow but does not apply it to the two operations that need it most. No criterion exercises either race; criterion 3 covers acquire only.
- Evidence: plan lines 162, 171-172; firstmate-scout-report.md FM-022, FM-058.
- Concrete edit: specify renew and takeover as verify-after-write: after the rename (or rewrite), re-read the file; if it does not contain the caller's holderId and expected expiresAt, the operation was lost to a concurrent writer and exits nonzero without retry. Add two criteria: (a) two concurrent --take-over invocations on an expired lease yield exactly one exit 0, and the file contains the winner's holderId; (b) a renew racing a takeover never produces a state where both callers' subsequent lock status reads report their own holderId (testable with a short lease and a scripted interleave).

### PR-203

- Severity: medium
- Claim in the plan: the lease has a duration ("extends expiresAt by the lease duration", line 162; criterion 5 uses "a short lease duration" in tests), but no default duration is stated anywhere, no renewal discipline exists (who renews, on what cadence), and the exit test acquires at step 3 and releases at step 10 with no renew in between, across a step 9 that waits on owner approval and a PR merge (lines 282-289).
- Why it is wrong: two lease failure modes fall straight through the gap. First, expiry-in-good-hands: if the duration is shorter than the exit-test run (step 9's wait is human-bounded), the lease legitimately expires mid-run while held; nothing breaks mechanically, but the one-orchestrator guarantee silently lapses and any second session may legitimately take over mid-milestone-run. Second, the paused-but-alive holder: a laptop lid close is not a crash; the holder resumes after expiry and a legitimate takeover, still believing it holds, and nothing stops it mutating fleet state, because no mutating command (spawn, teardown) verifies holdership; its first renew would fail, but nothing requires renewing before mutating. "Lease" without a renewal discipline and a holdership check reintroduces a dual-writer window through the front door.
- Evidence: plan lines 162, 169-173, 282-289; probe 1's paused-holder case.
- Concrete edit: (1) state the default lease duration in P3 step 1 and the renewal rule: the holder renews at or before half-life; (2) either wire a holdership check into mutating commands (spawn and teardown verify, when a lease file exists, that it carries the caller's holderId and is unexpired, refusing on mismatch; one criterion each) or record the paused-holder dual-writer window as an explicit accepted v1 limitation in the lock module docs and in P3's spec text (silence is the only wrong option); (3) exit test step 3 states the duration used for the run and that the harness renews before step 9's wait (or that the configured duration exceeds the bounded run length, recorded in the evidence).

### PR-204

- Severity: medium
- Claim in the plan: the watcher surfaces "signal <task-id> <event>" for "a new turn-end file for an open task" in both modes; all cadence state is persisted on disk so "resident restarts and single passes share one schedule" (line 225); criterion 4 witnesses --once surfacing a pending turn-end (line 233).
- Why it is wrong: "new" has no persisted definition, and single-pass mode cannot borrow the resident mode's implicit one (appeared while watching via fs.watch). A --once pass has no session memory: without persisted seen-state, every --once between a turn-end and its teardown re-surfaces the same signal forever (an external scheduler would re-wake the orchestrator indefinitely for one event); with seen-state, that state is unspecified: not named as a file, not given a format under the DR-0006 audit, not given atomicity for the case the plan's own design invites, a resident watcher and an external --once evaluating the same fleet concurrently (both could surface the same signal, or a seen-marker race could drop one). The scout hands over the exact pattern (FM-005 size:mtime signatures advanced only after surfacing, FM-046 enqueue-before-suppress ordering) and the plan harvests the cadence half (FM-006) but not the currency half. No criterion covers a second --once after a surfaced signal, and none covers resident-plus---once interleaving.
- Evidence: plan lines 225, 233; firstmate-scout-report.md FM-005, FM-046.
- Concrete edit: define signal currency in P5 step 1: a named state file (JSON, per DR-0006) recording per-task surfaced turn-end identity, advanced only when a wake is surfaced, updated with the same atomic write-then-verify discipline as the lock (or adopt surface-until-acknowledged with an explicit ack; either is fine, but it must be written). Add criteria: (a) after a --once surfaces "signal t turn-end", an immediately following --once exits with the no-wake code (or the documented ack semantics); (b) a resident watcher and a concurrent --once on the same fleet never both surface the same turn-end (one wins, one no-wakes).

### PR-205

- Severity: medium
- Claim in the plan: exit-test step 5: "Run tiphys watch --once and record the documented no-wake exit code 3" on the freshly initialized fleet (line 284); P5 step 1: in --once mode a heartbeat is surfaced "whenever the heartbeat is due" (line 225).
- Why it is wrong: on a virgin fleet no heartbeat has ever been recorded, and the plan never says whether missing cadence state means "due now" (--once prints "heartbeat 1", exits 0) or "initialize silently to now" (--once exits 3). Both are faithful implementations of the written spec; one of them fails the milestone exit run at step 5. A deterministic exit test may not depend on an unspecified initialization semantic. Criterion 4's "heartbeat not yet due" precondition silently assumes the second reading without stating it.
- Evidence: plan lines 225, 233, 284.
- Concrete edit: one sentence in P5 step 1: "absent cadence state is initialized to the current time on first evaluation without surfacing a heartbeat; the first heartbeat falls due one base interval later". Reference it from criterion 4 and note in exit-test step 5 that code 3 on a fresh fleet is guaranteed by this initialization rule.

### PR-206

- Severity: medium
- Claim in the plan: "every wake and heartbeat rewrites state/watcher.beacon" (line 225), and the PR-009 invariant (stale threshold strictly greater than backoff cap plus one poll interval) makes a healthy watcher never read stale (P5 step 2, criterion 8).
- Why it is wrong: the beacon-write rule excludes no-wake --once passes (exit 3, which are "nothing actionable", not wakes or heartbeats), and the PR-009 invariant is stated purely in resident terms. In --once-driven operation (the cloud/scheduler mode this revision exists to serve), the beacon advances only when a pass happens to surface something or a heartbeat falls due, so beacon gaps stretch toward the backoff cap plus the external trigger period, a quantity the kernel cannot know and liveness.ts cannot validate at load. The guard then oscillates between fresh and stale on a perfectly supervised fleet, which is exactly the cry-wolf regression PR-009 closed for resident mode, reopened for the new mode.
- Evidence: plan lines 225-226, criterion 8 (line 237 region), 293 (CI local mode as the cloud-like case).
- Concrete edit: change the beacon rule to "every watcher evaluation rewrites the beacon, including a no-wake --once pass" (the beacon then means "supervision executed recently" identically in both modes, and the PR-009 invariant becomes trigger-period-independent for any scheduler at least as frequent as the poll interval). Add a criterion: a no-wake --once pass (exit 3) strictly advances the beacon timestamp. Add one sentence to P5 step 2: in --once-only operation the guard's threshold additionally bounds the acceptable external trigger period, and doctor's beacon check wording should say "watcher not running or not scheduled".

### PR-207

- Severity: medium
- Claim in the plan: the ExecutorAdapter's "entire contract is: launch the payload in the task worktree and ensure the turn-end file is written with the payload exit code on completion", and "a multiplexer-window adapter and a cloud-session adapter are additional adapters written against the same interface, not kernel changes" (line 191).
- Why it is wrong: the contract is completion-only, and the substrate this revision adds makes non-completion the characteristic failure: a reclaimed cloud session (or a killed local spawn) leaves an open task with no turn-end, forever. That state is invisible by design: C-2 forbids process probing, the watcher's wake sources cover new turn-ends and "contradictory" worktree/meta states (an open task quietly missing its payload is not contradictory under any stated rule), and no file records that a payload was ever launched or how long it may reasonably run. So the abandoned task neither wakes the watcher nor exits, the canonical dead state, and the claim that a cloud adapter is purely additive is untrue as written: any real cloud adapter must add a non-completion signal, which is a contract change unless the contract grows it now. P4's criteria witness the local adapter's happy path (spawn blocks, exit code recorded) but nothing about the interface's obligations on abandonment.
- Evidence: plan lines 191, 196, 225 (stale enumeration); constraint C-2 (line 89).
- Concrete edit: extend the adapter contract with a launch record: the adapter writes tasks/<id>/executor.json (JSON per DR-0006: adapter name, launchedAt, optional deadline) at launch; the watcher's stale enumeration gains "open task whose executor record's deadline has passed with no turn-end" (file-based, C-2-compliant), with a P5 criterion driving that wake. If the deadline mechanism is judged post-M1, the alternative honest edit is one sentence in P4 and in the substrate-witnessed not-proven list: "abandoned tasks (payload dies without turn-end) are not detected in M1; recovery is manual teardown", so the gap is recorded rather than implied away.
