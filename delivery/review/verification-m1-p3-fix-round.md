## Finding V-1 (high): pool destroy force-deletes a task branch carrying committed work

- severity: high (data loss, silent, reachable today through the public CLI)
- found independently by lens 3 (pool destroy data-loss lens) and lens 5 (suite integrity and scope lens)
- refutation vote record: 0 refuted / 2 votes on the lens-3 formulation; 0 refuted / 2 votes on the lens-5 formulation. Four refuters total, none refuted.

### Claim

The CR-201 fix makes `pool destroy` delete the task branch with `git branch -D` unconditionally, so a destroy on a clean worktree silently and unrecoverably discards every commit made on that branch. The destructive behavior is not gated on `--discard`, is outside the plan's contract for destroy, and is the exact opposite of what the command's own dirty-worktree refusal tells the operator to do.

### Failure scenario

An operator runs `tiphys pool create --task t-work --project <clone>`, works in the worktree and commits, does not push, then runs `tiphys pool destroy --task t-work`, which is the ordinary way to release a task id. Because the work is committed, `git status --porcelain` in the worktree is empty, so the dirty guard does not fire. Destroy prints `destroyed t-work`, exits 0, force-deletes `task/t-work`, removes the worktree (and with it the per-worktree reflog), and unlinks the pool record. The branch reflog goes with the branch, the clone's HEAD reflog never mentions the branch, and the pool record that named it is gone. The commits survive only as dangling objects reachable through `git fsck --lost-found`, and `git gc --prune=now` (or ordinary auto-gc after gc.pruneExpire) erases them. The safety profile is inverted: the layer refuses to remove a worktree holding a scratch untracked file, but silently destroys committed work. The dirty refusal at src/pool.ts:490-495 literally advises "commit or land them first, or pass --discard to remove anyway"; after this round, following that advice destroys the work, and the documented destructive opt-in is bypassed entirely.

### Evidence

- Code: src/pool.ts:519-543 is the new CR-201 block. Line 535 is `const deleted = await runGitRetrying(contextDir, ["branch", "-D", branchName]);`. `discard` is never consulted there: `grep -n discard src/pool.ts` has its last hit at line 498 (`worktree remove --force`), so the default ship path and the `--discard` scout path have identical force semantics.
- Lens 3 executed repro: create, two commits (tip 1b8d8565d745bfa78a78e3523d20f31c18e0cbd4), never pushed, clean porcelain; destroy prints `destroyed t-work`, exit 0, no warning. Afterwards `git branch -a` shows main plus origin refs only, `git log --all --oneline` shows only the base commit, `.git/logs/refs/heads/` contains only `main`, the clone's `git reflog` has one entry and never mentions the lost sha, `git fsck --lost-found` reports `dangling commit 1b8d8565...`, and after `git gc --prune=now` a `git cat-file -t 1b8d8565...` fails with `fatal: git cat-file: could not get object info`, exit 128.
- Lens 5 independent repro: same shape, commit f7dca9638416cf4536cd48a9bdb586f28819f063, destroy exit 0, `git for-each-ref --contains f7dca96` empty, `git reflog show task/t-work` fails with "unknown revision".
- Orchestrator re-performance (fresh scratch fleet, this session, at b475546): `pool create --task t-work` (base 96f5a1e), one commit 6be726c87a1e41f9788e0bab7d95c07b58ba85a5, `git status --porcelain` empty, `pool destroy --task t-work` prints `destroyed t-work` exit 0, `git branch -a` shows only main and the origin refs, `git for-each-ref --contains 6be726c` returns nothing, `git fsck --lost-found` reports `dangling commit 6be726c87a1e41f9788e0bab7d95c07b58ba85a5`. - Recovery handle is discarded: `git branch -D <name>` writes `Deleted branch <name> (was <sha>).` to stdout (confirmed by redirecting stderr to /dev/null), and poolDestroy reads only `deleted.stderr`, and only on failure (src/pool.ts:535-543), so the operator is not even handed the sha.
- Contract: kernel-plan-v1.md M1-P3 step 3 and criterion 16 define destroy as refusing on a dirty worktree, otherwise removing the directory and pruning the worktree registration. Branch disposition is not in the contract; the clean-room review states "P4 teardown owns branch disposition", and CR-201's recommended fix was a create-side pre-check or documenting id reuse as unsupported. The create-side pre-check (src/pool.ts:224-243) alone closes CR-201.
- The stated justification (src/pool.ts:519-526 and delivery/work-history/m1-p3.md, disposition 1) is that "the teardown guard (M1-P4) refuses before ever calling destroy". M1-P4 does not exist yet, plan line 214 places landedness only in teardown's ship path (the scout path calls `pool destroy --discard` with no landedness check at all), nothing in the plan restricts who may call `pool destroy`, and `pool` is a registered public subcommand today (src/cli.ts:20) with `destroy --task <id>` in its USAGE line (src/commands/pool.ts:14-15).
- No test exercises the loss: test/pool.test.ts:375-397 (`pool-destroy-then-recreate`) creates and immediately destroys a branch still sitting at baseSha.

### Concrete fix

Make force deletion require explicit authorization at this layer, using state the pool already records. Before deleting, resolve the branch tip and compare it to the recorded base: `git rev-parse --verify refs/heads/<branch>^{commit}`; when the tip equals `record.baseSha`, the branch provably carries no commits and `-D` is lossless, so delete unconditionally (plain `-d` is not usable here: the clone's local default ref may be behind the fetched base, and squash-landed branches are not ancestors). When the tip differs from baseSha, refuse by default with one reason line naming the branch and its tip sha, for example `branch task/<id> carries commits beyond its base <baseSha> (tip <sha>); land them or pass <force flag> to delete it anyway`, and delete only when an explicit force option is passed. Add that option to DestroyOptions and the CLI as a distinct flag (for example `--delete-branch-force`) rather than overloading `--discard`, whose plan-defined meaning is the dirty-tree override; M1-P4 teardown then passes it from the ship path after its landedness judgement and from the scout path alongside `--discard`, which makes the dependency on teardown explicit instead of assumed. Independently of the gate, forward git's `Deleted branch <name> (was <sha>).` line (or emit the pre-delete tip sha) on the success path so a mistaken destroy leaves the operator a recovery handle. Add a regression test that commits in the worktree, runs `pool destroy` with no flags, and asserts either a refusal or that the commit is still reachable.

## Finding V-2 (high): the narrowed retry signature no longer matches git's concurrent ref-update refusal, so parallel pool creates fail hard

- severity: high (determinism regression in the exact path criterion 15 covers, plus a silent state-recording error under --offline)
- found independently by lens 4 (CR-203 false-negative lens) and lens 5 (suite integrity and race determinism lens)
- refutation vote record: 0 refuted / 2 votes on the lens-4 formulation; 0 refuted / 2 votes on the lens-5 formulation. Four refuters total, none refuted.

### Claim

The CR-203 narrowing of LOCK_CONTENTION to require a `.lock` path drops the message git actually emits for the concurrent-fetch contention that `pool create` provokes: `cannot lock ref '<ref>': is at <sha> but expected <sha>`. That failure is genuinely transient and was retried to success before this round; it is now classified permanent, so concurrent `pool create` invocations fail outright.

### Failure scenario

Two or more `tiphys pool create` runs for distinct task ids overlap against the same project clone whose remote-tracking ref is behind (the normal case after any upstream advance, and precisely the shape of criterion 15, of M1-P4 spawning several tasks, and of M1-P5 fan-out). Each runs `git fetch origin +refs/heads/main:refs/remotes/origin/main`. All read old_oid = OLD; one wins and writes NEW; the losers' ref transaction is refused with `error: cannot lock ref 'refs/remotes/origin/main': is at NEW but expected OLD` and git exits 1. That message names no lock file. Before this round it matched the `cannot lock ref` alternative and runGitRetrying retried it, and the retry succeeds immediately because the ref is already at NEW. Now nothing matches, runGitRetrying returns on attempt 1, and poolCreate refuses with `fetch of origin/main failed and --offline was not passed; refusing to base work on a stale ref`, exit 1. Secondary consequence: when `--offline` is passed, the same misclassification silently takes the offline fallback and writes `offline: true` into the pool record even though the remote was reachable and the fetch failure was pure local contention. M1-P4 copies that field into tasks/<id>/meta.json as baseOffline, so a correctly fetched base is recorded as stale (PR-212 witness inverted).

### Evidence

- Code: src/pool.ts:96 `const LOCK_CONTENTION = /index\.lock|Unable to create '[^']*\.lock'/;`, consumed at src/pool.ts:110 (runGitRetrying, which wraps the poolCreate fetch at src/pool.ts:257-261) and at src/pool.ts:429 (destroyGitStep).
- Real-message probe, lens 4 (git 2.43.0): 16 processes by 12 rounds, then 12 by 10 concurrent fetches of the same tracking ref with the ref behind. Of 120 fetches, 101 exit 0 and 19 exit 1, and every one of the 19 fails with `error: cannot lock ref 'refs/remotes/origin/main': is at <sha> but expected <sha>`. Classified with the shipped exported predicate: {"failed":19,"retriedByNewPattern":0,"retriedByOldPattern":19}.
- Independent probe, lens 5: 25 rounds of 8 concurrent fetches, 174 contention failures, 174 of that same shape, 0 naming a `.lock` file.
- Transience proof: after a losing fetch, an immediate identical retry exits 0 with empty stderr (observed in 2 independent rounds).
- End to end on the shipped CLI, fresh fleet per round: lens 4 measured 2/36, 3/48 and 1/48 creates failing with exit 1 and stderr `... refusing to base work on a stale ref: error: cannot lock ref 'refs/remotes/origin/main': is at ... but expected ...`; lens 5 measured 5/60. Counterfactual with only the pre-fix regex restored in an isolated copy: 0/36, 0/48 (lens 4) and 0/60 (lens 5).
- Orchestrator re-performance (this session, importing the shipped predicate from the worktree at b475546): `isTransientGitLockError("error: cannot lock ref 'refs/remotes/origin/main': is at a0e80f0 but expected a0d1254")` returns false, while the index.lock shape returns true.
- The suite cannot see it: `npm test` at head is green (64 tests, 62 pass, 0 fail, 2 reasoned skips) while the shipped binary fails under the real race. test/pool.test.ts:260-276 (the concurrent-create test) never advances the upstream after makeScratch clones it (test/pool.test.ts:128-146), so both fetches are no-ops and no ref transaction is ever opened; test/pool.test.ts:436-452 (`pool-retry-signature-narrow`) asserts only hand-written strings that were chosen to match the new regex, and no message emitted by a real racing git is in the assertion set.
- The implementer's own environment note 5 in delivery/work-history/m1-p3.md documents this exact scenario ("concurrent git fetches updating the same remote-tracking ref can transiently contend on ref locks; pool create retries on the lock-contention stderr signature"), and the round then removed the alternative that carried it.

### Concrete fix

Restore a retry alternative for git's concurrent-update refusals, anchored tightly enough that the permanent directory/file ref conflict CR-203 targeted still fails on attempt 1. Candidate validated by lens 4 in an isolated copy:

```
const LOCK_CONTENTION = /index\.lock|Unable to create '[^']*\.lock'|cannot lock ref '[^']*': (is at [0-9a-f]+ but expected|reference already exists|reference is missing but expected)/;
```

Measured with that in place: 0/48 concurrency failures, and the planted directory/file ref conflict still fails in a single attempt (162-168ms, against 1234ms with the fully generic pre-fix regex), so CR-203's actual benefit is fully preserved. Update the rationale comment at src/pool.ts:82-93 and the work-history disposition accordingly (see unrefuted candidate U-5). Extend `pool-retry-signature-narrow` with the real captured stderr `error: cannot lock ref 'refs/remotes/origin/main': is at <40-hex> but expected <40-hex>` asserted transient, and strengthen the concurrent-create test at test/pool.test.ts:260 so the tracking ref is actually behind before the concurrent creates (call `upstreamCommit` or rewind `refs/remotes/origin/main`) with 4 to 6 concurrent creates asserted to all exit 0: that turns red on head and green with the fix.
