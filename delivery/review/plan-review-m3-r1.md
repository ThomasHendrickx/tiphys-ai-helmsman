## VERDICT: FIX-ROUND-NEEDED

Two phases (M3-P2, M3-P3) have files-to-touch lists that cannot satisfy their own stated acceptance criteria without touching an undeclared file, which is a scope-audit failure baked into the plan rather than a implementer error. Several of the plan's "schema validates it, both directions" acceptance criteria describe cross-document or cross-array invariants that no candidate JSON Schema technology under DR-0013 can express as a schema keyword, so the plan's central testability claim is partly aspirational as written. None of these are fatal to the plan's architecture, and the plan's honesty about its own biggest weakness (44 of 74 rows are prose) is real and should be kept. But they are concrete, evidenced, and each requires an edit before dispatch, which is what FIX-ROUND-NEEDED means here.

### M3R-002 (HIGH): several "DANGEROUS-instance, schema keyword removed and restored" criteria describe cross-document or cross-array invariants that no JSON Schema under DR-0013's candidate options can express as a schema keyword

**Claim located:** section 2.3 rule 2 states the uniform methodology for every DANGEROUS-instance fixture in the plan: "demonstrated in both directions: rejected by the shipped schema, and accepted when the guarding keyword is removed from the schema." This methodology is then applied, by name, to checks that are not single-keyword properties of one document:

- M3-P1 criterion 3(b): "a plan with a `report-code-disagreement` entry `verified: false` and no `verification-first` step in the owning phase." This requires matching an entry in one array (`report-code-disagreement[]`) against a step nested inside a *different* array element (`phases[].steps[]`) picked out by a phase-id reference, all within one document. There is no JSON Schema keyword, in the base spec or in DR-0013's candidate keyword set (`type, required, enum, const, properties, items, additionalProperties, minItems, pattern, oneOf, if/then`), that performs this kind of foreign-key lookup across array elements.
- M3-P3 criterion 3(a): "a mode whose pipeline omits `clean-room-review` while `skips[]` is empty (an undeclared downgrade...)." Per the plan's own step 1, this rule can only be evaluated by knowing what `full` mode's pipeline contains, since only omitting a stage `full` contains counts as a downgrade. `full`, `direct-pr`, and `local-only` are three sibling top-level entries in the same `assurance-modes.yaml` file, so this is a cross-object comparison between siblings, again outside plain JSON Schema.
- M3-P3 criterion 3(b): "a mode whose pipeline places `implement` before `adversarial-plan-review`." JSON Schema has no keyword for relative ordering of two specific values inside a variable-length array; `contains`, `items`, and `if/then` each validate presence or per-element shape, not position-of-A-before-position-of-B.
- M3-P7 criterion 4(b) and exit-test step E1.7: "a verdict whose `criteria[]` omits an acceptance criterion present in the referenced plan phase." This compares one document (the verdict) against a *different* file (the plan), which a JSON Schema validating the verdict instance in isolation cannot see at all.

The plan already knows the correct pattern for this class of property: M3-P1 step 2's `dispatchable` boolean is explicitly described as "the schema expresses that as a `dispatchable` boolean *the validator computes and reports*": i.e., derived, validator-side logic, not a schema keyword. The same treatment is missing for the four checks above. Confirming the confusion is live in the plan's own text: M3-P4 criterion 2(h) restates the exact same property as criterion 4 twice, once framed as a schema DANGEROUS-instance witness ("a final report whose `input-findings[]` omits an id present in its own `inputs[]` list") and once, correctly, as a script check ("The M2-P6 coverage checker, run in finding-to-outcome parity mode... exits 0... against a copy with one `input-findings` row deleted it exits nonzero"). The second framing is the only one that actually works; the first should not have been listed as a schema-keyword witness at all.

**Why it is dangerous:** DR-0013's own recommendation note already anticipates that "the conditional rules M3-P1 step 2 and M3-P4 step 1 require turn out to need more of the specification than the extended subset can carry" is "a discovery the M3-P1 implementer must escalate rather than work around": but the note frames this as a risk confined to M3-P1 and M3-P4. It is not: M3-P3 and M3-P7 have the same class of gap, and they dispatch after DR-0013 is supposedly settled, so the discovery would recur mid-plan exactly the way T-003 warns fix-round churn does ("a fix round is not lower risk than the work it fixes"). Left as written, the criteria promise something JSON Schema cannot deliver, and an implementer will either fabricate a fake "keyword" demonstration to satisfy the letter of criterion or silently build the real check as an undeclared script (another scope-audit hit, compounding M3R-001).

**Evidence:** the quoted acceptance-criteria text from M3-P1, M3-P3, and M3-P7; the `dispatchable` boolean's own "validator computes and reports" framing in M3-P1 step 2 as the plan's own working counter-example; M3-P4 criteria 2(h) and 4 both targeting the same property under two different, inconsistent methodologies; DR-0013's keyword list in section 7.

**Concrete edit:** for each of the four checks above (and any others the M3-P1 implementer finds during DR-0013's dispatch-time audit), either (a) declare a dedicated checker script as a phase deliverable, on the model of `scripts/check-clause-map.mjs`, `scripts/check-brief-drift.mjs`, and `scripts/render-agent-rules-gates.mjs` already in the plan, with its own files-to-touch entry and its own red/green witness, replacing the "guarding keyword removed and restored" framing for that specific criterion; or (b) if DR-0013 later adopts a validator with a `$data`-style cross-reference extension, name that explicitly as a DR-0013 option and prove it handles all four cases before relying on it. Revise section 2.3 to state the distinction explicitly (single-document schema-keyword checks vs. cross-document or cross-array validator-computed checks) so later phases do not repeat the conflation.
