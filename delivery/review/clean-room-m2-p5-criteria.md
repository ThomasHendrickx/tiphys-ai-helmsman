(c) a not-applicable status for a changed set resolving zero local citations (not named by the plan), with the recorded consequence that a required gate going not-applicable makes the runner exit nonzero.
  Judgment: correctly reasoned and not a defect in this phase, but a real, cross-cutting consequence worth flagging as a non-blocking risk item, because it originates upstream of this phase.
  - M2-C-2 forces any green+units-0 record to error (`makeGateResult`'s constructor rule, already delivered by M2-P1). Given that, and given the genuine scenario (a diff that legitimately touches only configured documents with zero local citations, e.g. an all-external-citation plan-diff or a STATE.md-only change), the only remaining options are red (nothing is actually wrong -- would be a false positive) or a status the gate itself declares. M2-C-3's own definition of not-applicable ("asserts a precondition was evaluated and found unmet") matches this case precisely: the gate DID reach a verdict (it evaluated whether anything needed checking, and found nothing did), which is different from "cannot reach a verdict" (which M2-C-3 reserves for error). This is not a guessed reading -- it is the plan's own vocabulary applied consistently.
  - Independently traced the aggregate consequence through the ALREADY-MERGED M2-P1 runner code (src/gates/run.ts, decideAggregate, lines ~929-958): `counts.verdict === 0` (nothing at all reached a verdict) is checked BEFORE `requiredNotApplicable.length > 0`, and only when at least one OTHER gate in the bundle produced a real verdict does the citations gate's self-declared not-applicable route through `requiredNotApplicable`, giving exit code 20 (EXIT_NOT_APPLICABLE), not exit 21 (error) and not exit 0. This exact branch and its ordering are M2-P1's delivered design (CR-800), not something M2-P5 invented or could change; M2-P5 only newly EXERCISES it because `citations` is the first `required`+`diff-touches` gate merged that can legitimately reach a real not-applicable verdict mid-run rather than only via the runner's own coarse precondition.
  - Is the underlying POLICY correct, i.e. should an ordinary paperwork-only commit (say, a STATE.md update with no citations) legitimately fail the whole CI gate bundle? That is a real, open, project-level question this phase surfaces honestly (the work history states the consequence rather than routing around it) but did not invent and has no authority to resolve unilaterally: `citations`'s applicability ("required") is dictated by section 1.4's own table in kernel-plan-m2.md, not by this phase's own choice, and the exit-code semantics belong to M2-P1. Recommend the orchestrator treat this as a policy item for the M2-P9 exit harness or a future owner decision (should a self-declared not-applicable on a `required` gate be softer than an unmet runner-evaluated precondition on a `required` gate, given the two are documented as "the same thing to the counters" but arguably should not always carry the same operational consequence for merge-blocking) -- NOT a fix-round item for M2-P5, which implemented the specified contract faithfully and flagged the consequence rather than hiding it.
