## Are V-1 and V-2 genuinely closed

This is the question the round exists to answer, so it is answered separately from the verdict.

**V-1 (destroy discarding committed work): CLOSED as stated, but the fix is not a no-op on refusal, which is finding V-3.**

The gate itself is sound and was attacked directly. Verified by execution at 20b6a5a against scratch fleets:

- The original V-1 scenario now refuses. Create, commit on the task branch, clean porcelain, plain `pool destroy`: exit 1, branch and commit survive and remain reachable by `git log --all`. The same scenario at b475546 still exits 0 and loses the commit to `git fsck --lost-found`, so the round's red witness is real and not an artifact.
- Gate equivalence holds under attack: an empty commit refuses; an interrupted `rebase -i` paused at a `break` refuses (the pre-rebase tip is still on the branch); a commit followed by `reset --hard` back to base deletes (correctly: the operator already discarded the work); an `--offline` created worktree compares against the right base; a tampered or unreadable record fails closed on the base check.
- Flag distinctness holds in both directions. `--discard` alone does NOT authorize branch deletion: with commits present and the tree either clean or dirty, destroy refuses at the branch gate and the branch survives. `--delete-branch-force` alone does not bypass the dirty guard: the worktree is left intact. `pool create` rejects `--delete-branch-force` with exit 64. The last `discard` reference inside poolDestroy is the `worktree remove --force` argument, so the two flags are genuinely independent.
- The recovery handle exists and is real: `destroyed <id> (deleted branch task/<id> was <sha>)` on stdout, surviving `2>/dev/null`.
- No inverse regression: ordinary clean-at-base destroy, offline-created destroy, destroy after a manual worktree removal, and destroy of an already-deleted branch all still exit 0.

What is not closed is the ordering: the refusal the fix introduces fires AFTER the worktree has already been removed, so a refused destroy is destructive. That is V-3 below, and it is a new defect created by this round's fix, not a survival of V-1.

## Finding V-3 (high): a refused pool destroy is not a no-op, and on an unreadable record it permanently wedges the task id

- severity: high (unrecoverable state through the public CLI; loss of git-ignored files on an ordinary refusal path)
- found by the data-loss lens; independently reached by the test-witness lens from the opposite direction (it arrived through the U-3 test's stated rationale being false)
- refutation vote record: 1 refuted / 2 votes. Recorded honestly: this finding did not survive unanimously. It is reported as high anyway because the wedge is reproduced end to end through the shipped CLI, the control at b475546 shows the wedge is NEW and strictly worse than the pre-fix behavior, and a single-flag counterfactual isolates the ordering as the whole cause. The refuting vote is summarized in the refuted section below so the disagreement is legible rather than buried.

### Claim

poolDestroy removes the worktree before it evaluates the new branch gate, so a refused destroy is not a no-op. With an unreadable pool record that ordering destroys the only remaining way to resolve the git context, and the task id becomes permanently unusable through the CLI: strictly worse than the U-3 behavior this round claims to have fixed.

### Failure scenario

The fleet home is a git repository whose state is committed and synced (plan section 3), so `worktrees/<id>.pool.json` can end up carrying merge-conflict markers or a truncated write, which is exactly the unreadable-record state U-3 named. An operator runs `tiphys pool destroy --task t-x`. contextDir is resolved from the worktree's `--git-common-dir` (src/pool.ts:633-645), the worktree is then removed (src/pool.ts:655-694), and only afterwards does the branch gate refuse because `record?.baseSha` is undefined (src/pool.ts:715-752), exit 1.

The worktree is now gone, so contextDir can never be resolved again. Every subsequent destroy, with `--discard`, with `--delete-branch-force`, or with both, refuses at src/pool.ts:646-652 with `cannot resolve the project repository for task id t-x (pool record missing or unreadable and no usable worktree); nothing was removed`. `pool create --task t-x` refuses with `task id already used`. Deleting `task/t-x` by hand does not help, because the refusal happens before the branch probe and the record is never unlinked (src/pool.ts:764). The id is dead until the operator hand-deletes the record file, which no message mentions.

The same ordering also bites the everyday path this round created. A plain destroy on a clean worktree carrying commits refuses with `land them or pass --delete-branch-force`, but the worktree directory it names has already been deleted, taking every git-ignored file with it (a .env-style file, build output: content no git object holds). The advice "land them" is not performable in place, because the place is gone.

### Evidence

- Executed at 20b6a5a, fresh fleet, record replaced with merge-conflict markers. Destroy #1: `cannot verify branch task/t-x against its recorded base (pool record missing or unreadable), tip 635a36d...`, exit 1, with record present YES, worktree NO, branch YES. Destroy #2 with `--discard --delete-branch-force`: `cannot resolve the project repository for task id t-x ...; nothing was removed`, exit 1. `pool create --task t-x`: `task id already used: t-x`, exit 1. After `git branch -D task/t-x`, destroy again: same refusal, exit 1, record still present.
- Control at b475546, identical scenario: destroy exits 0, record dropped, branch left, and `pool create --task t-x` then gives the actionable `branch task/t-x already exists ...; delete or rename it`. The pre-fix wedge was escapable; this one is not. The round made U-3's silent-success half loud and made its recoverability half worse.
- Ordering isolated as the whole cause: on a fresh fleet with the same corrupt record, passing `--delete-branch-force` on the FIRST destroy exits 0, drops the record, deletes the branch, and the id is immediately re-creatable. Nothing but the order of operations separates the two outcomes.
- Ignored-file witness at 20b6a5a: worktree with `.gitignore` containing `build/` and `build/env.local` present, `git status --porcelain` empty, `pool destroy` exits 1 with the branch-gate refusal, and `build/env.local` plus the whole worktree directory are gone.
- The round's own test cannot see this. test/pool.test.ts:566-596 asserts on the failure branch that "the id must remain recoverable, so the record survives for a retry" and then only checks that the record file still exists. It never runs the retry that can no longer succeed. The comment states the property; the assertion states a proxy; the property is false.
- Mutation testing (test-witness lens, each mutation applied to 20b6a5a and reverted) shows neither half of the U-3 fix is individually witnessed. Disabling the fail-closed probe (`if (false)` for `tip.status !== 0 && tip.status !== 1`) leaves the full suite green at 70/68/0/2 exit 0, and no reachable path to that branch could be constructed. Reverting the contextDir resolution to the old `? record.project : worktree` fallback also leaves the corrupt-record test green, because the other guard catches it. Only the pair is witnessed, and the pair is witnessed on a property the pair does not have.

### Concrete fix

Move the branch gate ahead of every destructive step. Immediately after contextDir is resolved (src/pool.ts:651), run the `rev-parse --verify --quiet refs/heads/<branch>^{commit}` probe, apply the indeterminate-probe and baseSha comparisons there, and return the refusal before the `if (haveWorktree)` block at src/pool.ts:655, leaving the worktree, its registration and the record byte-identical. Keep the `branch -D` and the record unlink where they are today. That makes a refused destroy a true no-op, makes the "land them or pass --delete-branch-force" remedy performable, and removes the wedge, because a retry can still resolve contextDir from the surviving worktree.

Add two regression tests. First: plant an unreadable record, run destroy plain and assert BOTH the refusal AND that the worktree directory still exists, then run destroy `--delete-branch-force` and assert exit 0, record gone, branch gone, id re-creatable. Second: assert that a refused destroy on a clean worktree carrying commits leaves the worktree directory in place. Also correct the existing test's comment, which currently records a rationale the assertion does not check.

## Finding V-4 (high): the commondir transient also strikes the fetch, where nothing retries it, so concurrent pool create still fails with the exact V-2 refusal

- severity: high (the determinism regression V-2 named is still reachable on the create path, plus the same silent `offline: true` provenance inversion under `--offline`)
- found by the concurrency lens
- refutation vote record: 0 refuted / 2 votes

### Claim

The "commondir" transient the round discovered also strikes the fetch, not only worktree add, and on that path nothing retries it, so concurrent `pool create` still fails hard with exactly the V-2 refusal the round claims to have fixed. The deliberate decision to keep this shape out of LOCK_CONTENTION is correct for the add path (partial state must be rolled back first) but wrong for the fetch, which has created nothing yet and can simply be retried.

### Failure scenario

Several dozen `tiphys pool create --task <distinct id> --project <clone>` run at once (criterion 15, M1-P4 spawn, M1-P5 fan-out). One create's `git fetch` enumerates the worktrees of the shared clone while another create's `git worktree add` is mid-write, and the fetch dies with `fatal: failed to read .git/worktrees/<other id>/commondir: Success` plus `error: <remote> did not send all necessary objects`.

src/pool.ts:368-372 wraps that fetch in runGitRetrying, whose only predicate is LOCK_CONTENTION (src/pool.ts:134-135, consumed at :171). WORKTREE_ADD_CONTENTION (src/pool.ts:157) is consulted only in the worktree-add loop at src/pool.ts:440-454. So the fetch returns non-zero on attempt 1 and src/pool.ts:373-381 refuses: exit 1, `tiphys pool: fetch of origin/main failed and --offline was not passed; refusing to base work on a stale ref: fatal: failed to read .git/worktrees/t-046/commondir: Success`.

With `--offline` the same misclassification silently takes the stale fallback and writes `offline: true` into the pool record, which M1-P4 copies to meta.json as baseOffline: the exact PR-212 provenance inversion V-2 named, unchanged.

### Evidence

- Classification with the shipped predicates: `isTransientGitLockError("fatal: failed to read .git/worktrees/t-014/commondir: Success\nerror: ... did not send all necessary objects")` returns false; `isTransientWorktreeAddError` on the same string returns true, and that predicate is never applied to the fetch. This part is exact and machine-independent given the message shape.
- Live on the shipped CLI at 20b6a5a, distinct ids, real concurrency: 4/90 creates failed (unloaded, 21.7s round), 5/90 under 8 CPU hogs; at 120-way, 16/120, 5/120, 8/120, 17/120 and 32/120 in loaded rounds. Every one of those failures carries the commondir stderr on the fetch path. Several other rounds were clean, so the rate is load dependent; the classification is not.
- Under `--offline`, one 120-way round produced 6 records with `offline: true` whose baseSha equalled the true remote head, so the remote was reachable and the recorded provenance is inverted.
- Counterfactual, one-line change in an isolated copy (pass WORKTREE_ADD_CONTENTION as an extra retry pattern for the fetch call only, leaving the add path untouched): 0 failures of this class across 5 rounds of 120 under the same CPU load.
- Why the round did not see it: delivery/work-history/m1-p3.md:188 records the post-fix stress as "90 concurrent pool creates (15 rounds of 6), 0 failures", and the narrative at line 167 compresses that to "90 concurrent creates, 0 failures". Those are not the same measurement. Six-way concurrency almost never puts a fetch and an add in the same window, and the new guard test uses six concurrent creates. This is the CLAUDE.md red-witness rule's "a concurrency path where no contention can occur" in its stronger form: contention is possible but is throttled below the threshold at which the defect appears.

### Concrete fix

Give the fetch its own retry predicate that is the union of LOCK_CONTENTION and WORKTREE_ADD_CONTENTION, for example `runGitRetrying(project, ["fetch", ...], 5, WORKTREE_ADD_CONTENTION)` with runGitRetrying taking an optional extra RegExp. Record in the rationale comment why the commondir shape is retryable on the fetch (no partial state exists yet: the record is written later, at src/pool.ts:411) and not in place on the add. Keep WORKTREE_ADD_CONTENTION out of the generic signature so the add path still rolls back first.

Then make the guard test able to see it. Either raise the concurrent-create witness well above six (the failure appears from roughly 90-way concurrency on 4 cores), or, better for suite time and determinism, drive the contention directly by starting a background `git worktree add` in the same clone while the create fetches, and assert the create still exits 0. Re-run the `--offline` witness at the same width and assert `offline` is false in every record. Also correct work-history line 167 so the narrative and the measurement agree.

## Considered and refuted

One candidate was put through adversarial refutation and killed. It is recorded so it is not re-litigated.

**Refuted: "flagless pool destroy still silently destroys committed work made on a detached HEAD inside the worktree, and the success line offers a false recovery handle" (medium as claimed).**

The mechanics reproduce: a worktree put on a detached HEAD by the operator, committed there, then destroyed, does lose those commits. Both refuters, working independently, killed it on the same grounds:

1. Causally orthogonal to the fix under review. Driving destroy down the gate's REFUSAL path (commit on the task branch, then detach and commit again) preserves the branch, never runs `git branch -D`, and the detached commit is still dangling afterwards. The loss comes from `git worktree remove`, which is the plan's mandated behavior (M1-P3 step 3, criterion 16), not from anything this round added. Re-running the identical sequence at 9aa650b, the pre-fix-round head where no branch deletion existed anywhere in src/pool.ts, produces the same dangling commit. `git diff b475546..20b6a5a -- src/pool.ts` touches neither the cleanliness guard nor the `worktree remove` block.
2. Vanilla git semantics, unweakened. With no Tiphys involved: `git worktree add -b task/x`, `checkout --detach`, commit, then a non-force `git worktree remove` exits 0 and leaves the commit dangling on git 2.43.0. poolDestroy uses the non-force form and its dirty guard is `git status --porcelain`, the same test git's own `check_clean_worktree` applies. The pool inherits git's guard and adds one on top.
3. Strict improvement on this very path. Same scenario at b475546: destroy exits 0 and loses BOTH the on-branch commit and the detached one. At 20b6a5a the identical input refuses with exit 1 and preserves the on-branch commits. The delta reduces loss here; it does not create it.
4. The alleged false invariant is not stated. The comment reads "remove the task branch so a destroyed task id is fully released, but never silently discard commits" and scopes itself two sentences later to "a branch tip still equal to baseSha provably carries no commits, so deleting it is lossless". Both that and the work-history sentence are branch-scoped and both are true. The phrase "recovery handle" appears only in source comments, never in emitted text; the operator sees `destroyed <id> (deleted branch task/<id> was <sha>)`, which names the branch and the sha that branch was at, both facts.
5. The proposed fix would contradict the plan. Criterion 16 requires that "a clean worktree is likewise removed by pool destroy without flags", and a detached-HEAD worktree is clean by that definition. Making destroy refuse there is a contract change, and it is the mirror image of the mistake that produced V-1: going beyond what the finding and the contract asked for, on this exact command.

Honest residue, offered as context and not as a finding: a clean detached-HEAD worktree really does lose its commits on destroy, and the dirty-guard advice "commit or land them first" does not protect an operator who is off the task branch. That is a property of the plan's destroy contract and of `git worktree remove`, present since the phase's original implementation. If it is to be recorded it belongs in the phase's not-proven list or as a plan question for M1-P4 teardown, not as a defect in this round.

**Note on the refuting vote against V-3.** One of the two refuters on V-3 did not refute the wedge; it argued the finding was scope-inflated by the ignored-file half. The wedge repro, the b475546 control and the single-flag counterfactual were not contested by either refuter, and the test-witness lens reached the same defect independently through the test's false rationale. V-3 is therefore reported, with the split recorded here.
